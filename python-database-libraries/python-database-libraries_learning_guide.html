Module 1.1 — Connections, Cursors & the DB-API

Level: Beginner–Intermediate · Prereqs: SQL basics (SELECT, INSERT, JOIN) · Time: ~2h
Skip-check (test-out): Open a psycopg connection, run a query with a cursor, and fetch results as both tuples and dict-like rows, using context managers throughout.
Skip if: You already default to psycopg (not psycopg2) for new Postgres work and use context managers by habit.
Unlocks: Module 1.2, Module 2.1

psycopg3, not psycopg2, for new work

This guide teaches psycopg (package name psycopg, commonly called "psycopg 3" to distinguish it from the still-widely-deployed older psycopg2). For any new project there's no real reason to reach for psycopg2 instead: psycopg 3 has built-in async support, a native connection pool (Module 1.4), better type adaptation, and measured throughput roughly 2–3x higher on bulk fetches. If you're maintaining an older codebase, psycopg2's API is similar enough that the concepts here (cursors, parameterized queries, transactions) transfer directly — only the import name and a handful of APIs differ.

import psycopg

with psycopg.connect("postgresql://localhost/tindahub") as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT id, name, email FROM customers LIMIT 5")
        rows = cur.fetchall()
        for row in rows:
            print(row)         # each row is a plain tuple by default: (1, 'Maria Santos', '...')

Using with on both the connection and the cursor matters beyond tidiness: the connection's context manager commits the transaction on clean exit and rolls it back on an exception (Module 1.3 covers this in depth), so skipping it is a common source of silently-lost writes when an error occurs partway through a script.

Getting rows as dictionaries

Plain tuples require remembering column order by position, which gets fragile as a query grows. psycopg's row_factory parameter changes what shape each fetched row comes back as — dict_row gives you a dictionary keyed by column name instead.

import psycopg
from psycopg.rows import dict_row

with psycopg.connect("postgresql://localhost/tindahub", row_factory=dict_row) as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT id, name, email FROM customers LIMIT 5")
        for row in cur.fetchall():
            print(row["name"], row["email"])   # access by column name, not position

Module 1.2 — Parameterized Queries & SQL Injection Prevention

Level: Beginner–Intermediate · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Rewrite a query that string-formats a user-supplied value into SQL as a safely parameterized query, and explain exactly what attack the fix prevents.
Skip if: You already never build a SQL string with f-strings/%/.format() around a variable value.
Unlocks: Module 1.3, Module 4.1

Why string-building SQL is dangerous

Building a query by inserting a variable directly into a SQL string — via an f-string, %-formatting, or .format() — lets any value containing SQL syntax change the query's actual meaning. This is SQL injection: if a "customer name" input field ever gets to be "'; DROP TABLE customers; --" and that string is spliced directly into a query, the database executes it as written, not as the harmless text the application intended. This isn't a rare edge case; it's one of the most consistently exploited web application vulnerabilities in real breaches, precisely because it's easy to write by accident.

customer_name = "Maria Santos"

# DANGEROUS — never do this with any value that could originate from user input
bad_query = f"SELECT * FROM customers WHERE name = '{customer_name}'"
cur.execute(bad_query)

# SAFE — psycopg substitutes the placeholder itself, correctly escaped, never as raw text
cur.execute("SELECT * FROM customers WHERE name = %s", (customer_name,))

psycopg's placeholder substitution isn't string concatenation in disguise — it sends the query and the parameter values to Postgres separately, so a malicious value can never be interpreted as SQL syntax no matter what characters it contains. This is why the fix works even for values you're confident are "safe": the discipline of always using placeholders, with no exceptions for "trusted" input, is what actually prevents the mistake, not case-by-case judgment about which values need it.

Common mistake: assuming SQL injection only matters for values obviously derived from a web form. Any value that ever traces back to something outside your own hardcoded source — a CLI argument, a config file, an API response you're relaying — deserves the same parameterized treatment. Treat placeholders as the unconditional default, not a case-by-case judgment call.

Placeholders for identifiers vs. values

%s placeholders are for values only — they cannot be used for table or column names, since those are part of the query's structure, not data. When a table/column name genuinely needs to be dynamic (rare, and worth being suspicious of when it happens), psycopg's sql module provides sql.Identifier for safely composing identifiers instead.

from psycopg import sql

table_name = "orders"   # e.g., selected from a fixed, hardcoded allow-list — never raw user input
query = sql.SQL("SELECT * FROM {table} LIMIT 5").format(table=sql.Identifier(table_name))
cur.execute(query)

Module 1.3 — Transactions, Autocommit & Error Handling

Level: Intermediate · Prereqs: Module 1.1 · Time: ~2.5h
Skip-check (test-out): Write a multi-statement transaction that commits only if every statement succeeds, correctly rolling back on any error, and explain what autocommit mode changes about that behavior.
Skip if: Transaction boundaries and rollback-on-error are already a comfortable habit.
Unlocks: Module 1.4, Module 2.3

Transactions are on by default

By default, a psycopg connection is not in autocommit mode: every statement runs inside an implicit transaction that stays open until you call conn.commit() or conn.rollback() — or, when using with psycopg.connect(...) as conn:, until the block exits (committing on success, rolling back if an exception propagated). This matters for correctness whenever an operation involves more than one statement that must succeed or fail together — e.g., inserting an order and its order items should never leave one committed without the other.

import psycopg

with psycopg.connect("postgresql://localhost/tindahub") as conn:
    with conn.cursor() as cur:
        try:
            cur.execute(
                "INSERT INTO orders (customer_id, status) VALUES (%s, %s) RETURNING id",
                (3, "pending")
            )
            order_id = cur.fetchone()[0]
            cur.execute(
                "INSERT INTO order_items (order_id, product_id, quantity) VALUES (%s, %s, %s)",
                (order_id, 7, 2)
            )
            # no explicit commit needed here — the `with conn:` block commits on clean exit
        except Exception:
            conn.rollback()
            raise

Common mistake: assuming a failed statement automatically undoes itself. In Postgres, once a statement inside a transaction errors, the entire transaction is left in a failed state ("current transaction is aborted") and every subsequent statement in it will also fail until you explicitly rollback() — there's no partial-success recovery without an explicit SAVEPOINT.

Autocommit mode and savepoints

conn.autocommit = True makes every statement commit immediately on its own, with no multi-statement transaction wrapping it — appropriate for simple, independent reads or single-statement writes where you don't need atomicity across multiple statements, and required for certain administrative commands (like CREATE DATABASE) that Postgres won't allow inside a transaction block at all. For partial rollback within a larger transaction, a SAVEPOINT (via conn.transaction() as a nested context manager in psycopg) lets you undo just a portion of the work without losing everything already done.

with psycopg.connect("postgresql://localhost/tindahub") as conn:
    with conn.cursor() as cur:
        with conn.transaction():                 # outer transaction
            cur.execute("UPDATE orders SET status = %s WHERE id = %s", ("shipped", 1))
            try:
                with conn.transaction():          # nested — becomes a SAVEPOINT
                    cur.execute("UPDATE payments SET method = %s WHERE order_id = %s", ("invalid_method", 1))
            except psycopg.errors.CheckViolation:
                pass    # only the nested savepoint rolls back; the outer UPDATE above still commits

Module 1.4 — Connection Pooling & Async psycopg

Level: Intermediate · Prereqs: Module 1.3 · Time: ~2.5h

Skip if: Connection pooling and async psycopg are already familiar.

Why pool connections at all

Opening a new Postgres connection involves a TCP handshake, authentication, and server-side process setup — measured in milliseconds, not microseconds, which becomes a real bottleneck if a web application opens a fresh connection for every incoming request. A connection pool keeps a set of already-open connections ready to hand out and reuse, so a request borrows one, uses it, and returns it instead of paying the connection-setup cost every time.

from psycopg_pool import ConnectionPool

pool = ConnectionPool("postgresql://localhost/tindahub", min_size=2, max_size=10)

with pool.connection() as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT count(*) FROM orders")
        print(cur.fetchone())
# connection is returned to the pool here, not closed

Common mistake: pooling against a service that already pools for you in a mode that doesn't support certain session-level features. Supabase's transaction-mode pooler (Supavisor, typically on port 6543), for instance, does not support prepared statements or session-scoped SET commands the way a direct connection does — connecting through it with default settings can produce confusing "prepared statement already exists" errors under concurrent load. When connecting through any external pooler, check its mode (transaction vs. session) before assuming every psycopg feature behaves identically to a direct connection.

Async psycopg

psycopg's async API mirrors the sync one closely — AsyncConnection/AsyncCursor with await in front of the operations that hit the network — making it a natural fit inside an already-async application (like a FastAPI endpoint) where you don't want a blocking database call to stall the event loop.

import asyncio
import psycopg

async def get_customer_count():
    async with await psycopg.AsyncConnection.connect("postgresql://localhost/tindahub") as conn:
        async with conn.cursor() as cur:
            await cur.execute("SELECT count(*) FROM customers")
            return (await cur.fetchone())[0]

count = asyncio.run(get_customer_count())

Engine: a connection factory, not a connection

SQLAlchemy's Engine is a factory that manages a pool of connections (internally, similar in spirit to Module 1.4's ConnectionPool) and knows how to talk to your specific database dialect — it is created once per application, not per query. Under the hood, SQLAlchemy's Postgres dialect uses psycopg (or another driver you specify) to actually talk to the database; SQLAlchemy itself is a layer on top, not a replacement driver.

from sqlalchemy import create_engine, text

engine = create_engine("postgresql+psycopg://localhost/tindahub")   # +psycopg selects psycopg 3 as the driver

with engine.connect() as conn:
    result = conn.execute(text("SELECT id, name FROM customers LIMIT 5"))
    for row in result:
        print(row.id, row.name)   # named attribute access on the result row

text() wraps a raw SQL string for execution — and still requires parameterization the same way Module 1.2 does, via named bind parameters (:name) rather than psycopg's %s.

result = conn.execute(
    text("SELECT * FROM customers WHERE name ILIKE :pattern"),
    {"pattern": "%santos%"}
)

Core: building queries as Python objects, not strings

SQLAlchemy Core represents tables and queries as Python objects rather than SQL strings — Table objects describe schema, and select()/insert()/update() build a query as a composable expression tree that SQLAlchemy compiles to the correct SQL for your specific database dialect. This buys portability (the same Core query can target Postgres or SQLite without rewriting SQL syntax) and lets you build queries programmatically (conditionally adding a WHERE clause, say) without string concatenation.

from sqlalchemy import MetaData, Table, Column, Integer, String, select

metadata = MetaData()
customers = Table(
    "customers", metadata,
    Column("id", Integer, primary_key=True),
    Column("name", String),
    Column("email", String),
)

query = select(customers.c.id, customers.c.name).where(customers.c.name.ilike("%santos%"))
with engine.connect() as conn:
    for row in conn.execute(query):
        print(row.id, row.name)

Module 2.2 introduces the ORM layer, which sits on top of Core rather than replacing it — every ORM query still compiles down to the same Core expression machinery underneath.

Module 2.2 — ORM Mapping with Declarative Models

Level: Intermediate · Prereqs: Module 2.1 · Time: ~3h

The 2.0-style declarative pattern

SQLAlchemy 2.0 (this guide targets 2.0.51) standardized on typed, annotation-driven declarative models: a DeclarativeBase subclass as your model base, and each column declared with a Mapped[type] annotation paired with mapped_column() for ORM-specific configuration (primary key, foreign key, defaults). If you're reading older tutorials using bare Column assignments without Mapped type annotations, that's the pre-2.0 (1.x) style — it still works for backward compatibility, but the typed style gets you real IDE autocomplete and static type checking on model attributes, which the untyped style never could.

from typing import Optional
from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class Base(DeclarativeBase):
    pass

class Customer(Base):
    __tablename__ = "customers"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(120))
    email: Mapped[Optional[str]]           # Optional[...] maps to a nullable column

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    customer_id: Mapped[int] = mapped_column(ForeignKey("customers.id"))
    status: Mapped[str]

Note that these mapped classes describe the existing tindahub schema (created by schema.sql) — Base.metadata.create_all(engine) only creates tables that don't already exist, so running it against tindahub is safe (a no-op for these two) but is the tool you'd use to create a genuinely new table from a model.

Type mapping and defaults

SQLAlchemy infers a reasonable SQL column type from the Python type in Mapped[...] (str → String/VARCHAR, int → Integer, datetime → DateTime), but an explicit mapped_column(String(120)) is still worth writing whenever you need a specific length or database-level constraint the bare Python type can't express — relying purely on inference for anything beyond a quick prototype risks a schema that's technically valid but looser than intended.

Session: the ORM's unit-of-work

A Session tracks mapped objects you've loaded or created, and batches the resulting SQL when you call session.commit() — it plays a role loosely analogous to a psycopg connection-plus-transaction (Module 1.3), but adds object identity tracking (the same database row loaded twice in one session returns the same Python object) and change tracking (mutating an attribute on a loaded object is enough; SQLAlchemy generates the corresponding UPDATE for you on commit).

from sqlalchemy.orm import Session, sessionmaker
from sqlalchemy import select

SessionLocal = sessionmaker(bind=engine)

with SessionLocal() as session:
    customer = session.get(Customer, 1)              # primary-key lookup
    customer.email = "updated@example.com"            # tracked change
    session.commit()                                   # generates and runs the UPDATE

    stmt = select(Customer).where(Customer.name.ilike("%santos%"))
    matches = session.execute(stmt).scalars().all()    # 2.0-style: execute(select(...)), then .scalars()

relationship() and the N+1 problem

relationship() lets you navigate from one mapped model to related rows as Python attributes (order.items instead of a manual join query). Without care, looping over a list of orders and accessing .items on each triggers one extra query per order — the classic N+1 query problem, invisible in small test data and a serious performance bug at real scale. joinedload() (a SQL JOIN, one query total) or selectinload() (a second batched query, better for one-to-many collections) tell SQLAlchemy to eagerly load the related rows upfront instead.

from sqlalchemy.orm import relationship, selectinload

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    customer_id: Mapped[int] = mapped_column(ForeignKey("customers.id"))
    status: Mapped[str]
    items: Mapped[list["OrderItem"]] = relationship(back_populates="order")

# without eager loading: 1 query for orders + 1 query per order for .items (N+1)
orders = session.execute(select(Order)).scalars().all()
for o in orders:
    print(len(o.items))   # each access triggers a separate query — the bug

# with eager loading: 2 queries total, regardless of how many orders
stmt = select(Order).options(selectinload(Order.items))
orders = session.execute(stmt).scalars().all()

Common mistake: not noticing the N+1 problem because a local test database only has a handful of rows — 5 orders means 5 extra queries, easy to miss in a dev log. The bug scales linearly with row count and becomes a real production slowdown exactly when the data grows, which is precisely when it's hardest to just re-test your way into noticing.

Why migrations, not manual schema edits

Editing a production schema by hand (via ALTER TABLE run once, ad hoc) leaves no record of what changed, when, or in what order relative to your application code — and no reliable way to reproduce that exact schema state on a teammate's machine or a fresh environment. Alembic (the standard migration tool for SQLAlchemy) generates versioned, ordered migration scripts that can be applied (upgrade) or reversed (downgrade) as a sequence, giving schema changes the same reviewable, repeatable discipline as application code changes.

alembic init alembic                       # scaffolds the migration environment, once per project
# edit alembic/env.py to point target_metadata at Base.metadata and the DB URL at tindahub
alembic revision --autogenerate -m "add loyalty_points to customers"
alembic upgrade head                       # applies all pending migrations
alembic downgrade -1                       # reverses the most recent one

Autogenerate is a draft, not a guarantee

Alembic's --autogenerate compares your current models against the live database schema and drafts a migration script — it's genuinely useful, but it doesn't catch everything (data migrations, some constraint changes, column renames that look like a drop-plus-add to the diff). Always open and read the generated script before running upgrade; treating autogenerate output as ready-to-run without review is how a column rename accidentally becomes a silent data-dropping DROP COLUMN + ADD COLUMN pair instead.

# inside the generated migration file — review this before running upgrade
def upgrade() -> None:
    op.add_column("customers", sa.Column("loyalty_points", sa.Integer(), server_default="0"))

def downgrade() -> None:
    op.drop_column("customers", "loyalty_points")

In-process, not client-server

Postgres (and the psycopg/SQLAlchemy layers on top of it) is a client-server database: a separate server process holds the data, and your Python process connects to it over a socket. DuckDB runs inside your Python process — there's no server to start, no connection string pointing at a host/port, and no network round-trip per query. This makes it fundamentally a different tool for a different job: not a replacement for Postgres as your application's system of record, but an extremely fast local engine for analytical queries over data you already have in files or memory.

import duckdb

# no server, no connection string — an in-memory DuckDB "database" just exists
result = duckdb.sql("SELECT 42 AS answer").fetchall()
print(result)   # [(42,)]

con = duckdb.connect("tindahub_analytics.duckdb")   # a persistent on-disk file instead of :memory:
con.sql("CREATE TABLE demo AS SELECT * FROM range(5) AS t(n)")
print(con.sql("SELECT * FROM demo").fetchall())

OLAP vs. OLTP: why this matters for what DuckDB is good at

Postgres is optimized for OLTP (Online Transaction Processing) — many small, concurrent reads and writes of individual rows, exactly what Phase 1–2's order-placement code needs. DuckDB is a columnar engine optimized for OLAP (Online Analytical Processing) — scanning and aggregating huge numbers of rows across a smaller number of columns, exactly what "total revenue by category, by month" needs. Using DuckDB for row-by-row transactional writes, or Postgres for a full-table columnar aggregation over millions of rows, both work, but each is playing against its actual strength.

ATTACH: querying Postgres without an ETL step

DuckDB's postgres extension lets you ATTACH a live Postgres database and query its tables directly from DuckDB — the data is read from Postgres at query time, not copied in advance. This means you can join a DuckDB-local CSV or Parquet file against a live Postgres table in a single SQL statement, with no separate export/import pipeline, which is exactly the kind of one-off "join my file against the live database" analysis that would otherwise mean writing throwaway ETL code.

import duckdb

con = duckdb.connect()
con.sql("INSTALL postgres")
con.sql("LOAD postgres")
con.sql("ATTACH 'dbname=tindahub host=localhost' AS pg (TYPE postgres)")

# tables from Postgres now queryable as if they were local DuckDB tables
result = con.sql("SELECT status, count(*) FROM pg.orders GROUP BY status").fetchall()

# join a local CSV against a live Postgres table, in one query
joined = con.sql("""
    SELECT c.name, o.status, o.id
    FROM pg.customers AS c
    JOIN pg.orders AS o ON o.customer_id = c.id
    WHERE c.name ILIKE '%santos%'
""").fetchall()

The older postgres_attach() function-call syntax from early versions of this extension is deprecated in favor of the ATTACH ... (TYPE postgres) syntax shown above — if you see the old form in an older tutorial, treat it as outdated, not wrong-but-equivalent.

Common mistake: assuming DuckDB's cached view of an attached Postgres database's schema updates automatically. If a table's columns change via a different connection (e.g., an Alembic migration from Module 2.4) while DuckDB's attachment is still open, DuckDB may keep using stale cached schema info until you run CALL pg_clear_cache() or reattach.

supabase-py is a REST client, not a database driver

This is the single most important thing to understand before writing any supabase-py code: unlike psycopg or SQLAlchemy, supabase-py doesn't open a Postgres connection at all. It's an HTTP client wrapping Supabase's auto-generated REST API (PostgREST) plus separate Auth, Storage, and Realtime services. Every .table(...).select(...).execute() call is an HTTP request, translated into SQL server-side by PostgREST — which is precisely what makes it usable from contexts (browser JS, mobile apps, serverless functions with no persistent DB connection) where a raw Postgres connection wouldn't be practical or safe.

from supabase import create_client

url = "https://your-project.supabase.co"
key = "your-anon-or-service-role-key"   # see the key-choice warning below
supabase = create_client(url, key)

response = (
    supabase.table("orders")
    .select("id, status, customers(name)")   # nested select follows the foreign key relationship
    .eq("status", "delivered")
    .order("id", desc=True)
    .limit(10)
    .execute()
)
print(response.data)   # a list of dicts, already JSON-decoded

anon key vs. service role key: this choice is a security decision

The anon key is safe to embed in client-side code (a browser or mobile app) precisely because every request made with it is still subject to Row Level Security (Module 4.2) — it identifies the request as coming from an unauthenticated or authenticated end-user, not as a trusted backend. The service role key bypasses Row Level Security entirely and must never be shipped to a client; it belongs only in trusted server-side code (a backend service, a scheduled job) that you control. Using the service role key in a context an end user could inspect (a mobile app, a public repo, client-side JS) is a full database compromise, not a minor misconfiguration.

Common mistake: reaching for the service role key during development because it "just works" (no RLS policy debugging needed) and forgetting to switch back before shipping. Default to the anon key plus correctly-configured RLS policies for anything a client will run; reserve the service role key for genuinely trusted server-side code, and treat any accidental client-side exposure of it as an incident requiring an immediate key rotation.

Calling Postgres functions with .rpc()

For logic too complex for PostgREST's query-builder style (multi-step business logic, an operation that must be atomic across several tables), define a Postgres function (in SQL, deployed via a migration) and call it through .rpc() — the request still goes over HTTP, but the actual work runs as a single function call inside Postgres, which is both faster (one round-trip) and safer (atomic) than orchestrating the same multi-step logic from multiple separate .table() calls in Python.

response = supabase.rpc("place_order", {"p_customer_id": 3, "p_items": [{"product_id": 7, "quantity": 2}]}).execute()

Row Level Security: the policy lives in Postgres, not in your Python code

Row Level Security (RLS) is a genuine Postgres feature (not a Supabase invention) that filters which rows a query can see or modify, enforced by the database itself based on policies you define in SQL — a policy like "a customer can only see their own orders" applies no matter which client issues the query (supabase-py, a browser, psql directly), because the enforcement happens inside Postgres, not in application code that a client could bypass. This is precisely why the anon key is safe to expose (previous module): the key alone grants no access; the RLS policy is what actually decides what's visible.

-- run via the SQL editor or a migration, not from Python
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY "customers see only their own orders"
ON orders FOR SELECT
USING (customer_id = (SELECT id FROM customers WHERE auth_user_id = auth.uid()));

Once this policy exists, the exact same supabase.table("orders").select("*").execute() call from Module 4.1 returns a different result set depending on which user is authenticated when it runs — nothing changes in the Python code at all. This is the core mental model shift from Phase 1–2's direct-access tools: with psycopg/SQLAlchemy, your application code is typically the thing deciding what a user is allowed to see; with Supabase's RLS-first model, the database itself enforces that, and the client layer becomes deliberately less trusted by design.

Disambiguation: RLS is not the same thing as an application-level permission check (an if user.role == "admin" in Python). An application-level check only protects paths that actually run that check; RLS protects the data at the database layer regardless of which code path (or which client entirely) issues the query — a meaningfully stronger guarantee, and the reason Supabase's client-side-safe anon key model works at all.

Realtime and Storage, briefly

The Realtime client lets Python code subscribe to live database change events (insert/update/delete) over a WebSocket, rather than polling; the Storage client uploads/downloads files to Supabase's managed object storage, with the same RLS-style policy model applied to buckets.

def handle_change(payload):
    print("order changed:", payload)

channel = supabase.channel("orders-changes")
channel.on_postgres_changes("UPDATE", schema="public", table="orders", callback=handle_change)
channel.subscribe()

with open("receipt.pdf", "rb") as f:
    supabase.storage.from_("receipts").upload("order-42-receipt.pdf", f)

Need a quick, portable SQL layer over CSV/Parquet files or a fast local aggregation?DuckDBNo server, no ETL step, columnar execution built for exactly this.
Need one-off analysis joining live Postgres data against local files?DuckDB (ATTACH ... TYPE postgres)Federated querying with no separate export/import pipeline.
Building a client-side (browser, mobile) or serverless app that needs safe, per-user-scoped database access?supabase-py (anon key + RLS)No persistent DB connection required; security enforced at the database layer via RLS, not in client code.
Need real-time change notifications or file storage alongside your data?supabase-py (Realtime / Storage)Neither psycopg, SQLAlchemy, nor DuckDB has a built-in equivalent.
Need to evolve a schema safely, with a reviewable, reversible history?Alembic (via SQLAlchemy models)Migrations as versioned code, not one-off manual ALTER TABLE statements.

The throughline: trust boundary decides more than performance does

The deepest distinction across this guide isn't speed (though DuckDB's analytical performance and psycopg's raw-driver speed are both real) — it's where the trust boundary sits. psycopg and SQLAlchemy assume the code running them is fully trusted (a backend server you control), and every access-control decision lives in that trusted code. supabase-py's anon-key model assumes the opposite: the calling code (a browser tab, someone's phone) is not trusted, so access control has to live in the database itself via RLS, not in the client. Picking psycopg/SQLAlchemy for genuinely client-facing code, or picking supabase-py's anon key for genuinely trusted backend logic that then skips writing real RLS policies, both put access control in the wrong place relative to who's actually running the code.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

psycopg & the DB-API

Cursor
An object that executes queries against an open connection and exposes their results for fetching, one query (or a sequence of them) at a time.
Avoid: confusing a database cursor with a text/UI cursor — unrelated concepts sharing a name.
Parameterized query
A query containing placeholders whose actual values are sent separately from the query text, so a value can never be interpreted as SQL syntax.
Avoid: "escaped query" as a substitute term — manual escaping is exactly the fragile, error-prone approach parameterization exists to replace.
Autocommit
A connection mode where each statement commits immediately on its own, with no multi-statement transaction wrapping it.
Avoid: assuming autocommit is simply "no transactions" — each individual statement is still its own implicit transaction.
Connection pool
A managed set of already-open database connections that application code borrows and returns, avoiding the cost of opening a new connection per operation.
Avoid: "connection cache" — a pool actively manages connection lifecycle (health checks, min/max sizing), not just passive reuse.

SQLAlchemy Core & ORM

Engine
A factory object managing a connection pool and dialect-specific SQL generation for a given database, created once per application.
Avoid: "connection" as a substitute — an Engine issues connections; it is not itself one.
Core (expression language)
SQLAlchemy's layer for building SQL queries as composable Python objects (Table, select(), etc.), independent of the ORM.
Avoid: assuming Core requires the ORM — Core is usable entirely on its own, and the ORM is built on top of it.
Declarative model
A Python class mapped to a database table via DeclarativeBase, with columns declared using Mapped[...] type annotations and mapped_column().
Avoid: the legacy bare-Column style (no Mapped annotation) as the default to teach or learn — it still works, but the typed style is SQLAlchemy 2.0's idiomatic default.
N+1 query problem
A performance bug where accessing a relationship on each of N loaded objects triggers one additional query per object, instead of a single batched query.
Avoid: assuming this only matters at very large N — the bug exists (and costs real round-trips) at any N greater than 1, it just becomes visibly slow at scale.

DuckDB & OLAP

In-process database
A database engine that runs inside the calling application's own process, with no separate server process or network connection involved.
Avoid: "embedded database" as a strict synonym in casual use — the term is fine, but don't let it imply DuckDB is a stripped-down toy; it's a full columnar analytical engine.
OLAP (Online Analytical Processing)
A workload pattern of scanning and aggregating large numbers of rows across relatively few columns, as opposed to OLTP's many small single-row reads/writes.
Avoid: treating OLAP and OLTP as a strict "one is better" ranking — they're optimized for different, roughly opposite access patterns.
Columnar execution
A storage/execution model that processes data column-by-column rather than row-by-row, enabling vectorized operations over many values at once.
Avoid: "faster because it's in memory" as the explanation for DuckDB's speed — the columnar, vectorized execution model is the real driver, independent of whether data is on disk or in RAM.
ATTACH (Postgres extension)
A DuckDB command that connects a live external database (Postgres, in this guide) so its tables can be queried directly from DuckDB SQL, read at query time.
Avoid: assuming ATTACH copies or syncs data into DuckDB — it reads live from the source at query time, and its cached schema info can go stale if the source schema changes.

Supabase & RLS

PostgREST
The service that auto-generates a REST API from a Postgres schema; supabase-py's table-query methods are a Python wrapper around calls to it.
Avoid: "the Supabase database" as a substitute term — PostgREST is a layer in front of Postgres, not the database itself.
anon key
A Supabase API key safe for client-side exposure, identifying requests as coming from an untrusted client whose access is still filtered by RLS.
Avoid: "public key" as a substitute — correct in spirit but not Supabase's actual terminology, which is specifically "anon key."
service role key
A Supabase API key that bypasses Row Level Security entirely, intended only for trusted server-side code.
Avoid: "admin key" as a substitute — correct in spirit, but again not the actual term, and "admin" undersells how completely it bypasses every policy.
Row Level Security (RLS)
A Postgres feature that filters which rows a query can access or modify, based on policies enforced by the database itself regardless of which client issues the query.
Avoid: confusing RLS with an application-level permission check — RLS is enforced at the database layer and cannot be bypassed by a client skipping a check.
