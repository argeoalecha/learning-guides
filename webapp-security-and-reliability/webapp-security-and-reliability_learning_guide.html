Why a Threat Model, Not a Checklist

Security is not a list of boxes to check — it is reasoning about what an attacker with a browser, a proxy, and time can do to your system. The OWASP Top 10 is a consensus of the most common ways that reasoning plays out in practice, refreshed periodically from real breach and CVE data. Treating it as a checklist without understanding the underlying attacker motivation means you will pass an audit and still get breached by variant #11.

OWASP Top 10:2025 — What Changed

The 2025 edition (finalized January 2026) is the first refresh since 2021, built from analysis of over 175,000 CVE records. Two changes matter most for how you should think about defense in 2026:

  • A01:2025 — Broken Access Control stays #1, and now absorbs Server-Side Request Forgery (SSRF), which was a standalone 2021 category. The message: access control failures are the dominant real-world risk, and SSRF is fundamentally an access-control problem (the server accessing something it shouldn't on the attacker's behalf).
  • A02:2025 — Security Misconfiguration jumped from #5 to #2, reflecting how much modern risk now lives in cloud config, container defaults, and IaC — not just hand-written application code.
  • A03:2025 — Software Supply Chain Failures is new: dependency, build-pipeline, and CI/CD compromise are now common enough to warrant their own category (Module 2.3 goes deep here).
  • A10:2025 — Mishandling of Exceptional Conditions is new: improper error handling, fail-open logic, and logical edge cases that leak data or bypass checks.

The full 2025 list: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Insecure Design, A05 Cryptographic Failures, A06 Vulnerable & Outdated Components, A07 Identification & Authentication Failures, A08 Software & Data Integrity Failures, A09 Security Logging & Monitoring Failures, A10 Mishandling of Exceptional Conditions.

The Attacker's Toolkit (What You're Defending Against)

A minimally-equipped attacker uses a browser, an intercepting proxy (Burp Suite Community or OWASP ZAP), and a wordlist. They are not writing custom exploits for a typical web app — they are looking for the misconfigured S3 bucket, the IDOR in /api/orders/{id}, the debug endpoint left enabled in production. Module 2.4 puts these same tools in your hands so you learn to see your app the way they do.

Common mistake: Treating "we passed our last pentest" as proof of security. A pentest is a snapshot of one moment against one team's toolkit and time budget — it is not a guarantee against the next dependency CVE or the feature shipped the following week. Security is a continuous property (Module 2.3), not a certificate.

Module 1.2 — Authentication & Session Security

Level: Beginner · Prereqs: 1.1 · Time: ~4h
Skip-check (test-out): Implement an OAuth 2.1-compliant authorization code flow with PKCE and explain why the implicit grant is no longer acceptable.
Skip if: You have shipped OIDC/OAuth login flows in production and can explain token rotation and refresh-token theft mitigation.
Unlocks: 1.3, 1.4

Authentication Is Not Authorization

Authentication answers "who are you?" Authorization (Module 1.3) answers "what are you allowed to do?" Conflating them is a common root cause of A01 Broken Access Control — a system that verifies identity correctly but never separately checks permission on every request is not secure, just correctly logged-in.

OAuth 2.1: The Current Baseline

OAuth 2.1 consolidates RFC 6749, PKCE (RFC 7636), and the OAuth Security BCP (RFC 9700) into one profile. It is still an IETF draft, not yet a published RFC, but every major identity provider (Auth0, Okta, Keycloak, Google, Microsoft) already implements it — write new code against OAuth 2.1 rules, not legacy OAuth 2.0. The concrete changes that affect what you type:

  • PKCE is mandatory for every client, not just public/mobile clients as in OAuth 2.0.
  • The implicit grant and the resource owner password credentials (ROPC) grant are removed. Both leaked tokens or credentials into places they shouldn't be (URL fragments, first-party forms).
  • Redirect URIs require exact string matching — no wildcard or partial-match redirect validation.
// Authorization code + PKCE, server-side (Node/Express) — ShopFlow login initiation
import crypto from "node:crypto";

function base64url(buf) {
  return buf.toString("base64").replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

app.get("/auth/login", (req, res) => {
  const verifier = base64url(crypto.randomBytes(32));
  const challenge = base64url(crypto.createHash("sha256").update(verifier).digest());

  // Store verifier server-side, keyed to a short-lived state, not in a cookie the client can read
  req.session.pkceVerifier = verifier;
  req.session.oauthState = base64url(crypto.randomBytes(16));

  const authUrl = new URL("https://idp.shopflow.example/oauth2/authorize");
  authUrl.searchParams.set("response_type", "code");
  authUrl.searchParams.set("client_id", process.env.OAUTH_CLIENT_ID);
  authUrl.searchParams.set("redirect_uri", "https://shopflow.example/auth/callback");
  authUrl.searchParams.set("code_challenge", challenge);
  authUrl.searchParams.set("code_challenge_method", "S256");
  authUrl.searchParams.set("state", req.session.oauthState);
  authUrl.searchParams.set("scope", "openid profile email");

  res.redirect(authUrl.toString());
});

Sessions and Tokens: Where They Live Matters

A JWT stored in localStorage is readable by any script running on the page — one successful XSS (Module 2.1) becomes full account takeover with no further exploitation needed. An httpOnly, Secure, SameSite=Strict cookie is invisible to JavaScript entirely, which is why it remains the safer default for browser-based session storage even in an SPA architecture like ShopFlow's Next.js frontend.

// Setting a session cookie correctly after successful OAuth callback
res.cookie("sf_session", sessionToken, {
  httpOnly: true,       // JavaScript cannot read this cookie — mitigates XSS token theft
  secure: true,          // only sent over HTTPS
  sameSite: "strict",    // not sent on cross-site requests — mitigates CSRF
  maxAge: 15 * 60 * 1000, // short-lived access token; refresh via rotation, not long expiry
  path: "/",
});

Common mistake: Treating "we use JWTs" as a security feature. A JWT is just a signed data format — it carries the same risks as any bearer token (theft = impersonation) and adds its own footguns (the classic alg: none bypass, or trusting a client-supplied kid header without validating it against a known key set). JWTs are a transport choice, not a security control.

Module 1.3 — Authorization & Access Control

Level: Beginner–Intermediate · Prereqs: 1.2 · Time: ~4h
Skip-check (test-out): Given a REST endpoint and two user roles, write the authorization middleware and the specific test case that catches an IDOR regression.
Skip if: You already enforce object-level authorization checks on every request in a production system and can explain the difference between RBAC and ABAC with a real example.
Unlocks: 1.4, 2.1

Why This Is A01, the #1 Risk

Broken Access Control tops both the 2021 and 2025 OWASP lists because it is easy to get wrong and expensive to get right: every single request touching user data needs an explicit permission check, and missing even one creates a real breach. Authentication only has to be correct once per session; authorization has to be correct on every request, every time.

RBAC vs. ABAC

Role-Based Access Control (RBAC) grants permissions by role ("admin can refund orders"). It's simple and auditable, but coarse — it can't express "a user can view their own orders but not anyone else's" without an extra object-level check. Attribute-Based Access Control (ABAC) evaluates permissions against attributes of the user, resource, and context ("allow if request.user.id == order.owner_id"). ShopFlow needs both: RBAC for admin-vs-customer, ABAC for object ownership.

IDOR: The Access Control Bug That Keeps Recurring

Insecure Direct Object Reference (IDOR) happens when an endpoint trusts a client-supplied identifier without checking whether the current user is allowed to access that specific object. It is the single most common real-world instance of Broken Access Control, precisely because it's invisible in a code review that only checks "is the user logged in" — the missing check is "is the user logged in and this is their object."

// VULNERABLE — checks authentication, not authorization (IDOR)
app.get("/api/orders/:id", requireAuth, async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  res.json(order); // any logged-in user can read any order by guessing IDs
});

// FIXED — object-level authorization enforced on every request
app.get("/api/orders/:id", requireAuth, async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  if (!order) return res.status(404).json({ error: "Not found" });

  const isOwner = order.customerId === req.user.id;
  const isAdmin = req.user.roles.includes("admin");
  if (!isOwner && !isAdmin) {
    return res.status(403).json({ error: "Forbidden" });
  }
  res.json(order);
});

Least Privilege as a Default, Not an Afterthought

Design new endpoints deny-by-default: no route should return data until an explicit allow rule matches. Retrofitting least privilege onto an existing "open unless denied" system means auditing every endpoint one at a time — designing it in from the start costs one extra line per route.

Retrieval practice: before reading further, write from memory the authorization check you would add to a DELETE /api/reviews/:id endpoint on ShopFlow. Then compare against your own reasoning above — did you check both "logged in" and "owns this review or is admin"?

Module 1.4 — Secrets & Sensitive Data Protection

Level: Beginner–Intermediate · Prereqs: 1.1 · Time: ~3h
Skip-check (test-out): Explain the difference between encryption at rest and in transit, and configure a secrets manager to rotate a database credential without downtime.
Skip if: You already use a secrets manager (not .env files) in production and enforce field-level encryption for PII.
Unlocks: 2.2, 4.2, 4.4

Encryption in Transit vs. at Rest

TLS (Module 2.2) protects data while it moves between client, server, and database — it does nothing once that data is written to disk. Encryption at rest (database-level or field-level) protects data while it's stored, which matters if a disk, backup, or database snapshot is exfiltrated independently of any live request. Both are required; neither substitutes for the other.

Secrets Do Not Belong in Code, Env Files, or Git History

A `.env` file committed once and later deleted is still in git history forever unless the repo is rewritten — and a leaked API key or database password is exploitable the moment it's pushed, not the moment someone notices. A secrets manager (AWS Secrets Manager, HashiCorp Vault, Doppler) centralizes secrets, supports rotation without a redeploy, and gives you an audit log of who accessed what and when.

// Fetching a rotatable secret at runtime instead of baking it into env vars
import { SecretsManagerClient, GetSecretValueCommand } from "@aws-sdk/client-secrets-manager";

const client = new SecretsManagerClient({ region: "ap-southeast-1" });

async function getDbCredentials() {
  const res = await client.send(
    new GetSecretValueCommand({ SecretId: "shopflow/prod/db-credentials" })
  );
  return JSON.parse(res.SecretString); // { username, password } — rotated by the secrets manager, not the app
}

PII Minimization and Field-Level Encryption

The cheapest way to protect data is to not collect it. For data ShopFlow must retain (payment last-4, shipping address), apply field-level encryption so a database compromise doesn't expose plaintext PII even if the attacker has full read access to the table. Store the encryption key in the secrets manager, never alongside the encrypted data.

// Field-level encryption for a sensitive column (Node crypto, AES-256-GCM)
import crypto from "node:crypto";

function encryptField(plaintext, keyBuffer) {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv("aes-256-gcm", keyBuffer, iv);
  const ciphertext = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  const authTag = cipher.getAuthTag();
  return Buffer.concat([iv, authTag, ciphertext]).toString("base64");
}

Disambiguation: "Encrypted" and "hashed" are not interchangeable. Passwords are hashed (one-way, with a slow algorithm like bcrypt or argon2) because you never need to recover the original value — only verify a match. PII you must display back to a user (an address, a phone number) is encrypted (two-way, reversible with the key) because the plaintext is needed again later.

Module 2.1 — Input Validation & Injection Defense

Level: Intermediate · Prereqs: 1.3 · Time: ~4h
Skip-check (test-out): Given a raw SQL query built with string concatenation, rewrite it safely, and explain why output-encoding (not input-blocklisting) is the correct XSS defense.
Skip if: You already use parameterized queries and a strict CSP everywhere and can explain SSRF in one sentence.
Unlocks: 2.2, 2.3, 2.4

The Common Root Cause: Trusting Data That Crosses a Trust Boundary

SQL injection, XSS, CSRF, and SSRF look like different bugs but share one root cause — data crossing a trust boundary (user input → database, user input → HTML, attacker's browser → your session, attacker's payload → your server's outbound requests) without being treated as untrusted at that boundary. Fix the boundary, not the symptom.

SQL Injection: Parameterize, Never Concatenate

// VULNERABLE — string concatenation lets an attacker close the quote and inject SQL
const query = `SELECT * FROM products WHERE category = '${req.query.category}'`;
// attacker sends: category=x' OR '1'='1  →  returns every row in the table

// FIXED — parameterized query; the driver treats the value as data, never as SQL syntax
const result = await db.query(
  "SELECT * FROM products WHERE category = $1",
  [req.query.category]
);

XSS: Output Encoding Beats Input Blocklisting

Blocklisting input (stripping `<script>`) is a losing game against attacker creativity — there are dozens of encodings and contexts (`<img onerror=>`, `javascript:` URIs, SVG) a blocklist will miss. Encode output for the context it's rendered into instead: React/Next.js auto-escapes JSX text by default, so the real danger is `dangerouslySetInnerHTML` and direct DOM writes that bypass that protection.

// VULNERABLE — bypasses React's automatic escaping
function ProductReview({ review }) {
  return <div dangerouslySetInnerHTML={{ __html: review.text }} />; // attacker's <script> runs
}

// FIXED — render as text; React escapes it automatically
function ProductReview({ review }) {
  return <div>{review.text}</div>;
}

CSRF: SameSite Cookies + Explicit Tokens

Cross-Site Request Forgery tricks a logged-in user's browser into submitting a request the user never intended, relying on the browser automatically attaching session cookies. SameSite=Strict cookies (Module 1.2) close most of this; for state-changing requests, add an explicit CSRF token as defense-in-depth, since some legitimate cross-site navigation flows require SameSite=Lax.

SSRF: Now Filed Under A01 Broken Access Control

Server-Side Request Forgery tricks your server into making a request on the attacker's behalf — e.g., a "fetch image from URL" feature that instead targets http://169.254.169.254/ (a cloud metadata endpoint) to steal IAM credentials. OWASP 2025 folded SSRF into Broken Access Control because the fix is the same category of control: the server should only be authorized to reach an explicit allowlist of destinations, never an attacker-supplied one.

Common mistake: Assuming a modern framework's defaults make you immune. React escapes JSX, Express doesn't auto-parameterize raw SQL strings, and Next.js doesn't stop you from disabling CSP. Frameworks reduce the number of ways to get it wrong; they don't remove your responsibility to understand the boundary you're crossing.

TLS and HSTS: Making HTTPS Non-Optional

TLS encrypts traffic between client and server, but a user typing a bare domain or clicking an old `http://` link is briefly vulnerable to downgrade attacks unless the server tells the browser to never use plaintext again. HTTP Strict Transport Security (HSTS) does that — once a browser sees the header, it refuses plaintext HTTP to that domain for the specified duration, even if an attacker on the network tries to intercept and downgrade the connection.

app.use((req, res, next) => {
  res.setHeader("Strict-Transport-Security", "max-age=63072000; includeSubDomains; preload");
  next();
});

Content-Security-Policy: Nonce, Not a Blocklist

A strict CSP is the single most effective XSS mitigation layered on top of output encoding — it tells the browser which script sources are legitimate, so even an injected `<script>` tag simply won't execute. The current best practice is a nonce-based policy: generate a fresh, cryptographically random nonce per response, and only scripts carrying that exact nonce are allowed to run. A static allowlist of domains is weaker and easier to bypass than a per-request nonce.

import crypto from "node:crypto";

app.use((req, res, next) => {
  const nonce = crypto.randomBytes(16).toString("base64");
  res.locals.cspNonce = nonce; // pass to your templating layer to stamp onto <script nonce="...">

  res.setHeader(
    "Content-Security-Policy",
    `default-src 'self'; script-src 'self' 'nonce-${nonce}' 'strict-dynamic'; ` +
    `style-src 'self' 'nonce-${nonce}'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'`
  );
  next();
});

Common mistake: Writing middleware that regex-replaces every `<script>` tag with a nonce attribute. An attacker's injected script tag gets the same regex treatment and inherits the nonce too, defeating the whole point. Nonces must come from server-side template rendering that only stamps nonces onto scripts you authored — never a post-hoc string transform on the final HTML.

Rate Limiting and a WAF: Different Layers

Rate limiting protects a specific endpoint from abuse (credential stuffing on `/login`, scraping on `/api/products`) at the application layer. A Web Application Firewall (WAF — Cloudflare, AWS WAF) sits in front of the whole app and blocks known attack signatures, bad bots, and volumetric abuse before it reaches your servers at all. Use both: the WAF as a coarse first filter, rate limiting for endpoint-specific business logic the WAF can't know about.

import rateLimit from "express-rate-limit";

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5,                       // 5 attempts per IP per window
  standardHeaders: true,
  legacyHeaders: false,
  message: { error: "Too many login attempts, try again later." },
});

app.post("/auth/login", loginLimiter, loginHandler);

Why Supply Chain Got Its Own OWASP Category in 2025

A typical Next.js app pulls in hundreds of transitive dependencies — each one is code you did not write, did not review, and are nonetheless running with full application privileges. A compromised or vulnerable dependency (or a compromised build pipeline that injects malicious code at build time) bypasses every application-layer defense from Modules 2.1–2.2 entirely, because the malicious code runs as your application, not against it. This is exactly why OWASP introduced A03:2025 — Software Supply Chain Failures.

Three Tools, Three Jobs

The current standard open-source AppSec toolchain divides cleanly by what each tool actually scans: Semgrep (SAST) scans your own source code for insecure patterns; Trivy (SCA) scans your dependencies and container images for known CVEs; OWASP ZAP (DAST — Module 2.4) scans your running application from the outside. Together they catch roughly 60–70% of common vulnerability classes with zero manual review, which is why all three belong in CI, not just in an annual audit.

Manual Testing With a Proxy: Where Automation Stops

Automated DAST catches known patterns; it does not understand your business logic. A logic flaw like "the checkout API trusts a client-supplied `price` field" needs a human intercepting and modifying requests with Burp Suite Community or OWASP ZAP's manual proxy mode to find — the tool shows you every request, but deciding which parameter is worth tampering with is the tester's judgment, built from the OWASP Top 10 categories in Module 1.1.

Responsible Scope and Rules of Engagement

Every security test — automated or manual — needs an explicit, written scope before it runs: which environment (never production without sign-off), which endpoints are in/out of bounds, and who to notify if something breaks. Testing without authorization, even against your own company's systems, can violate internal policy or, in the worst case, computer-fraud law; a one-paragraph rules-of-engagement doc protects both the tester and the org.

Common mistake: Running a DAST scan once before launch and calling the app "pentested." A scan is a point-in-time result against the app's current state and the scanner's current ruleset — new code ships, new CVEs get disclosed, and yesterday's clean scan says nothing about today's app. DAST belongs in the ongoing pipeline (2.3's CI), not a pre-launch ritual.

Module 3.1 — SRE Principles, SLIs, SLOs & Error Budgets

Reliability Is a Product Decision, Not an Engineering Absolute

100% uptime is neither achievable nor, past a point, worth pursuing — every additional nine of reliability costs disproportionately more engineering effort for diminishing user-perceived benefit. SRE's founding insight (from Google's original SRE book) is to make reliability an explicit, negotiated target instead of an unstated assumption that engineering either silently over-invests in or silently fails to meet.

SLI, SLO, SLA: Three Different Things

  • SLI (Service Level Indicator) — a measured metric, e.g., "the percentage of HTTP requests to `/checkout` that complete in under 500ms with a 2xx status."
  • SLO (Service Level Objective) — the internal target for that SLI, e.g., "99.9% of checkout requests meet that bar, measured over a rolling 30 days."
  • SLA (Service Level Agreement) — an external, often contractual, commitment with consequences for missing it. Not every service needs one; every service should have SLIs and SLOs.

Error Budgets: Turning a Target Into a Decision Rule

An error budget is simply 1 − SLO: a 99.9% SLO leaves a 0.1% budget for failure. As long as that budget isn't spent, the team ships freely; once it is, the team stops shipping features and works on reliability until the budget recovers. This resolves the perennial tension between velocity and stability with a number instead of an argument.

# Error budget for a 99.9% SLO over a 30-day rolling window
# Total requests in window:        4,320,000
# Allowed failures (0.1% budget):  4,320
# Failures so far this window:     2,850
# Budget remaining:                (4320 - 2850) / 4320 = 34%

A common tiered policy: >75% budget remaining → normal deploy velocity; 50–75% → cautious deploys, extra review; 25–50% → reliability-focused, defer risky changes; <25% → feature freeze, reliability work only. If a single incident burns more than 20% of the budget in one event, that alone triggers a mandatory postmortem (Module 3.3) regardless of the running total.

Common mistake: Setting every service's SLO to 99.99% "to be safe." A service three hops downstream of the checkout flow, with graceful degradation already handling its failure, does not need the same reliability target as checkout itself — and chasing 99.99% everywhere burns engineering effort disproportionate to user impact. Set the SLO to match what users actually need for that specific service.

OpenTelemetry Is Now the Default

OpenTelemetry graduated the CNCF in May 2026 and is now the de facto observability standard — metrics, logs, and traces are stable across every major language SDK, unified under one wire protocol (OTLP) and one semantic-convention layer, with continuous profiling entering release-candidate status as a fourth signal. Instrument against OpenTelemetry rather than a vendor-proprietary SDK: you keep the freedom to swap Prometheus/Grafana, Datadog, or any OTLP-compatible backend without re-instrumenting the app.

// OpenTelemetry setup for a Node/Express service — traces + metrics
import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-http";
import { PeriodicExportingMetricReader } from "@opentelemetry/sdk-metrics";
import { OTLPMetricExporter } from "@opentelemetry/exporter-metrics-otlp-http";

const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter({ url: "http://otel-collector:4318/v1/traces" }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({ url: "http://otel-collector:4318/v1/metrics" }),
  }),
  instrumentations: [getNodeAutoInstrumentations()],
  serviceName: "shopflow-api",
});

sdk.start();

The Three Signals, Each With a Job

Metrics answer "how much / how often" cheaply at scale (request rate, error rate, p99 latency — the raw material for SLIs). Logs answer "what exactly happened" for one specific event, at the cost of volume. Traces answer "where did the time go across services" for one specific request, connecting a slow checkout to the exact downstream call that caused it. A dashboard built from metrics alone can tell you checkout is slow; only a trace tells you it's slow because the payment gateway call is retrying three times.

Alert on SLO Burn Rate, Not Raw Thresholds

A raw threshold alert ("latency > 500ms") fires on noise and misses slow-burning problems that never cross the instantaneous threshold but still consume the monthly error budget. A burn-rate alert compares the rate of budget consumption against the SLO window — "we're burning the 30-day budget fast enough to exhaust it in 6 hours" is a far more actionable, false-positive-resistant signal.

Structure Beats Heroics Under Pressure

An incident without defined roles collapses into everyone debugging the same log tail while no one is deciding what to communicate, to whom, or when to escalate. A minimal structure — an Incident Commander (coordinates, does not personally debug), a comms lead (updates stakeholders), and however many responders are actually needed — keeps an incident moving even when the people involved are stressed and tired.

Severity Levels Drive Response, Not Just Labeling

A severity scale should map directly to a response: SEV1 (full outage or data loss — page immediately, all-hands) down to SEV4 (minor, no user impact — ticket, business hours). The scale exists so the on-call engineer doesn't have to invent an escalation decision from scratch at 3 a.m.; they classify and the process tells them what happens next.

Blameless Postmortems: Fix the System, Not the Person

A blameless postmortem assumes every person involved made a reasonable decision given what they knew at the time — the useful question is never "who broke it" but "what about our system made this mistake possible, and easy to make." Blaming a person produces defensiveness and hidden information in the next incident; fixing the system produces a genuinely more reliable system.

Failure Is Guaranteed; Cascading Failure Is a Design Choice

A downstream dependency (payment gateway, email service, search index) will eventually be slow, erroring, or unreachable — that's guaranteed. Whether one dependency's failure takes down your entire application is not guaranteed; it's the direct result of whether you designed for isolation and graceful degradation, or let every request block synchronously on every dependency succeeding.

Retries With Backoff, Circuit Breakers, Timeouts

A naive retry on failure can make an already-struggling downstream service worse by adding load exactly when it can least handle it — exponential backoff with jitter spaces retries out and avoids synchronized retry storms across many clients. A circuit breaker goes further: after enough consecutive failures, it stops calling the downstream service entirely for a cooldown period, failing fast instead of piling up slow, doomed requests.

// Circuit breaker around ShopFlow's payment gateway call (using opossum)
import CircuitBreaker from "opossum";

async function callPaymentGateway(payload) {
  const res = await fetch("https://payments.example/charge", {
    method: "POST",
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(3000), // hard timeout — never wait forever
  });
  if (!res.ok) throw new Error(`Payment gateway error: ${res.status}`);
  return res.json();
}

const breaker = new CircuitBreaker(callPaymentGateway, {
  timeout: 3000,
  errorThresholdPercentage: 50, // trip after 50% of requests fail
  resetTimeout: 15000,          // try again after 15s cooldown
});

breaker.fallback(() => ({ status: "queued", message: "Payment queued for retry" }));

app.post("/api/checkout", async (req, res) => {
  const result = await breaker.fire(req.body);
  res.json(result);
});

Graceful Degradation: Decide What "Down" Means Per Feature

Not every feature needs to be available for the app to be "up." If ShopFlow's recommendation engine is down, showing the product page without recommendations is graceful degradation; if checkout is down, the app is genuinely down for its core purpose. Design each feature's failure mode deliberately at build time, not by accident when it actually fails.

Chaos Engineering: Verify Resilience, Don't Assume It

A circuit breaker you've never watched trip under real failure is a hypothesis, not a verified property. Chaos engineering deliberately injects failure (kill a service instance, add latency, drop network packets) in a controlled blast radius to confirm the system degrades the way you designed it to — run first in staging, with a clear hypothesis and an automatic abort condition, before ever considering production.

Why This Is Now OWASP's #2 Risk

Security Misconfiguration jumped from #5 to #2 in the 2025 OWASP Top 10 precisely because so much of a modern application's attack surface now lives in infrastructure config — a permissive IAM policy, a container running as root, a default-open security group — rather than application code. These misconfigurations are invisible to the SAST/DAST tooling from Modules 2.3–2.4, which look at application code and running behavior, not infrastructure definitions.

Hardened Containers: Small, Non-Root, Scanned

# Dockerfile — hardened multi-stage build for ShopFlow's API service
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .

FROM node:22-alpine
RUN addgroup -S shopflow && adduser -S shopflow -G shopflow
WORKDIR /app
COPY --from=build --chown=shopflow:shopflow /app .
USER shopflow
EXPOSE 3000
CMD ["node", "server.js"]

A minimal Alpine base reduces the attack surface (fewer packages, fewer CVEs to track); running as a non-root user means a container-escape vulnerability doesn't hand the attacker root on the host; the multi-stage build keeps dev dependencies and build tools out of the final image entirely.

Least-Privilege IAM: Scope to the Actual Task

A service account with broad admin permissions "to be safe" is the cloud-era equivalent of A01 Broken Access Control at the infrastructure layer — if that service is compromised, the attacker inherits every permission it was granted, whether or not the service ever used them. Scope IAM policies to exactly what the service does.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:ap-southeast-1:*:secret:shopflow/prod/*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::shopflow-product-images/*"
    }
  ]
}

This policy grants exactly two capabilities — reading ShopFlow's own secrets and reading/writing to one specific S3 bucket — nothing broader, so a compromised API container cannot pivot into unrelated AWS resources.

Kubernetes-Specific Hardening (If ShopFlow Runs on K8s)

Pod Security Standards (restricted profile), network policies that default-deny cross-namespace traffic, and read-only root filesystems on containers all apply the same least-privilege logic at the orchestration layer — a compromised pod should not be able to reach every other pod in the cluster or write to its own filesystem to persist malware.

Skip-check (test-out): Design a layered DDoS/bot mitigation strategy (edge, application, business-logic) and explain what "never trust, always verify" changes about internal service-to-service calls.
Skip if: You already operate behind a WAF/CDN with bot mitigation and enforce mTLS or equivalent for internal service calls.
Unlocks: 4.4, Phase 4 Capstone

Layered Defense Against Volumetric and Logic-Layer Abuse

Distributed Denial of Service defense works in layers because different attack types hit different layers: a CDN/edge network (Cloudflare, AWS CloudFront + Shield) absorbs volumetric network-layer floods before they ever reach your servers; a WAF filters application-layer attack patterns; and business-logic rate limiting (Module 2.2) catches abuse that looks like legitimate traffic at the network layer but isn't — like a bot checking out one item at a time to exhaust inventory.

Bot Mitigation Beyond Rate Limiting

Simple rate limiting catches naive scripted abuse; sophisticated bots rotate IPs and mimic human timing to stay under any per-IP threshold. Behavioral signals (mouse movement, request timing entropy, TLS fingerprinting) and challenge-response mechanisms (CAPTCHA as a last resort, not a first line) catch what pure rate limiting misses, typically delegated to the CDN/WAF layer rather than built in-house.

Zero Trust: No Implicit Trust From Network Location

Traditional "castle and moat" security trusts anything already inside the corporate network or VPC — a single compromised service inside that perimeter then has broad implicit access to everything else inside it. Zero Trust architecture removes that assumption entirely: every service-to-service call is authenticated and authorized on its own merits (mTLS, short-lived service tokens), regardless of whether the caller is "inside" the network. This directly limits blast radius — the same principle as least-privilege IAM (Module 4.2), applied to service-to-service traffic instead of service-to-cloud-resource permissions.

# Simplified service mesh policy — deny by default, allow explicit service-to-service calls with mTLS
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: shopflow-checkout-policy
  namespace: shopflow
spec:
  selector:
    matchLabels:
      app: checkout-service
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/shopflow/sa/api-gateway"]
      to:
        - operation:
            methods: ["POST"]
            paths: ["/internal/checkout"]

This policy allows only the API gateway's service identity to call the checkout service's internal endpoint — any other service in the cluster, even on the same internal network, is denied by default.

Disambiguation: Zero Trust is an architecture principle ("verify every call, trust no network location"), not a specific product — vendors selling "Zero Trust" appliances are implementing the principle, not defining it. The principle applies whether you use a service mesh, mTLS certificates, or short-lived signed service tokens to enforce it.

Compliance Frameworks as Minimum Bars, Not Ceilings

SOC 2, GDPR, and the Philippines Data Privacy Act (RA 10173) codify minimum expectations for handling user data responsibly — passing an audit proves you met that floor, not that you're secure. For a Philippines-market product like ShopFlow, RA 10173 is the binding legal baseline: it requires a lawful basis for processing, data subject rights (access, correction, erasure), breach notification within 72 hours to the National Privacy Commission, and privacy-by-design in system architecture. Everything built in Modules 1.4 and 4.2 (PII classification, encryption, least-privilege access) is what makes RA 10173 compliance achievable rather than a paperwork exercise bolted on after the fact.

SOC 2 for B2B Trust

SOC 2 evaluates a service against five trust principles — security, availability, processing integrity, confidentiality, privacy — through evidence collected over an observation period (a Type II report), not a point-in-time check. For a SaaS product selling to enterprise customers, SOC 2 is frequently the deciding factor in a procurement process; the SLOs, incident response, and access controls from Phases 1–3 of this guide are exactly the evidence a SOC 2 audit collects.

Game Days: Rehearsing Incidents Before They're Real

A game day is a scheduled, deliberate simulation of an incident — security or reliability — run against a real (usually staging) environment with the actual on-call team, to find gaps in tooling, runbooks, and communication before a real incident exposes them under pressure. It is chaos engineering (Module 4.1) extended beyond a single technical fault to the full human response process.

# Game Day Plan: Simulated Credential-Stuffing Attack on ShopFlow Login

## Objective
Verify the team detects and responds to a credential-stuffing attack within
the incident response process (Module 3.3), without being told in advance
what the scenario is.

## Scenario
A scripted load test sends 50 req/s of login attempts from a rotating pool
of IPs against staging, using a leaked-password-style username/password list.

## Success Criteria
1. Rate limiting (Module 2.2) engages within 60 seconds.
2. An alert fires and the on-call engineer acknowledges within 5 minutes.
3. The team correctly classifies this as a security incident, not a reliability
   incident, and follows the security escalation path.
4. A postmortem is written within 48 hours, blameless, with action items.

## Facilitator Notes
Do not reveal the scenario to the responding team in advance. Have an abort
switch ready to stop the load test immediately if staging is affected
unexpectedly. Debrief immediately after resolution while memory is fresh.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Application Security Terms

Authentication
The process of verifying that a user or system is who it claims to be.
Avoid: "Auth" alone — ambiguous with authorization; specify which.
Authorization
The process of determining whether an already-authenticated identity is permitted to perform a specific action on a specific resource.
Avoid: Using "permissions" and "authorization" interchangeably without distinguishing the check (authorization) from the data (permissions) it evaluates.
IDOR (Insecure Direct Object Reference)
An access control flaw where an endpoint trusts a client-supplied identifier without verifying the current user is permitted to access that specific object.
Avoid: Confusing with generic "authorization bug" — IDOR specifically refers to the object-identifier pattern.
OWASP Top 10
A community-consensus ranking of the ten most critical web application security risks, refreshed periodically from real-world CVE and breach data — currently the 2025 edition.
Avoid: Treating it as an exhaustive checklist rather than a prioritized starting point for threat modeling.
SAST (Static Application Security Testing)
Automated analysis of source code for insecure patterns, without running the application.
Avoid: Confusing with DAST, which tests a running application from the outside.
DAST (Dynamic Application Security Testing)
Automated testing of a running application by sending it requests and observing responses, with no source code access.
Avoid: "Pentest" as a synonym — DAST is automated and pattern-based; a pentest includes human judgment and business-logic testing.
SCA (Software Composition Analysis)
Automated scanning of third-party dependencies and container images for known vulnerabilities (CVEs).
Avoid: Assuming SCA covers your own code — it only covers dependencies, not first-party source (that's SAST).
SBOM (Software Bill of Materials)
A machine-readable inventory of every component and dependency included in a specific software release.
Avoid: None common — the term is specific and not usually confused.
CSP (Content-Security-Policy)
An HTTP response header that instructs the browser which sources of scripts, styles, and other resources are allowed to load or execute on a page.
Avoid: Confusing with CORS, which governs cross-origin requests, not what resources a page is allowed to load/execute.
Zero Trust
An architecture principle requiring every request — including internal service-to-service calls — to be authenticated and authorized on its own merits, with no implicit trust granted by network location.
Avoid: Treating it as a specific vendor product rather than the underlying principle a product implements.

Reliability & SRE Terms

SLI (Service Level Indicator)
A specific, measured metric quantifying some aspect of the service level provided (e.g., percentage of requests under 500ms).
Avoid: Confusing with SLO — the SLI is the measurement, the SLO is the target for that measurement.
SLO (Service Level Objective)
An internal target value or range for an SLI, over a defined measurement window.
Avoid: Confusing with SLA, which is an external, often contractual, commitment.
Error Budget
The allowable amount of unreliability (1 minus the SLO) within a measurement window, used as a data-driven trigger for deploy-freeze or reliability-focused work.
Avoid: Treating it as a punishment mechanism rather than a shared, negotiated decision rule between product and engineering.
Burn-Rate Alert
An alert that fires based on how fast an error budget is being consumed relative to the measurement window, catching both fast, dramatic failures and slow, sustained degradation.
Avoid: "Threshold alert" as a synonym — a raw threshold alert doesn't account for the budget window at all.
Circuit Breaker
A resilience pattern that stops calling a failing downstream dependency after a failure threshold is crossed, failing fast during a cooldown period instead of continuing to send doomed requests.
Avoid: Confusing with a simple retry — a circuit breaker actively stops calling, retries just repeat the call.
Blameless Postmortem
A structured incident review that assumes every participant made a reasonable decision given what they knew at the time, focused on identifying systemic contributing factors rather than individual fault.
Avoid: "Root cause analysis" used as a full synonym — RCA is one section of a postmortem, not the whole practice.
Chaos Engineering
The practice of deliberately injecting controlled failure into a system to verify it degrades the way it was designed to, rather than assuming resilience untested.
Avoid: Confusing with unplanned outages — chaos engineering is deliberate, scoped, and hypothesis-driven.
Game Day
A scheduled, deliberate simulation of an incident (security or reliability) run against a real environment with the actual response team, to find gaps before a real incident does.
Avoid: Treating it as identical to chaos engineering — a game day tests the human response process, not just the technical system.
Observability
The property of a system that lets you infer its internal state from its external outputs (metrics, logs, traces), especially for states you didn't anticipate needing to debug in advance.
Avoid: "Monitoring" as a full synonym — monitoring typically means watching known, predefined signals; observability supports investigating unknown-unknowns.
