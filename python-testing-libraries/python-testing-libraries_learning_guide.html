How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone tests the same realistic TindaHub domain code — small, pure pricing, discount, and order-validation functions modeled on the same Philippine sari-sari-store distribution business used elsewhere in this workspace, so every test you write is testing something a real order-management feature would actually need.

Scope note: this guide assumes you've already seen pytest basics — the Python Learning Guide's Module 5.1 covers writing a fixture, a parametrized test, and running coverage. It also assumes you may have already written FastAPI-specific tests using TestClient and database-fixture isolation, covered in the FastAPI guide's Module 3.3 — this guide doesn't repeat that web-specific material. What this guide covers instead: pytest's deeper fixture architecture, mocking, and plugin ecosystem (Phases 1–2); property-based testing with Hypothesis, a fundamentally different testing strategy from anything in either guide above (Phase 3); and realistic fake-data generation with Faker (Phase 4). All three are library-agnostic — useful whether the code under test is a FastAPI app, a CLI tool, or a plain Python package.

Module 1.1 — Fixture Scopes, Factories & conftest.py Architecture

Skip if: Fixture scoping and conftest.py organization are already deliberate choices, not defaults you never think about.
Unlocks: Module 1.2, Module 1.4, Module 2.1

Fixture scope: how often does setup actually need to run?

A fixture's scope controls how often pytest re-runs its setup: function (the default — fresh for every test), class, module, or session (once for the entire test run). Choosing too narrow a scope wastes time re-doing expensive setup (spinning up a database connection per test when one per session would do); choosing too broad a scope risks tests silently sharing state and passing or failing depending on execution order — one of the hardest categories of test bug to diagnose, because the test that fails isn't the test with the actual problem.

import pytest

@pytest.fixture(scope="session")
def db_engine():
    engine = create_test_engine()   # expensive: once per test run
    yield engine
    engine.dispose()

@pytest.fixture(scope="function")
def db_session(db_engine):
    connection = db_engine.connect()
    transaction = connection.begin()
    yield connection
    transaction.rollback()          # cheap: fresh, isolated state per test
    connection.close()

Common mistake: confusing a yield fixture (the pattern above — a fixture that uses yield to separate setup from teardown, still fully supported and the standard way to write pytest fixtures) with the old nose-style "yield tests" (a test function itself using yield to produce multiple sub-tests), which pytest 9 removed entirely. If you see a "yield tests are no longer supported" error migrating an old codebase, that's the removed pattern, not this one — yield-based fixture teardown is unaffected and still the correct, idiomatic approach.

Fixture factories: fixtures that return a function

Sometimes a single fixture value isn't enough — a test needs to create several similar-but-distinct objects. A fixture factory is a fixture whose return value is itself a function, which the test then calls (possibly multiple times, with different arguments) to produce what it actually needs.

@pytest.fixture
def make_order():
    created = []
    def _make_order(customer_id=1, status="pending", **overrides):
        order = {"customer_id": customer_id, "status": status, **overrides}
        created.append(order)
        return order
    yield _make_order
    # created list available here for any needed teardown/inspection after the test

def test_order_defaults(make_order):
    order = make_order()
    assert order["status"] == "pending"

def test_order_override(make_order):
    order = make_order(status="shipped", customer_id=7)
    assert order["status"] == "shipped"

conftest.py: sharing fixtures without importing them

Fixtures defined in a conftest.py file are automatically available to every test in that directory and its subdirectories — no explicit import required, which is what makes it the standard place for shared setup (database connections, app instances, common factories). A larger project typically has a top-level conftest.py for suite-wide fixtures and additional conftest.py files in specific subdirectories for fixtures only relevant to that subset of tests.

Module 1.2 — Parametrization Patterns & Test IDs

Level: Intermediate · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Stack two @pytest.mark.parametrize decorators to produce a cartesian product of cases, assign readable ids, and use indirect parametrization to run a fixture differently per case.
Skip if: All three of these patterns are already comfortable.
Unlocks: Module 1.3, Phase 1 Capstone

Stacking parametrize for combinations

A single @pytest.mark.parametrize runs a test once per listed case; stacking two decorators produces the cartesian product of both parameter sets — every combination of the two, not just a paired sequence. This is the tool for "test this function against every combination of input type A and input type B," which would otherwise require manually writing out every pair.

import pytest

@pytest.mark.parametrize("quantity", [1, 5, 100])
@pytest.mark.parametrize("discount_rate", [0.0, 0.1, 0.5])
def test_order_total_never_negative(quantity, discount_rate):
    total = calculate_order_total(unit_price=50.0, quantity=quantity, discount_rate=discount_rate)
    assert total >= 0
    # this runs 3 x 3 = 9 times, one per (discount_rate, quantity) combination

Readable test IDs

Without explicit ids, pytest generates test names from the parameter values themselves, which gets unreadable fast for complex objects (dicts, tuples). Passing ids= (a list of strings, or a function computing one from each parameter set) makes failing-test output immediately legible instead of requiring you to cross-reference a numeric index back to the parametrize list.

@pytest.mark.parametrize(
    "unit_price, quantity, discount_rate, expected",
    [
        (100.0, 1, 0.0, 100.0),
        (100.0, 2, 0.1, 180.0),
        (50.0, 10, 0.25, 375.0),
    ],
    ids=["no-discount", "ten-percent-two-units", "quarter-off-bulk"],
)
def test_order_total_known_values(unit_price, quantity, discount_rate, expected):
    assert calculate_order_total(unit_price, quantity, discount_rate) == expected

Indirect parametrization

Normally, parametrized values go straight into the test function's arguments. indirect=True instead routes them through a fixture first — useful when each parametrized case needs some setup logic applied to the raw value before the test uses it, rather than the raw value itself.

@pytest.fixture
def price_list_variant(request):
    variant_name = request.param
    if variant_name == "sale":
        return {"Lucky Me Pancit Canton": 12.0}
    return {"Lucky Me Pancit Canton": 15.0}

@pytest.mark.parametrize("price_list_variant", ["regular", "sale"], indirect=True)
def test_pricing_under_variant(price_list_variant):
    assert price_list_variant["Lucky Me Pancit Canton"] > 0

Built-in markers: skip, skipif, xfail

@pytest.mark.skip(reason=...) unconditionally skips a test; @pytest.mark.skipif(condition, reason=...) skips only when a condition is true (a Python version check, a missing optional dependency); @pytest.mark.xfail(reason=...) runs the test but expects it to fail — useful for a known bug you've filed but not yet fixed, tracked explicitly in the test suite rather than silently commented out. An xfail test that unexpectedly passes is reported as XPASS, which is worth paying attention to: it usually means the underlying bug got fixed and the marker should be removed.

import sys
import pytest

@pytest.mark.skipif(sys.version_info < (3, 12), reason="requires the 3.12 typing syntax")
def test_new_syntax_feature():
    ...

@pytest.mark.xfail(reason="known rounding bug in bulk discounts over 90% — see TICKET-142")
def test_extreme_bulk_discount():
    assert calculate_order_total(100.0, 1000, 0.95) >= 0

Custom markers and registering them

Custom markers (@pytest.mark.slow, @pytest.mark.integration) categorize tests for selective running, but pytest warns about unregistered markers by default — register them explicitly in pyproject.toml (or pytest.ini) so a typo in a marker name produces a clear warning instead of a silently-ignored, do-nothing marker.

[tool.pytest.ini_options]
markers = [
    "slow: marks tests as slow (deselect with '-m \"not slow\"')",
    "integration: marks tests requiring a real database connection",
]

pytest -m "not slow"              # run everything except slow tests
pytest -m "integration"           # run only integration tests
pytest -k "discount"              # run tests whose name contains "discount"

Common mistake: not registering custom markers and not enabling strict-marker checking, so a typo like @pytest.mark.slwo silently does nothing instead of erroring — add --strict-markers to your pytest configuration so unregistered markers fail the run immediately rather than quietly excluding tests you meant to include.

pytest-mock's mocker fixture vs. raw unittest.mock

unittest.mock (stdlib) is the actual mocking engine underneath both; pytest-mock is a thin wrapper providing a mocker fixture with one meaningful convenience: every patch made through mocker.patch(...) is automatically undone at the end of the test, with no manual stop() call or context-manager nesting required. Raw unittest.mock.patch as a decorator or context manager works identically in terms of what gets mocked; the difference is purely about cleanup ergonomics and code shape when several things need patching in one test.

import requests

def get_exchange_rate():
    response = requests.get("https://api.example.com/rates/PHP")
    return response.json()["rate"]

def test_get_exchange_rate(mocker):
    mock_response = mocker.Mock()
    mock_response.json.return_value = {"rate": 56.25}
    mocker.patch("requests.get", return_value=mock_response)

    assert get_exchange_rate() == 56.25
    # no manual cleanup needed — mocker undoes the patch automatically after this test

monkeypatch: pytest's built-in patching fixture

monkeypatch (built into pytest, no plugin required) covers a related but distinct need: temporarily setting an attribute, environment variable, dictionary item, or sys.path entry, with automatic restoration — it overlaps with mocker for simple attribute patching but is the more natural choice specifically for environment variables and similar process-level state.

import os

def get_api_key():
    return os.environ["TINDAHUB_API_KEY"]

def test_get_api_key(monkeypatch):
    monkeypatch.setenv("TINDAHUB_API_KEY", "test-key-123")
    assert get_api_key() == "test-key-123"
    # TINDAHUB_API_KEY is restored to its original state (or unset) after this test

When mocking signals a design problem

Needing to mock three or four internal collaborators just to test one function's basic logic is often a signal that the function is doing too much or is too tightly coupled to those collaborators — not a signal to write a more elaborate mock. A function that's mostly pure logic with side effects (network calls, file I/O, database access) pushed to its edges needs little or no mocking to test the logic itself; a function that interleaves logic and I/O throughout needs heavy mocking precisely because the design makes them inseparable. Treat a mock-heavy test as a prompt to ask whether the code under test could be restructured, not just as a testing inconvenience to push through.

Common mistake: mocking so much of a function's internals that the test ends up verifying "the mocks were called the way I told them to behave," which is nearly tautological, rather than verifying real behavior. Mock at the boundary (the actual network call, the actual file write) — not the business logic that sits on top of it.

Measuring coverage

pytest-cov (current version 7.1.0) reports what fraction of your code's lines (or, with branch coverage enabled, decision branches) actually executed during the test run — a proxy for "how much of this code do the tests even touch," not a direct measure of correctness.

pytest --cov=tindahub_pricing --cov-report=term-missing

Name                  Stmts   Miss  Cover   Missing
---------------------------------------------------
tindahub_pricing.py      12      2    83%   9-10

The Missing column gives exact line numbers not exercised by any test — the actionable output of a coverage report, more useful day-to-day than the percentage alone.

Enforcing a minimum threshold in CI

--cov-fail-under=N makes the test run itself fail if coverage drops below N percent, turning coverage from a report you might ignore into a gate that blocks a regression from merging.

pytest --cov=tindahub_pricing --cov-report=term-missing --cov-fail-under=90

What coverage does not guarantee

100% line coverage means every line ran at least once during the test suite — it says nothing about whether the assertions checking that line's behavior are actually correct, or complete. A test that calls calculate_order_total(100, 2, 0.1) and asserts only result > 0 gets full coverage of that line while missing an actual bug in the calculation (say, the discount being applied to the wrong operand) — the line executed, but nothing verified it executed correctly. Branch coverage (--cov-branch) closes part of this gap by also requiring every conditional branch to be taken at least once, but even that is a floor on thoroughness, not a ceiling.

Common mistake: treating "100% coverage" as equivalent to "well tested" and stopping there. Coverage answers "did this line run," never "was this line's behavior actually checked correctly." A high coverage number with weak assertions is a false sense of security — worse in some ways than a low, honest number, because it looks finished.

Running tests across multiple workers

pytest-xdist distributes a test suite across multiple worker processes, cutting wall-clock time roughly in proportion to available CPU cores for a suite whose tests are independent of each other.

pytest -n auto              # use one worker per available CPU core
pytest -n 4                 # use exactly 4 workers

What makes a test suite parallel-safe

Parallelization exposes exactly the same shared-state bugs Module 1.1's fixture-scope discussion warned about, just more reliably — two tests running concurrently in different worker processes and both writing to the same file, the same database row, or the same global variable will produce nondeterministic, hard-to-reproduce failures. A test suite that passes reliably in sequence but fails intermittently under -n auto almost always has a hidden shared-state dependency that sequential execution happened to mask.

Common mistake: assuming a flaky failure under -n auto is pytest-xdist's fault. It's almost always an existing isolation bug in the suite itself that sequential execution never surfaced — two tests sharing a database, a temp file path, or a module-level counter. Fix the isolation (per-test temp directories, per-worker database schemas) rather than treating parallelism itself as unreliable.

Module 2.3 — Testing Async Code with pytest-asyncio

Level: Intermediate · Prereqs: Module 1.1 · Time: ~2h

Why async tests need a plugin at all

pytest's test runner is fundamentally synchronous; an async def test_...() function, run without help, doesn't actually get awaited — pytest just calls it, gets back an unawaited coroutine object, and (depending on configuration) either silently "passes" without running any of the test's actual body, or warns about it. pytest-asyncio bridges this gap by running each async test inside an event loop pytest manages for you.

import pytest

async def fetch_delivery_status(order_id: int) -> str:
    # a real implementation would await an actual async HTTP call
    return "in_transit"

@pytest.mark.asyncio
async def test_fetch_delivery_status():
    status = await fetch_delivery_status(order_id=1)
    assert status == "in_transit"

With asyncio_mode = "auto" set in configuration, the @pytest.mark.asyncio marker becomes unnecessary — every async def test_... is treated as an async test automatically. Either mode is valid; the "strict" mode (explicit marker required) makes it harder to accidentally write a silently-not-actually-running async test, which is why it's worth knowing the marker exists even under auto mode.

Async fixtures

A fixture can itself be async def, for setup that requires awaiting something (an async database connection, an async HTTP client) — pytest-asyncio handles awaiting it before handing the result to the test, the same as any other fixture.

@pytest.fixture
async def async_courier_client():
    client = AsyncCourierClient()
    await client.connect()
    yield client
    await client.close()

@pytest.mark.asyncio
async def test_with_async_fixture(async_courier_client):
    eta = await async_courier_client.get_eta("Cebu City")
    assert eta is not None

Hooks in conftest.py: customizing pytest's own behavior

Beyond fixtures, a conftest.py can define pytest hooks — specially-named functions pytest calls automatically at specific points in the test run (collection, setup, reporting). pytest_collection_modifyitems is a common one: it runs after pytest has discovered all tests but before running them, letting you programmatically re-order, skip, or mark tests based on their location or name.

# conftest.py
def pytest_collection_modifyitems(config, items):
    for item in items:
        if "integration" in str(item.fspath):

Module 3.1 — From Examples to Properties: given() & Strategies

Level: Intermediate · Prereqs: Basic pytest · Time: ~2.5h

The mental shift: properties, not examples

Every test so far in this guide has been example-based: you pick specific input values, compute (by hand or by reasoning) the expected output, and assert they match. This works well but only tests exactly the cases you thought to write — if you didn't think of quantity 0, or a discount rate of exactly 1.0, that case simply isn't tested. Hypothesis flips this: instead of picking example inputs, you describe a property — something that should hold true for every valid input, not just the ones you happened to think of — and Hypothesis generates hundreds of varied inputs (biased toward tricky edge cases: zero, negative numbers, very large numbers, empty strings) looking for one that breaks the property.

from hypothesis import given, strategies as st

@given(
    unit_price=st.floats(min_value=0.01, max_value=10_000, allow_nan=False, allow_infinity=False),
    quantity=st.integers(min_value=1, max_value=10_000),
    discount_rate=st.floats(min_value=0.0, max_value=0.99),
)
def test_order_total_is_never_negative(unit_price, quantity, discount_rate):
    total = calculate_order_total(unit_price, quantity, discount_rate)
    assert total >= 0    # this property should hold for EVERY valid combination, not just a few examples

@given(
    unit_price=st.floats(min_value=0.01, max_value=10_000, allow_nan=False, allow_infinity=False),
    quantity=st.integers(min_value=1, max_value=10_000),
)
def test_zero_discount_equals_undiscounted_subtotal(unit_price, quantity):
    total_no_discount = calculate_order_total(unit_price, quantity, discount_rate=0.0)
    assert total_no_discount == round(unit_price * quantity, 2)

Hypothesis runs each @given-decorated test 100 times by default (configurable), each time with a different generated set of arguments — a single def test_... function body is doing the work of what would otherwise be dozens or hundreds of manually-written example cases.

Common strategies

st.integers(), st.floats(), st.text(), st.lists(...), st.dictionaries(...), and st.sampled_from([...]) (pick from a fixed set) cover most basic needs; each accepts constraints (min_value, max_value, min_size) narrowing the generated range to values that are actually valid for what you're testing — generating truly unconstrained floats (including NaN, infinity, and astronomically large values) is rarely what a specific test needs, so constraining strategies deliberately (as in the example above) is the normal, expected pattern, not a workaround.

st.builds: generating instances of a class or function

st.builds(SomeClass, field=strategy, ...) generates instances of SomeClass by calling it with generated arguments for each named field — the simplest way to get Hypothesis generating whole domain objects rather than bare primitives, when the object's fields don't need to satisfy relationships with each other.

from dataclasses import dataclass
from hypothesis import given, strategies as st

@dataclass
class OrderLine:
    unit_price: float
    quantity: int
    discount_rate: float

order_line_strategy = st.builds(
    OrderLine,
    unit_price=st.floats(min_value=0.01, max_value=10_000, allow_nan=False),
    quantity=st.integers(min_value=1, max_value=1000),
    discount_rate=st.floats(min_value=0.0, max_value=0.99),
)

@given(order_line_strategy)
def test_order_line_total_never_negative(line):
    total = calculate_order_total(line.unit_price, line.quantity, line.discount_rate)
    assert total >= 0

st.composite: when fields depend on each other

When one field's valid range depends on another's value (a "discount tier" that must match a specific quantity threshold, say), @st.composite gives you a function-based strategy where you explicitly draw each value in sequence, letting later draws depend on earlier ones.

from hypothesis import strategies as st

@st.composite
def bulk_discount_scenario(draw):
    quantity = draw(st.integers(min_value=1, max_value=1000))
    # discount tier is coupled to quantity: only larger orders can have larger discounts
    max_discount = 0.05 if quantity < 50 else 0.30
    discount_rate = draw(st.floats(min_value=0.0, max_value=max_discount))
    unit_price = draw(st.floats(min_value=0.01, max_value=10_000, allow_nan=False))
    return unit_price, quantity, discount_rate

@given(bulk_discount_scenario())
def test_bulk_discount_scenario_total(scenario):
    unit_price, quantity, discount_rate = scenario
    total = calculate_order_total(unit_price, quantity, discount_rate)
    assert total >= 0

filter and assume: rejecting invalid draws

.filter(predicate) on a strategy discards generated values failing the predicate before the test even runs; assume(condition) called inside a test body abandons that particular generated example (without failing the test) if the condition is false. Both exist for the same reason: sometimes it's easier to generate broadly and reject the invalid cases than to construct a strategy that only ever generates valid ones — but over-filtering (rejecting the vast majority of generated examples) slows Hypothesis down and is usually a sign the strategy itself should be redesigned instead.

Shrinking: why Hypothesis reports the simplest failure, not the first

When Hypothesis finds an input that breaks a property, it doesn't just report that raw (often large, complex, hard-to-read) input — it automatically searches for a simpler input that still triggers the same failure, a process called shrinking. A failure first found with quantity=8472, discount_rate=0.73128841 might shrink down to quantity=1, discount_rate=1.0, which is far easier to reason about and almost always points more directly at the actual bug's root cause than the original, more complicated failing example would.

Reproducibility: seeds and the example database

Hypothesis is randomized by nature, but a specific found failure is not lost between runs: it's automatically cached in a local .hypothesis/ example database and re-tried first on every subsequent run, so a bug found once keeps failing (and getting reported) until it's actually fixed — it doesn't require a lucky re-roll of the random generator to reproduce. For a specific regression you want permanently pinned into the test itself (not just cached locally, but committed and visible in the test code), @example(specific_value) adds an explicit, guaranteed-to-run case alongside the randomly generated ones.

from hypothesis import given, example, strategies as st

@given(quantity=st.integers(min_value=1, max_value=10_000))
@example(quantity=1)          # always explicitly tested, regardless of what's randomly generated
@example(quantity=10_000)     # the documented upper boundary, pinned as a permanent regression check
def test_quantity_boundary_handling(quantity):
    total = calculate_order_total(unit_price=10.0, quantity=quantity, discount_rate=0.0)
    assert total > 0

Common mistake: deleting the local .hypothesis/ directory (e.g., as part of an overly broad "clean" script) and assuming nothing is lost. Doing so discards the cache of previously-found failing examples, meaning a known-flaky edge case might not resurface on the very next run purely by chance — treat it as a genuinely useful local cache, not disposable build output, though it should still be gitignored rather than committed (each developer's cache is independent).

Module 3.4 — Stateful Testing with RuleBasedStateMachine

Level: Advanced · Prereqs: Module 3.2 · Time: ~2.5h

Beyond single function calls: testing sequences of operations

Every property test so far has tested one function call in isolation. Real bugs often live in sequences of operations on stateful objects — an order's status transitions (pending → shipped → delivered, but never delivered → pending), a shopping cart's add/remove/checkout flow — where the bug only appears after a specific, non-obvious sequence of calls. RuleBasedStateMachine lets Hypothesis generate and try random sequences of operations (not just random single-call arguments), checking that declared invariants hold after every single step, no matter what sequence led there.

from hypothesis.stateful import RuleBasedStateMachine, rule, invariant
from hypothesis import strategies as st

class OrderStatusMachine(RuleBasedStateMachine):
    def __init__(self):
        super().__init__()
        self.status = "pending"

    @rule()
    def ship(self):
        if self.status == "pending":
            self.status = "shipped"

    @rule()
    def deliver(self):
        if self.status == "shipped":
            self.status = "delivered"

    @rule()
    def cancel(self):
        if self.status in ("pending", "shipped"):
            self.status = "cancelled"

    @invariant()
    def never_reverts_from_delivered(self):
        # once delivered, no rule in this machine should ever be able to change it back
        if self.status == "delivered":
            assert self.status == "delivered"   # trivially true here — a real invariant would check history

TestOrderStatusMachine = OrderStatusMachine.TestCase

Hypothesis explores many different random sequences of ship/deliver/cancel calls (including calling the same rule multiple times, calling them out of the "expected" order, and every combination in between), checking the @invariant after each step — exactly the kind of exploratory, sequence-sensitive testing that would be tedious and incomplete to hand-write as individual example-based tests.

Faker instances and providers

A Faker() instance exposes dozens of providers — categories of realistic-looking fake data (name, address, email, date_of_birth, company, and many more), each returning a plausible-looking value that is not real data. This makes Faker the right tool for filling in realistic-looking demo data, seed scripts, or fixtures where the actual content doesn't matter but its shape (a name that looks like a name, an email that looks like an email) does.

from faker import Faker

fake = Faker()
print(fake.name())            # "Maria Elena Reyes" — a plausible name, not a real person
print(fake.email())           # a plausible email
print(fake.address())         # a plausible multi-line address

fake_ph = Faker("fil_PH")     # locale-specific: Filipino/Philippine-flavored names and formats
print(fake_ph.name())

Seeding for reproducibility

Faker's output is randomized by default — two runs produce different fake data. Faker.seed(n) makes that randomness deterministic, which matters whenever you need the exact same "random" data across runs (a reproducible demo, a test asserting against generated data, a bug report that needs to reproduce exactly).

from faker import Faker

Faker.seed(42)
fake = Faker()
print(fake.name())    # always the same output, every run, given the same seed

Avoiding accidental duplicates with .unique

Generating many fake emails or usernames independently can (rarely, but eventually) produce a duplicate, which breaks a test relying on unique values (a unique-constraint database column, say). fake.unique.email() guarantees no duplicate is returned within that Faker instance's lifetime, raising an error instead if it genuinely runs out of unique values for the given constraints (call fake.unique.clear() to reset between test runs if needed).

Faker for realistic fixtures, Hypothesis for adversarial inputs

Faker and Hypothesis solve genuinely different problems, and conflating them is a common source of a test suite that's neither properly realistic nor properly thorough. Faker generates data that looks like real-world data — useful when a test's setup needs a plausible customer, address, or order, but the test's actual logic doesn't depend on exploring edge cases in that data. Hypothesis generates data specifically biased toward breaking your code — zeros, negative numbers, empty strings, maximum-length strings, values right at a boundary — useful when the test's whole point is finding those edge cases. A fixture using Faker to build a "realistic" order in a test that isn't actually about pricing edge cases is the correct use; using Faker's realistic-but-not-adversarial names as the input to a property test whose entire purpose is edge-case-hunting would quietly defeat that test's purpose.

import pytest
from faker import Faker

@pytest.fixture
def fake_customer():
    fake = Faker()
    Faker.seed(1)
    return {"name": fake.name(), "email": fake.email(), "city": fake.city()}

def test_order_confirmation_includes_customer_name(fake_customer):
    # this test is about the confirmation-message logic, not about pricing edge cases —
    # a realistic Faker-generated customer is exactly the right fixture here
    message = build_order_confirmation(fake_customer, order_total=250.0)
    assert fake_customer["name"] in message

Common mistake: using Faker to generate the numeric inputs (prices, quantities) for what's supposed to be a thorough edge-case test. Faker's fake.pyfloat() or similar generates plausible-looking numbers, not the deliberately awkward ones (zero, negative, boundary values) Hypothesis is specifically designed to find — reach for Hypothesis strategies, not Faker, whenever the test's actual job is hunting for numeric edge cases.

Faker inside a Hypothesis-generated domain object's non-tested fields

The two can still combine within a single test: a composite Hypothesis strategy (Module 3.2) can use Faker to fill in fields that need to look realistic but aren't themselves the property under test, while still using proper Hypothesis strategies for the fields that are. This keeps the "realistic-looking data, adversarial numbers" distinction intact within a single generated object.

from hypothesis import given, strategies as st
from faker import Faker

fake = Faker()
Faker.seed(0)

@st.composite
def order_with_realistic_customer(draw):
    quantity = draw(st.integers(min_value=1, max_value=1000))       # Hypothesis: adversarial
    discount_rate = draw(st.floats(min_value=0.0, max_value=0.99))  # Hypothesis: adversarial
    customer_name = fake.name()    # Faker: realistic, not the thing under test here
    return customer_name, quantity, discount_rate

A decision framework

QuestionToolWhy
Testing one specific, known scenario with a clear expected result?pytest example-based testDirectly readable, directly maps to a documented requirement or bug report.
Need to verify an invariant holds across a wide, hard-to-enumerate input range?Hypothesis @givenGenerates and shrinks adversarial inputs you likely wouldn't think to write by hand.
Need to test whether a sequence of stateful operations ever breaks an invariant?Hypothesis RuleBasedStateMachineExplores operation sequences, not just single-call arguments.
Need realistic-looking (not adversarial) data to set up a test's fixture?FakerPlausible names/addresses/emails; not designed to hunt edge cases.
Need to isolate a function's logic from a network/file/database dependency?pytest-mock / monkeypatchMock at the boundary; a design smell if overused deep inside logic.
Need confidence a test suite hasn't quietly stopped exercising some code?pytest-covAnswers "did this run," not "was this correctly checked" — pair with real assertions.
Need to seed a demo, staging environment, or manual QA pass with plausible data?FakerThe same realistic-data need as a fixture, just outside the test suite itself.

The throughline: each tool answers a different question about correctness

An example-based test answers "does this specific, known case work?" A property-based test answers "does this general rule hold, across inputs I didn't specifically think of?" Fake data (Faker) answers neither question directly — it answers "does this code behave reasonably against data that looks like the real world?", which is a different, complementary concern from correctness under adversarial input. A mature test suite uses all three deliberately, not by default reflex: example-based tests to document and lock in specific known behaviors, property-based tests to search for the edge cases nobody wrote down, and Faker to keep fixtures realistic enough that example-based tests aren't accidentally testing against unrealistic toy data.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

pytest Architecture

Fixture scope
How often a fixture's setup (and teardown) runs relative to the tests using it — function, class, module, or session.
Avoid: assuming scope only affects performance — too broad a scope risks tests sharing state and becoming order-dependent.
Yield fixture
A fixture using yield to separate setup (before the yield) from teardown (after it) — the standard, fully-supported pattern for fixtures needing cleanup.
Avoid: confusing this with the removed nose-style "yield tests" (a test function itself using yield, unrelated and gone as of pytest 9) — different concept, same keyword.
Marker
A label (@pytest.mark.name) attached to a test, used to categorize it for selective running, skipping, or expected-failure handling.
Avoid: using an unregistered custom marker without --strict-markers enabled — a typo silently does nothing instead of erroring.
N+1-style flakiness (parallel isolation bug)
A test failure that appears only intermittently under parallel execution, caused by two tests sharing mutable state (a file, a database row, a global) that sequential execution happened to keep safe.
Avoid: blaming the parallelization tool itself for this kind of flakiness — it's almost always a pre-existing isolation bug the tool merely exposed.

Hypothesis & Property-Based Testing

Property
A statement that should hold true for every valid input to some code, as opposed to a single expected input/output pair.
Avoid: "assertion" as a strict synonym — every property test contains assertions, but a property is specifically the general rule being tested, not the specific check.
Strategy
A Hypothesis object describing how to generate values of a particular kind or shape, used to supply arguments to a @given-decorated test.
Avoid: "generator" as a strict synonym — Python generators are a distinct language feature; "strategy" is Hypothesis's specific term.
Shrinking
Hypothesis's automatic process of simplifying a found failing input down to the smallest/simplest input that still triggers the same failure.
Avoid: assuming the first failing input Hypothesis mentions in its search is the one it ultimately reports — the reported one is post-shrinking, deliberately simplified.
Stateful testing
Testing a sequence of operations against an object with internal state, checking declared invariants after each step, rather than testing one function call in isolation.
Avoid: "integration testing" as a substitute term — stateful testing is specifically about operation sequences and invariants, independent of whether real external systems are involved.

Faker & Fake Data

Provider
A Faker category of realistic-looking fake data generation (name, address, email, etc.), exposed as a method on a Faker instance.
Avoid: "field" as a substitute term — a provider is the generator itself; a field is where its output ends up.
Seeding (Faker)
Setting Faker's random state to a fixed value via Faker.seed(n) so the same sequence of "random" fake data is produced on every run.
Avoid: confusing Faker's seeding with Hypothesis's example database — they solve a similar reproducibility problem in unrelated, non-interchangeable ways.
Realistic vs. adversarial data
The core distinction this guide draws between Faker's output (plausible-looking, representative of typical real-world values) and Hypothesis's output (deliberately biased toward edge cases: zero, negative, boundary, and malformed-looking values).
Avoid: using Faker where the test's actual purpose is edge-case hunting, or Hypothesis where a fixture just needs to look plausible — each is a poor substitute for the other's actual strength.
