How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone uses the same realistic TindaHub marketplace dataset — a Philippine online store with COD orders priced in pesos. schema.sql and seed.sql now live in the shared datasets folder — Module 1.2's psql command below points there.

Already studied the Data Analyst guide? Its Phase 4 — SQL Mastery covers analyst-style querying (SELECT, joins, window functions, CTEs) against a sales table. This guide treats PostgreSQL itself as the subject — schema design, indexing, performance, JSONB, transactions — and then layers a full Metabase BI track on top. The querying modules here (Phase 2) overlap by design so this guide stands alone; if you tested out of analyst SQL, jump straight to Phase 3 and Phase 4.

Module 1.1 — Setup & psql

Level: Beginner · Prereqs: None · Time: ~2h
Skip-check (test-out): From a clean machine, start a PostgreSQL 16 server in Docker, connect with psql, and run \dt against a database you created.
Skip if: You already run PostgreSQL locally and are fluent with psql meta-commands.
Unlocks: 1.2, 4.1

Run PostgreSQL the reproducible way

Installing a database server globally on your laptop leaves version drift and leftover data directories you forget about. Running it in Docker gives you a disposable, version-pinned server you can throw away and rebuild — which matters because every exercise here assumes a known PostgreSQL version and a clean slate you can return to.

# Start PostgreSQL 16 with a named volume so data survives container restarts
docker run --name tindahub-pg \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_DB=tindahub \
  -p 5432:5432 \
  -v tindahub_data:/var/lib/postgresql/data \
  -d postgres:16

# Connect with the psql client running inside the same container
docker exec -it tindahub-pg psql -U postgres -d tindahub

No Docker? Native setup on macOS (Homebrew). If you don't have a container runtime, Homebrew's PostgreSQL gives you the same server natively — only the start-up step differs; every SQL exercise is identical. The trade-off: it runs as a long-lived background service rather than a disposable container, so "throw it away and rebuild" becomes "re-run schema.sql" instead of docker rm.

# Install and start PostgreSQL 17 as a background service (persists across reboots)
brew install postgresql@17
brew services start postgresql@17

# Homebrew puts the binaries off-PATH; add them for this shell
export PATH="$(brew --prefix postgresql@17)/bin:$PATH"

# Your macOS username is the default superuser role (no password — local trust auth)
createdb tindahub
psql -d tindahub                       # connect; \q to quit

# Connection URI for Metabase / other tools later:
#   postgresql://localhost:5432/tindahub

Loading the schema and seed is then a one-liner you can re-run any time to reset to a clean slate — this replaces the Docker volume as your "known starting point". schema.sql and seed.sql live in the shared datasets folder, not alongside this guide — adjust the path to wherever you cloned/downloaded it:

psql -d tindahub -f ../datasets/tindahub/schema.sql -f ../datasets/tindahub/seed.sql

psql meta-commands you will use daily

psql is the official terminal client. Its backslash meta-commands are not SQL — they are client shortcuts that inspect the database far faster than writing catalog queries by hand.

\l              -- list databases
\dt             -- list tables in the current schema
\d customers    -- describe the customers table (columns, types, indexes)
\dn             -- list schemas
\di             -- list indexes
\x              -- toggle expanded display (great for wide rows)
\timing on      -- show how long each query takes
\copy orders FROM 'orders.csv' WITH (FORMAT csv, HEADER)   -- bulk load a CSV
\q              -- quit

The difference between \copy (runs client-side, reads a file on your machine) and the SQL COPY (runs server-side, reads a file on the server) trips up beginners constantly — inside Docker the server cannot see your laptop's filesystem, so you almost always want \copy.

Connection strings

Tools like Metabase, Prisma, and psql itself all accept a libpq connection URI. Knowing its anatomy means you can connect anything.

postgresql://USER:PASSWORD@HOST:PORT/DBNAME?sslmode=require
# example for the local container:
postgresql://postgres:devpass@localhost:5432/tindahub

pgAdmin: a GUI alternative to psql

Everything in this guide is written against psql because the terminal is scriptable, reproducible, and works identically on any machine — but you are not locked into it. pgAdmin is the official PostgreSQL GUI client, and many learners find it easier to build a mental model of the database when they can see the object tree (databases → schemas → tables → columns) rather than typing \d repeatedly. Use whichever fits how you think — the SQL you write is identical either way.

Rule of thumb: reach for pgAdmin when you want to browse (inspect an unfamiliar schema, eyeball data in a grid, click through foreign keys) and reach for psql when you want to automate (re-run a script, chain commands, work over SSH with no display). Most people end up using both — pgAdmin to explore, psql for the repeatable one-liners in this guide.

Installing pgAdmin

# macOS — download the .dmg from pgadmin.org, or via Homebrew Cask:
brew install --cask pgadmin4

pgAdmin runs as a desktop app that opens a local browser tab (it's a web UI served on your own machine, not a hosted service — your credentials and query results never leave your laptop).

Connecting to the same server this guide uses

  1. Open pgAdmin → right-click Servers in the left tree → Register → Server…
  2. General tab: Name it anything, e.g. TindaHub local.
  3. Connection tab:
    • Host: localhost (or 127.0.0.1 if the Docker native-Homebrew setup earlier in this module used that)
    • Port: 5432
    • Maintenance database: tindahub
    • Username: postgres (Docker path) or your macOS username (native Homebrew path, trust auth — leave password blank)
  4. Save. The left tree now shows Servers → TindaHub local → Databases → tindahub → Schemas → public → Tables — expand it to browse columns, indexes, and constraints without typing \d.

"Connection refused" on port 5432? pgAdmin can prompt for a password before it even reaches the server, which makes a stopped server look like a login problem. Rule it out first: on native Homebrew installs, brew services list shows the status of postgresql@17 — if it says anything other than started, run brew services start postgresql@17 and retry the connection. If it's already running, the error is a genuine auth/network issue instead.

Module 1.2 — Data Types & Schema Design

Skip-check (test-out): Draw the TindaHub ERD and write the CREATE TABLE statements for all six tables with correct types, keys, and constraints.
Skip if: You can confidently choose between numeric, integer, text, and timestamptz and normalize a schema to 3NF.

Choosing the right type

The column type is the first and cheapest integrity control you have. A money amount stored as float will silently accumulate rounding errors; a date stored as text cannot be sorted or filtered by range. Get the type right and a whole class of bugs never happens.

Use caseTypeWhy
Surrogate keybigint GENERATED ALWAYS AS IDENTITYStandard, gap-tolerant auto-increment; preferred over serial
Money (₱)numeric(12,2)Exact decimal — never float for currency
Counts / quantitiesintegerWhole numbers, 4 bytes
Free texttextNo length penalty in PostgreSQL; varchar(n) only when a real limit exists
TimestamptimestamptzStores an instant in UTC; timestamp (no tz) drops the offset
Yes/no flagbooleanClearer than 0/1 integers
Fixed set of valuestext + CHECK or an enumConstrains to known states like order status

Common mistake: using float/double precision for prices. 0.1 + 0.2 is not 0.3 in binary floating point. Money is always numeric. Reserve float for genuinely approximate measurements like sensor readings.

The TindaHub schema

TindaHub is a Philippine online marketplace: customers place orders that contain line items of products, and each order is paid (usually by Cash on Delivery). Six tables, normalized so each fact lives in exactly one place.

CREATE TABLE categories (
  category_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name         text NOT NULL UNIQUE
);

CREATE TABLE customers (
  customer_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  full_name    text NOT NULL,
  email        text NOT NULL UNIQUE,
  city         text NOT NULL,
  province     text NOT NULL,
  region       text NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  product_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  category_id  bigint NOT NULL REFERENCES categories(category_id),
  name         text NOT NULL,
  price        numeric(12,2) NOT NULL CHECK (price >= 0),
  is_active    boolean NOT NULL DEFAULT true,
  attributes   jsonb NOT NULL DEFAULT '{}'::jsonb
);

CREATE TABLE orders (
  order_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  bigint NOT NULL REFERENCES customers(customer_id),
  status       text NOT NULL DEFAULT 'pending'
               CHECK (status IN ('pending','shipped','delivered','cancelled')),
  ordered_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_item_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id      bigint NOT NULL REFERENCES orders(order_id) ON DELETE CASCADE,
  product_id    bigint NOT NULL REFERENCES products(product_id),
  quantity      integer NOT NULL CHECK (quantity > 0),
  unit_price    numeric(12,2) NOT NULL CHECK (unit_price >= 0)
);

CREATE TABLE payments (
  payment_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id     bigint NOT NULL UNIQUE REFERENCES orders(order_id),
  method       text NOT NULL CHECK (method IN ('cod','gcash','card','bank')),
  amount       numeric(12,2) NOT NULL CHECK (amount >= 0),
  paid_at      timestamptz
);

Keys, foreign keys, and normalization

Notice unit_price is copied onto order_items rather than always read from products.price. That is deliberate: a product's price changes over time, but an order must remember what the customer actually paid. Normalization removes redundant data, not historical data — telling them apart is the core schema-design judgment call.

Foreign keys (REFERENCES) make the database reject orphan rows — you cannot insert an order item for a product that does not exist. ON DELETE CASCADE on order_items means deleting an order automatically removes its lines, while the absence of cascade on products protects you from deleting a product that orders still reference.

Module 1.3 — Inserting & Modifying Data

Level: Beginner · Prereqs: 1.2 · Time: ~3h
Skip-check (test-out): Seed all six tables with realistic data, then write an idempotent upsert that re-runs without creating duplicates.
Skip if: You are fluent with multi-row INSERT, UPDATE...FROM, DELETE, and ON CONFLICT.
Unlocks: 2.1, 3.4

INSERT, including multi-row and RETURNING

RETURNING is a PostgreSQL feature that hands back generated values (like the new identity key) in the same round trip, so you don't need a second query to find out what id you just created.

INSERT INTO categories (name) VALUES
  ('Electronics'), ('Home & Living'), ('Groceries'), ('Fashion');

INSERT INTO customers (full_name, email, city, province, region) VALUES
  ('Maria Santos', 'maria@example.com', 'Cebu City', 'Cebu', 'Central Visayas'),
  ('Jose Reyes',   'jose@example.com',  'Davao City', 'Davao del Sur', 'Davao Region')
RETURNING customer_id, full_name;

UPDATE and DELETE

The single most expensive mistake in SQL is an UPDATE or DELETE with no WHERE clause — it rewrites or removes every row in the table. Always write the WHERE first, and consider running the matching SELECT before you commit.

-- Mark an order delivered
UPDATE orders SET status = 'delivered' WHERE order_id = 1;

-- UPDATE ... FROM: deactivate products whose category was discontinued
UPDATE products p
SET is_active = false
FROM categories c
WHERE p.category_id = c.category_id AND c.name = 'Fashion';

DELETE FROM orders WHERE status = 'cancelled' AND ordered_at < now() - interval '1 year';

UPSERT with ON CONFLICT

An upsert inserts a row, or updates it if a unique key already exists. This is what makes a seed or sync script idempotent — safe to run repeatedly without creating duplicates, which is essential for reproducible data pipelines.

INSERT INTO categories (name) VALUES ('Electronics')
ON CONFLICT (name) DO NOTHING;

-- Or update on conflict:
INSERT INTO products (category_id, name, price)
VALUES (1, 'USB-C Charger 30W', 499.00)
ON CONFLICT (product_id) DO UPDATE
  SET price = EXCLUDED.price;

Module 2.1 — SELECT, Filtering & Sorting

Level: Beginner · Prereqs: 1.3 · Time: ~3h
Skip-check (test-out): Write a query that returns active products under ₱500 in Electronics, sorted by price descending, showing only the first 10.

Unlocks: 2.2, 2.3, 3.2, 4.1

SELECT, projection, and aliases

SQL is declarative: you describe the result you want, not the steps to get it. The clauses are written in a fixed order but evaluated in another — FROM then WHERE then SELECT then ORDER BY then LIMIT — which is why you cannot reference a SELECT alias inside WHERE.

SELECT name AS product_name,
       price,
       price * 1.12 AS price_with_vat   -- 12% PH VAT
FROM products
WHERE is_active = true;

Filtering with WHERE

SELECT * FROM products
WHERE category_id = 1                 -- Electronics
  AND price BETWEEN 100 AND 500
  AND name ILIKE '%charger%'          -- ILIKE = case-insensitive LIKE
  AND is_active = true;

SELECT * FROM orders
WHERE status IN ('shipped','delivered')
  AND ordered_at >= date '2026-01-01';

Common mistake: filtering for missing values with = NULL. NULL means "unknown", so anything = NULL is itself NULL (never true). Use IS NULL / IS NOT NULL. This is the single most common reason a "correct-looking" filter returns zero rows.

Sorting, DISTINCT, and LIMIT

SELECT DISTINCT region FROM customers ORDER BY region;

SELECT name, price
FROM products
WHERE category_id = 1 AND is_active = true
ORDER BY price DESC
LIMIT 10;

Module 2.2 — Aggregation & Grouping

Level: Beginner–Intermediate · Prereqs: 2.1 · Time: ~3h
Skip-check (test-out): Compute revenue per category and return only categories with revenue above ₱10,000, sorted high to low.
Skip if: You know the difference between WHERE and HAVING and can use COUNT/SUM/AVG with GROUP BY and FILTER.
Unlocks: 2.4, 2.5, 4.1

Aggregate functions

An aggregate collapses many rows into one summary value. The mental model: GROUP BY sorts rows into buckets, then each aggregate runs once per bucket.

SELECT COUNT(*)            AS order_count,
       SUM(quantity)       AS units_sold,
       AVG(unit_price)     AS avg_line_price,
       MAX(unit_price)     AS top_line_price
FROM order_items;

GROUP BY and HAVING

WHERE filters rows before grouping; HAVING filters groups after aggregating. Using the wrong one either misses the aggregate (you can't put SUM(...) in WHERE) or scans rows you could have eliminated cheaply.

SELECT c.name AS category,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM order_items oi
JOIN products p   ON p.product_id = oi.product_id
JOIN categories c ON c.category_id = p.category_id
GROUP BY c.name
HAVING SUM(oi.quantity * oi.unit_price) > 10000
ORDER BY revenue DESC;

The FILTER clause

PostgreSQL's FILTER lets one query compute several conditional aggregates in a single pass — cleaner than wrapping each in a CASE.

SELECT
  COUNT(*)                                   AS total_orders,
  COUNT(*) FILTER (WHERE status = 'delivered') AS delivered,
  COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled
FROM orders;

The join types

A join matches rows across tables on a condition. The type decides what happens to rows with no match — and choosing wrong is how analysts silently drop or duplicate data.

JoinKeepsTypical use
INNER JOINonly matched rowsorders that have a payment
LEFT JOINall left rows + matchesall customers, even with no orders
FULL JOINall rows from bothreconciling two sources
CROSS JOINevery combinationbuilding a date × category grid
-- All customers and how many orders each placed (zero included)
SELECT c.full_name, COUNT(o.order_id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.full_name
ORDER BY orders DESC;

Multi-table joins

SELECT o.order_id, c.full_name, p.name AS product, oi.quantity, oi.unit_price
FROM orders o
JOIN customers c    ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
JOIN products p     ON p.product_id  = oi.product_id
WHERE o.status = 'delivered'
ORDER BY o.order_id;

Anti-joins and self-joins

An anti-join finds rows with no match — the classic "customers who never ordered". A LEFT JOIN keeping only the NULL side is the readable way to express it.

SELECT c.full_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

Subqueries

-- Scalar subquery: products priced above the catalog average
SELECT name, price FROM products
WHERE price > (SELECT AVG(price) FROM products);

-- Correlated subquery: customers whose latest order is delivered
SELECT c.full_name
FROM customers c
WHERE (SELECT o.status FROM orders o
       WHERE o.customer_id = c.customer_id
       ORDER BY o.ordered_at DESC LIMIT 1) = 'delivered';

Common Table Expressions (CTEs)

A CTE (WITH) names a query so you can build a result in readable, testable stages instead of deeply nested parentheses. Each step can be selected on its own while debugging.

WITH order_totals AS (
  SELECT o.order_id, o.customer_id,
         SUM(oi.quantity * oi.unit_price) AS order_value
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  GROUP BY o.order_id, o.customer_id
),
customer_spend AS (
  SELECT customer_id, SUM(order_value) AS lifetime_value
  FROM order_totals
  GROUP BY customer_id
)
SELECT c.full_name, cs.lifetime_value
FROM customer_spend cs
JOIN customers c ON c.customer_id = cs.customer_id
ORDER BY cs.lifetime_value DESC;

Recursive CTEs

A recursive CTE walks a hierarchy or generates a series by repeatedly feeding its own output back in. Here it produces a continuous calendar — invaluable for filling gaps in time-series charts later in Metabase.

WITH RECURSIVE calendar AS (
  SELECT date '2026-01-01' AS day
  UNION ALL
  SELECT day + 1 FROM calendar WHERE day < date '2026-01-31'
)
SELECT day FROM calendar;

Module 2.5 — Window Functions

Windows vs GROUP BY

A window function computes across a set of rows without collapsing them — you keep every row and add a calculated column. That is the key difference from GROUP BY, and it is what makes running totals, rankings, and row-to-row comparisons possible.

SELECT order_id, customer_id, ordered_at,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ordered_at) AS order_seq,
       RANK()       OVER (ORDER BY ordered_at)                          AS overall_rank
FROM orders;

Running totals and frames

WITH daily AS (
  SELECT date_trunc('day', o.ordered_at)::date AS day,
         SUM(oi.quantity * oi.unit_price)       AS revenue
  FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
  GROUP BY 1
)
SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM daily
ORDER BY day;

LAG, LEAD, and growth

LAG pulls a value from a previous row, letting you compute period-over-period change in pure SQL instead of exporting to a spreadsheet.

WITH monthly AS (
  SELECT date_trunc('month', o.ordered_at)::date AS month,
         SUM(oi.quantity * oi.unit_price)         AS revenue
  FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
  GROUP BY 1
)
SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev_revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS mom_growth_pct
FROM monthly
ORDER BY month;

Reading EXPLAIN ANALYZE

An index is a separate data structure that lets PostgreSQL find rows without scanning the whole table. But an index you never query is pure cost — it slows every write and takes disk. EXPLAIN ANALYZE shows you what the planner actually does, so you index based on evidence, not guesses.

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;
-- Look for "Seq Scan on orders" (reads every row) vs
-- "Index Scan using ..." (jumps straight to matches).
-- Compare "actual time" before and after adding an index.

Choosing an index

IndexBest for
B-tree (default)equality and range on a column: customer_id = 42, price < 500
Compositequeries filtering on several columns together; column order matters
Partialindexing only relevant rows: active products, undelivered orders
GINjsonb, arrays, full-text search (see 3.2)
-- Foreign keys are NOT indexed automatically — this one speeds up the join in 2.3
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- Composite: filter by customer then sort by date
CREATE INDEX idx_orders_customer_date ON orders (customer_id, ordered_at DESC);

-- Partial: only index the orders you actually query hot
CREATE INDEX idx_orders_open ON orders (ordered_at)
  WHERE status IN ('pending','shipped');

Common mistake: assuming PostgreSQL auto-indexes foreign keys. It indexes primary keys and unique constraints, but a plain foreign-key column gets no index. The join in your hottest report can quietly run a sequential scan until you add one.

When an index won't help

On a tiny table a Seq Scan is faster than an index lookup, so the planner ignores your index — that is correct, not a bug. Indexes earn their keep on large tables and selective filters. Functions on a column (WHERE lower(email) = ...) also bypass a plain index unless you build a matching expression index.

Module 3.2 — JSONB & Semi-structured Data

Level: Intermediate · Prereqs: 2.1 · Time: ~3h
Skip-check (test-out): Query a jsonb attribute, filter on a nested key, and add a GIN index that the planner uses.
Skip if: You are fluent with ->, ->>, @>, jsonb_array_elements, and GIN indexing.
Unlocks: Final Capstone

Why jsonb, and when not to

The products.attributes column is jsonb because different categories have different specs — a charger has wattage, a shirt has size. Modeling every possible attribute as its own column would leave most of them null. But jsonb is for genuinely variable data only: anything you filter or join on constantly still belongs in a real typed column, because relational constraints don't reach inside JSON.

UPDATE products SET attributes = '{"watts": 30, "ports": ["usb-c","usb-a"]}'
WHERE name = 'USB-C Charger 30W';

SELECT name,
       attributes ->> 'watts'           AS watts_text,   -- ->> returns text
       attributes -> 'ports'            AS ports_json    -- ->  returns jsonb
FROM products
WHERE attributes ? 'watts';                              -- ? = key exists

Filtering and containment

-- Containment: products that ship with a usb-c port
SELECT name FROM products
WHERE attributes @> '{"ports": ["usb-c"]}';

-- Expand a JSON array into rows
SELECT p.name, port
FROM products p, jsonb_array_elements_text(p.attributes -> 'ports') AS port;

Indexing jsonb with GIN

A GIN index makes containment (@>) and key-existence queries fast over jsonb — without it, every such query scans and parses every row's JSON.

CREATE INDEX idx_products_attrs ON products USING gin (attributes);

EXPLAIN ANALYZE
SELECT name FROM products WHERE attributes @> '{"ports": ["usb-c"]}';

Views

A view is a saved query that behaves like a table. It gives every consumer — including Metabase — one canonical definition of "order revenue", so the logic lives in one place instead of being re-pasted into a dozen dashboards.

CREATE VIEW order_revenue AS
SELECT o.order_id, o.customer_id, o.status, o.ordered_at,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
GROUP BY o.order_id, o.customer_id, o.status, o.ordered_at;

SELECT * FROM order_revenue WHERE status = 'delivered';

Materialized views

A materialized view stores the computed result on disk, so an expensive aggregate is paid once and read instantly. The trade-off: it is a snapshot and goes stale until you REFRESH it — fine for a dashboard that updates hourly, wrong for live balances.

CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', ordered_at)::date AS day, SUM(revenue) AS revenue
FROM order_revenue GROUP BY 1;

REFRESH MATERIALIZED VIEW daily_revenue;   -- run on a schedule

PL/pgSQL functions

CREATE OR REPLACE FUNCTION revenue_between(start_d date, end_d date)
RETURNS numeric
LANGUAGE plpgsql AS $$
DECLARE total numeric;
BEGIN
  SELECT COALESCE(SUM(revenue), 0) INTO total
  FROM order_revenue
  WHERE ordered_at >= start_d AND ordered_at < end_d;
  RETURN total;
END;
$$;

SELECT revenue_between(date '2026-01-01', date '2026-02-01');

Transactions and ACID

A transaction groups statements so they all succeed or all fail together — atomicity. Placing an order means inserting into orders, order_items, and payments; if the payment insert fails, you must not be left with a half-created order. Without a transaction, a crash mid-sequence leaves corrupt data that no query can trust.

BEGIN;
  INSERT INTO orders (customer_id) VALUES (1) RETURNING order_id;  -- say it returns 101
  INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (101, 5, 2, 499.00);
  INSERT INTO payments (order_id, method, amount, paid_at)
    VALUES (101, 'cod', 998.00, NULL);
COMMIT;   -- or ROLLBACK; to discard everything above

Isolation levels

Concurrency creates anomalies — two transactions reading and writing the same rows can interfere. The isolation level is the dial between speed and correctness.

LevelPreventsNote
Read Committed (default)dirty readsfine for most apps
Repeatable Read+ non-repeatable readssnapshot for a whole transaction
Serializable+ phantom readssafest; may abort with a serialization error you must retry

Constraints as the last line of defense

Application code has bugs; constraints do not get bypassed. NOT NULL, UNIQUE, CHECK, and foreign keys enforce rules at the storage layer, so even a buggy script or a direct psql session cannot write data that violates them.

ALTER TABLE order_items
  ADD CONSTRAINT positive_line_total CHECK (quantity * unit_price >= 0);

-- A deferrable constraint checked only at COMMIT (useful for circular inserts)
ALTER TABLE payments
  ADD CONSTRAINT fk_order FOREIGN KEY (order_id) REFERENCES orders(order_id)
  DEFERRABLE INITIALLY IMMEDIATE;

Variables and field filters

Metabase variables turn a static query into an interactive one. A plain {{var}} is a simple input; a field filter maps the variable to a real column so Metabase renders a smart widget (a date picker, a searchable category dropdown) and handles the SQL safely. The [[ ... ]] wrapper makes a filter optional — the clause vanishes when the user leaves it blank.

SELECT c.name AS category,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM order_items oi
JOIN products p   ON p.product_id = oi.product_id
JOIN categories c ON c.category_id = p.category_id
JOIN orders o     ON o.order_id = oi.order_id
WHERE 1=1
  [[ AND {{ ordered_at }} ]]     -- field filter mapped to orders.ordered_at (date picker)
  [[ AND c.name = {{ category }} ]]  -- simple text variable
GROUP BY 1
ORDER BY revenue DESC;

Retrieval practice: before reading the next paragraph, predict what the dashboard shows if the user leaves both filters blank. Then verify by running it.

With both filters blank, the [[ ]] clauses drop out and you get all-time revenue per category — optional filters degrade gracefully to "no filter".

Models — the reusable building block

A Metabase model is a curated, saved question other questions build on, with cleaned-up column names and types. Models are the BI-layer equivalent of a database view: define "what an order is worth" once, then let the whole team build on it without re-writing the join.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Relational Core

Relation
A table: a set of rows (tuples) sharing the same typed columns.
Avoid: "spreadsheet", "sheet" — a relation has a fixed typed schema and no inherent row order.
Primary key
The column(s) that uniquely identify each row; implies NOT NULL and UNIQUE and is auto-indexed.
Avoid: "ID column" loosely — not every id is a primary key, and a key can be composite.
Foreign key
A column whose values must match a primary key in another table, enforcing referential integrity.
Avoid: "reference column", "link" — those don't imply the database enforces the match.
Normalization
Organizing tables so each fact is stored once, removing redundancy that could go inconsistent.
Avoid: confusing with statistical "normalization" (scaling numbers) — unrelated meaning.
Surrogate key
A system-generated identifier (an identity/sequence value) with no business meaning.
Avoid: "natural key" — that is a key made of real-world data like an email; the opposite choice.

Querying

Predicate
A boolean condition in a WHERE/HAVING/ON clause that a row must satisfy.
Avoid: "filter" used vaguely — a predicate is the specific boolean expression, not the whole step.
Aggregate
A function (SUM, COUNT, AVG) that collapses many rows into one summary value per group.
Avoid: "window function" — a window keeps every row; an aggregate collapses them.
Join
An operation that combines rows from two relations based on a matching condition.
Avoid: "merge", "lookup" — those are spreadsheet/code framings, not the relational operation.
CTE (Common Table Expression)
A named, temporary result defined with WITH that exists only for the duration of one query.
Avoid: "temp table", "subquery" — a CTE is neither persisted nor (usually) nested in parentheses.
Window function
A calculation across a set of related rows (a "window") that returns one value per row without collapsing the result.
Avoid: "analytic function" loosely, and never "aggregate" — the no-collapse behavior is the distinction.

PostgreSQL Internals

Index
An auxiliary data structure that lets the engine locate rows without scanning the whole table.
Avoid: "key" — a key is a constraint; an index is the physical lookup structure (though keys create one).
Sequential scan (Seq Scan)
A query plan step that reads every row of a table; correct and fast on small tables, costly on large ones.
Avoid: "full scan" loosely — in Postgres plans the exact term is "Seq Scan".
Transaction
A unit of work that is atomic: all its statements commit together or none do.
Avoid: "batch", "session" — a session can contain many transactions; a batch implies no atomicity.
Materialized view
A view whose result is physically stored and must be explicitly refreshed; trades freshness for speed.
Avoid: "view" unqualified — a plain view stores no data and is always current.
jsonb
PostgreSQL's binary JSON type, storing decomposed JSON that supports indexing and containment operators.
Avoid: "json" type — the plain json type stores raw text and can't be GIN-indexed the same way.

Metabase & BI

Question
A single saved query in Metabase plus its chosen visualization.
Avoid: "report", "chart" alone — a question bundles the query and the chart.
Model
A curated, reusable saved question (clean columns and types) that other questions build on — the BI analogue of a view.
Avoid: "dataset" (old Metabase term) and "table" — a model is derived and curated, not raw.
Field filter
A Metabase variable mapped to a real database column, which renders a smart widget (date picker, dropdown) and injects SQL safely.
Avoid: plain "variable" — a basic {{var}} has no column mapping and no smart widget.
Dashboard
A single screen arranging multiple questions, optionally driven by shared filters.
Avoid: "report" — a dashboard is interactive and multi-card, not a static document.
Subscription
A scheduled delivery of a dashboard snapshot by email or Slack on a recurring cadence.
Avoid: "alert" — an alert fires on a threshold/condition; a subscription fires on a schedule.
