How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. All exercises use the same benchmark project: rotabrain-blades — a Next.js web app deployed on Vercel. There's no starter code to download — see the rotabrain-blades note in the shared datasets folder for a minimal equivalent to scaffold locally, or substitute any Next.js repo you already have.

Quick Start: Three Ways to Use This Guide

  1. Complete beginner → Start at Module 1.1 and follow phases sequentially.
  2. Some experience → Take the Placement Quiz below to find your entry point.
  3. Targeting a specific skill → Jump via the Module Index or choose a Learning Track.

Phase 1: Shell Foundations

Weeks 1–2 | Goal: A configured, alias-powered terminal and git identity

Module 1.1 — Terminal Orientation & zsh Setup

Level: Beginner · Prereqs: None · Time: ~1h
Skip-check: Navigate to any directory, grep for a pattern in all .tsx files, and add a shell alias — without googling anything.
Skip if: You edit ~/.zshrc comfortably, use aliases daily, and understand pipe (|) and redirect (>).
Unlocks: Module 1.2

1.1.1 The Terminal Mental Model

The terminal is a text interface to your OS. On macOS, the default shell is zsh. Your shell reads ~/.zshrc on startup — this is where aliases, paths, and environment variables live.

Three concepts unlock 80% of terminal usage:

  • Current directory (pwd) — every command runs relative to here.
  • Paths — ~ is your home directory; absolute paths start with /; relative paths start from pwd.
  • Pipes (|) — the output of one command becomes the input of the next.

1.1.2 Essential Navigation

# Where am I?
$ pwd

# List files (long format, show hidden)
$ ls -la

# Navigate
$ cd ~/projects/rotabrain-blades
$ cd ..            # up one level
$ cd -             # back to previous directory

# Create and view files
$ mkdir -p src/components
$ touch src/components/HealthScoreCard.tsx
$ cat package.json

# Find files (excluding node_modules)
$ find . -name "*.tsx" -not -path "*/node_modules/*"

# Grep file contents recursively
$ grep -r "HealthScore" src/

1.1.3 Shell Config — ~/.zshrc

Aliases live in ~/.zshrc. Changes take effect after source ~/.zshrc or opening a new terminal tab.

# Open ~/.zshrc in VS Code
$ code ~/.zshrc

# Add project navigation shortcuts
alias rotabrain="cd ~/projects/rotabrain-blades"
alias hayah="cd ~/projects/hayah-ai"

# Apply immediately
$ source ~/.zshrc
$ rotabrain    # now works

1.1.4 Pipes and Redirection

# Pipe: pass output into another command
$ npm run build 2>&1 | grep "Error"

# Redirect output to a file (stdout + stderr)
$ npm run build > build.log 2>&1

# Chain: run second command only if first succeeds
$ git add . && git commit -m "chore: initial commit"

# Chain: run second command regardless
$ git stash ; cd ..

Module 1.2 — Git Global Config & Aliases

Level: Beginner · Prereqs: Module 1.1 · Time: ~1h
Skip-check: Run git lg and see a decorated one-line graph; push a new branch with no flags (autoSetupRemote handles it).
Skip if: Your ~/.gitconfig already has rebase pull, autoSetupRemote, and a full alias set.
Unlocks: Module 2.1

1.2.1 Git Identity

$ git config --global user.name "Your Name"
$ git config --global user.email "you@example.com"
$ git config --global core.editor "code --wait"

1.2.2 The Three Most Valuable Config Lines

# pull --rebase by default (keeps history linear, no merge commits on pull)
$ git config --global pull.rebase true

# Auto -u origin on first push (no --set-upstream flag needed)
$ git config --global push.autoSetupRemote true

# autosquash: fixup!/squash! commits reorder automatically in interactive rebase
$ git config --global rebase.autosquash true

1.2.3 Git Aliases

# One-line decorated graph log (most-used alias)
$ git config --global alias.lg "log --oneline --graph --decorate"

# Shorthand for status
$ git config --global alias.st "status"

# Save everything as a WIP checkpoint
$ git config --global alias.save "!git add -A && git commit -m 'WIP: checkpoint'"

# Undo last commit, keep changes staged
$ git config --global alias.undo "reset HEAD~1"

# Nuclear: discard everything
$ git config --global alias.wipe "reset --hard HEAD"

1.2.4 Shell Aliases for Git in ~/.zshrc

alias gc="git commit -m"
alias gp="git push"
alias gpl="git pull"
alias gd="git diff"

alias gb="git branch -a"
alias gco="git checkout"
alias gcob="git checkout -b"
alias grb="git rebase"
alias gst="git stash"
alias gstp="git stash pop"

Phase 2: The Daily Loop

Weeks 2–4 | Goal: Ship features cleanly from branch creation to merged PR

Module 2.1 — Branch Naming & Creation

Level: Beginner · Prereqs: Module 1.2 · Time: ~1h
Skip-check: Create a feat/health-score-tooltip branch from a fresh main pull in under 30 seconds — from memory.
Skip if: You know all five branch prefixes and always pull main before branching.
Unlocks: Module 2.2

2.1.1 The Branching Contract

Three rules that eliminate most production incidents: main is always deployable. Every feature, fix, or chore lives on a branch. A PR is the gate between branch and main.

2.1.2 Branch Naming Convention

PrefixUse ForExample
feat/New feature or capabilityfeat/health-score-tooltip
fix/Bug fixfix/chart-overflow
chore/Config, deps, refactorchore/update-dependencies
docs/Documentation onlydocs/api-reference
hotfix/Urgent production fixhotfix/auth-crash

2.1.3 Creating a Branch — The Correct Pattern

# Always pull main first — branch from a fresh state
$ git checkout main && git pull

# Create and switch in one command
$ git checkout -b feat/health-score-tooltip

# Confirm you are on the right branch
$ git branch

2.1.4 Accidentally Committed to Main?

# Do not panic. Move it to a branch — never force-push main.
$ git checkout -b fix/oops-committed-to-main
$ git push -u origin fix/oops-committed-to-main
# Then open a PR. Never force-push main.

Module 2.2 — Staging & Commit Messages

Level: Beginner · Prereqs: Module 2.1 · Time: ~1.5h
Skip-check: Stage a single hunk from a multi-file diff using git add -p and write a correct conventional commit message for it.
Skip if: You use git add -p habitually and know all commit type prefixes.
Unlocks: Module 2.3, Module 3.2, Module 3.3

2.2.1 Staging with Precision

git add . stages everything. git add -p (patch mode) stages individual hunks — letting you craft logical commits even when multiple unrelated changes are open in your editor.

# Stage a specific file
$ git add src/components/HealthScoreCard.tsx

# Interactive patch mode — stage hunk by hunk
$ git add -p
# At each hunk: y=stage  n=skip  s=split  e=edit manually  q=quit

# Verify what is staged before committing
$ git diff --staged

2.2.2 Commit Message Format

Format: type(scope): short imperative description

# Good
$ git commit -m "feat(dashboard): add tooltip to health score card"
$ git commit -m "fix(dashboard): correct tooltip z-index"
$ git commit -m "chore(deps): upgrade react to 18.3.1"

# Bad — vague, wrong tense, no scope
$ git commit -m "fix stuff"
$ git commit -m "Added tooltip"
TypeUse For
featNew feature
fixBug fix
choreBuild, config, deps — no prod change
docsDocumentation only
styleFormatting, whitespace — no logic change
testAdding or fixing tests
perfPerformance improvement
refactorCode restructure, no behavior change
revertReverting a previous commit

2.2.3 Multiple Commits on a Branch

# Multiple commits are fine — they squash into one clean commit on merge
$ git add src/components/HealthScoreCard.tsx
$ git commit -m "feat(dashboard): add tooltip component"

$ git add src/styles/tooltip.css
$ git commit -m "style(dashboard): add tooltip positioning"

# See your branch commits vs main
$ git log main..HEAD --oneline

2.3.1 First Push vs Subsequent Pushes

# First push — with autoSetupRemote=true, no flags needed

# Without autoSetupRemote (old way):

2.3.2 Vercel Auto-Preview

The moment your branch lands on GitHub, Vercel builds a preview URL automatically. No configuration needed — it is wired to the repo. The preview is a full live environment with real Supabase data — exactly what production looks like.

$ gh pr checks

$ git commit -m "fix(dashboard): correct tooltip z-index on mobile"
$ git push
# Vercel rebuilds the preview within ~30 seconds

2.4.1 Installing and Authenticating GitHub CLI

# Install (macOS)
$ brew install gh

# Authenticate (opens browser OAuth flow)
$ gh auth login

# Verify
$ gh auth status

2.4.2 Opening a PR

$ gh pr create \
  --title "feat: add tooltip to health score card" \
  --body "## What
Adds a tooltip to HealthScoreCard showing the raw score value.

## Why
Users were confused about the scale — the tooltip eliminates the ambiguity."

# Or open in browser for a richer editor

Open a draft when the branch is not review-ready but you want the Vercel preview running immediately.

$ gh pr ready

Module 2.5 — PR Review, CI Checks & Merge

Level: Beginner–Intermediate · Prereqs: Module 2.4 · Time: ~1.5h
Skip-check: Review a PR locally, leave a change request, squash-merge your own PR, and sync main — all from the terminal.
Skip if: You routinely review, approve, and squash-merge PRs via the CLI.
Unlocks: Module 3.1

2.5.1 Reviewing a PR

# Check out a PR locally to test it
$ gh pr checkout 42

# Approve
$ gh pr review 42 --approve

# Request changes
$ gh pr review 42 --request-changes --body "Fix the N+1 query in the sensor loader first"

# Leave a comment
$ gh pr review 42 --comment --body "Looks good — verify on mobile before merging"

2.5.2 Merge Strategies

StrategyCommandWhen to Use
Squashgh pr merge --squashRecommended — one clean commit per feature on main
Merge commitgh pr merge --mergeWhen you need full history preserved on main
Rebasegh pr merge --rebaseWhen commits are already clean and linear

2.5.3 Post-Merge Sync

# Squash merge (recommended)
$ gh pr merge --squash

# Sync main locally
$ git checkout main && git pull

# Delete the local feature branch
$ git branch -d feat/health-score-tooltip
# Vercel promotes the already-verified build — no rebuild needed

2.5.4 Keeping a Branch Current with Main

If main has moved while you were working, rebase — it keeps history linear and avoids a merge commit on your branch.

$ git checkout main && git pull
$ git checkout feat/health-score-tooltip
$ git rebase main

# Resolve any conflicts, then:
$ git rebase --continue

# Force push because history was rewritten
$ git push --force-with-lease

--force-with-lease vs --force
Always default to --force-with-lease. It fails safely if someone else pushed to the branch since your last fetch. --force overwrites regardless — never use it on shared branches.

Phase 3: Parallel Work & Recovery

Weeks 4–6 | Goal: Work on multiple branches simultaneously and recover from any mistake

Module 3.1 — Git Worktrees

Level: Intermediate · Prereqs: Module 2.5 · Time: ~2h
Skip-check: Set up two worktrees, run both dev servers on different ports simultaneously, and push a commit from the feature worktree — without stashing anything.
Skip if: You use worktrees regularly and never stash to switch branches.
Unlocks: Module 4.1, Module 4.3

3.1.1 The Problem Worktrees Solve

Without worktrees, switching branches means stashing WIP, waiting for the dev server to restart, and losing context. Worktrees check out multiple branches simultaneously in separate directories — no stashing, no context switching, no lost work. Essential when pairing with Claude on one branch while keeping a reference branch running.

3.1.2 Core Commands

# Add a worktree (creates new branch from current HEAD)
$ git worktree add ../rotabrain-feat-tooltip feat/health-score-tooltip

# Add a worktree from an existing remote branch
$ git worktree add ../rotabrain-hotfix origin/hotfix/auth-crash

# List all active worktrees
$ git worktree list

# Remove a worktree when done
$ git worktree remove ../rotabrain-feat-tooltip

# Prune stale metadata (after manually deleting a directory)
$ git worktree prune

3.1.3 Directory Convention

~/projects/
  rotabrain-blades/         # main repo (main branch)
  rotabrain-feat-tooltip/   # worktree: feat/health-score-tooltip
  rotabrain-feat-sensors/   # worktree: feat/sensor-grid
  rotabrain-hotfix-auth/    # worktree: hotfix/auth-crash

3.1.4 Dual-Terminal Pattern

# Terminal A — main branch, reference build on port 3000
$ cd ~/projects/rotabrain-blades
$ PORT=3000 npm run dev

# Terminal B — feature worktree, Claude building on port 3001
$ cd ~/projects/rotabrain-feat-tooltip
$ PORT=3001 npm run dev

# Both live simultaneously — compare side by side in the browser
# localhost:3000  vs  localhost:3001

# When done, push from Terminal B
$ git push
$ gh pr create --title "feat: health score tooltip"

Module 3.2 — Git Stash & WIP Management

Level: Beginner–Intermediate · Prereqs: Module 2.2 · Time: ~1h
Skip-check: Stash with a label including untracked files, switch branches, apply the specific stash by index, then drop it.
Skip if: You use worktrees instead of stash for branch-switching (the better habit), but know stash for emergencies.
Unlocks: Module 3.3

3.2.1 When to Stash

Stash is for short interruptions — a hotfix lands while you are mid-feature. If you find yourself stashing frequently to switch branches, switch to worktrees (Module 3.1) instead. Each branch in its own directory eliminates the need for stash entirely.

3.2.2 Core Stash Commands

# Always label your stash — you will forget what stash@{0} was
$ git stash push -m "WIP: tooltip styling half done"

# Include untracked new files
$ git stash -u

# List all stashes
$ git stash list
# stash@{0}: On feat/tooltip: WIP: tooltip styling half done
# stash@{1}: On feat/sensors: WIP: initial sensor layout

# Apply latest stash and remove from list
$ git stash pop

# Apply a specific stash without removing
$ git stash apply stash@{1}

# Drop a stash after applying
$ git stash drop stash@{0}

# Clear all stashes (destructive)
$ git stash clear

3.2.3 The WIP Checkpoint Pattern (Better Than Stash)

For longer interruptions, a WIP commit is safer than stash — it is in the reflog and has a message.

# Commit everything as WIP (the git alias from Module 1.2)
$ git save

# Switch to another branch or worktree for the hotfix...

# Come back and undo the WIP commit, restoring working state
$ git undo    # alias for: git reset HEAD~1

3.3.1 The Undo Reference

SituationCommandSafe?
Undo last commit (keep staged)git reset --soft HEAD~1Yes
Undo last commit (keep unstaged)git reset HEAD~1Yes
Undo last commit (discard)git reset --hard HEAD~1Destructive
Discard all unstaged changesgit checkout -- .Destructive
Discard one filegit checkout -- path/to/fileDestructive
Revert a pushed commit safelygit revert <sha>Yes — adds a new commit
Recover lost commit or stashgit reflogYes — read-only

3.3.2 The Three Reset Modes

# --soft: undo the commit, keep changes staged.
# Use when you want to recommit with a different message.
$ git reset --soft HEAD~1

# Default (--mixed): undo the commit, unstage changes.
# Use when you want to re-stage selectively.
$ git reset HEAD~1

# --hard: undo the commit and discard all changes. Destructive.
# Use when you are certain you do not want those changes.
$ git reset --hard HEAD~1

3.3.3 git reflog — Your Safety Net

Every HEAD movement is logged — even after a hard reset. This is your recovery tool when you think work is gone.

$ git reflog
# abc1234 HEAD@{0}: reset: moving to HEAD~1
# def5678 HEAD@{1}: commit: feat(dashboard): add tooltip to health score card
# ghi9012 HEAD@{2}: commit: chore: checkpoint before refactor

# Recover to the state before the hard reset
$ git reset --hard def5678

3.3.4 Safe Revert for Pushed Commits

# Never hard-reset a pushed commit — use revert instead.
# git revert creates a new commit that undoes the target, keeping history intact.
$ git revert abc1234
$ git push

Module 4.1 — Interactive Rebase & Clean History

Level: Intermediate · Prereqs: Module 3.1, Module 3.3 · Time: ~2h

4.1.1 Why History Matters

Clean commit history is not vanity — it is searchable blame. When a production bug surfaces months later, git log --oneline and git bisect are your first tools. WIP commits and "fix typo" noise make those tools slower.

4.1.2 Interactive Rebase Workflow

# Rebase the last 4 commits interactively
$ git rebase -i HEAD~4

# Editor opens with commits listed oldest-first:
# pick abc1234 feat: add tooltip component
# pick def5678 WIP: tooltip almost working
# pick ghi9012 fix typo in tooltip
# pick jkl3456 fix tooltip z-index
#
# Change to:
# pick abc1234 feat: add tooltip component
# squash def5678 WIP: tooltip almost working
# fixup ghi9012 fix typo in tooltip
# reword jkl3456 fix tooltip z-index
# Save and close
CommandWhat It Does
pickKeep the commit as-is
squashCombine into previous commit, edit the combined message
fixupCombine into previous commit, discard this commit's message
rewordKeep the changes, edit the commit message
dropDelete the commit entirely

The Golden Rule of Rebase: Never rebase commits that have been pushed and others are working on. Interactive rebase rewrites history (new SHAs). On a personal feature branch before merge: always safe. On a shared branch or after a colleague has checked it out: never.

4.2.1 Cherry-Pick

4.2.2 git bisect — Binary Search for Regressions

$ git bisect start
$ git bisect bad             # current commit is broken
$ git bisect good abc1234    # this commit was working fine

# Git checks out the midpoint commit. Test it, then tell git:
$ git bisect good   # or:
$ git bisect bad

# Repeat until git prints: "abc1234 is the first bad commit"
$ git bisect reset  # return to HEAD when done

4.5.1 Workflow YAML Anatomy

A GitHub Actions workflow is a YAML file in .github/workflows/. Every workflow has the same four top-level keys:

name: CI                          # displayed in the Actions UI

on:                               # trigger(s)
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:                             # one or more parallel jobs
  test:                           # job id (arbitrary name)
    runs-on: ubuntu-latest        # runner image

    steps:
      - uses: actions/checkout@v4           # check out the repo
      - uses: actions/setup-node@v4         # install Node
        with:
          node-version: 20
      - run: npm ci                          # install deps
      - run: npm test                        # run tests

Always pin actions/checkout to a version tag (@v4), not @main. Floating refs can silently change behaviour when the upstream action updates. Same rule for any community action you add.

4.5.2 Pattern 1 — CI on Pull Request

The most important workflow you will ever write. Runs tests and linting on every PR push so CI status is visible before merge.

# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm             # cache node_modules between runs

      - run: npm ci
      - run: npm run lint        # fails fast if lint errors exist
      - run: npm test            # unit tests

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run typecheck   # tsc --noEmit

Two jobs run in parallel — test and typecheck. Both must pass for the PR to be mergeable (once you configure branch protection in GitHub Settings → Branches).

4.5.3 Pattern 2 — Deploy on Merge to Main

Triggers only when a PR is squash-merged into main. For a Vercel-hosted project, Vercel's own GitHub integration already handles this automatically — but this pattern matters for any non-Vercel deployment target (custom server, Docker push, etc.).

# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]             # only fires on commits to main

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production      # requires manual approval if configured

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci
      - run: npm run build

      - name: Deploy to server
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}   # injected at runtime
        run: |
          echo "Deploying build to production..."
          # your deployment command here

Secrets are never in the YAML file. They live in GitHub → repo Settings → Secrets and variables → Actions, and are injected as environment variables at runtime.

4.5.4 Managing Secrets & Workflows from the Terminal

You don't need to leave the terminal to manage Actions.

# Add a secret (prompts for the value, never echoed)
$ gh secret set DEPLOY_KEY

# List secret names (values are never revealed)
$ gh secret list

# List workflows in the repo
$ gh workflow list

# Trigger a workflow manually (must have workflow_dispatch trigger)
$ gh workflow run ci.yml

# List recent runs
$ gh run list

# Watch a run live (streams each step in real time)
$ gh run watch

# View a specific run — shows step logs if it failed
$ gh run view 12345678

# View just the failed step log
$ gh run view 12345678 --log-failed

4.5.5 Debugging Failed Runs

When CI goes red, the fastest path to the root cause is:

# Step 1 — find the failed run id
$ gh run list --limit 5

# Step 2 — view only the failed steps (much less noise than full log)
$ gh run view <run-id> --log-failed

# Step 3 — if you need the full log locally
$ gh run view <run-id> --log > /tmp/run.log
$ grep -i "error\|failed\|ENOENT" /tmp/run.log

The three most common failure causes:

  • Missing npm ci before the test step — node_modules is never present on a fresh runner; always install first.
  • Environment variable not set — you added a secret locally but forgot to add it in GitHub Settings → Secrets. The runner gets an empty string, not an error.
  • Node version mismatch — your local Node is 22, the runner is 18 (or vice versa). Always pin the version in setup-node to match .nvmrc or your engines field in package.json.
