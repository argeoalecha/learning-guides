How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone builds the same running scenario: TindaHub, a synthetic Philippine e-commerce marketplace, needs an AI support copilot that answers order questions, triages tickets, and escalates refunds to a human.

Quick Start: Three Ways to Use This Guide

  1. Complete beginner to LLM app development → Start at Module 1.1 and go sequentially through all four phases.
  2. Some experience with LLM APIs or old LangChain → Take the Placement Quiz (next section) to find your entry point — most returning LangChain users should start at Module 2.1.
  3. Targeting a specific skill (e.g., "I just need LangGraph agents" or "I just need observability") → Jump via the Module Index or pick a Learning Track.

Phase 1: LangChain Foundations

Weeks 1–2 | Goal: build and compose LLM calls — prompts, tools, and retrieval — using LangChain 1.x's current APIs

Module 1.1 — LLMs, Chat Models & Messages

Level: Beginner · Prereqs: Python basics, an Anthropic or OpenAI API key · Time: ~2h
Skip-check (test-out): Instantiate a chat model, send a list of messages, and print the response's text content and token usage.
Skip if: You've already called init_chat_model or a provider-specific chat class and read a response object.
Unlocks: 1.2, 1.3, 4.1

Why LangChain exists

Every LLM provider (Anthropic, OpenAI, Google, local models via Ollama) has a slightly different request/response shape. LangChain's core value is a unified interface over these differences — you write one chat-model call and swap providers by changing a string, not rewriting your integration. Skipping this abstraction is fine for a single-provider prototype, but it means every prompt, tool schema, and streaming handler you write is locked to one vendor's SDK — a costly rewrite the day you need a cheaper or faster model for one workload.

Chat models and the message object

LangChain 1.x standardizes on chat models (not raw text completion) as the default interface, and on a single content block format for messages across providers. Getting the message roles wrong (e.g., putting instructions in a user message instead of system) is the single most common beginner mistake — it works by accident on some models and silently degrades output quality on others.

from langchain.chat_models import init_chat_model

# init_chat_model resolves "provider:model" strings to the right integration class —
# swapping providers means changing this one string, nothing else in your code.
model = init_chat_model("anthropic:claude-sonnet-5", temperature=0)

response = model.invoke([
    {"role": "system", "content": "You are a support assistant for TindaHub, a Philippine online marketplace."},
    {"role": "user", "content": "My order #TH-88213 hasn't arrived in 9 days. What should I do?"},
])

print(response.content)          # the assistant's text
print(response.usage_metadata)   # {'input_tokens': ..., 'output_tokens': ..., 'total_tokens': ...}

Why token usage matters from day one

Every response carries usage_metadata. Reading it from your very first call — not bolting it on later — is what makes Module 4.3's cost dashboards possible without re-instrumenting every call site. A support bot that silently sends the entire order history as context on every turn can burn 50x the tokens of one that retrieves only what's relevant; that gap only becomes visible if you're watching usage from the start.

Exercise 1.1 — First TindaHub Support Reply

Scenario: TindaHub, the running example for this whole guide.

  1. Install langchain and a provider package (pip install langchain langchain-anthropic).
  2. Set your API key as an environment variable — never hardcode it in the script.
  3. Use init_chat_model to create a chat model with temperature=0 for deterministic support replies.
  4. Send a system message that establishes the assistant as TindaHub support, plus 3 different user messages (a shipping delay, a refund request, a product question).
  5. For each response, print the text content and the total token count.
  6. Sum the total tokens across all 3 calls and estimate the cost using your model's published per-token price.

Module 1.2 — Prompt Templates & LCEL Composition

Level: Beginner · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Build a ChatPromptTemplate with variables and pipe it into a model and output parser using the | operator.
Skip if: You've written a multi-step LCEL chain and can explain what | does under the hood.
Unlocks: 1.3, 1.4

Templates instead of string concatenation

Hardcoded f-strings for prompts work until you need to reuse the same prompt structure across 10 call sites, or a teammate needs to edit wording without touching Python logic. ChatPromptTemplate separates the fixed instruction text from the variable slots, and validates at call time that every variable you declared actually got filled — an unfilled variable in an f-string just silently sends the literal placeholder text to the model.

from langchain_core.prompts import ChatPromptTemplate

triage_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a triage assistant for TindaHub support tickets. "
               "Classify the ticket into exactly one category: shipping, refund, "
               "product_question, or account. Respond with only the category."),
    ("human", "{ticket_text}"),
])

formatted = triage_prompt.invoke({"ticket_text": "Wala pa dumadating yung order ko, 9 days na."})
print(formatted.to_messages())

LCEL: composing steps with the pipe operator

LangChain Expression Language (LCEL) lets you chain a prompt, a model, and an output parser into one runnable using |, similar to Unix pipes. It still has a place in LangChain 1.x for straight-line, non-branching compositions — prompt → model → parse — even though branching agent logic has moved to LangGraph (Module 2.1). Reach for LCEL when the flow is linear; reach for LangGraph the moment you need a decision point.

from langchain_core.output_parsers import StrOutputParser

triage_chain = triage_prompt | model | StrOutputParser()

category = triage_chain.invoke({"ticket_text": "I want a refund for order TH-88213, it's damaged."})
print(category)  # "refund"

Common mistake: Treating LCEL as the tool for building agents. LCEL chains are static — the same steps run every time. The moment your logic needs to loop, branch conditionally, or call tools in an open-ended way, you've outgrown LCEL and need LangGraph (Phase 2), not a longer chain.

Module 1.3 — Tool Calling & Structured Output

Level: Beginner–Intermediate · Prereqs: Module 1.2 · Time: ~3h
Skip-check (test-out): Define a Python function tool with a typed signature, bind it to a model, and execute the tool call the model returns.
Skip if: You've built a function-calling loop by hand with any LLM SDK.
Unlocks: 1.4, 2.1

Tools: giving the model hands

A chat model only produces text. A tool is a Python function with a schema the model can choose to call — the model doesn't execute anything itself, it returns a structured request (tool_calls) that your code executes and feeds back. Miss this distinction and you'll expect the model to "just look up the order," when in fact your code has to run get_order_status(order_id) and pass the result back as a new message.

from langchain_core.tools import tool

@tool
def get_order_status(order_id: str) -> str:
    """Look up the shipping status of a TindaHub order by its order ID."""
    orders = {
        "TH-88213": "In transit, last scan: Cebu sorting facility, ETA 2 days.",
        "TH-90441": "Delivered on 2026-07-20, signed by J. Reyes.",
    }
    return orders.get(order_id, "Order ID not found.")

model_with_tools = model.bind_tools([get_order_status])
response = model_with_tools.invoke("What's the status of order TH-88213?")
print(response.tool_calls)  # [{'name': 'get_order_status', 'args': {'order_id': 'TH-88213'}, ...}]

Structured output: forcing a schema, not free text

When you need the model's answer (not a tool call) shaped as data — a category, a confidence score, a refund amount — use with_structured_output with a Pydantic model. This is different from tool calling: tools let the model take an action; structured output constrains the model's final response to a schema you can parse without regex or hopeful JSON parsing.

from pydantic import BaseModel, Field

class TicketClassification(BaseModel):
    category: str = Field(description="shipping, refund, product_question, or account")
    urgency: str = Field(description="low, medium, or high")
    refund_amount_php: float | None = Field(default=None, description="Requested refund in PHP, if any")

structured_model = model.with_structured_output(TicketClassification)
result = structured_model.invoke("Order TH-88213 pa rin wala, 9 days na. Gusto ko na lang ma-refund yung ₱1,250.")
print(result.category, result.urgency, result.refund_amount_php)

Disambiguation: "Structured output" and "tool calling" both use the model's function-calling machinery under the hood, but they answer different questions. Tool calling asks "what should I do next?" (fetch data, send an email). Structured output asks "shape your final answer as this schema" — there's no execution step, just parsing.

Module 1.4 — Retrieval-Augmented Generation (RAG)

Level: Intermediate · Prereqs: Module 1.2 · Time: ~4h
Skip-check (test-out): Embed a set of documents into a vector store, run a similarity search, and inject the top results into a prompt as context.
Skip if: You've built an embed → store → retrieve → generate pipeline with any vector database.
Unlocks: Phase 1 Capstone, 4.2

Why RAG instead of putting everything in the prompt

A model's context window is finite and costs money per token — pasting your entire FAQ or product catalog into every prompt doesn't scale past a few dozen documents. RAG retrieves only the most relevant chunks for a given question by comparing embeddings (numeric vectors that capture meaning) rather than keywords, so a question phrased differently from the source text still matches.

from langchain_core.documents import Document
from langchain_openai import OpenAIEmbeddings
from langchain_core.vectorstores import InMemoryVectorStore

faq_docs = [
    Document(page_content="TindaHub refunds are processed within 5-7 business days after the returned item is received at our warehouse.", metadata={"topic": "refund"}),
    Document(page_content="Standard shipping within Metro Manila takes 2-3 days; provincial shipping takes 5-9 days depending on courier.", metadata={"topic": "shipping"}),
    Document(page_content="Cash on Delivery (COD) orders can be cancelled free of charge any time before the courier is dispatched.", metadata={"topic": "cod"}),
]

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = InMemoryVectorStore(embeddings)
vector_store.add_documents(faq_docs)

results = vector_store.similarity_search("How long until I get my money back?", k=2)
for doc in results:
    print(doc.page_content)

Chunking and the retrieval-generation prompt

Real documents are longer than one FAQ line, so you split them into chunks before embedding — too large and irrelevant text dilutes the match; too small and you lose surrounding context the model needs to answer correctly. Getting chunk size wrong is the most common reason a RAG system "hallucinates" — it isn't inventing facts, it's answering from a chunk that's missing the qualifying sentence two lines below the cut.

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(faq_docs)

rag_prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer the TindaHub customer's question using ONLY the provided context. "
               "If the context doesn't contain the answer, say you'll escalate to a human agent."),
    ("human", "Context:\n{context}\n\nQuestion: {question}"),
])

def answer_question(question: str) -> str:
    docs = vector_store.similarity_search(question, k=2)
    context = "\n\n".join(d.page_content for d in docs)
    chain = rag_prompt | model | StrOutputParser()
    return chain.invoke({"context": context, "question": question})

print(answer_question("Pwede ba icancel kahit COD?"))

Phase 2: Agents with LangGraph

Weeks 3–5 | Goal: build stateful, branching, tool-using agents on LangGraph's graph runtime

Module 2.1 — From AgentExecutor to create_agent

Level: Intermediate · Prereqs: Module 1.3 · Time: ~2h
Skip-check (test-out): Explain why AgentExecutor is deprecated and build a working tool-using agent with create_agent.
Skip if: You've already migrated an agent off AgentExecutor / initialize_agent.
Unlocks: 2.2

Why the old agent API was retired

AgentExecutor (and initialize_agent, create_react_agent from pre-1.0 LangChain) implemented agent looping as a simple "call model, run tool, repeat" loop with almost no control over what happens between steps. It could not natively support branching logic, human approval gates, or resuming a crashed run — because those all require a real state machine, not a loop. LangChain 1.0 (October 2025) replaced it with create_agent, which builds the same "tool-calling agent" pattern on top of LangGraph's graph runtime instead of a bare loop. As of mid-2026, AgentExecutor is in maintenance-only mode through December 2026 — treat any code you find using it as legacy to migrate, not a pattern to copy.

from langchain.agents import create_agent

agent = create_agent(
    model="anthropic:claude-sonnet-5",
    tools=[get_order_status, get_refund_policy],
    system_prompt=(
        "You are TindaHub's support agent. Use the tools to look up real order "
        "and policy data before answering. Never guess an order status."
    ),
)

result = agent.invoke({"messages": [{"role": "user", "content": "Where is order TH-88213?"}]})
print(result["messages"][-1].content)

create_agent vs. hand-rolled StateGraph

create_agent is the fast path: it wires up a standard tool-calling loop (call model → if tool call, run tool → feed result back → repeat until a final answer) with sensible defaults, and it's what LangGraph runs under the hood. Reach for the full StateGraph API (Module 2.2) the moment you need node-level control the prebuilt loop doesn't expose — custom routing between more than "call tool or answer," per-node checkpointing, or a human-approval step in the middle of the loop.

Common mistake: Assuming create_agent and StateGraph are competing choices. They aren't — create_agent returns a compiled graph, and you can inspect, extend, or even embed it as a node inside a larger StateGraph (see Module 3.1). Start with create_agent; drop to raw StateGraph only when you hit its ceiling.

Module 2.2 — LangGraph Fundamentals: StateGraph, Nodes & Edges

Level: Intermediate · Prereqs: Module 2.1 · Time: ~3h
Skip-check (test-out): Define a typed state, add 3 nodes and edges between them, compile the graph, and run it end-to-end.
Skip if: You've built a StateGraph with more than one node from scratch.
Unlocks: 2.3, 2.4, 3.2

Graphs as the mental model for agent orchestration

LangGraph (currently v1.2.x) models an agent as a graph: a shared state object, nodes that are functions reading and updating that state, and edges that determine which node runs next. This is a deliberate shift from thinking "what's my next API call" to thinking "what are the states my workflow can be in, and what moves it between them" — the latter model is what makes branching, cycles, and resumability possible later in this phase.

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class SupportState(TypedDict):
    messages: Annotated[list, add_messages]
    category: str

def classify_node(state: SupportState) -> dict:
    last_user_msg = state["messages"][-1].content
    category = triage_chain.invoke({"ticket_text": last_user_msg})
    return {"category": category}

def respond_node(state: SupportState) -> dict:
    reply = model.invoke(state["messages"])
    return {"messages": [reply]}

graph = StateGraph(SupportState)
graph.add_node("classify", classify_node)
graph.add_node("respond", respond_node)
graph.add_edge(START, "classify")
graph.add_edge("classify", "respond")
graph.add_edge("respond", END)

app = graph.compile()
result = app.invoke({"messages": [{"role": "user", "content": "Saan na yung order ko?"}], "category": ""})

Why state is annotated, not just assigned

Notice messages uses Annotated[list, add_messages] — this tells LangGraph how to merge a node's return value into existing state, rather than overwriting it. Without add_messages, every node that returns {"messages": [...]} would replace the entire conversation history instead of appending to it — a bug that silently erases context and is easy to miss until a multi-turn conversation loses earlier messages.

Module 2.3 — Conditional Edges, Cycles & Control Flow

Level: Intermediate · Prereqs: Module 2.2 · Time: ~3h
Skip-check (test-out): Add a conditional edge that routes to different nodes based on state, and a cycle that loops until a condition is met.
Skip if: You've built a graph with branching AND a loop that terminates on a state condition.
Unlocks: 2.4, 3.1

Routing with conditional edges

A conditional edge is a function that inspects state and returns the name of the next node — this is how a graph makes decisions instead of always running the same fixed sequence. This is the capability AgentExecutor never had cleanly: routing a refund request to a human-approval node while letting a shipping question go straight to auto-reply, from the same graph.

def route_by_category(state: SupportState) -> str:
    if state["category"] == "refund":
        return "human_review"
    return "auto_respond"

graph.add_node("human_review", human_review_node)
graph.add_node("auto_respond", respond_node)
graph.add_conditional_edges(
    "classify",
    route_by_category,
    {"human_review": "human_review", "auto_respond": "auto_respond"},
)

Cycles: looping until state says stop

Unlike a straight-line LCEL chain, a graph can point an edge backward — this is how an agent "keeps calling tools until it has enough information to answer," a pattern that's structurally impossible in a linear chain. The termination condition lives in your routing function; forgetting to define one that eventually returns END produces an infinite loop that silently burns API credits until you hit a rate limit or bill shock.

def should_continue(state: SupportState) -> str:
    last_message = state["messages"][-1]
    if getattr(last_message, "tool_calls", None):
        return "tools"
    return END

graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")  # loop back after running a tool

Common mistake: Writing a conditional edge that can return a node name not present in the routing map passed to add_conditional_edges. LangGraph raises at runtime, not at compile time, so this bug only surfaces on the specific state that triggers the missing branch — test every branch explicitly, don't just run the happy path.

Module 2.4 — Persistence, Checkpointers & Memory

Level: Intermediate · Prereqs: Module 2.2 · Time: ~3h
Skip-check (test-out): Compile a graph with a checkpointer, run it across 2 separate invoke calls using the same thread ID, and show state persisted between them.
Skip if: You've used a checkpointer with thread-scoped conversation memory in production.
Unlocks: 2.5, 3.3, 4.4

Checkpointers: state that survives between calls

Without a checkpointer, every invoke starts from a blank state — the graph has no memory of a previous turn. A checkpointer saves state after every node runs, keyed by a thread_id, so a support conversation can span multiple HTTP requests (a real chat UI) without you manually re-sending the whole history every time.

from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()  # in-memory — swap for a Postgres/Redis checkpointer in production
app = graph.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "ticket-th-88213"}}

app.invoke({"messages": [{"role": "user", "content": "Where's my order?"}]}, config)
# ... later, same thread_id — the graph remembers the earlier turn ...
app.invoke({"messages": [{"role": "user", "content": "And what if it doesn't arrive by Friday?"}]}, config)

Why thread_id, not session ID, is the right mental model

A thread_id maps 1:1 to one continuous conversation or workflow run — in TindaHub's case, one support ticket, not one user. A single customer can have 3 open tickets (3 thread_ids) or a shared "account" thread; the checkpointer doesn't assume anything about your business's identity model, so getting the thread_id granularity wrong (e.g., one thread per user instead of per ticket) mixes unrelated conversations into the same memory.

MemorySaver is process-local and disappears on restart — fine for development, wrong for production, where a PostgresSaver or RedisSaver is required so a crash or redeploy doesn't lose every in-flight conversation.

Module 2.5 — Human-in-the-Loop: Interrupts & Approval Gates

Level: Intermediate–Advanced · Prereqs: Module 2.4 · Time: ~3h
Skip-check (test-out): Add an interrupt that pauses a graph mid-run for approval, then resume it with Command(resume=...).
Skip if: You've shipped an approval gate that pauses agent execution and waits for external input.
Unlocks: Phase 2 Capstone, 3.1

Why some decisions shouldn't be fully autonomous

A refund of ₱50 is low-stakes; a refund of ₱15,000 is not. Human-in-the-loop (HITL) lets a graph pause execution at exactly the node where the stakes justify a human check, without giving up automation everywhere else. This only works because of the checkpointer from Module 2.4 — interrupt relies on persisted state to pause and later resume from the exact same point, potentially minutes or hours later.

from langgraph.types import interrupt, Command

def human_review_node(state: SupportState) -> dict:
    decision = interrupt({
        "question": "Approve this refund?",
        "order_id": state.get("order_id"),
        "amount_php": state.get("refund_amount_php"),
    })
    if decision["approved"]:
        return {"messages": [{"role": "assistant", "content": "Refund approved and processed."}]}
    return {"messages": [{"role": "assistant", "content": "Refund denied — escalating to account manager."}]}

# First call pauses at the interrupt and returns control to your app:
result = app.invoke({"messages": [...], "order_id": "TH-88213", "refund_amount_php": 15000}, config)
print(result["__interrupt__"])  # the payload passed to interrupt()

# ... your app shows this to a human agent, gets a decision, then resumes ...
app.invoke(Command(resume={"approved": True}), config)

Interrupt vs. exception

An interrupt is not an error — it's a deliberate, resumable pause built into the graph's control flow, distinct from a crash. Confusing the two leads to wrapping interrupts in try/except blocks meant for real failures, which either swallows the pause silently or crashes a workflow that was working exactly as designed.

Module 3.1 — Multi-Agent Architectures: Supervisor & Swarm

Level: Advanced · Prereqs: Module 2.5 · Time: ~4h
Skip-check (test-out): Build a supervisor graph that routes work to 2+ specialist sub-agents and hands control back.
Skip if: You've built a multi-agent system with either a supervisor or peer-handoff pattern.
Unlocks: Phase 3 Capstone

When one agent isn't enough

A single agent with 15 tools and a 3-paragraph system prompt covering shipping, refunds, and account issues tends to confuse itself — it picks the wrong tool or blends instructions meant for different scenarios. Splitting into specialist agents, each with a narrow toolset and focused prompt, mirrors how a real support team routes tickets to specialized queues, and is easier to prompt-engineer and evaluate in isolation.

Supervisor architecture: one coordinator, many workers

In a supervisor pattern, one agent's only job is to read the request and route it to the right specialist — it doesn't do the work itself. The specialist returns control to the supervisor, which decides the next step or ends the run. This is the easiest multi-agent pattern to reason about, because there is always exactly one place that owns "what happens next."

from langgraph.types import Command
from typing import Literal

def supervisor_node(state: SupportState) -> Command[Literal["billing_agent", "shipping_agent", "__end__"]]:
    category = state["category"]
    if category == "refund":
        return Command(goto="billing_agent")
    if category == "shipping":
        return Command(goto="shipping_agent")
    return Command(goto="__end__", update={"messages": [{"role": "assistant", "content": "Ticket resolved."}]})

def billing_agent_node(state: SupportState) -> Command[Literal["supervisor"]]:
    reply = billing_agent.invoke(state)
    return Command(goto="supervisor", update={"messages": reply["messages"]})

Swarm / handoff architecture: peer agents pass control directly

A swarm lets any agent hand off directly to any other agent it decides is better suited — there's no central router. This scales better to many specialists but is harder to debug, since "what happens next" is distributed across every agent's own logic instead of living in one place. Use a supervisor by default; reach for swarm handoffs only when the routing logic itself needs to be dynamic and context-dependent (e.g., a billing agent realizing mid-conversation that the real issue is a shipping delay, and handing off itself).

Common mistake: Building a swarm architecture because it sounds more sophisticated, when a supervisor would be simpler to build, test, and debug for the same use case. Multi-agent complexity should be justified by an actual routing need that a single supervisor can't express cleanly — not chosen by default.

Module 3.2 — Streaming: Tokens, Updates & Custom Data

Level: Intermediate · Prereqs: Module 2.2 · Time: ~2h

Why streaming matters for a chat product

A user staring at a blank screen for 8 seconds while a multi-step agent runs tool calls feels broken, even if the final answer is correct — streaming intermediate progress ("looking up your order…", then the answer token-by-token) is what makes an agent feel responsive rather than frozen. LangGraph's 2026 releases added a content-block-centric streaming API specifically to make this easier to wire into modern chat UIs.

# stream_mode="updates" — one event per node completion, showing what changed
for chunk in app.stream({"messages": [{"role": "user", "content": "Where's TH-88213?"}]}, config, stream_mode="updates"):
    print(chunk)  # {'classify': {'category': 'shipping'}}, then {'respond': {'messages': [...]}}

# stream_mode="messages" — token-by-token streaming of the LLM's own output
for token, metadata in app.stream({"messages": [...]}, config, stream_mode="messages"):
    print(token.content, end="", flush=True)

Custom streaming for non-LLM progress

Not every "in progress" signal comes from the model — a slow tool call (a real database lookup, an external courier API) has no tokens to stream. A node can push arbitrary custom events via get_stream_writer so your frontend can show "checking courier status…" while a tool call is still running, not just while the model is generating text.

from langgraph.config import get_stream_writer

def shipping_lookup_node(state: SupportState) -> dict:
    writer = get_stream_writer()
    writer({"status": "Checking courier API..."})
    status = get_order_status.invoke({"order_id": state["order_id"]})
    return {"messages": [{"role": "assistant", "content": status}]}

Module 3.3 — Durable Execution, Retries & Error Recovery

Level: Advanced · Prereqs: Module 2.4 · Time: ~3h
Skip-check (test-out): Configure a node-level retry policy and explain what a checkpoint protects against on process crash.
Skip if: You've configured retry/timeout policies on a production LangGraph deployment.
Unlocks: Phase 3 Capstone, 4.4

Durable execution: surviving a crash mid-run

Because a checkpointer persists state after every node (Module 2.4), a graph can resume from its last completed node after a process crash or redeploy, instead of restarting the entire run from scratch. For a multi-step agent that's already made 3 paid API calls, this is the difference between losing that work on a crash and picking up exactly where it left off.

Retry policies on flaky nodes

External calls — a courier tracking API, a payment gateway — fail transiently. A RetryPolicy on a node retries with backoff automatically, instead of failing the whole graph run on one dropped connection.

from langgraph.types import RetryPolicy

graph.add_node(
    "check_courier_api",
    check_courier_node,
    retry_policy=RetryPolicy(max_attempts=3, initial_interval=1.0, backoff_factor=2.0),
)

Timeouts and graceful shutdown

2026 LangGraph releases added finer-grained node execution control — timeouts so one hung external call doesn't stall an entire ticket queue, plus graceful shutdown so an in-flight run isn't corrupted mid-checkpoint when a worker is scaled down. Without a timeout, a single unresponsive tool call can block the node indefinitely, and every other ticket routed to that worker queues up behind it.

app = graph.compile(checkpointer=checkpointer)
result = app.invoke(
    {"messages": [...]}, config,
    config={"configurable": {"thread_id": "ticket-th-99120"}, "recursion_limit": 25},
)

Common mistake: Relying on a checkpointer alone for reliability and skipping retry policies. A checkpoint protects work already completed — it does nothing to make a currently-failing external call succeed. You need both: checkpoints for crash recovery, retries for transient failures.

Module 4.1 — Tracing & Debugging with LangSmith

Level: Beginner–Intermediate · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Enable tracing on a chain or graph and inspect a full run — including nested tool calls — in the LangSmith UI.

Why "it works on my machine" isn't enough for LLM apps

An LLM call's failure mode is rarely a stack trace — it's a subtly wrong answer, a tool called with the wrong argument, or a retrieval that missed the right chunk. None of that shows up in application logs unless you specifically capture the full prompt, model response, and intermediate steps for every run. LangSmith is LangChain's observability platform built for exactly this: automatic, zero-code tracing of every chain, agent, and graph run.

export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=your-api-key
export LANGSMITH_PROJECT=tindahub-support

With those environment variables set, every invoke, stream, or batch call on a LangChain or LangGraph object is traced automatically — no code changes required. Each trace shows the full tree: the top-level graph run, every node it entered, every tool call and its arguments, every LLM call's prompt and response, and the token/latency/cost for each.

Reading a trace to debug a wrong answer

When TindaHub's agent gives a wrong order status, the trace tells you exactly where it went wrong: did the tool return bad data, did the model misread correct tool output, or did classification route the ticket to the wrong specialist? Without tracing, you're guessing between three different root causes from the same symptom; with it, you click into the exact node and see the actual input/output.

from langsmith import traceable

@traceable(name="classify_ticket", run_type="chain")
def classify_ticket(ticket_text: str) -> str:
    # Custom, non-LangChain functions can be traced too via the @traceable decorator —
    # useful for wrapping business logic that sits between LangChain calls.
    return triage_chain.invoke({"ticket_text": ticket_text})

Module 4.2 — Evaluations, Datasets & LLM-as-Judge

Level: Intermediate · Prereqs: Module 4.1 · Time: ~3h

Why "it looked right when I tried it" doesn't scale

Manually eyeballing 5 example outputs before shipping a prompt change catches the obvious breaks, but not the 1-in-20 regression that only shows up on an edge case you didn't happen to test. A LangSmith dataset is a fixed, reusable set of example inputs (and ideally expected outputs) you can run any version of your chain against — this turns "does the new prompt still work" into a repeatable, quantified check instead of a vibe.

from langsmith import Client

client = Client()
dataset = client.create_dataset("tindahub-triage-eval", description="Ticket triage regression set")

examples = [
    {"inputs": {"ticket_text": "Order TH-88213 wala pa 9 days na"}, "outputs": {"category": "shipping"}},
    {"inputs": {"ticket_text": "Gusto ko ma-refund yung sira na item"}, "outputs": {"category": "refund"}},
    {"inputs": {"ticket_text": "Ano po ang warranty ng product na 'to?"}, "outputs": {"category": "product_question"}},
]
client.create_examples(dataset_id=dataset.id, examples=examples)

Evaluators: exact match vs. LLM-as-judge

Some outputs (like a triage category) can be checked with plain code — string equality. Others (like a drafted reply's tone or helpfulness) can't be checked programmatically, so LangSmith supports LLM-as-judge evaluators — a second LLM call that scores the output against a rubric you write. LLM-as-judge is powerful but not free of its own error rate; use exact-match or rule-based evaluators wherever the output is structured enough to allow it, and reserve LLM-as-judge for genuinely subjective qualities.

from langsmith.evaluation import evaluate

def category_exact_match(run, example) -> dict:
    predicted = run.outputs.get("category")
    expected = example.outputs.get("category")
    return {"key": "category_correct", "score": int(predicted == expected)}

def target(inputs: dict) -> dict:
    return {"category": triage_chain.invoke(inputs)}

results = evaluate(
    target,
    data="tindahub-triage-eval",
    evaluators=[category_exact_match],
    experiment_prefix="triage-v2",
)

Common mistake: Only building a dataset from "nice" examples. A regression set that never includes the Taglish, sarcastic, or deliberately ambiguous tickets your real users actually send will pass every evaluation while still failing in production the day it ships.

Alerts: catching problems before users report them

LangSmith Alerts fire on error rate, run latency, feedback score, or cost, aggregated over a 5- or 15-minute window, and route to PagerDuty, Dynatrace, or any webhook. Alerting on aggregated windows (not single failures) matters because LLM calls have natural transient failure noise — alerting on every single error would page someone every few minutes for nothing actionable.

LangSmith Engine and Context Hub

Two additions announced at LangChain's Interrupt 2026 conference are worth knowing: LangSmith Engine watches production traces, clusters recurring failures into a single issue instead of hundreds of individual traces, and can open a pull request with a proposed fix — you mark an issue "Fixing" or "Watching," and watching an issue gets you a Slack alert the next time a matching trace recurs. Context Hub is a versioned store — "Git for agent context" — for the files that actually govern agent behavior (instructions like AGENTS.md, skill definitions, policy documents), with environment tagging (dev/staging/prod) and CLI push/pull (langsmith hub push / langsmith hub pull) so a prompt regression traces back to a specific commit and can be rolled back the same way you'd revert code.

Swapping to a production checkpointer

The one code change every deployment needs: replacing MemorySaver with a durable backend. This is the single most common production incident in LangGraph apps — shipping with the in-memory saver and losing every conversation on the first redeploy.

from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DATABASE_URL) as checkpointer:

    app = graph.compile(checkpointer=checkpointer)

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

LangChain Core

Chat Model
A model interface that takes a list of role-tagged messages and returns a message, as opposed to raw text completion.
Avoid: "LLM" as a synonym in LangChain's own API — LLM is a separate, legacy text-completion interface class.
Message
A single turn in a conversation, with a role (system/human/ai/tool) and content, optionally including tool calls or usage metadata.
Avoid: "prompt" as a synonym — a prompt is a template that produces messages, not a message itself.
Tool
A Python function with a schema that a model can request be called; the model never executes it directly.
Avoid: "function" alone — every tool is a function, but not every function passed around your code is a tool the model can see.
Structured Output
Constraining a model's final response to a defined schema (typically a Pydantic model), parsed without free-text parsing.
Avoid: Confusing with tool calling — structured output shapes the answer, tool calling requests an action.
LCEL (LangChain Expression Language)
The |-based syntax for composing linear, non-branching sequences of runnables (prompt → model → parser).
Avoid: Using LCEL to describe agent logic — branching/looping agent flows are LangGraph's job.
Retrieval-Augmented Generation (RAG)
A pattern where relevant document chunks are retrieved by embedding similarity and injected into a prompt as grounding context.
Avoid: "fine-tuning" — RAG changes what the model reads at query time, not the model's weights.
Embedding
A numeric vector representation of text that captures semantic meaning, used to compare texts by similarity rather than keyword overlap.
Avoid: "token" — tokens are units of text the model processes; embeddings are a derived vector representation of that text.

LangGraph

StateGraph
LangGraph's core graph-builder class: a typed shared state, a set of nodes, and edges connecting them, compiled into a runnable app.
Avoid: "chain" — a chain is LCEL's linear composition; a StateGraph can branch and cycle.
Node
A function in a graph that reads the current state and returns a partial update to be merged into it.
Avoid: "step" — used loosely elsewhere, but in LangGraph a node is a specific, named unit registered on the graph.
Conditional Edge
An edge whose destination is decided at runtime by a routing function that inspects state.
Avoid: "branch" alone — a conditional edge is the mechanism; a branch is the resulting path.
Checkpointer
A persistence backend that saves graph state after every node, keyed by thread_id, enabling resumable and multi-turn execution.
Avoid: "cache" — a checkpoint is durable conversation state, not a performance optimization layer.
Thread
One continuous, checkpointed run or conversation, identified by a thread_id passed in the config at invoke time.
Avoid: "session" or "user" — a thread maps to one conversation, which may not be 1:1 with a user or login session.
Interrupt
A deliberate, resumable pause in graph execution that hands control to an external actor (typically a human) before continuing.
Avoid: "exception" or "error" — an interrupt is expected control flow, not a failure.
create_agent
LangChain 1.x's prebuilt function for constructing a standard tool-calling agent loop, compiled as a LangGraph graph under the hood.
Avoid: AgentExecutor, initialize_agent, create_react_agent (pre-1.0) — all deprecated, in maintenance mode through December 2026.
Supervisor Pattern
A multi-agent architecture where one coordinating agent routes work to specialist agents and receives control back after each.
Avoid: "orchestrator" as a precise synonym — used loosely across the industry; this guide reserves "supervisor" for the specific centralized-routing pattern.
Swarm / Handoff Pattern
A multi-agent architecture where agents transfer control directly to one another without a central router.
Avoid: Assuming it's always better than supervisor — it trades debuggability for routing flexibility.

LangSmith

Trace
The full recorded tree of a single run — every node, tool call, and LLM call, with inputs, outputs, latency, and token cost.
Avoid: "log" — a trace is structured and hierarchical, not a flat text log line.
Dataset (LangSmith)
A fixed, reusable collection of example inputs (and optionally expected outputs) used to run repeatable evaluations.
Avoid: Confusing with a RAG knowledge-base document set — different purpose entirely.
Evaluator
A function that scores a run's output against expected output or a rubric, either by code (exact-match) or by a second LLM call (LLM-as-judge).
Avoid: "test" alone — an evaluator produces a score, not a pass/fail assertion, though you can threshold it into one.
LLM-as-Judge
An evaluator implemented as an LLM call that scores a subjective quality (tone, helpfulness, groundedness) against a written rubric.
Avoid: Treating its score as ground truth — it carries its own error rate and should be spot-checked against human judgment.
Alert
A rule that fires when a production metric (error rate, latency, cost, feedback score) crosses a threshold over an aggregation window.
Avoid: Alerting on single-event failures — LLM calls have natural transient noise; windowed aggregation is the default for a reason.
