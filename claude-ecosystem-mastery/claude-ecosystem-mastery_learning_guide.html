How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone builds one running project — a small SQLite database of Hayah-AI sales leads (leads.db) — that grows from a skill, into an MCP server, into a distributable plugin.

Quick Start: Three Ways to Use This Guide

  1. Already run Claude Code daily but never built a skill or MCP server → Take the Placement Quiz to confirm, then jump to Phase 2.
  2. Comfortable with skills, new to MCP → Start at Module 3.1 and work through Phase 4 (server building) — that's the deepest, least-documented part of the ecosystem.
  3. Want the whole stack, in order → Follow the Full Ecosystem Mastery track from Module 1.1 through the Final Capstone.

Phase 1: CLI Foundations

Week 1 | Goal: run Claude Code confidently, interactively and headlessly, and control which model and session you're using

Module 1.1 — Install, Auth & Your First Session

Level: Beginner · Prereqs: None · Time: ~1.5h
Skip-check (test-out): Install Claude Code, run claude doctor, and get a clean report with no errors.
Skip if: You already run claude daily in at least one project.
Unlocks: All of Phase 1–5 — every later module assumes a working install.

Choosing an install method

Claude Code ships as a full-featured terminal CLI, a VS Code / JetBrains extension, a desktop app, and a web surface at claude.ai/code — all backed by the same engine, so your CLAUDE.md files, settings, and MCP servers work identically across them. This guide focuses on the terminal CLI, since it's the surface every other module builds on. The native installer is the right default for almost everyone: it updates itself in the background, so you're never stuck two months behind a security fix. Homebrew and WinGet are reasonable alternatives if you already manage your toolchain that way, but neither auto-updates — skipping brew upgrade for a few months is a common source of "why doesn't this flag exist yet" confusion.

# macOS / Linux / WSL — native installer (recommended)
curl -fsSL https://claude.ai/install.sh | bash

# Homebrew (does not auto-update — run `brew upgrade claude-code` periodically)
brew install --cask claude-code

# Windows PowerShell
irm https://claude.ai/install.ps1 | iex

First run & authentication

Start Claude Code inside any project directory. The first run prompts you to log in — a Claude subscription or Anthropic Console account both work, and the Terminal CLI additionally supports third-party providers (Bedrock, Vertex, etc.) if your org routes billing that way.

cd your-project
claude
# first run: browser opens, log in, then you land in an interactive session

claude doctor       # diagnostics: install health, config, auth status
claude auth status  # confirm which account/method is active

Run claude doctor right after install and again any time something feels off — it's the fastest way to rule out a broken install before you start debugging a skill or MCP server that "isn't working." A stale native install or a half-migrated Homebrew cask is a more common root cause than people expect.

Interactive vs. everything else

Everything from here forward is a variation on one loop: you (or a script) send Claude a prompt, it uses tools, it responds. The interactive session you just started is one mode of driving that loop. Module 1.2 covers the headless mode you'll use for scripting and CI, and Module 1.3 covers keeping multiple loops going in parallel. Skills (Phase 2) and MCP servers (Phases 3–4) don't change the loop — they add what Claude can read and do inside it.

Module 1.2 — Headless Mode & Scripting the CLI

Level: Beginner–Intermediate · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Write a one-line pipeline that feeds a file into claude -p and parses JSON output with jq.
Skip if: You already run claude -p in CI or cron jobs.
Unlocks: Module 1.3, Phase 1 Capstone, and every later "script this" exercise.

The -p flag and piping

Claude Code follows the Unix philosophy: composable, pipeable, scriptable. -p (--print) runs a query non-interactively and exits, which is what makes Claude usable inside a shell pipeline, a cron job, or a CI step rather than only a chat window. Without -p, Claude waits for more input forever — the single most common reason a "simple" CI script hangs is forgetting this flag.

# Analyze recent log output
tail -200 app.log | claude -p "Slack me if you see any anomalies"

# Bulk review across changed files
git diff main --name-only | claude -p "review these changed files for security issues"

Output formats for machine consumption

A CI step that parses free-text prose is a script waiting to break the first time Claude phrases something differently. --output-format json gives you a stable, parseable shape instead; --json-schema goes further and validates the response against a schema you supply, which matters when a downstream step (a Slack bot, a dashboard) depends on specific fields always being present.

claude -p --output-format json "list the 3 riskiest functions in src/auth.ts" > risk.json
jq '.result' risk.json

# Stream turn-by-turn events instead of waiting for the final answer
claude -p --output-format stream-json "refactor src/utils/date.ts"

Budgets, turns, and permission modes for unattended runs

An interactive session has you as a backstop — you can stop Claude if it goes somewhere unexpected. A headless script run from cron has no one watching, so the flags that bound its behavior aren't optional polish, they're the difference between a contained failure and an unattended agent burning through your API budget or touching files it shouldn't. --max-turns caps how many agentic steps a single -p call can take; --max-budget-usd stops the run once it hits a spending ceiling; --permission-mode decides whether tool calls need approval at all (in headless mode there's no one to approve them interactively, so most CI usage picks acceptEdits or scopes to a very narrow allowed-tools set rather than reaching for --dangerously-skip-permissions).

claude -p --max-turns 8 --max-budget-usd 2.00 \
  --permission-mode acceptEdits \
  "run the test suite and fix any failures"

Common mistake: Reaching for --dangerously-skip-permissions to make a CI script "just work" is almost always the wrong fix — it removes every guardrail at once. A tighter --allowed-tools list or --permission-mode acceptEdits solves the same "it keeps asking me" problem without giving an unattended process free rein over your filesystem and shell.

Module 1.3 — Sessions, Background Agents & Model Control

Level: Intermediate · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Kick off a background agent, check its logs, and resume a named session from two days ago (simulate with a fresh session name).
Skip if: You already use --bg/claude agents or resume sessions by name routinely.
Unlocks: Phase 1 Capstone.

Continuing and resuming sessions

-c continues the most recent conversation in the current directory — the fast path when you just closed the terminal. -r "<name>" resumes a specific named session, which matters once you have more than one thread of work going in the same project; without a name, Claude Code has no way to know which of several past conversations you mean.

claude -c                                    # continue most recent
claude -r "auth-refactor" "finish this PR"   # resume a named session with a new prompt
claude --resume                              # interactive picker across sessions

Running work in the background

--bg starts a session as a background agent and returns your terminal immediately, so a long investigation doesn't block you from doing anything else. You check on it, not the other way around — forgetting this and leaving a terminal tab pinned to a running session is the most common way people accidentally block themselves for twenty minutes.

claude --bg "investigate the flaky test in leads_tracker.test.ts"
claude agents           # list running/background sessions
claude logs <id>        # tail recent output
claude attach <id>      # switch into it interactively
claude stop <id>        # stop it

Choosing model and effort per task

Not every task needs your most capable (or most expensive) model at maximum reasoning effort. --model accepts an alias (sonnet, opus, haiku, fable) or a full model name; --effort trades latency and cost against reasoning depth (low through max). A quick lint-fix pass doesn't need --effort max; a gnarly race-condition investigation might be exactly where it pays for itself.

claude --model haiku -p "format this JSON file consistently"
claude --model opus --effort high -p "find the root cause of the intermittent 500s in checkout"

Module 2.1 — Anatomy of a Skill

Level: Beginner–Intermediate · Prereqs: Module 1.1 · Time: ~2h
Skip-check (test-out): Write a SKILL.md from scratch with frontmatter and a working /name invocation, no reference material.
Skip if: You've already written and used a custom skill.
Unlocks: Module 2.2, 2.3, all of Phase 5.

The SKILL.md file

A skill is a directory containing a SKILL.md: YAML frontmatter that tells Claude when to use it, and a markdown body with the instructions Claude follows once it does. Skills follow the open Agent Skills standard, so what you learn here transfers to other tools that support the same format. Unlike CLAUDE.md, which is loaded into every session's context whether you need it or not, a skill's body only loads when it's invoked — so a 400-line reference doc costs you nothing until the moment it's actually relevant. That's the real reason to reach for a skill instead of growing CLAUDE.md indefinitely: token cost that scales with usage, not with project size.

mkdir -p ~/.claude/skills/leads-status
---
description: Reports lead counts by status from the leads-tracker database. Use when asked about lead pipeline, lead counts, or lead status breakdown.
---

## Current lead counts by status

!`sqlite3 leads.db "SELECT status, COUNT(*) FROM leads GROUP BY status;"`

## Instructions

Summarize the counts above in one short paragraph. If the query returned nothing, say the leads database is empty or missing.

The !`command` line is dynamic context injection — Claude Code runs it and substitutes the output before Claude ever sees the skill, so the instructions arrive pre-loaded with live data instead of Claude having to guess or ask you to paste it. This one line is why a skill beats a saved prompt: a saved prompt is static text, a skill can pull the current state of the world into itself every time it runs.

Frontmatter that actually matters

Every field in frontmatter is optional, but description is the one field you should never skip — it's what Claude matches against your request to decide whether to load the skill automatically. A vague description ("helps with leads") means Claude either never finds it or finds it for the wrong requests; a specific one with the trigger phrasing spelled out ("Use when asked about lead pipeline, lead counts...") is what actually gets it invoked reliably.

Your first skill

Skill names come from where the file lives, not from frontmatter (with one exception covered in Module 5.1): a skill at ~/.claude/skills/leads-status/SKILL.md is invoked as /leads-status, regardless of what name: says inside it.

Module 2.2 — Where Skills Live: Locations, Precedence & Discovery

Level: Intermediate · Prereqs: Module 2.1 · Time: ~1.5h
Skip-check (test-out): Predict, without testing, which of two same-named skills (one project-level, one personal) wins — then verify.
Skip if: You can already state the full precedence order from memory.
Unlocks: Module 2.3, Phase 5.

The four locations and who they reach

LocationPathApplies to
Enterprisemanaged settingsAll users in your organization
Personal~/.claude/skills/<name>/SKILL.mdAll your projects
Project.claude/skills/<name>/SKILL.mdThis project only
Plugin<plugin>/skills/<name>/SKILL.mdWherever the plugin is enabled

Precedence when names collide

When two skills share a name, enterprise overrides personal, and personal overrides project — the opposite order from what many people guess, since "closest to the code wins" is the more familiar pattern from tools like .eslintrc. Getting this backwards matters in practice: if you've been quietly overriding a bundled skill (like /code-review) with a personal one, and a teammate adds a project-level skill of the same name expecting it to win for the whole team, it silently won't — your personal copy still wins for you. Plugin skills sidestep this entirely because they're always namespaced (/plugin-name:skill-name), so they can never collide with anything.

Nested skills in monorepos

Skills also load from nested .claude/skills/ directories below your working directory — so a package inside a monorepo can ship its own skills that only apply when you're touching that package. If a nested skill shares a name with a root-level one, both survive: the nested one gets a directory-qualified name (apps/web:deploy), and typing the unqualified /deploy still runs the root one, but Claude Code appends a note pointing it at any directory-qualified variant relevant to the files you're actually working on.

Module 2.3 — Advanced Skill Patterns

Level: Intermediate · Prereqs: Modules 2.1, 2.2 · Time: ~2.5h
Skip-check (test-out): Build a skill that takes a positional argument, only you can invoke it, and it's restricted to one allowed tool — without consulting reference material.
Skip if: You've already used $ARGUMENTS, context: fork, and allowed-tools together in one skill.
Unlocks: Phase 2 Capstone, Phase 5.

Passing arguments

$ARGUMENTS captures everything typed after the skill name; $N (or $ARGUMENTS[N]) accesses a specific positional argument. Quote multi-word values, since arguments use shell-style splitting — /leads-note 3 "called, no answer" gives you $0 = 3 and $1 = called, no answer as two clean arguments rather than four.

Injecting dynamic context vs. running the task yourself

You already used !`command` in Module 2.1 to pull live data into a skill's prompt. The same mechanism works with any shell command, and for multi-line commands you can use a fenced code block opened with ```! instead of the inline form. This runs once, before Claude ever sees the content — it's preprocessing, not something Claude decides to do, which is exactly why it's safe to rely on for grounding a skill in current state rather than trusting the model to remember or infer it.

Running a skill in a forked subagent

context: fork runs the skill's content as the prompt for an isolated subagent instead of inline in your conversation — useful when a task shouldn't see (or pollute) your main thread's history, like a broad research pass. It only makes sense for skills with an actual task in them; a skill that's just reference guidance ("use these conventions") gives the subagent nothing to act on and it returns empty-handed.

Controlling who invokes it

disable-model-invocation: true means only you can trigger the skill — the right choice for anything with a side effect you want to time deliberately, like writing to a database. user-invocable: false is the inverse: only Claude can invoke it, useful for background knowledge that isn't a meaningful command on its own. allowed-tools pre-approves specific tools while the skill is active, scoped tightly with pattern syntax like Bash(sqlite3 *) so the skill can only do the one narrow thing it's supposed to, not "anything in Bash."

---
name: leads-note
description: Append a note to a lead's record by ID
disable-model-invocation: true
allowed-tools: Bash(sqlite3 *)
---

Append the note "$1" to the lead with id $0 in leads.db:

!`sqlite3 leads.db "UPDATE leads SET notes = COALESCE(notes || ' | ', '') || '$1' WHERE id = $0;"`

Confirm the update by showing the row for id $0.

Common mistake: Writing a side-effecting skill (one that inserts, updates, or deletes data) without disable-model-invocation: true means Claude can decide on its own, mid-conversation, that now's a good time to run it. For anything you want to happen only when you explicitly ask, set this field — don't rely on the description alone to hold Claude back.

What MCP actually gives Claude Code

The Model Context Protocol is an open standard for connecting AI tools to external systems — databases, issue trackers, design tools, your own scripts. Without it, "ask Claude about the ticket" means you copy-pasting the ticket into chat by hand, every time, and Claude working from whatever you thought to paste rather than the live source of truth. An MCP server closes that gap: Claude reads and acts on the system directly.

Three transports, one deprecated

Stdio servers run as a local child process that Claude Code spawns and talks to over standard input/output — the simplest setup, ideal for tools needing direct filesystem or system access, and what you'll build in Phase 4. HTTP (Streamable HTTP) is the recommended transport for remote, cloud-hosted servers — a single endpoint, works with OAuth, and is the most widely supported transport for hosted services. SSE is deprecated — the MCP spec moved to Streamable HTTP, and most servers that used to support SSE now support HTTP on the same URL, so a new server should skip SSE entirely and an existing --transport sse connection error is usually fixed by switching to --transport http.

# Remote HTTP server (recommended default for hosted services)
claude mcp add --transport http notion https://mcp.notion.com/mcp

# Local stdio server — note the `--` separating Claude's flags from the server's
claude mcp add --transport stdio everything -- npx -y @modelcontextprotocol/server-everything

That -- matters more than it looks: everything after it is passed to the server untouched. Omit it and Claude Code tries to parse the server's own flags (like a hypothetical --port 8080) as its own options and rejects the command.

Managing what's connected

claude mcp list             # all configured servers
claude mcp get everything   # details for one server
claude mcp remove everything

.mcp.json and environment variable expansion

Committing .mcp.json means the API key can't live inside it in plaintext. Environment variable expansion (${VAR}, with an optional ${VAR:-default}) solves this: the file is safe to commit, and each teammate supplies the secret through their own environment.

{
  "mcpServers": {
    "internal-api": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${API_KEY}" }
    }
  }
}

OAuth and header-based auth

Claude Code marks a remote server as needing authentication when it responds with a 401 or 403, and flags it in /mcp so you can complete an OAuth flow in-browser. For servers that don't support automatic dynamic client registration, or for non-OAuth schemes (Kerberos, short-lived internal tokens), headersHelper runs a command at connect time and merges its JSON output into the request headers — the escape hatch for internal SSO that doesn't fit the standard flow.

@-mentioning MCP resources

Resources are file-like data a server exposes — API responses, documents, records — referenced the same way you'd @-mention a local file: @server:protocol://resource/path. Unlike tools, which Claude decides to call, resources are things you pull in explicitly, which makes them the right choice when you already know exactly what data you want attached rather than trusting the model to go find it.

Can you analyze @github:issue://123 and suggest a fix?
Compare @postgres:schema://users with @docs:file://database/user-model

MCP prompts as slash commands

A server can expose reusable prompt templates that show up as /mcp__servername__promptname — a way for a server author to standardize a common workflow (a bug-report template, a PR-review checklist) without you having to remember the exact phrasing every time.

How tool search keeps context cheap at scale

Tool search is on by default, and it's why you can connect a dozen MCP servers without your context window filling up with tool definitions you're not using this turn: only tool names and server instructions load at session start, and Claude searches for the relevant tool schema only when a task actually needs it. This is also why the server instructions field matters if you ever build your own server (Phase 4) — it's the first thing Claude sees when deciding whether to search your server's tools at all, functioning much like a skill's description.

Tools, resources, and prompts — the three primitives

Every MCP server capability is one of three types. Tools are functions the model calls, with your approval, to take an action or fetch something dynamic — the primitive you'll use for almost everything. Resources are fetched by the client (not the model) and injected into context — background data like docs or config the user references explicitly, not something Claude decides on its own to go pull. Prompts are reusable templates a user selects to kick off a standardized workflow. Getting this classification right matters for more than vocabulary: a "read-only lookup" implemented as a tool costs a permission prompt and a model decision every time, where the same data as a resource is just referenced directly — cheaper and more predictable when the caller already knows what they want.

SDKTierPick it when…
TypeScript1You want the largest ecosystem and reference examples, or you're already in a Node toolchain.
Python1Your data/logic already lives in Python (pandas, existing scripts, ML tooling).

Java, Rust2Feature-complete, actively maintained, smaller ecosystem than Tier 1.
Swift, Ruby, PHP, Kotlin3Community-maintained — check activity before depending on it for anything production-critical.

The stdout rule

A stdio server talks to its client over standard input/output using JSON-RPC. Any stray write to stdout — a leftover console.log, a bare print() — corrupts that stream and silently breaks the server. This is the single most common first bug when building an MCP server, and it's why every official quickstart leads with it: log to stderr (console.error in Node, print(..., file=sys.stderr) or the logging module in Python), never stdout.

Project setup (TypeScript)

mkdir leads-tracker-mcp && cd leads-tracker-mcp
npm init -y
npm install @modelcontextprotocol/sdk zod@3 better-sqlite3
npm install -D @types/node @types/better-sqlite3 typescript
mkdir src
// src/index.ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";
import Database from "better-sqlite3";

const db = new Database("leads.db");

const server = new McpServer({ name: "leads-tracker", version: "1.0.0" });

server.registerTool(
  "query_leads",
  {
    description: "List leads, optionally filtered by status (new, contacted, closed)",
    inputSchema: {
      status: z.string().optional().describe("Filter by lead status"),
    },
  },
  async ({ status }) => {
    const rows = status
      ? db.prepare("SELECT id, name, company, status FROM leads WHERE status = ?").all(status)
      : db.prepare("SELECT id, name, company, status FROM leads").all();
    return { content: [{ type: "text", text: JSON.stringify(rows, null, 2) }] };
  },
);

server.registerTool(
  "add_lead_note",
  {
    description: "Append a note to a lead's record by ID. This is a write operation.",
    inputSchema: {
      id: z.number().describe("Lead ID"),
      note: z.string().describe("Note text to append"),
    },
  },
  async ({ id, note }) => {
    db.prepare(
      "UPDATE leads SET notes = COALESCE(notes || ' | ', '') || ? WHERE id = ?",
    ).run(note, id);
    const row = db.prepare("SELECT * FROM leads WHERE id = ?").get(id);
    return { content: [{ type: "text", text: JSON.stringify(row, null, 2) }] };
  },
);

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("leads-tracker MCP server running on stdio");
}

main().catch((error) => {
  console.error("Fatal error in main():", error);
  process.exit(1);
});

The same server in Python with FastMCP

FastMCP reads your type hints and docstring to generate the tool schema automatically, which is why the Python version below needs no explicit JSON Schema — it's inferred instead of hand-written like the Zod version above.

uv init leads-tracker-mcp && cd leads-tracker-mcp
uv add "mcp[cli]"
import sqlite3
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("leads-tracker")

def get_db():
    return sqlite3.connect("leads.db")

@mcp.tool()
def query_leads(status: str | None = None) -> str:
    """List leads, optionally filtered by status (new, contacted, closed).

    Args:
        status: Filter by lead status. Omit to list all leads.
    """
    conn = get_db()
    if status:
        rows = conn.execute(
            "SELECT id, name, company, status FROM leads WHERE status = ?", (status,)
        ).fetchall()
    else:
        rows = conn.execute("SELECT id, name, company, status FROM leads").fetchall()
    conn.close()
    return str(rows)

@mcp.tool()
def add_lead_note(id: int, note: str) -> str:
    """Append a note to a lead's record by ID. This is a write operation.

    Args:
        id: Lead ID
        note: Note text to append
    """
    conn = get_db()
    conn.execute(
        "UPDATE leads SET notes = COALESCE(notes || ' | ', '') || ? WHERE id = ?", (note, id)
    )
    conn.commit()
    row = conn.execute("SELECT * FROM leads WHERE id = ?", (id,)).fetchone()
    conn.close()
    return str(row)

if __name__ == "__main__":
    mcp.run(transport="stdio")

Common mistake: Both versions open leads.db with a relative path, which resolves against the server process's working directory — not where the file lives. When Claude Code spawns the server from leads-tracker/ it happens to work, but run it under the Inspector from leads-tracker-mcp/ and you'll query an empty, freshly-created database and wonder where your leads went. Harden it with an absolute path, or read CLAUDE_PROJECT_DIR (which Claude Code sets in the spawned server's environment: process.env.CLAUDE_PROJECT_DIR in Node, os.environ["CLAUDE_PROJECT_DIR"] in Python) with a fallback for non-Claude clients.

Logging, error handling, and output-size limits

A tool that throws an unhandled exception on bad input takes down the whole server connection, not just that one call — wrap tool logic so a bad argument returns a clear error message in the tool result instead. If a tool can legitimately return a very large result (a full schema dump, say), the default 25,000-token output limit will truncate it to a file reference; set _meta["anthropic/maxResultSizeChars"] in that tool's definition to raise its own threshold rather than asking every caller to raise MAX_MCP_OUTPUT_TOKENS globally.

Publishing to the Anthropic Directory

A server built for personal use stays a local stdio process pointed at with an absolute path. Sharing it more broadly means deploying it as a remote HTTP server (so others don't need your source tree locally) and following the Claude connector building docs for authentication and Directory submission — the same review path Anthropic's own listed connectors go through.

The plugin.json manifest

A plugin is a directory containing skills, agents, hooks, or MCP servers, optionally alongside a .claude-plugin/plugin.json manifest declaring its identity. The manifest is what turns a folder of loose configuration into something with a name, a version, and a namespace — the difference between "files in .claude/" and "a thing you can hand to someone else."

{
  "name": "hayah-ops-toolkit",
  "description": "Lead-tracking skill and MCP server for the Hayah-AI leads database",
  "version": "1.0.0",
  "author": { "name": "Your Name" }
}

name becomes the skill namespace — a skill at skills/leads-digest/SKILL.md inside this plugin is invoked as /hayah-ops-toolkit:leads-digest, never the bare /leads-digest. This namespacing is deliberate: it's what lets two different plugins each ship a skill called deploy without ever conflicting, unlike standalone project or personal skills which collide by name (Module 2.2).

What a plugin can bundle

Directory / fileLocationPurpose
.claude-plugin/Plugin rootContains plugin.json only — never put skills/, agents/, or hooks/ here.
skills/Plugin rootSkills as <name>/SKILL.md directories.
agents/Plugin rootCustom subagent definitions.
hooks/hooks.jsonPlugin rootEvent handlers (PostToolUse, etc).
.mcp.jsonPlugin rootMCP server configuration.
bin/Plugin rootExecutables added to the Bash tool's PATH while enabled.

The most common structural mistake, called out explicitly in the docs, is nesting skills/ or hooks/ inside .claude-plugin/ — that folder holds exactly one file, the manifest, and nothing else.

Skills-directory plugins

For a plugin you only use yourself, claude plugin init my-tool scaffolds one directly inside your skills directory (~/.claude/skills/my-tool/) — it loads automatically on the next session with no marketplace or install step, useful when a skill has grown complex enough to want its own MCP server or agent but doesn't need to be shared yet.

--plugin-dir for fast iteration

--plugin-dir loads a plugin directly from a local folder for the current session, with no install or marketplace step — the right tool for every stage of building a plugin before it's ready to share. It even takes precedence over an already-installed marketplace plugin of the same name for that session, so you can test changes to something you use daily without uninstalling it first.

claude --plugin-dir ./hayah-ops-toolkit
# load two at once while comparing versions:
claude --plugin-dir ./hayah-ops-toolkit --plugin-dir ./hayah-ops-toolkit-v2

/reload-plugins and live testing

Editing a plugin's SKILL.md text is picked up live in most standalone cases, but a plugin's other components — hooks, its .mcp.json, agents — need an explicit /reload-plugins to take effect, since those involve process restarts (an MCP server subprocess, for instance) that can't happen silently mid-session. Run it after every change to a plugin's non-skill files, and test each component individually: skills with /plugin-name:skill-name, agents by checking /context, hooks by triggering the event they match.

Converting your standalone skill + MCP server into a plugin

Nothing about the skill or server content changes — only where the files live and how the server is declared. A plugin's .mcp.json uses ${CLAUDE_PLUGIN_ROOT} instead of a hardcoded absolute path, so the plugin works on any machine it's installed on, not just yours.

{
  "mcpServers": {
    "leads-tracker": {
      "command": "node",
      "args": ["${CLAUDE_PLUGIN_ROOT}/servers/leads-tracker/build/index.js"]
    }
  }
}

marketplace.json and hosting on git

A marketplace is a catalog file, .claude-plugin/marketplace.json, that lists plugins and where to fetch them from — the mechanism that turns "here's a zip file, unpack it and point --plugin-dir at it" into "add this URL, then install by name." Hosting it in a normal git repository is enough; there's no special infrastructure requirement.

{
  "name": "hayah-ai-tools",
  "owner": { "name": "Your Name" },
  "plugins": [
    {
      "name": "hayah-ops-toolkit",
      "source": "./hayah-ops-toolkit",
      "description": "Lead-tracking skill and MCP server for the Hayah-AI leads database"
    }
  ]
}

Installing from a marketplace

# team member adds your marketplace once
claude plugin marketplace add your-org/hayah-ai-tools

# then installs the plugin from it
/plugin install hayah-ops-toolkit@hayah-ai-tools

# you push an update; they refresh with:
/plugin marketplace update hayah-ai-tools

This is the meaningful upgrade over --plugin-dir: a marketplace gives you centralized discovery, a name people can install by, and a clear update path — push to the repo, teammates run one command to pick it up, instead of everyone re-pulling a folder and re-pointing a flag by hand.

Official vs. community marketplace, and private ones

claude-plugins-official is Anthropic-curated and registers automatically on first interactive launch; claude-community is the public catalog third-party plugins land in after automated review (claude plugin validate runs the same check locally before you submit). Neither is what you want for something internal to Hayah-AI — for that, host your own marketplace in a private git repository, which keeps it invisible to anyone without repo access while still giving your own tooling the same install/update ergonomics as a public one.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

CLI & Sessions

Headless mode
Running Claude Code non-interactively via -p/--print, for scripting, CI, or piping.
Avoid: "print mode" alone — fine informally, but "headless" is the term used for the broader scripting context (budgets, output formats, permission modes).
Session
A single conversation thread with Claude Code, identifiable by ID or name, resumable with -c or -r.
Avoid: "chat" — the docs and CLI consistently say "session."
Background agent
A session started with --bg that runs without occupying your terminal, managed via claude agents/logs/attach/stop.
Avoid: confusing this with a "subagent" (a Task-tool delegate within one session) — a background agent is a whole separate top-level session.
Effort level
A per-request reasoning-depth setting (low through max) that trades latency and cost against how much the model reasons before answering.
Avoid: "temperature" or "creativity" — effort controls reasoning depth, not randomness.
Permission mode
The policy governing whether tool calls need your approval (default, acceptEdits, plan, bypassPermissions, etc.), settable per-run with --permission-mode.
Avoid: treating --dangerously-skip-permissions as a normal permission mode — it's an escape hatch, not a default choice.
Native installer
The curl | bash / irm | iex install method that self-updates in the background.
Avoid: assuming Homebrew or WinGet installs also auto-update — they don't.
CLAUDE.md
A project-root markdown file loaded into every session's context at startup, for standing instructions and conventions.
Avoid: growing it into a procedure library — that's what a skill is for (loads on demand, not every session).
Auto memory
Learnings (build commands, debugging insights) Claude Code saves across sessions on its own, without explicit authoring.
Avoid: confusing this with a skill — auto memory is discovered by Claude, a skill is authored by you.

Skills

SKILL.md
The entrypoint file of a skill: YAML frontmatter plus a markdown instruction body.
Avoid: "custom command" — that's the older, still-supported .claude/commands/ format; skills are the superset with more features.
Frontmatter
The YAML block between --- markers at the top of SKILL.md that configures invocation, tool access, and behavior.
disable-model-invocation
A frontmatter field that restricts a skill so only you (not Claude) can trigger it.
Avoid: confusing with user-invocable: false, which is the opposite restriction (only Claude can trigger it).
Dynamic context injection
The !`command` syntax that runs a shell command and substitutes its output into a skill's content before Claude reads it.
Avoid: thinking Claude executes this — it runs as preprocessing, before the model ever sees the skill.
context: fork
A frontmatter field that runs a skill's content as the prompt for an isolated subagent instead of inline in the current conversation.
allowed-tools
A frontmatter field pre-approving specific tools (often scoped with a pattern like Bash(git *)) while a skill is active, so Claude doesn't prompt for them.
Avoid: assuming it restricts tool access — it only grants pre-approval; every tool remains callable subject to your normal permission settings.
Skill precedence
The resolution order when two skills share a name: enterprise, then personal, then project; plugin skills never collide because they're namespaced.
Avoid: assuming "closest to the code wins" — it's the opposite of many linter/config precedence patterns.
Nested skill
A skill in a .claude/skills/ directory below the session's starting directory, auto-discovered when working on files in that subtree.
Skill listing budget
The context-window fraction reserved for skill names/descriptions shown to Claude; descriptions get shortened or dropped once it's exceeded.
Avoid: assuming every skill's full description is always in context — only up to the budget.

MCP

MCP (Model Context Protocol)
An open standard for connecting AI applications to external tools, data sources, and systems.
Transport
The connection mechanism between an MCP client and server: stdio (local process), HTTP/Streamable HTTP (remote, recommended), or SSE (remote, deprecated).
Avoid: starting a new remote server on SSE — the spec has moved to Streamable HTTP.
Tool (MCP)
A function an MCP server exposes that the model can call, with user approval, to take an action or fetch dynamic data.
Resource (MCP)
File-like data an MCP server exposes that the client (not the model) fetches and injects into context, typically via an @ mention.
Avoid: implementing something the user should explicitly reference as a tool instead — that costs an extra model decision and permission prompt for no benefit.
Prompt (MCP)
A reusable template an MCP server exposes, surfaced as a slash command (/mcp__server__prompt).
Avoid: confusing with a "system prompt" — an MCP prompt is a user-invoked template, unrelated to model configuration.
Scope (MCP)
Where an MCP server's configuration is stored and who it's visible to: local (private, this project), project (shared via .mcp.json), or user (private, all projects).
Tool search
The default behavior of deferring MCP tool schemas out of context until a task actually needs them, keeping context cost roughly flat as you add servers.
Elicitation
A mechanism letting an MCP server request structured input (a form, or a browser-based auth flow) mid-task from the user.
Dynamic Client Registration (DCR)
The OAuth mechanism that lets Claude Code register itself with an MCP server's authorization server automatically, without pre-shared credentials.
Avoid: assuming every server supports it — servers that don't require pre-configured --client-id/--client-secret instead.

Plugins

Plugin
A directory bundling skills, agents, hooks, or MCP servers, optionally with a .claude-plugin/plugin.json manifest, distributable as one unit.
plugin.json
The manifest file at .claude-plugin/plugin.json declaring a plugin's name, version, description, and author.
Avoid: placing anything besides this one file inside .claude-plugin/ — components live at the plugin root.
Marketplace
A catalog (defined by a marketplace.json) that lists plugins and where to fetch them, enabling discovery and one-command install/update.
marketplace.json
The catalog file at .claude-plugin/marketplace.json in a marketplace repository, listing plugin names and sources.
Avoid: confusing with plugin.json — one describes a marketplace (many plugins), the other describes a single plugin.
Namespace (plugin)
The plugin-name: prefix automatically applied to every skill and agent a plugin provides, preventing name collisions across plugins.
--plugin-dir
A CLI flag that loads a plugin directly from a local folder for the current session only, with no install step.
Avoid: treating it as a distribution mechanism — it's for local development and testing, not sharing with others.
Skills-directory plugin
A plugin created with claude plugin init that lives inside ~/.claude/skills/ and loads automatically every session, no marketplace required.
/reload-plugins
The command that picks up changes to a plugin's hooks, MCP servers, or agents without restarting the session.
Avoid: assuming it's needed for every skill text edit — plain skill content is often picked up live already.
