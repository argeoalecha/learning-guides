How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone maps the same realistic TindaHub scenario — the same 17-city Philippine sari-sari-store distribution network used in this workspace's Python GIS guide, so every map you build in R represents a real, consistent business geography rather than toy coordinates.

Scope note: this guide assumes you already know R fundamentals and basic ggplot2 (aes(), geoms, themes, facet_wrap) — covered in the R Markdown in RStudio guide's Module 2.3, which this guide does not repeat. That guide's Module 3.4 (htmlwidgets & the Shiny runtime) also uses leaflet once as a generic example of an htmlwidget; this guide is the actual deep dive into leaflet for mapping specifically, plus three packages that guide never touches at all: sf (the modern spatial-data foundation everything else in this guide sits on), mapview (one-line interactive exploration), and geom_sf (the spatial extension of the ggplot2 you already know). If you've only ever seen R spatial work done with sp, rgdal, or rgeos, be aware those packages were retired from CRAN in October 2023 — this guide teaches only their modern replacement, sf, which is the current standard the entire R-spatial ecosystem (including terra for raster data, out of this guide's vector-focused scope) has converged on.

Module 1.1 — Simple Feature Geometries: sfg, sfc & sf Objects

Level: Beginner–Intermediate · Prereqs: R and tidyverse basics (data frames, pipes, dplyr) · Time: ~2h
Skip-check (test-out): Build an sf object from a data frame with lon/lat columns using st_as_sf(), and explain what the geometry list-column actually stores.
Skip if: You already default to sf for spatial data and understand the sfg/sfc/sf hierarchy.
Unlocks: Module 1.2, Module 2.1, Module 3.2, Module 4.1

Three layers: sfg, sfc, sf

sf (Simple Features for R) represents spatial data across three nested layers. An sfg (simple feature geometry) is a single geometry — one point, one line, one polygon — created with functions like st_point(). An sfc (simple feature geometry column/list) is a vector of sfg objects sharing one CRS, created with st_sfc(). An sf object is an ordinary data frame (or tibble) with one column that is an sfc — conventionally named geometry. This is the single most important thing to understand about sf: it doesn't introduce a separate spatial-table class the way some other ecosystems do; a spatial dataset in R is just a data frame with one special list-column, so every dplyr verb (filter(), mutate(), group_by(), summarise()) works on it directly, no special spatial-aware syntax required for non-geometric operations.

library(sf)

manila_pt <- st_point(c(120.9842, 14.5995))   # an sfg — a single geometry, x then y (lon, lat)
print(st_as_text(manila_pt))                   # "POINT (120.9842 14.5995)" — Well-Known Text

geom_column <- st_sfc(manila_pt, crs = 4326)   # an sfc — a geometry list, with a CRS attached
print(st_crs(geom_column)$input)               # "EPSG:4326"

cities_df <- data.frame(city = "Manila", pop = 1780000)
cities_sf <- st_sf(cities_df, geometry = geom_column)   # an sf object — a data frame + geometry column
print(class(cities_sf))                        # "sf" "data.frame" — it really is both

Common mistake: passing (latitude, longitude) instead of (longitude, latitude) to st_point() or st_as_sf(coords = ...). Like most geometry libraries, sf orders coordinates as (x, y) — geographic x is longitude, y is latitude. Swap them and every point silently lands in the wrong place with no error raised.

The common shortcut: st_as_sf() from an existing data frame

Building geometries one st_point() call at a time is rarely how you actually start — more often you already have a data frame with lon/lat columns and want to convert the whole thing at once. st_as_sf(df, coords = c("lon_col", "lat_col"), crs = 4326) does exactly that, vectorized, in one call.

library(sf)
library(readr)

city_coords <- read_csv("../python-gis-mapping/tindahub_city_coords.csv")
cities_sf <- st_as_sf(city_coords, coords = c("Lon", "Lat"), crs = 4326, remove = FALSE)
# remove = FALSE keeps the original Lon/Lat columns alongside the new geometry column
print(cities_sf)

Module 1.2 — Coordinate Reference Systems & st_transform

Level: Intermediate · Prereqs: Module 1.1 · Time: ~2.5h
Skip-check (test-out): Explain the difference between a geographic and a projected CRS, reproject an sf object with st_transform(), and compute a real-world distance in kilometers.
Skip if: CRS concepts and st_transform() are already comfortable.
Unlocks: Module 1.3, Module 1.4, Module 2.2

Geographic vs. projected CRS

A geographic CRS (like EPSG:4326/WGS84) expresses positions as angles on a sphere/ellipsoid — degrees of latitude and longitude, what GPS coordinates natively come in. A projected CRS flattens that sphere onto a 2D plane, expressing positions in linear units (usually meters) — the form that makes area, distance, and buffer calculations behave the way intuition expects. Every distance or area computed directly on EPSG:4326 data is in degrees, not meters — technically well-defined, but not a real-world distance.

EPSG codes and st_transform

st_transform(x, crs) reprojects an sf object to a new CRS, identified by its EPSG code. EPSG:32651 (UTM Zone 51N) covers most of the Philippines with good local accuracy for area/distance work; EPSG:3857 (Web Mercator) is what most web-map tile providers use for display but distorts area badly at higher latitudes, making it a poor choice for actual measurement.

library(sf)

manila <- st_sfc(st_point(c(120.9842, 14.5995)), crs = 4326)
cebu <- st_sfc(st_point(c(123.8854, 10.3157)), crs = 4326)

print(st_distance(manila, cebu))          # a value in degrees — not meaningful on its own

manila_utm <- st_transform(manila, 32651)
cebu_utm <- st_transform(cebu, 32651)
distance_km <- as.numeric(st_distance(manila_utm, cebu_utm)) / 1000
print(distance_km)                         # a real, trustworthy distance in kilometers

Common mistake: calling st_buffer(), st_distance(), or st_area() on an sf object still in EPSG:4326 and treating the result as meters or square meters. sf will compute something either way (recent sf versions even do geodesic/spherical distance calculations on unprojected data by default via the underlying s2 library, which is more defensible than a naive degree-based calculation would be) — but for buffering, and for full control over which projection's distortions you're accepting, an explicit st_transform() to an appropriate projected CRS first remains the deliberate, predictable choice.

Module 1.3 — Spatial Predicates, Joins & st_join

Unlocks: Module 1.4, Module 2.3, Module 3.2

Core spatial predicates

st_intersects(a, b) is true if the geometries share any point at all (including just touching at an edge); st_contains(a, b) is true if b is entirely inside a with no boundary touching; st_within(a, b) is the mirror of st_contains; st_touches(a, b) is true only if they share a boundary point but no interior points. A point sitting exactly on a polygon's edge satisfies st_intersects but not st_contains — the same boundary-exact distinction that matters for any real "is this order inside my delivery zone" business rule.

library(sf)

zone <- st_sfc(st_polygon(list(rbind(
  c(120.95, 14.55), c(121.05, 14.55), c(121.05, 14.65), c(120.95, 14.65), c(120.95, 14.55)
))), crs = 4326)
inside_pt <- st_sfc(st_point(c(121.00, 14.60)), crs = 4326)
edge_pt <- st_sfc(st_point(c(120.95, 14.60)), crs = 4326)      # exactly on the zone's left edge

print(st_contains(zone, inside_pt, sparse = FALSE))    # TRUE
print(st_contains(zone, edge_pt, sparse = FALSE))       # FALSE — boundary doesn't count as "contained"
print(st_intersects(zone, edge_pt, sparse = FALSE))     # TRUE — touching the boundary is enough

sparse = FALSE returns a plain logical matrix; the default sparse = TRUE returns a more memory-efficient sparse list representation, which matters once you're testing many-against-many geometries rather than one pair.

st_join: joining by location, not by key

st_join(x, y, join = st_within) (or any other predicate function) attaches y's attribute columns onto x wherever the chosen spatial predicate is true — no shared key column required at all, unlike a normal dplyr::left_join(), which matches on column values. The default join predicate, if you don't specify one, is st_intersects — worth stating explicitly in code rather than relying on the default, since the boundary-edge-case behavior differs from st_within/st_contains in exactly the way Module 1.2's callout warned about.

library(sf)
library(dplyr)

# points_sf: cities; zones_sf: candidate hub coverage polygons with a hub_name column
assigned <- st_join(points_sf, zones_sf, join = st_within, left = TRUE)
# left = TRUE keeps every point even if it matches no zone (hub_name becomes NA for those)

Module 1.4 — Geometric Operations: Buffers, Unions & Measurements

Level: Intermediate · Prereqs: Module 1.2 · Time: ~2.5h
Skip-check (test-out): Compute a buffer, a union of overlapping polygons, and their intersection, all on projected data, and interpret each in a real coverage-area scenario.

st_buffer, st_union, st_intersection, st_difference

st_buffer(x, dist) grows a geometry outward by dist in its own CRS's units (meters, once projected); st_union() combines geometries into one (either unioning a whole column into a single merged shape, or unioning two specific geometries together); st_intersection(a, b) returns only the overlapping area between two geometries; st_difference(a, b) returns a with b's area removed.

library(sf)
library(dplyr)

hub_a <- st_buffer(st_transform(manila_sf, 32651), dist = 100000)   # 100 km, in meters, on projected data
hub_b <- st_buffer(st_transform(cebu_sf, 32651), dist = 100000)

overlap <- st_intersection(hub_a, hub_b)      # area served by both hubs
combined <- st_union(hub_a, hub_b)             # total footprint served by either hub
exclusive_a <- st_difference(hub_a, hub_b)     # area only hub_a covers

st_area, st_length, st_distance

These three measurement functions all return values with explicit units attached (an R units object, e.g. "m^2" or "km") when run on projected data — as.numeric() strips the units back to a plain number once you're confident which unit it's actually in, but keeping the units-aware object around during analysis is worth it specifically because it makes an accidental unprojected-data mistake (Module 1.2's caution) visible immediately: a suspiciously tiny "distance" reported in raw degree-equivalent units stands out much more than a bare number would.

Skip-check (test-out): Plot an sf object with geom_sf(), map a data column to fill or color, and control the plot's projection and extent with coord_sf().

geom_sf: one geom for points, lines, and polygons

geom_sf() is unusual among ggplot2 geoms in that it automatically draws the right shape — points, lines, or polygons — based purely on what kind of geometry is in the sf object's geometry column, with no separate geom_point()/geom_polygon() choice required. This is the same aes()-based grammar you already know from any other ggplot2 chart; the only genuinely new piece is that the geometry column itself supplies the x/y positions, so you don't write aes(x = ..., y = ...) for it the way you would for an ordinary scatterplot.

library(ggplot2)
library(sf)

ggplot(cities_sf) +
  geom_sf(aes(color = Province), size = 3) +
  theme_minimal() +
  labs(title = "TindaHub City Network")

coord_sf: reprojecting and cropping at plot time

coord_sf() is where geom_sf()'s real power over a purely manual workflow shows up: it can reproject the plotted data to a different CRS at draw time, without you calling st_transform() on the underlying data first — and it automatically keeps geographic aspect ratio correct (a degree of longitude and a degree of latitude aren't the same real-world distance, and coord_sf() accounts for that by default, unlike plain coord_cartesian()). xlim/ylim arguments to coord_sf() crop the visible extent without subsetting the underlying data.

ggplot(cities_sf) +
  geom_sf() +
  coord_sf(crs = st_crs(32651)) +             # reproject for display only — data itself is untouched
  theme_minimal()

ggplot(cities_sf) +
  geom_sf() +
  coord_sf(xlim = c(120.5, 121.5), ylim = c(14.3, 14.8)) +   # crop to Metro Manila, no data subsetting
  theme_minimal()

Common mistake: manually filtering or cropping an sf object's rows to "zoom in," when coord_sf(xlim=, ylim=) achieves the same visual result without discarding data — useful because the same underlying sf object can then be reused for a wide shot and a zoomed-in inset without keeping two separate filtered copies.

Mapping fill to a numeric column

A choropleth maps a numeric or categorical data column to each polygon's fill color. ggplot2 4.0's viridis-family scales (scale_fill_viridis_c() for continuous, scale_fill_viridis_b() for binned) are a strong default: perceptually uniform and colorblind-safe, unlike an arbitrary red-to-green gradient that can misrepresent the data's actual structure to a meaningful fraction of viewers.

library(ggplot2)
library(sf)

ggplot(province_summary_sf) +
  geom_sf(aes(fill = total_revenue), color = "white", linewidth = 0.2) +
  scale_fill_viridis_c(option = "mako", labels = scales::label_currency(prefix = "₱")) +
  theme_minimal() +
  labs(title = "TindaHub Revenue by Province", fill = "Revenue")

As of ggplot2 4.0, geom_sf()'s default polygon outline linewidth is 0.2 (thinner than earlier ggplot2 versions defaulted to) — worth knowing if you're following an older tutorial's exact linewidth values, or if a map you're porting from an older ggplot2 looks visually different after upgrading without any code change.

Continuous vs. binned scales

A continuous scale (scale_fill_viridis_c) shows a smooth gradient legend, appropriate when the underlying value is genuinely continuous and precise comparison matters. A binned scale (scale_fill_viridis_b, or manually with scale_fill_stepsn) groups values into discrete bins, which is often easier for a map reader to compare across regions at a glance — the trade-off is losing fine-grained precision in exchange for readability, a real design decision rather than a default to leave unexamined.

facet_wrap() works on sf-backed plots exactly as it does on any other ggplot2 chart — splitting the data by a categorical column into a grid of small, identically-scaled maps. leaflet(): a Leaflet.js map, built with pipes

The R leaflet package is a wrapper around Leaflet.js, the same JavaScript library Python's Folium wraps — the R version's distinctive style is building a map by piping (%>% or native |>) a sequence of add*() functions onto an initial leaflet() call, each one adding a layer or setting.

library(leaflet)

leaflet() %>%
  addTiles() %>%                                     # default OpenStreetMap tiles
  setView(lng = 121.0, lat = 12.5, zoom = 6) %>%
  addMarkers(
    lng = 120.9842, lat = 14.5995,
    popup = "Manila Hub — 1,204 orders this month",
    label = "Manila Hub"
  )

popup opens on click and stays open until dismissed; label shows on hover and disappears immediately — the same popup/tooltip distinction as any web-mapping library, just under R's own argument names.

addProviderTiles() swaps the default OpenStreetMap tiles for any of dozens of alternative providers (providers$CartoDB.Positron for a clean, low-contrast base good for data-heavy overlays, among many others), without needing a raw tile URL template for the common cases.

Color palette functions for choropleths

Toggleable layers via group

Unlike some web-mapping libraries that require a separate explicit layer-group object, leaflet in R associates any layer with a toggle group simply by passing a group = "some name" argument to the add*() call that creates it — addLayersControl(overlayGroups = c(...)) then builds the actual toggle UI referencing those same group names.

leaflet(orders_sf) %>%
  addProviderTiles(providers$CartoDB.Positron) %>%
  addCircleMarkers(data = filter(orders_sf, Status == "Delivered"), color = "#0d7a6e", group = "Delivered") %>%
  addCircleMarkers(data = filter(orders_sf, Status == "Cancelled"), color = "#ff6b47", group = "Cancelled") %>%
  addLayersControl(overlayGroups = c("Delivered", "Cancelled"), options = layersControlOptions(collapsed = FALSE))

Clustering markers at scale

Plotting one marker per order across thousands of rows produces an unreadable wall of overlapping pins. clusterOptions = markerClusterOptions(), passed to addCircleMarkers() or addMarkers(), groups nearby markers into a single numbered cluster icon that expands as the viewer zooms in.

leaflet(orders_sf) %>%
  addProviderTiles(providers$CartoDB.Positron) %>%
  addCircleMarkers(clusterOptions = markerClusterOptions(), popup = ~as.character(OrderID))

Embedding a map in Shiny

leafletOutput("map_id") in the UI and renderLeaflet({ ... }) in the server are the standard Shiny output/render pair for any htmlwidget, leaflet included — the same pattern covered generically in the R Markdown guide's Module 3.4, applied here specifically to a map.

library(shiny)
library(leaflet)

ui <- fluidPage(
  selectInput("region_filter", "Region", choices = c("All", unique(cities_sf$Region))),
  leafletOutput("map")
)

server <- function(input, output, session) {
  output$map <- renderLeaflet({
    leaflet(cities_sf) %>% addProviderTiles(providers$CartoDB.Positron) %>% addCircleMarkers()
  })
}

leafletProxy: updating without a full redraw

Re-running the entire renderLeaflet({ ... }) block on every user input change rebuilds the whole map from scratch — including resetting the current pan/zoom position, which is a jarring user experience for something like a dropdown filter that should just update the visible markers in place. leafletProxy("map_id") lets you issue incremental updates (clear and re-add specific layers) against the already-rendered map, preserving view state.

server <- function(input, output, session) {
  output$map <- renderLeaflet({
    leaflet(cities_sf) %>% addProviderTiles(providers$CartoDB.Positron)
  })

  observeEvent(input$region_filter, {
    filtered <- if (input$region_filter == "All") cities_sf else filter(cities_sf, Region == input$region_filter)
    leafletProxy("map", data = filtered) %>%
      clearMarkers() %>%
      addCircleMarkers(popup = ~City)
    # note: no leaflet(...) / setView() call here — the existing map's pan/zoom state is preserved
  })
}

One line, a fully interactive map

mapview(sf_object) produces a complete interactive map — tile basemap, popups showing every attribute column, a working layer control, appropriate default styling — from a single function call on any sf object, with no manual palette or popup configuration required. This makes it the natural first thing to reach for the moment you have a new sf object and want to actually look at it, rather than the tool for building a final, polished, custom-styled deliverable (that's leaflet's job, Phase 3).

library(mapview)
library(sf)

mapview(cities_sf)                                  # instant interactive map, sensible defaults throughout
mapview(cities_sf, zcol = "Region")                  # colored by a column, in one added argument
mapview(province_summary_sf, zcol = "total_revenue") # an instant choropleth, no manual palette needed

mapview vs. leaflet: convenience-first vs. control-first

Both packages ultimately render Leaflet.js maps, but they optimize for opposite ends of a trade-off: mapview optimizes for speed of getting something useful on screen, auto-detecting reasonable defaults for popups, colors, and legends from whatever sf object you hand it; leaflet requires you to specify each of those explicitly, in exchange for full control over exactly how the final map looks and behaves. Neither is strictly "better" — mapview for the first look at data during analysis, leaflet once you know exactly what the final, shareable map needs to show.

mapview objects contain a real leaflet map underneath

A mapview object isn't a separate, closed rendering system — its @map slot holds the actual underlying leaflet htmlwidget mapview built to produce the display. This means a genuinely useful workflow is: start with mapview() for the fast, auto-configured first look, then pull out @map and keep customizing with ordinary leaflet pipe syntax once you know what specific adjustments the final version needs — getting mapview's speed for the first 80% and leaflet's control for the last 20%, rather than starting a hand-built leaflet map completely from scratch.

  addScaleBar(position = "bottomleft") %>%     # keep adding ordinary leaflet layers/controls
  setView(lng = 121.0, lat = 12.5, zoom = 6)

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

sf & Spatial Data

sfg (simple feature geometry)
A single geometry object (one point, line, or polygon), created with functions like st_point().
Avoid: "geometry" alone when precision matters — use it to mean the concept generally, but sfg specifically refers to sf's single-geometry object type.
sfc (simple feature geometry column)
A vector of sfg objects sharing one CRS, created with st_sfc(); the type of an sf object's geometry column.
Avoid: confusing an sfc with the full sf object — an sfc has no other data columns attached; it's just the geometry list plus CRS.
sf object
An ordinary data frame (or tibble) with one column that is an sfc, conventionally named geometry — a spatial dataset that is simultaneously a normal, dplyr-compatible data frame.
Avoid: "spatial data frame" as a substitute term in code or documentation — the actual class name and community term is "sf object."
CRS (Coordinate Reference System)
The specific system, including its unit of measurement and reference surface, that gives a geometry's coordinates real-world meaning.
Avoid: "projection" as a strict synonym — a geographic CRS (like WGS84) isn't a projection at all; "projected CRS" is the narrower term for CRSes that flatten the earth onto a plane.
Spatial join (st_join)
A join between two sf objects based on the spatial relationship between their geometries, rather than a matching key column.
Avoid: "merge" or plain left_join() as a substitute — those match on column values and have no concept of spatial relationship.

geom_sf & Cartography

Choropleth
A map where regions are shaded according to a data value associated with each region.
Avoid: "heat map" as a synonym — a heat map typically shades continuous density from point data, not discrete regions from a joined attribute.
coord_sf
The ggplot2 coordinate system for geom_sf() plots, controlling display-time projection, extent cropping, and correct geographic aspect ratio — without modifying the underlying data.
Avoid: assuming coord_sf(crs=...) permanently reprojects your sf object — it only affects that plot's rendering; the underlying data's CRS is unchanged.
Small multiples (faceted map)
A grid of identically-scaled small maps, one per category value, produced with facet_wrap() on spatial data.
Avoid: "subplots" as a casual substitute — small multiples specifically implies consistent scale and layout across every panel, which manually-arranged subplots don't guarantee.

leaflet & mapview

Leaflet.js
The JavaScript mapping library both the R leaflet package and mapview generate code for underneath.
Avoid: describing R's leaflet package as a rendering engine in its own right — it's an R interface generating Leaflet.js-compatible output, not a separate rendering system.
Palette function (colorNumeric/colorBin/colorQuantile)
An R function, built from a data range, that maps a data value to a color — used for both a layer's fill color and its matching legend.
Avoid: "color vector" as a substitute — these return a function to call on data, not a fixed, pre-computed list of colors.
leafletProxy
A reference to an already-rendered leaflet map inside a Shiny server, used to issue incremental layer updates without a full re-render.
Avoid: assuming any change to reactive input requires re-running the whole renderLeaflet() block — that approach resets pan/zoom state unnecessarily.
mapview
A package producing an instantly-configured interactive map from an sf object in one function call, whose result internally wraps a real leaflet htmlwidget accessible via @map.
Avoid: treating mapview and leaflet as fully separate, non-interoperable tools — a mapview object's underlying map can be extracted and further customized with ordinary leaflet functions.
