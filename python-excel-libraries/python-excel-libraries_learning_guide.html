Skip if: You can already explain why two libraries reading the same file return different types for the same cell.

An .xlsx is a ZIP archive of XML

Since Excel 2007, the .xlsx format (OOXML) is a ZIP container. Rename a copy to .zip, unzip it, and you get a directory tree of XML. Every Python library in this guide is, underneath, either an XML parser or a wrapper around one. Knowing this is not trivia: it explains why writing a cell is cheap but recalculating a formula is impossible, why styles are stored once and referenced by index, and why a "corrupt file" error is usually a malformed XML part rather than anything mysterious.

cp TindaHub_Orders.xlsx /tmp/tinda.zip
unzip -o -d /tmp/tinda /tmp/tinda.zip
find /tmp/tinda -name '*.xml' | sort

You will see roughly this layout:

[Content_Types].xml          part-type manifest — Excel refuses the file if this is wrong
_rels/.rels                  top-level relationships
xl/workbook.xml              sheet names, defined names, workbook-level settings
xl/worksheets/sheet1.xml     the actual cells of the first sheet
xl/sharedStrings.xml         every distinct text value, stored once, referenced by index
xl/styles.xml                fonts, fills, borders, number formats — referenced by index
xl/charts/chart1.xml         chart definitions, when present

The shared-strings table is why text-heavy sheets compress so well, and why a library must resolve an integer index to a string on every read. That indirection is a real cost at scale, and it is one reason the Rust-based readers in Module 3.2 are so much faster.

Five formats, and they are not interchangeable

"Excel file" is ambiguous. The extension determines which libraries can even open it, so establish the format before choosing a tool.

FormatWhat it isRead withWrite with
.xlsxOOXML, ZIP of XML. The default since 2007.openpyxl, calamine, pandas, polarsopenpyxl, XlsxWriter, pandas
.xlsmSame as .xlsx but permitted to contain VBA macros.openpyxl (keep_vba=True), calamineopenpyxl with keep_vba=True
.xlsbBinary workbook. Much smaller and faster for huge sheets.calamine (pyxlsb is unmaintained)No pure-Python writer — use xlwings or Excel

Disambiguation: xlrd is not a general Excel reader any more. Version 2.0 (2020) removed .xlsx support entirely and now handles only legacy .xls. Tutorials that say "use xlrd to read Excel" predate that change; following them produces XLRDError: Excel xlsx file; not supported. If you need .xls today, prefer calamine — it reads .xls too, and unlike xlrd it is actively developed.

Check when each library last shipped, because it tells you what kind of dependency you are taking on:

The two questions that decide everything

Almost every Excel-library choice collapses to two questions, asked in this order:

  1. Do you need Excel itself to be running? If the task requires live recalculation, a running PivotTable, an interactive user, or a format only Excel can produce (like a real .xlsb write), you need xlwings and an installed Excel. Everything else is a file-manipulation job that needs no Excel at all.
  2. Do you care about cells, or about the table? If you care about formatting, styles, charts, validation, comments — the things that make a workbook a document — you want openpyxl or XlsxWriter. If you only care about the rectangle of values and want to compute on it, you want pandas or polars.

Getting this backwards is the single most common and most expensive mistake in Python-Excel work. Reading a formatted template with pandas and writing it back does not "preserve most of it" — it silently discards every style, chart, and validation rule in the file, because pandas only ever held the values.

Combining them is normal, not a compromise

These libraries are not rivals; production code routinely uses two in one script. The standard pattern is read fast, compute in a DataFrame, write pretty:

from pathlib import Path
import pandas as pd
from openpyxl import load_workbook
from openpyxl.styles import Font

SRC = Path("TindaHub_Orders.xlsx")

# 1. Read values fast — calamine, no styles needed here
orders = pd.read_excel(SRC, sheet_name="Orders", engine="calamine")

# 2. Compute in pandas
by_region = (orders.groupby("Region", as_index=False)["Amount"]
                   .sum()
                   .sort_values("Amount", ascending=False))

# 3. Write, then reopen with openpyxl to format what pandas cannot
out = Path("region_summary.xlsx")
by_region.to_excel(out, sheet_name="ByRegion", index=False)

wb = load_workbook(out)
ws = wb["ByRegion"]
for cell in ws[1]:
    cell.font = Font(bold=True, color="FFFFFF")
ws.column_dimensions["A"].width = 22
ws.freeze_panes = "A2"
wb.save(out)
print(f"wrote {out} with {ws.max_row - 1} regions")

Note what step 3 buys you: pandas produced the numbers, but it has no vocabulary for a frozen header row or a bold white font. Reopening the file it just wrote is the cheapest way to get both.

Install into a virtual environment, and pin

Pin your versions. Excel libraries change defaults between releases — pandas is actively changing which engine it reaches for — and an unpinned pipeline that worked in March can read dates differently in September.

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install "openpyxl==3.1.5"
python -c "import openpyxl; print(openpyxl.__version__)"

openpyxl pulls in exactly one dependency, et-xmlfile (2.0.0), which streams XML writes. If you plan to work with images in Module 2.6 you also need Pillow; openpyxl will raise ImportError only at the moment you try to insert one.

Workbook, worksheet, cell

openpyxl models the file exactly as Excel does: a Workbook holds Worksheet objects, which hold Cell objects. Two loading flags matter from the very first line, and both are covered in depth later — data_only in Module 2.4 and read_only in Module 2.7.

from openpyxl import load_workbook

wb = load_workbook("TindaHub_Orders.xlsx", data_only=True)

print(wb.sheetnames)
# ['Orders', 'Products', 'Customers', 'RawContacts', 'MessyImport']

ws = wb["Orders"]
print(ws.title, ws.dimensions, ws.max_row, ws.max_column)
# Orders A1:Q5001 5001 17

print(ws["A1"].value)                    # 'OrderID'
print(ws.cell(row=2, column=2).value)    # 2026-01-01 00:00:00  (a real datetime)
print(ws["A2"].value, ws["M2"].value)    # ORD-20260000 234

max_row is 5001, not 5000 — row 1 is the header. That off-by-one is the most common source of a stray None row at the end of a loop.

Two ways to address a cell, and they are interchangeable: ws["M2"] reads naturally when you know the letter, while ws.cell(row=2, column=13) is what you need inside a loop. Convert between them with the utils:

from openpyxl.utils import get_column_letter, column_index_from_string

print(get_column_letter(13))            # 'M'
print(column_index_from_string("M"))    # 13

Iterating properly: values_only is not optional at scale

Indexing cell by cell constructs a Cell object per access, each carrying style and format references you are not using. iter_rows(values_only=True) yields plain tuples instead and skips that construction entirely. On a 5,000-row sheet the difference is noticeable; on a 500,000-row sheet it is the difference between seconds and minutes.

from openpyxl import load_workbook

wb = load_workbook("TindaHub_Orders.xlsx", data_only=True)
ws = wb["Orders"]

# Build a name -> position map from the header row, so column moves don't break the script
header = next(ws.iter_rows(min_row=1, max_row=1, values_only=True))
col = {name: i for i, name in enumerate(header)}

mismatches = []
for row in ws.iter_rows(min_row=2, values_only=True):
    qty, price, amount = row[col["Qty"]], row[col["UnitPrice"]], row[col["Amount"]]
    if amount != qty * price:
        mismatches.append((row[col["OrderID"]], qty, price, amount, qty * price))

print(f"{len(mismatches)} rows where Amount != Qty * UnitPrice")
for m in mismatches:
    print(m)
# 3 rows where Amount != Qty * UnitPrice
# ('ORD-20263901', ...)
# ('ORD-20264520', ...)
# ('ORD-20264637', ...)

Never hard-code row[12] for Amount. Building the col dictionary from the header costs one line and survives someone inserting a column — which, on a shared workbook, is a matter of when rather than if.

Creating from scratch versus editing in place

There are two distinct workflows and confusing them causes data loss. Workbook() creates a brand-new file in memory. load_workbook() opens an existing one, and save() then overwrites the original — openpyxl has no concept of "save a copy" unless you pass a different path.

from openpyxl import Workbook

wb = Workbook()          # comes with one sheet already, named 'Sheet'
ws = wb.active
ws.title = "Summary"

ws.append(["Region", "Orders", "Amount"])       # append writes the next free row
ws.append(["NCR", 1240, 1_875_400])
ws.append(["CALABARZON", 980, 1_402_115])

detail = wb.create_sheet("Detail")              # appended at the end
audit  = wb.create_sheet("Audit", 0)            # inserted at position 0

print(wb.sheetnames)     # ['Audit', 'Summary', 'Detail']
wb.save("tindahub_report.xlsx")

append() is the workhorse for writing tabular output: it tracks the current row for you, so you never manage a row counter. Pass a list for positional writes or a dict keyed by column letter for sparse ones.

Restructuring: move, copy, insert, delete

from openpyxl import Workbook

wb = Workbook()
ws = wb.active
ws.title = "Summary"
for r in [["Region", "Amount"], ["NCR", 1875400], ["Davao Region", 640230]]:
    ws.append(r)

wb.move_sheet("Summary", offset=-1)     # shift one position toward the front
copy = wb.copy_worksheet(ws)            # duplicates values AND styles
copy.title = "Summary (backup)"
del wb["Sheet"] if "Sheet" in wb.sheetnames else None

ws.insert_rows(1)                       # push everything down, e.g. for a title banner
ws["A1"] = "TindaHub — Regional Summary"
ws.insert_cols(3)                       # new blank column C
ws.delete_cols(3)                       # and remove it again

print(wb.sheetnames)

One caveat worth internalising: insert_rows() and delete_rows() move cell values and styles, but they do not rewrite formula references, conditional-formatting ranges, chart references, or data-validation ranges that point into the shifted area. Excel fixes those up for you; openpyxl does not. If your sheet has formulas and you need to insert rows, either insert before adding the formulas or rewrite the affected ranges yourself.

copy_worksheet() has a matching limitation — it copies within a workbook only. To move a sheet between workbooks you must read the values and write them into the target yourself.

Sheet-level presentation

These four settings turn a raw dump into something a colleague can actually use, and they cost one line each:

ws.freeze_panes = "A2"                  # header row stays visible while scrolling
ws.auto_filter.ref = "A1:C3"            # filter dropdowns on the header
ws.column_dimensions["A"].width = 24    # width is in characters, not pixels
ws.row_dimensions[1].height = 22        # height is in points
ws.merge_cells("A1:C1")                 # banner across the top
ws.sheet_view.showGridLines = False

Merged cells behave in a way that surprises people: only the top-left cell holds the value. Every other cell in the merge becomes a read-only MergedCell, and assigning to one raises AttributeError. Write your value first, then merge — or write to the anchor cell afterwards.

The four style objects

Every visual property of a cell comes from one of four immutable objects, assigned to the matching cell attribute. Because they are immutable, you cannot mutate a cell's font in place — cell.font.bold = True silently fails. You must assign a whole new object.

from openpyxl.styles import Font, PatternFill, Border, Side, Alignment

cell = ws["A1"]
cell.font = Font(name="Calibri", size=11, bold=True, color="FFFFFF")
cell.fill = PatternFill(fill_type="solid", start_color="075249")

thin = Side(style="thin", color="D0D7DE")
cell.border = Border(left=thin, right=thin, top=thin, bottom=thin)

cell.alignment = Alignment(horizontal="center", vertical="center", wrap_text=True)

Colours are aRGB hex strings without a leading # — "075249" or "FF075249". Passing "#075249" is the most frequent styling bug and produces a file Excel reports as corrupt.

NamedStyle: define once, apply everywhere

Assigning individual style objects to hundreds of cells bloats styles.xml and makes a later restyle a find-and-replace exercise. A NamedStyle is registered on the workbook once and referenced by name — it is also a real Excel cell style, so users can apply it themselves from the ribbon.

from openpyxl import Workbook
from openpyxl.styles import NamedStyle, Font, PatternFill, Alignment, Border, Side

wb = Workbook()
ws = wb.active

thin = Side(style="thin", color="D0D7DE")

header = NamedStyle(name="tindahub_header")
header.font = Font(bold=True, color="FFFFFF", size=11)
header.fill = PatternFill(fill_type="solid", start_color="075249")
header.alignment = Alignment(horizontal="center", vertical="center", wrap_text=True)
header.border = Border(bottom=Side(style="medium", color="075249"))

peso = NamedStyle(name="tindahub_peso")
peso.number_format = '"\u20b1"#,##0.00'
peso.alignment = Alignment(horizontal="right")
peso.border = Border(left=thin, right=thin, top=thin, bottom=thin)

wb.add_named_style(header)
wb.add_named_style(peso)

cols = ["OrderID", "Region", "Amount"]
ws.append(cols)
for c in ws[1]:
    c.style = "tindahub_header"

ws.append(["ORD-20260000", "CALABARZON", 234])
ws["C2"].style = "tindahub_peso"

wb.save("styled.xlsx")

Register a style name only once per workbook; calling add_named_style twice with the same name raises ValueError. Guard with if "tindahub_header" not in wb.named_styles: when your code might run against an existing file.

Styling rows and columns efficiently

There is no "style this whole column" call that applies to future rows — openpyxl styles cells, and a cell must exist. Iterate the range you actually wrote:

from openpyxl.utils import get_column_letter

# Header row
for cell in ws[1]:
    cell.style = "tindahub_header"

# Currency column, data rows only
for row in ws.iter_rows(min_row=2, min_col=3, max_col=3):
    for cell in row:
        cell.style = "tindahub_peso"

# Auto-fit column widths from the longest rendered value
for i, column_cells in enumerate(ws.columns, start=1):
    longest = max((len(str(c.value)) for c in column_cells if c.value is not None), default=0)
    ws.column_dimensions[get_column_letter(i)].width = min(longest + 3, 45)

Excel has no real auto-fit that a file-writing library can trigger — the width is stored in the file, and Excel only recalculates it if a human double-clicks the column border. The loop above is the standard approximation, and capping at 45 stops one long product name from producing an unusable column.

A date in Excel is a number wearing a costume

Excel stores dates as days elapsed since 1899-12-30, and formatting alone decides whether you see 45658 or 2026-01-01. The value and its display are entirely separate, which is why a column can look like dates and still be text — and why sorting it puts 01/12/2026 before 02/01/2026.

openpyxl handles the conversion for you on read: a cell whose number format is a date format comes back as a Python datetime. The Orders!B2 cell you found as a bare number in the XML in Module 1.1 arrives as datetime(2026, 1, 1).

from openpyxl import load_workbook

wb = load_workbook("TindaHub_Orders.xlsx", data_only=True)
ws = wb["Orders"]

print(repr(ws["B2"].value), ws["B2"].number_format, ws["B2"].is_date)
# datetime.datetime(2026, 1, 1, 0, 0) 'mm/dd/yyyy' True

print(repr(ws["Q2"].value), ws["Q2"].number_format, ws["Q2"].is_date)
# '01/01/2026' 'General' False   <- ImportedDates is TEXT

Those two cells hold the same calendar day. One sorts, filters, and subtracts correctly; the other is a string that happens to contain digits. Finding this distinction is the first thing to do with any workbook you did not create.

Writing number formats

Set cell.number_format to an Excel format code. The codes are the same strings you would type into Excel's Format Cells dialog.

from datetime import datetime

ws["A1"] = datetime(2026, 1, 1)
ws["A1"].number_format = "yyyy-mm-dd"          # unambiguous, sorts correctly

ws["B1"] = 1234.5
ws["B1"].number_format = "#,##0.00"            # 1,234.50

ws["C1"] = 1234.5
ws["C1"].number_format = '"\u20b1"#,##0.00'    # ₱1,234.50

ws["D1"] = 0.1234
ws["D1"].number_format = "0.0%"                # 12.3%

ws["E1"] = -5000
ws["E1"].number_format = '#,##0;[Red](#,##0)'  # (5,000) in red

ws["F1"] = 45658
ws["F1"].number_format = "General"             # stays 45658 — no costume

Always write yyyy-mm-dd for any date a machine or another country will read. The TindaHub workbook ships as mm/dd/yyyy precisely because that ambiguity is realistic: 03/04/2026 is March 4th to a US reader and April 3rd to a Philippine one, and nothing in the file resolves it.

Repairing a text-date column

This is the single most common Excel cleanup task. The fix has two halves, and doing only the first leaves you with dates that still sort as text.

from datetime import datetime
from openpyxl import load_workbook

wb = load_workbook("TindaHub_Orders.xlsx")
ws = wb["Orders"]

header = next(ws.iter_rows(min_row=1, max_row=1, values_only=True))
q = header.index("ImportedDates") + 1        # 1-based column number

converted, failed = 0, []
for r in range(2, ws.max_row + 1):
    cell = ws.cell(row=r, column=q)
    raw = cell.value
    if isinstance(raw, str):
        try:
            cell.value = datetime.strptime(raw.strip(), "%d/%m/%Y")   # 1. real value
            cell.number_format = "yyyy-mm-dd"                         # 2. real display
            converted += 1
        except ValueError:
            failed.append((r, raw))

print(f"converted {converted} cells, {len(failed)} failures")
wb.save("orders_dates_fixed.xlsx")

check = load_workbook("orders_dates_fixed.xlsx")["Orders"]
print(repr(check.cell(row=2, column=q).value), check.cell(row=2, column=q).is_date)
# datetime.datetime(2026, 1, 1, 0, 0) True

Note "%d/%m/%Y", not "%m/%d/%Y". The ImportedDates column is day-first, matching Philippine convention. Parsing it month-first does not raise an error for the first twelve days of any month — it silently produces the wrong date. That is why the verification read at the end matters: a conversion that "worked" is not the same as a conversion that is correct.

Module 2.4 — Formulas & the Cached-Value Trap

Level: Intermediate · Prereqs: 2.1 · Time: ~4h
Skip-check (test-out): Explain, with a reproduction, why a workbook openpyxl wrote returns None for every formula cell when reloaded with data_only=True.
Skip if: You can already state what data_only does on read AND what it destroys on save.
Unlocks: 2.5, Phase 2 Capstone

openpyxl writes formulas; it does not evaluate them

Writing a formula is just writing a string that begins with =. openpyxl has no calculation engine — it never computes a result, because doing so would mean reimplementing several hundred Excel functions plus the dependency graph.

from openpyxl import Workbook, load_workbook

wb = Workbook()
ws = wb.active
ws["A1"], ws["A2"] = 10, 32
ws["A3"] = "=SUM(A1:A2)"
wb.save("trap.xlsx")

print(repr(load_workbook("trap.xlsx", data_only=False)["Sheet"]["A3"].value))
# '=SUM(A1:A2)'   the formula text
print(repr(load_workbook("trap.xlsx", data_only=True)["Sheet"]["A3"].value))
# None            <- there is no cached result to return

Every .xlsx stores two things per formula cell: the formula, and the cached result Excel computed the last time it recalculated. data_only=True asks for that cached result. When openpyxl wrote the file, no Excel ever ran, so no cache exists and you get None. Open the file in Excel once and save it, and the same read returns 42.

Common mistake: loading with data_only=True and then saving permanently destroys every formula in the file. openpyxl only holds what it read — the cached values — so save() writes those numbers back in place of the formulas, and the workbook silently becomes a dead snapshot. Reproduce it once so you never do it by accident: load trap.xlsx with data_only=True, save it under a new name, reload with data_only=False, and observe that A3 is no longer =SUM(A1:A2). Rule: never save a workbook you opened with data_only=True. If you need both values and formulas, open the file twice into two variables.

The two-workbook pattern

from openpyxl import load_workbook

SRC = "TindaHub_Orders.xlsx"

wb_values   = load_workbook(SRC, data_only=True)    # read only — never save this one
wb_formulas = load_workbook(SRC, data_only=False)   # edit and save this one

amount = wb_values["Orders"]["M2"].value            # the number
formula = wb_formulas["Orders"]["M2"].value         # the formula, if any

wb_formulas["Orders"]["R1"] = "Flag"
wb_formulas.save("orders_flagged.xlsx")             # formulas preserved

Writing useful formulas

Formulas are strings, so build them with f-strings. Two rules save real debugging time: openpyxl always writes in US locale with commas as argument separators regardless of your system settings, and sheet names containing spaces need single quotes.

from openpyxl import Workbook

wb = Workbook()
ws = wb.active
ws.title = "Audit"
ws.append(["OrderID", "Qty", "UnitPrice", "Amount", "Expected", "Delta", "Status"])
ws.append(["ORD-20263901", 12, 25, 295, None, None, None])

last = ws.max_row
for r in range(2, last + 1):
    ws.cell(row=r, column=5).value = f"=B{r}*C{r}"
    ws.cell(row=r, column=6).value = f"=D{r}-E{r}"
    ws.cell(row=r, column=7).value = f'=IF(ABS(F{r})<0.01,"OK","MISMATCH")'

ws.cell(row=last + 2, column=4).value = f"=SUM(D2:D{last})"
ws.cell(row=last + 2, column=5).value = f"=SUM(E2:E{last})"
ws.cell(row=last + 2, column=7).value = f'=COUNTIF(G2:G{last},"MISMATCH")'

wb.save("audit_formulas.xlsx")

The < in that IF is a literal less-than inside the formula string. Excel takes the string exactly as written, so the comparison operators you need are plain Python characters — no escaping in the file itself.

If your pipeline must read those computed values later, something has to recalculate them. Your options are: open and save once in Excel, drive a recalculation through xlwings (Module 4.1), or compute the values in Python and write numbers instead of formulas. Choose the third whenever the consumer is another program — formulas are for humans who will open the file.

Conditional formatting: three rule types

from openpyxl.styles import PatternFill, Font
from openpyxl.formatting.rule import CellIsRule, ColorScaleRule, FormulaRule

red  = PatternFill(fill_type="solid", start_color="FFC7CE")
warn = PatternFill(fill_type="solid", start_color="FFEB9C")
last = ws.max_row

# 1. Value comparison — flag unusually large orders
ws.conditional_formatting.add(
    f"M2:M{last}",
    CellIsRule(operator="greaterThan", formula=["5000"],
               fill=warn, font=Font(bold=True)),
)

# 2. Colour scale — gradient across the Qty column
ws.conditional_formatting.add(
    f"K2:K{last}",
    ColorScaleRule(start_type="min", start_color="FFFFFF",
                   end_type="max",  end_color="075249"),
)

# 3. Formula rule — highlight the ENTIRE row when Status is Cancelled
ws.conditional_formatting.add(
    f"A2:Q{last}",
    FormulaRule(formula=['$O2="Cancelled"'], fill=red),
)

The formula rule is the one worth studying. $O2 locks the column with $ but leaves the row relative, so Excel evaluates it against column O of whichever row it is painting — which is what makes the whole row highlight. Write $O$2 instead and every row is coloured according to row 2 alone. The formula must also be written relative to the top-left cell of the applied range, so a range starting at row 2 uses O2.

from openpyxl.worksheet.datavalidation import DataValidation

Why the default mode is memory-hungry

A normal load_workbook() builds a Python Cell object for every populated cell, each holding value, style reference, format, and a parent pointer. For the 85,000 cells in the Orders sheet that is fine. For a 500,000-row × 30-column sheet it is 15 million objects, and the process is measured in gigabytes.

import time, tracemalloc
from openpyxl import load_workbook

SRC = "TindaHub_Orders.xlsx"

def total_amount(read_only: bool) -> tuple[float, float, float]:
    tracemalloc.start()
    t0 = time.perf_counter()
    wb = load_workbook(SRC, read_only=read_only, data_only=True)
    ws = wb["Orders"]
    header = next(ws.iter_rows(min_row=1, max_row=1, values_only=True))
    m = header.index("Amount")
    total = 0.0
    for row in ws.iter_rows(min_row=2, values_only=True):
        if row[m] is not None:
            total += row[m]
    wb.close()
    elapsed = time.perf_counter() - t0
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return total, elapsed, peak / 1_048_576

for flag in (False, True):
    total, secs, mb = total_amount(flag)
    print(f"read_only={flag!s:<5} total={total:,.0f}  {secs:.2f}s  peak {mb:.1f} MB")

Always call wb.close() in read-only mode. The workbook holds an open file handle to the underlying ZIP, and without an explicit close a long-running job leaks handles until it hits the OS limit.

What read_only takes away

Read-only mode returns lightweight cells and streams rows on demand. In exchange:

  • Cells are read-only — assigning raises an error.
  • Styles are not fully populated, so do not inspect fonts or fills.
  • ws.max_row and ws.max_column may be None or wrong, because they come from a dimension hint some writers omit or misreport. Call ws.calculate_dimension() if you truly need them, and accept the extra pass.
  • You can iterate a sheet only once per load. A second pass needs a fresh load_workbook.

write_only for large outputs

The mirror image: rows are streamed straight to disk instead of being held in memory. You must use append() — there is no random cell access — and every sheet must come from create_sheet().

from openpyxl import Workbook
from openpyxl.cell import WriteOnlyCell
from openpyxl.styles import Font

wb = Workbook(write_only=True)
ws = wb.create_sheet("Export")

header = []
for name in ("OrderID", "Region", "Amount"):
    c = WriteOnlyCell(ws, value=name)
    c.font = Font(bold=True, color="FFFFFF")
    header.append(c)
ws.append(header)

for i in range(200_000):
    ws.append([f"ORD-{i:08d}", "NCR", i * 1.5])

wb.save("big_export.xlsx")

Styling in write-only mode requires the WriteOnlyCell wrapper, since you never get a normal cell object to assign to. If your output needs heavy formatting and volume, XlsxWriter (Module 3.4) is usually the better tool — it was designed for exactly this and has a constant_memory mode of its own.

pandas does not read Excel — an engine does

Every pd.read_excel() call delegates to one of several engines: openpyxl, calamine, xlrd, pyxlsb, or odf. pandas parses whatever that engine hands back into a DataFrame. This matters because the engine determines speed, format support, and some type behaviour — and because the default engine is changing. As of pandas 3.x the docs state plainly that for xlsx/xlsm the default will move from openpyxl to calamine in a future version.

The practical consequence: always pass engine= explicitly. A pipeline that relies on the default will change behaviour under you at some upgrade.

One engine now covers every format, is faster than all of them, and is the only one under active development. That is why the deprecations landed together.

Benchmark it yourself

import time
import pandas as pd

SRC = "TindaHub_Orders.xlsx"

def bench(engine: str, repeats: int = 3) -> float:
    best = float("inf")
    for _ in range(repeats):
        t0 = time.perf_counter()
        df = pd.read_excel(SRC, sheet_name="Orders", engine=engine)
        best = min(best, time.perf_counter() - t0)
    assert df.shape == (5000, 17)
    return best

base = bench("openpyxl")
for engine in ("openpyxl", "calamine"):
    t = bench(engine)
    print(f"{engine:<10} {t:6.3f}s   {base / t:4.1f}x")

Take the minimum of several runs, not the mean. You are measuring the library, and the mean is dominated by whatever else your machine was doing. Expect calamine to land several times faster on a file this size; the gap widens with row count.

Where calamine differs

calamine is a reader only — there is no calamine writer, so writing stays with openpyxl or XlsxWriter. It also gives you no access to styles, charts, comments, or validation: it returns values, which is precisely why it is fast. And because it is a different parser, edge-case type inference can differ from openpyxl's, most visibly on cells that are ambiguously typed.

import pandas as pd

a = pd.read_excel("TindaHub_Orders.xlsx", sheet_name="MessyImport", engine="openpyxl")
b = pd.read_excel("TindaHub_Orders.xlsx", sheet_name="MessyImport", engine="calamine")

print(a.dtypes.to_dict() == b.dtypes.to_dict())
for col in a.columns:
    if a[col].dtype != b[col].dtype:
        print(f"{col}: openpyxl={a[col].dtype}  calamine={b[col].dtype}")

Run this before swapping engines in an existing pipeline. The MessyImport sheet is deliberately adversarial — 76 of its 500 Amount values are stored as text — so it is exactly the kind of sheet where two parsers can legitimately disagree, and exactly the kind you must check rather than assume.

You can also use calamine directly, without pandas, when you just want rows:

Strategies when the file is too big

Once a workbook stops fitting comfortably in memory, ranked by how much they help:

  1. Stop using Excel as the interchange format. Convert once to Parquet or CSV and read that repeatedly. A one-time conversion beats re-parsing XML on every run, and Parquet keeps the types.
  2. Read fewer columns. usecols in pandas, columns= in polars. Usually the biggest easy win.
  3. Read in chunks by row range with fastexcel's row-limit options, processing and discarding each slice.
  4. Stream with openpyxl read_only (Module 2.7) when you need per-cell control rather than a DataFrame.
  5. Ask for .xlsb or CSV from the source. The cheapest optimisation is the file you never had to parse.
import polars as pl

# One-time conversion; every later run reads the Parquet
pl.read_excel("TindaHub_Orders.xlsx", sheet_name="Orders").write_parquet("orders.parquet")

# Subsequent runs — lazy, and orders of magnitude faster
lazy = pl.scan_parquet("orders.parquet")
result = (lazy.filter(pl.col("Status") == "Delivered")
              .group_by("Region")
              .agg(pl.col("Amount").sum())
              .sort("Amount", descending=True)
              .collect())
print(result)

Write-only by design

XlsxWriter creates .xlsx files and cannot read them. That sounds like a limitation, and for editing it is disqualifying — but it is exactly what makes the library fast and lets it support formatting features openpyxl does not, like rich strings, sparklines, and a far more complete chart API. Choose it when you are generating a report from scratch, every time.

import pandas as pd
import xlsxwriter

orders = pd.read_excel("TindaHub_Orders.xlsx", sheet_name="Orders", engine="calamine")
by_region = (orders.groupby("Region", as_index=False)
                   .agg(Orders=("OrderID", "count"), Amount=("Amount", "sum"))
                   .sort_values("Amount", ascending=False))

wb = xlsxwriter.Workbook("xlsxwriter_report.xlsx")
ws = wb.add_worksheet("ByRegion")

header_fmt = wb.add_format({
    "bold": True, "font_color": "#FFFFFF", "bg_color": "#075249",
    "border": 1, "align": "center", "valign": "vcenter",
})
peso_fmt = wb.add_format({"num_format": '"\u20b1"#,##0.00', "border": 1})
int_fmt  = wb.add_format({"num_format": "#,##0", "border": 1})
text_fmt = wb.add_format({"border": 1})

for c, name in enumerate(by_region.columns):
    ws.write(0, c, name, header_fmt)

for r, row in enumerate(by_region.itertuples(index=False), start=1):
    ws.write(r, 0, row.Region, text_fmt)
    ws.write_number(r, 1, row.Orders, int_fmt)
    ws.write_number(r, 2, row.Amount, peso_fmt)

last = len(by_region)
ws.freeze_panes(1, 0)
ws.autofilter(0, 0, last, 2)
ws.set_column("A:A", 22)
ws.set_column("B:C", 16)

ws.conditional_format(1, 2, last, 2, {
    "type": "3_color_scale", "min_color": "#FFFFFF", "max_color": "#075249",
})

chart = wb.add_chart({"type": "column"})
chart.add_series({
    "name":       "Amount",
    "categories": ["ByRegion", 1, 0, last, 0],
    "values":     ["ByRegion", 1, 2, last, 2],
    "fill":       {"color": "#0d7a6e"},
})
chart.set_title({"name": "TindaHub Amount by Region"})
chart.set_y_axis({"name": "Amount (PHP)"})
chart.set_size({"width": 640, "height": 380})
ws.insert_chart("E2", chart)

print("wrote xlsxwriter_report.xlsx")

Three differences from openpyxl to keep straight: coordinates are zero-based (row, col) rather than "A1"; colours carry a leading #; and formats are workbook-level objects created with add_format() and reused, rather than per-cell style objects. A different category of tool

Every library so far manipulates a file. xlwings automates the application — it sends instructions to a running copy of Excel over COM on Windows or AppleScript on macOS. That single difference decides everything: Excel must be installed, it will not run on a Linux server, and in exchange you get access to literally everything Excel can do, including formula recalculation, PivotTables, and writing .xlsb.

python -m pip install "xlwings==0.36.14"
import xlwings as xw

# visible=False runs Excel hidden; add_book=False stops it opening a blank workbook
app = xw.App(visible=False, add_book=False)
try:
    book = app.books.open("TindaHub_Orders.xlsx")
    sheet = book.sheets["Orders"]

    print(sheet.range("A1").value)                   # 'OrderID'
    print(sheet.range("A1:C1").value)                # ['OrderID', 'OrderDate', 'CustomerID']
    print(sheet.range("A1").expand("down").last_cell.row)   # 5001

    # used_range is Excel's own idea of the extent — no dimension-hint guessing
    print(sheet.used_range.address)                  # '$A$1:$Q$5001'

    sheet.range("S1").value = "Generated by Python"
    book.save("TindaHub_live.xlsx")
finally:
    app.quit()          # ALWAYS quit, or you leak an invisible Excel process

That try/finally is not decoration. A hidden Excel process left running holds a file lock and is invisible in the dock or taskbar; do this a few times in a loop and you have a dozen zombie processes and a workbook nobody can open. Wrap every xlwings script this way.

Reading the user's live selection has no equivalent in any file-based library, and it is the foundation of the interactive tools in Module 4.3.

Recalculation: the thing openpyxl cannot do

This closes the loop on the Module 2.4 trap. openpyxl writes formulas but never computes them; xlwings can make Excel compute them and hand back the numbers.

import xlwings as xw

app = xw.App(visible=False, add_book=False)
try:
    book = app.books.open("audit_formulas.xlsx")   # written by openpyxl in Module 2.4
    sheet = book.sheets["Audit"]

    print(sheet.range("G2").formula)   # '=IF(ABS(F2)<0.01,"OK","MISMATCH")'
    print(sheet.range("G2").value)     # 'OK'  — a real computed result

    app.calculate()                    # force a full recalculation
    book.save()                        # cached values are now stored in the file
finally:
    app.quit()

After that save, openpyxl's data_only=True returns real numbers for those cells, because a real Excel finally populated the cache. "Write with openpyxl, recalculate once with xlwings, then read with openpyxl" is a completely standard production pattern.

Converters bridge Excel ranges and Python types

By default a range returns nested lists. options() tells xlwings what you actually want, and handles the header row, the index, and the type conversion in one step.

import xlwings as xw
import pandas as pd

book = xw.Book("TindaHub_Orders.xlsx")
sheet = book.sheets["Orders"]

df = (sheet.range("A1")
           .expand()
           .options(pd.DataFrame, index=False, header=True)
           .value)

print(df.shape)                  # (5000, 17)
print(df.dtypes["OrderDate"])    # datetime64[ns]
print(df.dtypes["Amount"])       # float64

index=False is the one to remember. Leave it out and xlwings treats your first column — OrderID — as the DataFrame index, and every downstream groupby and to_excel behaves oddly in a way that takes a while to trace back.

Other converters cover the common cases:

sheet.range("M2:M11").options(ndim=1).value          # flat list, not nested
sheet.range("M2").options(numbers=int).value          # int instead of float
sheet.range("A1:Q1").options(empty="").value          # empty cells as "" not None
sheet.range("B2").options(dates=str).value            # dates as strings
sheet.range("A1").expand().options(transpose=True).value

The numbers=int converter earns its keep: Excel stores all numbers as floats, so Qty arrives as 18.0. That is harmless until it lands in a filename or a database integer column.

Writing back, in place

import xlwings as xw
import pandas as pd

book = xw.Book("TindaHub_Orders.xlsx")
orders = (book.sheets["Orders"].range("A1").expand()
              .options(pd.DataFrame, index=False, header=True).value)

by_region = (orders.groupby("Region", as_index=False)
                   .agg(Orders=("OrderID", "count"), Amount=("Amount", "sum"))
                   .sort_values("Amount", ascending=False))

if "ByRegion" in [s.name for s in book.sheets]:
    book.sheets["ByRegion"].delete()
out = book.sheets.add("ByRegion", after=book.sheets["Orders"])

out.range("A1").options(index=False).value = by_region
out.range("A1:C1").api  # available for platform-specific formatting

out.range("B2:B10").number_format = "#,##0"
out.range("C2:C10").number_format = '\u20b1#,##0.00'

Writing a DataFrame is a single assignment — xlwings expands it across the range automatically. And unlike the pandas + openpyxl round-trip, this happens in the open workbook: the user watching their screen sees the new sheet appear. Nothing was rewritten from scratch, so charts, PivotTables, and macros elsewhere in the file are untouched.

Where xlwings costs you

Every read and write is a cross-process call, so chatty code is slow. One call moving 5,000 rows is fast; 5,000 calls moving one row each is unusably slow. Batch aggressively:

import xlwings as xw

sheet = xw.Book("TindaHub_Orders.xlsx").sheets["Orders"]

# SLOW — 5,000 round-trips across the process boundary
# for r in range(2, 5002):
#     sheet.range(f"R{r}").value = sheet.range(f"K{r}").value * 2

# FAST — two calls total
qty = sheet.range("K2:K5001").options(ndim=1).value
sheet.range("R2").options(transpose=True).value = [q * 2 for q in qty]

Also switch off screen updating and automatic calculation around bulk writes, and restore them in a finally:

app = sheet.book.app
app.screen_updating = False
app.calculation = "manual"
try:
    ...   # bulk writes here
finally:
    app.calculation = "automatic"
    app.screen_updating = True

Excel calling Python, instead of the reverse

Everything so far has Python in charge. UDFs invert that: the user types =TINDA_MARGIN(M2, 0.18) into a cell and Excel calls your Python function. This is the feature that lets you retire VBA without retraining anyone — the spreadsheet still looks and behaves like a spreadsheet.

UDFs are Windows-only. They depend on the COM automation server, which does not exist on macOS. Mac users get RunPython and macros (below), or xlwings Lite (Module 4.4), which does support custom functions cross-platform.

Scaffold a project, which creates a matched .xlsm and .py pair:

xlwings quickstart tindatools
cd tindatools
# Then in Excel: File > Options > Trust Center > Trust Center Settings
#   > Macro Settings > tick "Trust access to the VBA project object model"
# In the xlwings ribbon tab, click "Import Functions" after any signature change.
"""tindatools.py — functions Excel can call directly."""
import xlwings as xw
import pandas as pd


@xw.func
def TINDA_MARGIN(amount, rate=0.18):
    """Net amount after a commission rate."""
    return float(amount) * (1 - float(rate))


@xw.func
@xw.arg("qty", numbers=int)
def TINDA_LINE_CHECK(qty, unit_price, amount):
    """Return OK or a signed delta — the Module 1.3 audit as a formula."""
    expected = qty * float(unit_price)
    delta = float(amount) - expected
    return "OK" if abs(delta) < 0.01 else f"MISMATCH {delta:+.2f}"


@xw.func
@xw.arg("orders", pd.DataFrame, index=False, header=True)
@xw.ret(index=False, header=True)
def TINDA_BY_REGION(orders):
    """Array formula: pass a range, get a summary table back."""
    return (orders.groupby("Region", as_index=False)
                  .agg(Orders=("OrderID", "count"), Amount=("Amount", "sum"))
                  .sort_values("Amount", ascending=False))


@xw.func
@xw.arg("region")
def TINDA_REGION_TOTAL(region):
    """Look up one region's total from the live Orders sheet."""
    sheet = xw.Book.caller().sheets["Orders"]
    df = sheet.range("A1").expand().options(pd.DataFrame, index=False, header=True).value
    return float(df.loc[df["Region"] == region, "Amount"].sum())

In the workbook the user now types =TINDA_BY_REGION(Orders!A1:Q5001) and gets a spilled table. xw.Book.caller() is the key to context-aware functions — it returns the workbook that invoked the call, so the function works in any copy of the file without a hard-coded path.

RunPython and buttons: cross-platform automation

For actions rather than formulas — "rebuild the report", "refresh from the database" — use RunPython from VBA, which works on Windows and macOS.

"""In tindatools.py — a routine, not a formula."""
import xlwings as xw
import pandas as pd


def refresh_summary():
    book = xw.Book.caller()
    orders = (book.sheets["Orders"].range("A1").expand()
                  .options(pd.DataFrame, index=False, header=True).value)

    summary = (orders.groupby("Region", as_index=False)
                     .agg(Orders=("OrderID", "count"), Amount=("Amount", "sum"))
                     .sort_values("Amount", ascending=False))

    names = [s.name for s in book.sheets]
    if "ByRegion" in names:
        book.sheets["ByRegion"].delete()
    out = book.sheets.add("ByRegion", after=book.sheets["Orders"])
    out.range("A1").options(index=False).value = summary
    out.range("C2").expand("down").number_format = '\u20b1#,##0.00'
    out.autofit()
    book.app.status_bar = f"Refreshed {len(summary)} regions"


if __name__ == "__main__":
    xw.Book("tindatools.xlsm").set_mock_caller()
    refresh_summary()

The VBA side is two lines, attached to a form button:

Sub RefreshSummary()
    RunPython "import tindatools; tindatools.refresh_summary()"
End Sub

That set_mock_caller() block is what makes the function testable. Without it, xw.Book.caller() only resolves when Excel invokes it, so you could not run or debug the routine from a terminal — you would be stuck debugging through Excel, which is exactly the VBA experience you are trying to escape.

The deployment problem

Classic xlwings requires a local Python installation next to a local Excel. That is fine for you and impossible for most finance teams, where laptops are locked down and installing Python is a ticket nobody will approve. Three approaches now solve this, and they are genuinely different products.

xlwings Lite — Python in the browser sandbox

Distributed through the Office add-in store, free for personal and commercial use. Python runs inside Excel via Pyodide, a WebAssembly build of CPython. No installation, no server, no per-user cost, and it works on Windows, macOS, and Excel on the web. Custom functions work on all platforms — including the macOS UDF gap from Module 4.3.

The sandbox is the trade-off, and it is a real one:

  • No access to the local file system — you cannot read C:\reports\input.xlsx.
  • Not every package builds for Pyodide; polars is currently unavailable, though pandas and NumPy work.
  • No direct connection to a database server such as PostgreSQL; SQLite is supported.
  • No built-in authentication.

Start here unless one of those four is disqualifying. Because the API is the xlwings API, migrating to Server later is a small change rather than a rewrite.

xlwings Server — your Python, your infrastructure

Your code runs on a server you control; Excel talks to it over HTTPS via an add-in, Office Scripts, or VBA. No local Python either, and it additionally supports Google Sheets. Choose it when you hit a Lite limitation: real authentication, direct database access, unrestricted packages, heavy compute, or code that must stay on your infrastructure. The cost is that you now operate a service — availability, scaling, and latency become your problem.

Python in Excel — Microsoft's own, in the cloud

Generally available since September 2024, built with Anaconda. You type =PY(...) in a cell and write Python directly in the formula bar; the code executes in a Microsoft-hosted container, not on your machine.

  • Availability: Microsoft 365 Business and Enterprise. Windows from Version 2408 (Current Channel), Excel for Mac from 16.96, and Excel on the web.
  • Licensing: standard compute with automatic recalculation is included with a qualifying subscription; premium compute and manual or partial recalculation modes require the paid Python in Excel add-on.
  • Libraries: a curated Anaconda distribution — pandas, NumPy, Matplotlib, seaborn, scikit-learn and more. You cannot pip-install arbitrary packages.
  • Connectivity: the code runs in the cloud, so it cannot reach your local files or internal databases, and it does not work offline.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

File Format & Structure

OOXML
The Office Open XML standard behind .xlsx — a ZIP container holding XML parts for the workbook, each worksheet, shared strings, and styles.
Avoid: "Excel format", "the new format" — both are ambiguous now that four Excel formats are in active use.
Shared strings table
The xl/sharedStrings.xml part storing each distinct text value once; cells reference it by integer index rather than repeating the text.
Avoid: "string pool", "string cache" — accurate as analogies but not what the spec or any error message calls it.
Serial date
Excel's numeric representation of a date: days elapsed since 1899-12-30, with the display governed entirely by the cell's number format.
Avoid: "date value", "timestamp" — both blur the distinction between the stored number and the rendered text.
Number format
A per-cell format code such as yyyy-mm-dd or #,##0.00 that controls only how a stored value is displayed, never what is stored.
Avoid: "cell format", "formatting" — those also cover fonts, fills, and borders, which are separate objects.
Cached value
The result Excel computed for a formula cell at its last recalculation, stored in the file alongside the formula text.
Avoid: "computed value", "the answer" — they hide the fact that it can be stale, absent, or destroyed on save.

Library Concepts

Engine
The library pandas or polars delegates to for actually parsing an Excel file — openpyxl, calamine, xlrd, pyxlsb, or odf.
Avoid: "backend", "driver" — "backend" collides with pandas' plotting and storage backends.
read_only mode
An openpyxl load mode that streams rows on demand with lightweight cells, trading away writes, full style access, and repeat iteration.
Avoid: "lazy loading", "streaming mode" — descriptive but not the parameter name you must actually type.
write_only mode
An openpyxl workbook mode that flushes appended rows straight to disk, forbidding random cell access and requiring WriteOnlyCell for styling.
Avoid: "append mode" — that suggests adding to an existing file, which this cannot do.
NamedStyle
A reusable, workbook-registered bundle of font, fill, border, alignment, and number format, applied by name and visible to users as an Excel cell style.
Avoid: "style template", "theme" — a theme is a separate workbook-wide colour and font scheme.
Converter
An xlwings options() setting that controls how a range is translated between Excel values and Python types, such as pd.DataFrame or ndim=1.
Avoid: "parser", "adapter" — neither appears in the xlwings API you will be searching.
Structured reference
A formula reference addressing an Excel Table by name and column, such as Orders[Amount], which stays correct as rows are added.
Avoid: "named range" — a named range is a separate feature pointing at a fixed address.

Automation & Deployment

UDF (User-Defined Function)
A Python function exposed to Excel as a worksheet formula the user types into a cell, decorated with @xw.func.
Avoid: "custom function" when discussing classic xlwings — that is the xlwings Lite and Office.js term, and the platform support differs.
RunPython
The VBA call that executes a Python function from inside a workbook, typically bound to a button; works on Windows and macOS.
Avoid: "macro" — a macro is the VBA wrapper, not the Python it invokes.
Pyodide
The WebAssembly build of CPython that runs Python inside the browser sandbox, and the runtime underneath xlwings Lite.
Avoid: "WASM Python", "browser Python" — informal names that will not match documentation.
Python in Excel
Microsoft's built-in =PY() feature, developed with Anaconda, executing a curated Python distribution in a Microsoft-hosted cloud container.
Avoid: "Excel Python", "native Python" — both get confused with xlwings Lite, which also needs no local install but runs locally in the browser sandbox.
