Module 1.1 — Why Not Docker Desktop? The macOS Runtime Landscape

Level: Beginner · Prereqs: None · Time: ~2h
Skip-check (test-out): Explain in writing, without notes, why docker run alpine on a Mac involves a Linux kernel that is not macOS's, and name the licence threshold that makes Docker Desktop a paid product.
Skip if: You already run containers daily on macOS and know why your employer pays (or refuses to pay) for Docker Desktop.
Unlocks: 1.2, and therefore all of Phase 1.

Containers are a Linux kernel feature — macOS does not have one

A container is not a virtual machine. It is a normal Linux process that the kernel has fenced off using namespaces (what the process can see: its own PID table, mount table, network stack) and cgroups (what it can consume: CPU shares, memory limits). Both are features of the Linux kernel specifically. macOS runs the XNU kernel, which has neither.

This is the single fact that explains every macOS container quirk you will ever hit. Because there is no Linux kernel on your Mac, something must supply one — and that something is a lightweight Linux virtual machine. Docker Desktop, Colima, OrbStack, Podman Desktop, and Rancher Desktop are all, at bottom, the same trick: run a small Linux VM, run the container engine inside it, and forward your docker CLI's commands into it over a socket. If you forget this, you will spend hours confused about why a bind mount is slow or why localhost means something different inside a container.

│  macOS (XNU kernel) — your laptop           │
│                                             │
│   docker CLI  ──socket──▶ ┌───────────────┐ │
│   (a client,               │ Linux VM     │ │
│    nothing more)           │              │ │
│                            │  dockerd     │ │
│                            │   ├ container│ │
│                            │   ├ container│ │
│                            │   └ container│ │
│                            │              │ │
│                            │ Linux kernel │ │
│                            │ (namespaces, │ │
│                            │  cgroups)    │ │
│                            └───────────────┘ │
│   VM supplied by: Colima / OrbStack /       │
│                   Docker Desktop / Podman   │
└─────────────────────────────────────────────┘

Notice what the diagram implies: the docker command on your Mac is just a client. It speaks HTTP over a Unix socket to a daemon somewhere else. Swap which VM is listening on that socket and the same docker binary drives a completely different runtime. That is why Phase 2 of this guide is runtime-agnostic, and why switching from Colima to OrbStack does not mean relearning Docker.

Common mistake: Believing "Docker Desktop is Docker." Docker Desktop is a commercial GUI and VM bundle around open-source components — the Docker Engine (Apache 2.0), the Docker CLI, and BuildKit. Uninstalling Docker Desktop does not take Docker away from you; it takes away one particular way of supplying the Linux VM. The engine and CLI are free software you can keep using forever.

The licence change that started the migration

Docker Desktop remains free for personal use, education, non-commercial open-source projects, and small businesses. Above a size threshold — currently companies with more than 250 employees or more than $10 million in annual revenue — a paid subscription is required per user. That threshold is why an engineering team of twelve at a large enterprise still needs twelve paid seats, and why procurement teams started asking uncomfortable questions in 2021 that they are still asking today.

The consequence of getting this wrong is not technical, it is legal and financial: a company that quietly keeps Docker Desktop installed on managed laptops past the threshold is out of compliance, and audits do happen. This is the reason most teams reading this guide are reading it at all.

Exercise 1.1 — Audit Your Current Setup

Scenario: you are the engineer nominated to move a 30-person team off Docker Desktop, and you must justify it in writing.

  1. Run docker version and docker info on your current machine. Record the client version, the server version, and the Operating System field of the server — note that it says Linux even though you are on a Mac.
  2. Run docker info --format '{{.OperatingSystem}} / {{.Architecture}} / {{.KernelVersion}}'. Write one sentence explaining where that kernel is running.
  3. Check whether Docker Desktop is installed: ls /Applications/Docker.app 2>/dev/null && echo INSTALLED || echo ABSENT.
  4. Look up your own organisation's employee count and revenue. State plainly whether Docker Desktop requires paid seats for you.
  5. Write a five-line memo: what a container is, why a Mac needs a VM to run one, what the licence threshold is, and which two alternatives you intend to evaluate.
  6. List the three things you personally use Docker Desktop's GUI for. For each, name the CLI command that replaces it. If you cannot, mark it as an open question for Module 1.2.

Module 1.2 — Choosing Your Runtime: Colima vs OrbStack

Level: Beginner · Prereqs: 1.1 · Time: ~2h
Skip-check (test-out): Given a team of eight engineers on company-paid Macs with a $0 tooling budget and a hard requirement for linux/amd64 builds, recommend a runtime and defend the choice in three sentences citing licence, performance, and cross-architecture support.
Skip if: Your runtime choice is already mandated by your employer and you have no say in it.
Unlocks: 1.3, 1.4.

They are not competitors in the way you think

Colima and OrbStack solve the same problem with opposite philosophies. Colima is a thin, MIT-licensed CLI wrapper around Lima (Linux Machines), which is itself a wrapper around Apple's Virtualization framework or QEMU. It ships no GUI, no daemon of its own, and no opinions — you get a VM and a Docker socket, and everything beyond that is your ~/.colima/default/colima.yaml.

OrbStack is a ground-up native macOS application written in Swift, with its own custom Linux kernel build, its own filesystem sharing layer, its own network stack, and a GUI. It is not a wrapper around Lima; it shares almost no code with Colima. That is why its performance numbers are different in kind, not just degree: OrbStack reports roughly 2-second cold starts and file I/O in the 75–95% range of native macOS speed, where VM-based approaches have historically landed far lower.

Common mistake: Assuming OrbStack is "a GUI for Colima" or that it is a fork of Docker Desktop. It is neither. It is an independent implementation, which is precisely why its behaviour differs in the places that matter: file sharing is bidirectional rather than one-way, IPv6 and ICMP work, and its Kubernetes exposes real ClusterIP and LoadBalancer addresses directly to macOS.

A decision procedure, not a preference

Work down this list and stop at the first line that matches. Runtime choice is a governance decision as much as a technical one — picking OrbStack for a team whose budget was never approved creates a licence problem identical to the Docker Desktop one you are trying to escape.

1. Are the Macs company-paid AND is there no budget for per-seat tooling?
   → COLIMA. OrbStack's commercial licence would be unfunded.

2. Do you need the same runtime on Linux CI runners or Linux workstations?
   → COLIMA. OrbStack is macOS-only.

3. Do you need the runtime config committed to git so every teammate
   gets an identical VM from a single `colima start --config`?
   → COLIMA. Its YAML is designed for this.

4. Do you need IPv6, ICMP/ping into containers, or corporate VPN
   coexistence that has already broken under other runtimes?
   → ORBSTACK.

5. Is developer time the scarcest resource, and is ~$96/user/year
   cheaper than the hours lost to slow file sync and VM restarts?
   → ORBSTACK.

6. Otherwise → start with COLIMA (zero cost, zero commitment),
   and trial OrbStack for two weeks before deciding.

There is a legitimate third answer: run both. They coexist cleanly on one machine because each just registers a different Docker context, and Module 3.4 shows you how to switch between them with a single command. Many engineers keep Colima for reproducible, committed team configs and reach for OrbStack when they need speed on a specific project.

Exercise 1.2 — Write the Runtime Decision Record

Scenario: NotesFlow is built by a team of eight on company-supplied MacBooks. Two engineers run Intel Macs; the rest are Apple Silicon. Production is linux/amd64. The team lead has asked for a one-page recommendation.

  1. Run the six-step decision procedure above against this scenario. Record which line you stop at.
  2. Write an Architecture Decision Record with these headings: Context, Options considered, Decision, Consequences. Keep it to one page.
  3. In Consequences, name at least two things the team gives up by your choice — every real decision has a cost, and a record that lists none is not trusted.
  4. Price the alternative: calculate the annual cost of OrbStack commercial licences for eight engineers, and the annual cost of Docker Desktop Pro seats for eight. Put both numbers in the record.
  5. Identify which of the two Intel-Mac engineers' requirements might change your answer, and note it as a risk.
  6. State the review trigger: what would have to happen for the team to revisit this decision?

Module 1.3 — Installing Colima, Docker CLI & Compose v5

Level: Beginner · Prereqs: 1.2 · Time: ~3h
Skip-check (test-out): From a Mac with nothing installed, get docker run --rm hello-world and docker compose version both succeeding, using only Homebrew and Colima, in under ten minutes.
Skip if: You already have a working Colima install and can explain what docker context ls shows you.
Unlocks: Phase 2, Module 3.1, Module 4.1.

Install the three pieces separately

Docker Desktop bundled the VM, the engine, the CLI, and Compose into one installer. Without it you install the parts yourself — which is more transparent and, once you have done it once, faster. The docker formula in Homebrew is the CLI only, not the daemon; that is exactly what you want, since Colima supplies the daemon inside its VM.

# 1. The CLI clients (no daemon, no GUI)
brew install docker docker-compose docker-buildx

# 2. The VM + runtime
brew install colima

# 3. Register the CLI plugins so `docker compose` and `docker buildx` resolve
mkdir -p ~/.docker/cli-plugins
ln -sfn "$(brew --prefix)/opt/docker-compose/bin/docker-compose" \
        ~/.docker/cli-plugins/docker-compose
ln -sfn "$(brew --prefix)/opt/docker-buildx/bin/docker-buildx" \
        ~/.docker/cli-plugins/docker-buildx

# 4. Start the VM
colima start

# 5. Verify all three layers
colima status
docker version                # client AND server must both report
docker compose version        # expect Docker Compose version v5.x
docker run --rm hello-world

Step 3 is the one people skip, and it produces the single most common Colima complaint: docker compose reports 'compose' is not a docker command while the standalone docker-compose binary works fine. Homebrew installs the Compose binary but does not link it into Docker's plugin directory, because doing so would write into your home directory during a package install. Without the symlink the CLI simply cannot find the subcommand.

What colima start actually did

It created a Lima VM named colima, booted a minimal Linux distribution inside it, installed and started dockerd, exposed the daemon's socket at ~/.colima/default/docker.sock, and — the important part — created and activated a Docker context pointing at that socket.

docker context ls
# NAME       DESCRIPTION                               DOCKER ENDPOINT
# default    Current DOCKER_HOST based configuration   unix:///var/run/docker.sock
# colima *   colima                                    unix:///Users/you/.colima/default/docker.sock

colima status
# INFO[0000] colima is running using macOS Virtualization.Framework
# INFO[0000] arch: aarch64
# INFO[0000] runtime: docker
# INFO[0000] mountType: sshfs
# INFO[0000] socket: unix:///Users/you/.colima/default/docker.sock

The asterisk in docker context ls is the whole mechanism. Change the active context and every subsequent docker command talks to a different daemon, with a different set of images and containers. Understanding this now saves you from the classic "my image disappeared" panic later, when in fact you merely switched contexts.

Defaults you will immediately outgrow

Colima starts with 2 CPUs, 2 GB of memory, and a 60 GB disk. Two gigabytes is not enough to run NotesFlow's Postgres, Redis, API, and worker at once — you will hit OOM kills that look like random container crashes. Set real numbers now:

colima stop
colima start --cpu 4 --memory 8 --disk 100 --vm-type vz --mount-type virtiofs

# Or persist it so plain `colima start` uses these values forever
colima start --edit    # opens ~/.colima/default/colima.yaml in $EDITOR

--vm-type vz selects Apple's native Virtualization framework instead of QEMU, and --mount-type virtiofs selects the fastest file-sharing transport available to it. Both require macOS 13 or newer on Apple Silicon and both are covered properly in Modules 3.1 and 3.2 — for now, take them as the sane defaults.

Note on Compose versions: Compose v5 is the current line as of August 2026. It brought a rewritten reconciliation algorithm that models volume and network lifecycle in the plan, native init containers via pre_start_init_containers, and an official Go SDK. Compose files written for v2 overwhelmingly still work, but if you inherit a project pinned to docker-compose v1 (the Python implementation, end-of-life since 2023), migrating it is a prerequisite, not an optional cleanup.

Exercise 1.3 — Bootstrap and Prove the Stack

Scenario: you are writing the setup instructions the other seven NotesFlow engineers will follow.

  1. Install Colima and the CLI plugins from scratch using the commands above. If you already have them, run colima delete first so you genuinely test the cold path.
  2. Run docker context ls and record which context is active and what socket it points to.
  3. Start Colima with 4 CPUs, 8 GB memory, and a 100 GB disk. Confirm with colima status and docker info --format '{{.NCPU}} CPUs / {{.MemTotal}} bytes'.
  4. Run docker run --rm postgres:17 postgres --version and docker run --rm redis:8 redis-server --version. Both are NotesFlow dependencies; confirm both pull and run.
  5. Deliberately break it: run docker context use default, then docker ps. Record the exact error. Then fix it with docker context use colima. You have now seen the error message that will otherwise cost you an hour someday.
  6. Write the setup instructions as a numbered list a new hire could follow without asking you anything, including the plugin symlink step and the verification commands.
  7. Add a troubleshooting section with the two failures you actually hit (or, if you hit none, the 'compose' is not a docker command and wrong-context errors).

Module 1.4 — Installing OrbStack & the orb CLI

Level: Beginner · Prereqs: 1.2 · Time: ~2h
Skip-check (test-out): Install OrbStack, run a container, reach it in a browser at a .orb.local domain with no published port, and create a Ubuntu Linux machine you can shell into — all from the terminal.
Skip if: You are committed to the FOSS-only track (Track 4) and will never run OrbStack. Read the domains section anyway; it explains what you are trading away.
Unlocks: Phase 2, Module 3.3, Module 4.2.

Installation is one command

brew install --cask orbstack

# Or download the .dmg from https://orbstack.dev

# OrbStack sets up the docker context for you on first launch
docker context ls
# NAME         DESCRIPTION                    DOCKER ENDPOINT
# default      Current DOCKER_HOST based ...  unix:///var/run/docker.sock
# orbstack *   OrbStack                       unix:///Users/you/.orbstack/run/docker.sock

orb status          # running / stopped — exit code 0, 1, or 2
docker run --rm hello-world

OrbStack bundles the docker CLI, Compose, and buildx, so there is no separate plugin-symlink dance. If you previously installed the Homebrew docker formula for Colima, both can coexist — the CLI is the same binary talking to whichever context is active.

The orb CLI: machines, files, and control

OrbStack's GUI is optional. Everything is reachable from orb (aliased as orbctl, which you should prefer in scripts where a bare orb could collide with a machine name).

# --- Lifecycle ---
orb start                       # start OrbStack
orb stop                        # stop everything
orb status                      # is it running?
orb doctor                      # verify Docker integration
orb doctor --fix                # repair a broken docker context/socket
orb update                      # self-update

# --- Full Linux machines (not containers — real VMs sharing one kernel) ---
orb create ubuntu notesflow-box     # provision a Ubuntu machine
orb list                            # all machines and their state
orb info notesflow-box -f json      # machine details as JSON
orb -m notesflow-box uname -a       # run one command inside it
orb -m notesflow-box -u root apt update
orb                                 # interactive shell in the default machine
orb clone notesflow-box box-copy    # duplicate a machine
orb delete notesflow-box            # remove it

# --- Moving files between macOS and Linux ---
orb push ~/notesflow/seed.sql /tmp/
orb pull /var/log/postgresql/postgresql.log ./logs/

# --- Config and diagnostics ---
orb config show
orb logs

Linux machines are the feature with no Colima equivalent worth noting. They are not containers: each is a full distribution with its own package manager and init system, sharing OrbStack's kernel. They are useful for reproducing a Linux CI environment locally, or for testing an install script the way a fresh server would see it — and they boot in about two seconds.

Container domains: the feature you will miss most if you leave

OrbStack gives every container a DNS name and terminates HTTPS for it automatically. No published ports, no -p 8080:80, no remembering which service took port 5432 this week.

docker run -d --name notesflow-api nginx
curl http://notesflow-api.orb.local          # works immediately, no -p flag

# Compose services get project-scoped names
# service `api` in project `notesflow` becomes:
curl https://api.notesflow.orb.local         # HTTPS, valid cert, no config

The reason this matters beyond convenience: port collisions are the most common source of "works on my machine" failures in multi-project teams. When every engineer runs three Compose projects that each want port 5432, someone always loses. Stable per-container domains remove the shared namespace entirely, so two projects can both believe they own Postgres's default port.

Licence reminder: OrbStack is free for personal use. Any use on a company-paid Mac, or for freelance and business work, requires a paid licence. If you are evaluating for a team, start the trial deliberately and diarise the end date — Module 1.2's decision record should already name who owns that budget line.

Exercise 1.4 — OrbStack From Zero

Scenario: you are running the two-week OrbStack trial that your Module 1.2 decision record called for, and you must produce evidence rather than impressions.

Image, container, layer — three words people use interchangeably and should not

An image is an immutable, read-only stack of filesystem layers plus a manifest of metadata (default command, exposed ports, environment). A container is one running instance of an image with a thin writable layer on top. A layer is the filesystem delta produced by one build instruction.

The consequence of confusing them is data loss: everything a container writes goes into that thin writable layer, and docker rm deletes it permanently. Engineers who think of a container as "a little server" eventually lose a database that way. A container is disposable by design; anything you need to survive must be deliberately placed on a volume (Module 2.3).

Tags are not versions, and latest is not a promise

A tag is a mutable pointer to an image digest. postgres:17 today and postgres:17 in three months are different images — the tag moves as patch releases ship. postgres:latest is worse: it moves across major versions, which is how a team wakes up to a Postgres 18 container refusing to open a Postgres 17 data directory.

# Resolve a tag to its immutable digest
docker inspect --format '{{index .RepoDigests 0}}' postgres:17
# postgres@sha256:0c4f21a...

# Pin by digest where reproducibility matters (CI, production base images)
docker pull postgres@sha256:0c4f21a...

The working rule: pin to a minor tag (postgres:17) in development where you want security patches, and pin to a digest in CI and production where you want byte-identical rebuilds. Never use latest for anything stateful.

Where the disk actually goes

On macOS, images and volumes live inside the runtime's VM disk image, not on your Mac's filesystem where Finder can see them. That is why docker system df can report 40 GB while your Mac reports plenty free, and why deleting images does not immediately shrink the VM's disk file — the guest frees the blocks but the sparse image file does not always return them to macOS. Colima and OrbStack both handle reclamation differently; Module 3.1 covers Colima's disk sizing and Module 3.3 covers OrbStack's automatic reclamation.

Layer caching is the whole game

Every instruction in a Dockerfile produces a layer, and Docker reuses a cached layer only if that instruction and every instruction before it are unchanged. Get the order wrong and every one-character source edit reinstalls all your dependencies — turning a 3-second rebuild into a 3-minute one, fifty times a day.

The rule that follows: order instructions from least-frequently-changed to most-frequently-changed. Dependency manifests change weekly; application source changes every few minutes. So the manifest is copied and installed first, and the source is copied last.

The NotesFlow API image

# syntax=docker/dockerfile:1

# ---------- Stage 1: build dependencies into a virtualenv ----------
FROM python:3.13-slim AS builder

ENV PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential libpq-dev \
 && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# Dependency manifest FIRST — this layer is cached until requirements change
COPY requirements.txt .
RUN python -m venv /opt/venv \
 && /opt/venv/bin/pip install -r requirements.txt

# ---------- Stage 2: the runtime image ----------
FROM python:3.13-slim AS runtime

ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

# Runtime needs the Postgres client library, not the compiler toolchain
RUN apt-get update \
 && apt-get install -y --no-install-recommends libpq5 curl \
 && rm -rf /var/lib/apt/lists/* \
 && useradd --create-home --uid 10001 notesflow

COPY --from=builder /opt/venv /opt/venv

WORKDIR /app
# Application source LAST — the only layer that rebuilds on a code edit
COPY --chown=notesflow:notesflow ./app ./app

USER notesflow
EXPOSE 8000

HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:8000/healthz || exit 1

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Three ways to get data into a container, with very different properties

TypeSyntaxStoredmacOS speedUse for
Named volume-v notesflow-pgdata:/var/lib/postgresql/dataInside the VM, managed by DockerNative Linux speedDatabases, caches, anything write-heavy
Bind mount-v "$PWD/app:/app/app"On your Mac, shared into the VMSlow — crosses the VM boundarySource code you edit and want hot-reloaded
tmpfs--tmpfs /tmpGuest RAM onlyFastestScratch space, secrets that must not touch disk

The macOS speed column is the one that separates people who enjoy containers on a Mac from people who complain about them. A named volume lives inside the Linux VM's own filesystem, so a Postgres write is an ordinary local write. A bind mount has to traverse a file-sharing protocol between macOS and the guest on every single stat() and read() — and a Python or Node application startup performs tens of thousands of those. Putting a database on a bind mount is the single most common cause of "Docker is unusably slow on my Mac."

Working with named volumes

docker volume ls

  -e POSTGRES_PASSWORD=devpassword \
  -e POSTGRES_DB=notesflow \
  -v notesflow-pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:17

# Destroy the container — the data survives
docker rm -f notesflow-db

# Recreate it against the same volume
docker run -d --name notesflow-db \
  -e POSTGRES_PASSWORD=devpassword \
  -v notesflow-pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:17

docker exec notesflow-db psql -U postgres -d notesflow -c 'SELECT count(*) FROM notes;'

Backup and restore without a database client

A volume is just a directory inside the VM, so any container can mount it. The standard trick is a throwaway Alpine container that mounts both the volume and a bind-mounted output directory:

# Back up a named volume to a tarball on your Mac
docker run --rm \
  -v notesflow-pgdata:/data:ro \
  -v "$PWD/backups:/backup" \
  alpine tar czf /backup/pgdata-$(date +%Y%m%d).tar.gz -C /data .

# Restore into a fresh volume
docker volume create notesflow-pgdata-restored
docker run --rm \
  -v notesflow-pgdata-restored:/data \
  -v "$PWD/backups:/backup" \
  alpine sh -c 'cd /data && tar xzf /backup/pgdata-20260816.tar.gz'

Stop the database before taking a filesystem-level backup of its data directory. A tarball of a running Postgres data directory is a torn copy — it may restore, and it may restore corrupt, which is worse than failing outright. For anything you actually care about, use pg_dump instead.

Bind mounts for development, done correctly

You do want a bind mount for source code — that is how hot reload works. The trick is mounting only the source, and shielding the dependency directory with an anonymous volume so the host's empty or wrong-architecture copy does not shadow the container's:

docker run -d --name notesflow-api \
  -v "$PWD/app:/app/app" \
  -v /app/.venv \
  -p 8000:8000 \
  -e NOTESFLOW_ENV=development \
  notesflow-api:dev \
  uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

The bare -v /app/.venv creates an anonymous volume at that path, which takes precedence over the bind mount beneath it. Without it, a macOS-built virtualenv containing darwin/arm64 binaries gets mounted over the Linux one and imports fail with architecture errors that read as nonsense.

localhost means four different things, and that is the whole difficulty

Inside a container, localhost is that container's own network namespace. Inside the Linux VM, it is the VM. On your Mac, it is macOS. And to a service being addressed, it may be none of these. Almost every macOS networking bug is a mismatch between which localhost someone meant.

macOS                          Linux VM                 Container
─────                          ────────                 ─────────
localhost:8000  ──published──▶ VM :8000  ──bridge──▶    container :8000
                                                        (its own localhost)

From the API container, "localhost:5432" = the API container itself → refused.
From the API container, "notesflow-db:5432" = the DB container    → works.
From macOS,   "localhost:5432" works ONLY if you published -p 5432:5432.
From a container, your Mac's own services = host.docker.internal

User-defined bridges give you DNS; the default bridge does not

This is the practical reason to always create a network. On the default bridge, containers can only reach each other by IP address — which changes on every restart. On a user-defined bridge, Docker runs an embedded DNS server at 127.0.0.11 that resolves container names and network aliases automatically.

docker network create notesflow-net
docker network ls
docker network inspect notesflow-net

docker run -d --name notesflow-db --network notesflow-net \
  -e POSTGRES_PASSWORD=devpassword -e POSTGRES_DB=notesflow postgres:17

docker run -d --name notesflow-cache --network notesflow-net redis:8

docker run -d --name notesflow-api --network notesflow-net \
  -e DATABASE_URL=postgresql://postgres:devpassword@notesflow-db:5432/notesflow \
  -e REDIS_URL=redis://notesflow-cache:6379/0 \
  -p 8000:8000 \
  notesflow-api:dev

# Prove name resolution from inside the API container
docker exec notesflow-api getent hosts notesflow-db
docker exec notesflow-api python -c \
  "import socket; print(socket.gethostbyname('notesflow-cache'))"

Note what is not published: neither Postgres nor Redis has a -p flag. They are reachable by the API over the bridge but invisible from macOS. That is correct — publishing a database port to your host is a habit worth breaking, because it is the same habit that exposes 5432 on a staging box to the office network.

Compose is the Module 2.4 commands, written down

Everything in the previous module — the network, the volumes, the environment variables, the ordering — becomes declarative. The value is not that it is shorter; it is that it is reviewable in a pull request and identical on every teammate's machine.

name: notesflow

services:

    image: postgres:17
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-devpassword}
      POSTGRES_DB: notesflow
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d notesflow"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  cache:
    image: redis:8
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build:
      context: .
      target: runtime
    environment:
      DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD:-devpassword}@db:5432/notesflow
      REDIS_URL: redis://cache:6379/0
    ports:
      - "8000:8000"
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy

  worker:
    build:
      context: .
      target: runtime
    command: ["python", "-m", "app.worker"]
    environment:
      DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD:-devpassword}@db:5432/notesflow
      REDIS_URL: redis://cache:6379/0
    depends_on:
      api:
        condition: service_started

volumes:
  pgdata:
  redisdata:

Two details carry most of the weight. First, there is no networks: block — Compose creates a default network named after the project and attaches every service, so db and cache resolve by service name automatically. Second, condition: service_healthy is what makes the stack come up reliably: a bare depends_on: [db] waits only for the container to start, and Postgres takes several seconds after starting before it accepts connections. Without the health gate, the API crash-loops on every cold start and everyone learns to type docker compose up twice.

Override files: one base, many environments

compose.override.yaml is merged automatically when present. Keep the base file production-shaped and put development conveniences in the override, so the file you deploy is the file you reviewed.

# compose.override.yaml — applied automatically in development
services:
  api:
    build:
      target: runtime
    command: ["uvicorn", "app.main:app", "--host", "0.0.0.0",
              "--port", "8000", "--reload"]
    volumes:
      - ./app:/app/app
      - /app/.venv
    environment:
      NOTESFLOW_ENV: development
      LOG_LEVEL: debug

  db:
    ports:
      - "5432:5432"      # expose to your Mac for psql/TablePlus, dev only
# Development: base + override merged automatically
docker compose up -d

# Production-shaped: base only, override explicitly ignored
docker compose -f compose.yaml up -d

# See the fully merged, resolved configuration — the best debugging tool here
docker compose config

docker compose up -d --build          # rebuild changed images first
docker compose ps                     # status, including health

What Compose v5 changed

Compose v5 is the current line (v5.4 as of August 2026). Three changes matter for a guide-level understanding: a rewritten reconciliation algorithm that models volume and network lifecycle in the plan, so resources are no longer recreated unnecessarily on an up against a running stack; native init containers via pre_start_init_containers, replacing the old pattern of a one-shot migration service with a hand-rolled dependency chain; and an official Go SDK, which lets tools load and validate Compose projects without shelling out to the CLI. The version: key at the top of a Compose file has been obsolete since v2 — delete it if you inherit a file that has one.

Module 3.1 — Colima Resource Tuning: CPU, Memory, Disk, Profiles

Level: Intermediate · Prereqs: 1.3 · Time: ~3h
Skip-check (test-out): Raise a running Colima instance from 2 CPUs / 2 GB to 6 CPUs / 12 GB without losing your images, and run a second independent Colima profile simultaneously on a different Docker context.
Skip if: You maintain a version-controlled colima.yaml for your team and use named profiles daily.

The defaults are deliberately small, and they will bite you

Colima starts with 2 CPUs, 2 GB of memory, and a 60 GB disk. Running NotesFlow's four services inside 2 GB means Postgres, Redis, the API and the worker compete for memory the guest kernel does not have, and the OOM killer starts terminating processes. The symptom is misleading: containers exit with code 137 at apparently random moments, which reads like an application bug rather than a VM sizing problem.

# Inspect what you currently have
colima status
colima list
docker info --format 'CPUs={{.NCPU}} Mem={{.MemTotal}}'

# CPU and memory can be changed on a running instance
colima stop
colima start --cpu 6 --memory 12

# Disk can only GROW, and only with an explicit restart
colima stop
colima start --disk 150

The asymmetry between memory and disk matters. CPU and memory are runtime allocations the hypervisor can renegotiate, so raising or lowering them is a restart away. The disk is a sparse image file with a filesystem on it — Colima can grow it, but there is no supported shrink. Over-provision the disk from the start (150 GB costs you nothing until it is used, because the file is sparse) and be conservative with memory, which is genuinely taken from macOS while the VM runs.

The config file is the real interface

Flags are for experiments; the YAML is for teams. colima start --edit opens the active profile's config, and the file can be committed and shared so every engineer gets an identical VM.

# ~/.colima/default/colima.yaml
cpu: 6
memory: 12
disk: 150
arch: host

# vz = Apple Virtualization.framework (fast, macOS 13+ on Apple Silicon)
# qemu = portable fallback, slower, needed for some cross-arch cases
vmType: vz
rosetta: true

# virtiofs is the fastest mount type, and requires vmType: vz
mountType: virtiofs
mountInotify: true

runtime: docker
autoActivate: true

mounts:
  - location: ~/projects
    writable: true
  - location: ~/.ssh
    writable: false

env:
  DOCKER_BUILDKIT: "1"
# Start a profile from a committed config — the team-reproducibility path
colima start --config ./infra/colima.yaml

# Or edit the active profile in place
colima start --edit

Note the mounts: block. Colima shares only your home directory by default; if your code lives on an external volume or a path outside $HOME, a bind mount to it silently produces an empty directory inside the container rather than an error. That silent-empty-directory failure is one of the most confusing things a new Colima user can hit.

Profiles: separate VMs for separate jobs

A profile is an entirely independent VM with its own images, containers, volumes, and Docker context. Use them when workloads have genuinely different resource shapes or must not see each other's state.

# A small, fast profile for everyday NotesFlow work
colima start --profile dev --cpu 4 --memory 8 --disk 100

# A large one for Kubernetes, which needs headroom
colima start --profile k8s --cpu 6 --memory 12 --disk 150 --kubernetes

# A deliberately x86_64 profile for reproducing an Intel-only bug
colima start --profile amd64 --arch x86_64 --vm-type qemu --cpu 4 --memory 8

colima list
# PROFILE  STATUS   ARCH      CPUS  MEMORY  DISK  RUNTIME
# dev      Running  aarch64   4     8GiB    100GiB  docker
# k8s      Running  aarch64   6     12GiB   150GiB  docker
# amd64    Stopped  x86_64    4     8GiB    100GiB  docker

# Each profile registers its own docker context

Every running profile holds its allocated memory from macOS for as long as it runs. Three profiles at 12 GB each on a 32 GB Mac will swap your laptop into unusability — start the profile you need and stop the ones you do not.

vz versus qemu

The distinction that confuses people: vz plus Rosetta runs x86_64 user-space binaries on an arm64 kernel by translating instructions. qemu with --arch x86_64 emulates an entire x86_64 machine including the kernel. Rosetta is far faster and covers almost every real case; full emulation is the fallback for software that inspects the kernel architecture or uses instructions Rosetta does not translate.

Rosetta: running amd64 images on Apple Silicon

colima stop
colima start --vm-type vz --vz-rosetta --cpu 6 --memory 12

# Run an amd64-only image on an arm64 Mac

# x86_64

# Confirm which architectures the daemon can run
docker run --privileged --rm tonistiigi/binfmt
# ... emulators: linux/amd64, linux/arm64, ...

Colima still labels Rosetta support experimental; OrbStack ships it as a stable feature. In practice both work for the common case of an amd64 base image with no exotic instructions, and both occasionally fail on the same edge cases — JIT-heavy runtimes and anything shipping hand-written SSE/AVX assembly.

Multi-architecture builds with buildx

Building for one architecture on another is not the same problem as running it. buildx creates a builder instance that can target multiple platforms and emit a single manifest list — one tag that resolves to the right image per puller.

# Create a builder that supports multiple platforms
docker buildx create --name notesflow-builder --driver docker-container --use
docker buildx inspect --bootstrap

# Build both architectures and push as one manifest list
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t ghcr.io/yourorg/notesflow-api:1.0.0 \
  --push .

# Verify the manifest lists both
docker buildx imagetools inspect ghcr.io/yourorg/notesflow-api:1.0.0

# Single-platform build loaded into the LOCAL image store
docker buildx build --platform linux/arm64 -t notesflow-api:dev --load .

--load and multi-platform are mutually exclusive, and the error message is not obvious the first time. The local Docker image store holds one image per tag, so it has nowhere to put a manifest list that references two. Multi-arch therefore requires --push to a registry (or --output type=oci to a tarball). Plan for this: your local development tag and your published multi-arch tag are separate build invocations.

Cross-compiling properly instead of emulating

Emulated builds are slow — often five to twenty times slower than native. For compiled languages, the fast path is to build natively and cross-compile, using the build platform's toolchain with buildx's automatic platform arguments:

# syntax=docker/dockerfile:1
# BUILDPLATFORM = the machine doing the building (your Mac, arm64)
# TARGETOS/TARGETARCH = what we are building FOR
FROM --platform=$BUILDPLATFORM golang:1.24-alpine AS builder
ARG TARGETOS
ARG TARGETARCH
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /out/notesflow-worker ./cmd/worker

FROM alpine:3.21
RUN adduser -D -u 10001 notesflow
COPY --from=builder /out/notesflow-worker /usr/local/bin/notesflow-worker
USER notesflow
ENTRYPOINT ["/usr/local/bin/notesflow-worker"]

The builder stage is pinned to $BUILDPLATFORM, so it always runs natively on your Mac's arm64 CPU at full speed, and only the compiler's output targets the other architecture. Interpreted languages cannot use this trick for their own code, but they can for any native extensions they compile.

Module 3.3 — OrbStack Configuration, Domains & Networking

Configuration lives in orb config, not a YAML file

OrbStack's design goal is that you should rarely need to configure anything — memory and CPU are allocated dynamically and returned to macOS when idle, rather than reserved up front the way Colima reserves them. Where Colima asks "how much RAM do you want to give the VM?", OrbStack asks nothing and takes what it needs.

orb config show

# Cap resources if you want a hard ceiling rather than dynamic allocation
orb config set cpu 6
orb config set memory_mib 12288

# Network behaviour
orb config set network_proxy auto
orb config set docker.set_context true

orb doctor           # verify the docker context, socket, and CLI integration
orb doctor --fix     # repair it

The practical consequence of dynamic allocation: OrbStack's idle footprint is small enough that leaving it running all day is normal, whereas a 12 GB Colima profile is memory macOS cannot use until you stop it. That difference — not raw throughput — is what most people mean when they say OrbStack "feels" lighter.

Container domains eliminate the port namespace

Every container and every Compose service gets a DNS name with automatic HTTPS. This is OrbStack's most distinctive feature and the hardest thing to give up if you later move to Colima.

# A plain container: <container-name>.orb.local
docker run -d --name notesflow-api -p 8000 notesflow-api:dev
curl http://notesflow-api.orb.local:8000/healthz

# A Compose service: <service>.<project>.orb.local
# project "notesflow", service "api":
curl https://api.notesflow.orb.local/healthz     # HTTPS, trusted cert, no setup

# Add your own domain with a label
docker run -d --name notesflow-api \
  -l dev.orbstack.domains=notes.local,api.notes.local \
  notesflow-api:dev
curl https://notes.local/healthz
# Same thing declaratively in compose.override.yaml
services:
  api:
    labels:
      dev.orbstack.domains: "notes.local,api.notes.local"
    # No `ports:` needed at all — the domain reaches the container port directly

This solves a real organisational problem, not just a convenience one. When five engineers each run three Compose projects, published ports become a shared, contended namespace that someone has to arbitrate — the team ends up with a wiki page assigning port ranges to projects. Per-container domains remove the namespace, so two projects can both run Postgres on 5432 and neither knows about the other.

Networking capabilities Colima does not have

# ICMP works — you can ping containers
ping -c 3 notesflow-api.orb.local

# Container IPs are routable from macOS directly, no publishing needed
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' notesflow-db
psql -h 192.168.215.3 -U postgres -d notesflow    # works from macOS

# IPv6 is supported
docker run --rm curlimages/curl:latest curl -6 -s https://ipv6.google.com

# Corporate proxy and VPN
orb config set network_proxy http://proxy.corp.example:3128

Direct container-IP routing is the quiet productivity win: database GUI tools like TablePlus or DataGrip can connect to a container's real address without anyone publishing a port, which means no port conflicts and no accidentally exposing a database on a shared network.

Module 3.4 — File Sharing Performance & Runtime Switching

Level: Intermediate · Prereqs: 2.3, 3.1 · Time: ~3h

Skip if: You can explain virtiofs versus sshfs and already shield dependency directories from bind mounts by reflex.

Why macOS bind mounts are slow, specifically

A bind mount is not a mount in the Linux sense — it is a network-style file-sharing protocol bridging two operating systems. Every open(), stat(), and read() inside the container becomes a message across the VM boundary. A single file read is fine. The problem is volume: a Python interpreter importing a large dependency tree, or Node resolving node_modules, performs tens of thousands of stat() calls at startup, and each one now pays VM-crossing latency instead of page-cache latency.

This is why the fix is never "make the protocol faster" alone. The fix is to stop the hot paths from crossing the boundary at all.

virtiofsColima with vmType: vzFastest available to ColimaRequires macOS 13+; the correct default
sshfsColima, any VM typeSlowColima's portable fallback default
9pColima with vmType: qemuSlowestLegacy; avoid
Native bidirectionalOrbStack75–95% of native macOSCustom implementation, not a generic protocol

Four fixes, in order of effectiveness

# FIX 1 — Use virtiofs on Colima (the single biggest win)
colima stop
colima start --vm-type vz --mount-type virtiofs --cpu 6 --memory 12

# FIX 2 — Never bind-mount write-heavy state; use a named volume
#   BAD:  -v "$PWD/pgdata:/var/lib/postgresql/data"
#   GOOD: -v notesflow-pgdata:/var/lib/postgresql/data

# FIX 3 — Shield dependency directories with anonymous volumes
docker run -v "$PWD:/app" -v /app/.venv -v /app/node_modules notesflow-api:dev

# FIX 4 — Mount narrowly. Share the source directory, not all of $HOME
#   BAD:  -v "$HOME:/host"
#   GOOD: -v "$PWD/app:/app/app"

Fix 3 deserves emphasis because it fixes correctness as well as speed. A macOS-built .venv or node_modules contains darwin/arm64 native binaries; mounted over the container's Linux copy, imports fail with architecture errors that look like packaging bugs. The anonymous volume takes precedence over the bind mount at that path, so the container keeps its own Linux-built dependencies.

Measuring rather than guessing

# Sequential write throughput: named volume
docker run --rm -v notesflow-perf:/data alpine \
  sh -c 'dd if=/dev/zero of=/data/testfile bs=1M count=1024 conv=fsync'

# Same test through a bind mount
docker run --rm -v "$PWD/perf:/data" alpine \
  sh -c 'dd if=/dev/zero of=/data/testfile bs=1M count=1024 conv=fsync'

# Metadata-heavy test — closer to what a real app startup does
docker run --rm -v "$PWD/perf:/data" alpine \
  sh -c 'time (for i in $(seq 1 5000); do touch /data/f$i; done)'

# Real-world proxy: how long does the API take to import its dependencies?
time docker compose run --rm api python -c 'import app.main'

Measure the metadata test, not just the dd throughput. Sequential write throughput often looks acceptable on a bind mount while metadata operations are ten times slower — and metadata is what application startup is made of.

Switching between runtimes cleanly

Both runtimes register a Docker context, so switching is one command and requires no config editing. Only one should be running at a time unless you have memory to spare.

docker context ls
# NAME        DOCKER ENDPOINT
# colima      unix:///Users/you/.colima/default/docker.sock
# orbstack    unix:///Users/you/.orbstack/run/docker.sock

docker context use colima
docker context use orbstack

# Or per-command, without changing the default
docker --context orbstack ps
DOCKER_HOST=unix://$HOME/.colima/default/docker.sock docker ps
# A shell function worth keeping in ~/.zshrc
dr() {
  case "$1" in
    colima)   colima start && docker context use colima ;;
    orb)      orb start    && docker context use orbstack ;;
    off)      colima stop 2>/dev/null; orb stop 2>/dev/null ;;
    *)        docker context ls ;;
  esac
}

Images, volumes, and containers do not transfer between runtimes — each has its own VM and its own storage. Switching contexts and finding an empty docker ps is expected behaviour, not a bug. To move an image across, save and load it: docker --context colima save notesflow-api:dev | docker --context orbstack load.

Where local Kubernetes lies to you — on either runtime

Both clusters are single-node, which quietly removes several classes of problem you will meet in production. Knowing which ones prevents shipping a manifest that only ever worked because it never had to schedule across machines:

Works locally, fails in production:
  - ReadWriteOnce PVCs shared by pods    (fine on 1 node, fails across nodes)
  - Missing resource requests/limits     (no scheduling pressure locally)
  - No PodDisruptionBudget               (nothing ever drains a node)
  - hostPath volumes                     (node-specific; breaks on reschedule)
  - Node affinity / topology spread      (untestable with one node)
  - NetworkPolicy                        (k3s and OrbStack both need it enabled)
  - Image pull secrets                   (local images skip the registry entirely)

Write manifests as if there were many nodes even though there is one. Set resource requests and limits from the start; a workload with no requests schedules fine on an empty single node and then behaves unpredictably the first time it meets a real scheduler.

Readiness and liveness must not be the same check in spirit, even when they hit the same endpoint. Readiness failing removes the pod from the Service's endpoints — traffic stops, the pod lives. Liveness failing kills and restarts the container. Point liveness at a dependency such as the database and a brief database blip becomes a cluster-wide restart storm, because every replica kills itself simultaneously.

CI without Docker Desktop anywhere

GitHub-hosted runners are Linux machines with a native Docker Engine — no VM, no Docker Desktop, and nothing to license. The whole macOS runtime question simply does not arise in CI, which is why local/CI parity is a matter of pinning versions rather than matching tooling.

name: build-and-push

on:
  push:
    branches: [main]
    tags: ["v*"]

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up QEMU for cross-architecture builds
        uses: docker/setup-qemu-action@v3

      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Derive tags and labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/notesflow-api
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=sha,format=long

      - name: Build and push (multi-arch)
        id: build
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Publish the immutable digest
        run: echo "digest=${{ steps.build.outputs.digest }}" >> "$GITHUB_STEP_SUMMARY"

cache-from: type=gha is the line that decides whether CI takes ninety seconds or nine minutes. It stores buildx's layer cache in GitHub Actions' cache service, so an unchanged dependency layer is restored rather than rebuilt. Without it, every push reinstalls every dependency from scratch, and the emulated linux/amd64 leg makes that painful.

Making local and CI produce the same image

Three practices close the gap, and the reason to care is that "works locally, fails in CI" is nearly always one of them:

# 1. Pin base images by digest, not tag — the same bytes everywhere
FROM python:3.13-slim@sha256:1e8f4c2b...

# 2. Verify the published manifest lists both architectures
docker buildx imagetools inspect ghcr.io/yourorg/notesflow-api:1.0.0

# 3. Deploy by digest, never by mutable tag
kubectl set image deployment/notesflow-api \
  api=ghcr.io/yourorg/notesflow-api@sha256:9a3f2c1b...

Deploying by digest is the one that matters most in a cluster. A Deployment referencing :1.0.0 can silently run two different images across its replicas if the tag was repushed between pod starts; a digest cannot.

A diagnostic sequence, not a list of guesses

Container problems on macOS almost always live at one of four layers. Testing them in order finds the fault fast, because each step eliminates everything beneath it:

# LAYER 1 — Is the CLI even pointed at a daemon?
docker context ls              # which context is active?
docker version                 # does the SERVER section appear at all?
# Server section missing  → the daemon is unreachable. Layer 2.
# Wrong context active    → docker context use colima|orbstack. Done.

# LAYER 2 — Is the VM running?
colima status                  # or: orb status
colima list
# Not running → colima start / orb start. Then retry layer 1.

# LAYER 3 — Is the VM healthy inside?
colima ssh -- systemctl status docker
colima ssh -- df -h            # a full VM disk breaks builds in odd ways
colima ssh -- free -m          # OOM kills look like random exits
colima ssh -- journalctl -u docker --no-pager -n 100
orb doctor                     # OrbStack's equivalent, plus --fix

# LAYER 4 — Is it the workload?
docker logs <container>
docker inspect <container> --format '{{.State.ExitCode}} {{.State.Error}}'
docker events --since 10m

# Back up every named volume before uninstalling anything
mkdir -p ~/docker-volume-backups
for v in $(docker volume ls -q); do
  echo "Backing up $v"
  docker run --rm \
    -v "$v":/data:ro \
    -v "$HOME/docker-volume-backups":/backup \
    alpine tar czf "/backup/$v.tar.gz" -C /data . 2>/dev/null \
    || echo "  SKIPPED $v (in use or empty)"
done
ls -lh ~/docker-volume-backups
# Restore into the new runtime, after switching context
docker context use colima
for f in ~/docker-volume-backups/*.tar.gz; do
  v=$(basename "$f" .tar.gz)
  docker volume create "$v"
  docker run --rm -v "$v":/data -v "$HOME/docker-volume-backups":/backup \
    alpine sh -c "cd /data && tar xzf /backup/$(basename "$f")"
done

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Runtime & VM Layer

Container
A Linux process isolated by kernel namespaces and constrained by cgroups. It shares the host kernel and has no kernel of its own.
Avoid: "lightweight VM", "Docker" — a VM has its own kernel, and Docker is one tool for making containers, not a synonym for them.
Container runtime
The component that actually creates and runs containers from images — runc, containerd, or CRI-O. It sits below the engine.
Avoid: "Docker", "engine" — the engine is the API and build layer above the runtime.
Container engine
The daemon exposing an API for building, distributing, and managing containers, delegating actual execution to a runtime. dockerd is the canonical example.
Avoid: "Docker Desktop" — that is a commercial GUI and VM bundle wrapping an engine.
Colima
An MIT-licensed CLI tool that provisions a Lima-based Linux VM on macOS or Linux and runs a container engine inside it, exposing a Docker socket.
Avoid: "Docker for Mac replacement" — it replaces the VM layer only; the Docker CLI and engine are unchanged.
OrbStack
A native macOS application, written in Swift with its own kernel build and network stack, providing Docker containers, Kubernetes, and full Linux machines. Free for personal use; commercial use requires a licence.
Avoid: "a GUI for Colima", "Docker Desktop fork" — it is an independent implementation sharing code with neither.
Lima
The open-source "Linux Machines" project that provisions and manages Linux VMs on macOS. Colima is built on top of it.
Avoid: "Colima's backend" as though interchangeable — Lima is usable directly, without Colima.
Docker context
A named pointer to a Docker daemon endpoint. The active context determines which daemon — and therefore which set of images and containers — every docker command addresses.
Avoid: "profile", "environment" — a Colima profile is a whole VM, which merely registers a context.
Colima profile
An independent Colima VM with its own CPU, memory, disk, images, containers, and Docker context. Profiles share nothing.
Avoid: "instance" used loosely — say profile when you mean the named, separately-addressable VM.
vz
Apple's Virtualization.framework, used as Colima's fastest VM backend on macOS 13 and later. It cannot emulate a foreign architecture.
Avoid: "Rosetta" — Rosetta is user-space binary translation running inside a vz VM.
Rosetta
Apple's binary translation layer that runs x86_64 user-space executables on Apple Silicon. In containers it allows amd64 images to run on an arm64 kernel.
Avoid: "emulation" — full emulation (qemu) simulates a whole machine including the kernel and is far slower.
virtiofs
A shared-filesystem transport between a host and a VM guest, and the fastest mount type available to Colima. It requires vmType: vz.
Avoid: "bind mount" — virtiofs is the transport a bind mount travels over, not the mount itself.

Docker & Compose

Image
An immutable, read-only stack of filesystem layers plus metadata describing how to start a container from it.
Avoid: "container" — a container is a running instance of an image with a writable layer.
Layer
The filesystem delta produced by a single build instruction, content-addressed and shareable between images.
Avoid: "step" — a build step may produce no layer at all.
Manifest list
An index mapping platform identifiers to per-architecture image digests, so one tag resolves correctly on both amd64 and arm64.
Avoid: "multi-arch image" — it is an index of images, not a single image containing several.
Digest
The immutable SHA-256 content hash of an image or manifest. Unlike a tag, it can never point at different bytes later.
Avoid: "tag", "version" — both are mutable pointers.
Named volume
Docker-managed storage living inside the runtime's VM filesystem, independent of any container's lifecycle and running at native Linux speed.
Avoid: "bind mount", "persistent volume" — the latter is a Kubernetes object.
Bind mount
A host directory shared into a container. On macOS it crosses the VM boundary on every filesystem operation, making metadata-heavy work slow.
Avoid: "volume" unqualified — the performance characteristics are opposite.
Build context
The set of files sent to the daemon before a build begins, filtered by .dockerignore.
Avoid: "working directory", "Docker context" — the latter is a daemon endpoint and entirely unrelated.
Multi-stage build
A Dockerfile with several FROM stages where only the final stage becomes the shipped image, leaving build tooling behind.
Avoid: "multi-arch build" — one concerns image size, the other target platforms.
BuildKit
Docker's build engine, providing parallel stage execution, cache mounts, and multi-platform output. It backs docker buildx.
Avoid: "buildx" — buildx is the CLI front end to BuildKit.
Compose project
A named group of services, networks, and volumes defined by one or more Compose files. The project name scopes every resource it creates.
Avoid: "stack" — that means a Swarm or Kubernetes deployment elsewhere.
Health gate
A depends_on entry using condition: service_healthy, which delays a service's start until its dependency's healthcheck passes.
Avoid: "depends_on" alone — bare depends_on waits only for the container to start, not to be usable.

Kubernetes & Operations

k3s
A CNCF-certified Kubernetes distribution packaged as a single binary, with SQLite instead of etcd by default and cloud controllers removed. Colima bundles it.
Avoid: "not real Kubernetes" — it is conformant; it differs in defaults, not in API.
Deployment
A Kubernetes object managing a replicated, interchangeable set of stateless pods and their rollout strategy.
Avoid: "deployment" as a verb for shipping code — say release or rollout.
StatefulSet
A workload object giving each pod a stable identity and its own persistent volume, used for databases and anything with per-instance state.
Avoid: "Deployment with a PVC" — that shares one volume across replicas and corrupts most databases.
Readiness probe
A periodic check deciding whether a pod should receive traffic. Failing it removes the pod from Service endpoints without restarting it.
Avoid: "liveness probe" — that one restarts the container, with very different blast radius.
Liveness probe
A periodic check that restarts the container when it fails. It should test only the process itself, never a downstream dependency.
Avoid: "health check" unqualified — Compose's healthcheck maps more closely to readiness.
ClusterIP
The default Service type, giving a stable virtual IP reachable only from inside the cluster — unless the runtime routes cluster addresses to the host, as OrbStack does.
Avoid: "internal IP", "pod IP" — a pod IP belongs to one pod and changes on reschedule.
NodePort
A Service type publishing a port on every node, which on a single-node local cluster means localhost:<port>.
Avoid: "published port" — the Compose concept does not involve a Service object.
Kustomize overlay
A directory that patches a shared base manifest set for one environment, without templating or duplicating the base.
Avoid: "Helm chart" — Helm templates and packages; Kustomize patches structured YAML.
Image pull policy
The field controlling whether the kubelet contacts a registry before starting a container. IfNotPresent is required for locally built images.
Avoid: leaving it unset with a :latest tag — the default becomes Always and local images fail to start.
OOM kill
Termination of a process by the Linux kernel when memory is exhausted, surfacing as container exit code 137.
Avoid: "crash", "the container died" — the exit code names the cause precisely.
