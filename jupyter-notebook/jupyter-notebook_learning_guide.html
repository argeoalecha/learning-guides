Three platforms, one learning order

There's no single "correct" way to run a notebook — Colab, Anaconda, and VS Code are all legitimate, and most people who use notebooks seriously end up touching all three eventually. What matters is the order: each stage removes one piece of friction the previous stage still had, so learning them in this sequence means you only deal with one new concept at a time instead of fighting installation problems and the notebook interface simultaneously.

  1. Google Colab — zero install, runs in a browser tab. Best for your very first cell, and for quick one-off experiments later. Can't easily touch your own local files.
  2. Anaconda — a local install with Python, JupyterLab, and the common data-science packages bundled together. Best once you're working with your own files, larger data, or need to work offline.
  3. VS Code + Git — notebooks live inside a real, version-controlled project instead of standing alone. Best once a notebook needs to survive being edited by more than just "future you," or be tracked in a repository at all.

Stage 1 — Google Colab: run your first cell with nothing installed

Go to colab.research.google.com, sign in with a Google account, and choose New notebook. This opens an .ipynb-compatible document running entirely on Google's infrastructure — no Python, no Jupyter, nothing installed on your machine at all, and free (rate-limited) GPU/TPU access if you ever need it later. This is the lowest-friction way to find out whether the core notebook loop (write code, run it, see output immediately below) makes sense to you, before installing anything.

Colab's tradeoff: the environment is Google's, not yours. Working with your own CSV files means uploading them each session (they don't persist by default) or mounting Google Drive — workable, but noticeably more friction than a file already sitting on your own disk. That's the signal to move to Stage 2. (Module 4.2 comes back to Colab later — specifically for sharing a finished notebook so someone else can run it with zero setup, which is a different use case than working in it yourself.)

Stage 2 — Anaconda: move the work onto your own machine

Once you're ready to work with your own local files, install Anaconda (the full distribution — Python, JupyterLab, and roughly 250 data-science packages including pandas and matplotlib, preinstalled) or Miniconda (a minimal installer that gives you just conda itself, so you install only what each project actually needs). Either way, you get conda, Anaconda's package and environment manager.

conda install -c conda-forge jupyterlab
jupyter lab

This starts a local server and opens JupyterLab in your default browser at localhost:8888 — or, with the full Anaconda distribution, open Anaconda Navigator and click Launch under JupyterLab instead of using the command line at all. If you'd rather skip conda entirely, pip install jupyterlab works identically — Anaconda is a convenience for environment/package management, not a requirement to run notebooks locally. Module 4.1 covers proper environment isolation (multiple projects, no version conflicts) in depth; for this first local install, one shared environment is fine.

JupyterLab vs. classic Notebook — there is only one real choice today

JupyterLab (currently 4.6.x) is the actively developed, modern interface — a file browser, multiple tabs, a built-in terminal, and an extension ecosystem, all in one browser tab. Jupyter Notebook 7 is not a separate legacy product anymore; since version 7 it's rebuilt on the same underlying components as JupyterLab, just presented in the simpler, single-document classic layout. The old "classic Notebook 6" interface is retired — anything you read online referencing it describes a superseded UI, not what installing notebook gives you today. Install JupyterLab for full functionality, or plain Notebook 7 if you specifically want the simpler single-document view; either way, you get the modern engine underneath.

Stage 3 — VS Code + Git: notebooks as part of a real project

Once a notebook is worth keeping — not just a one-off scratch exploration — move it into a git-tracked project and open it in VS Code with the official Jupyter extension (ms-toolsai.jupyter) installed from the Extensions panel. VS Code auto-detects the same kernels your Anaconda/conda or pip install already registered, opens .ipynb files with the same cell-based interface, and gives you the same Shift+Enter loop — but now inside an editor that also has a git-aware sidebar and an integrated terminal, so committing, branching, and reviewing history don't require switching windows.

This stage deliberately comes last. A raw .ipynb committed to git diffs terribly by default (Module 3.2 covers why, and the fix) — that problem only matters once you're actually about to put a notebook under version control, which usually isn't the same day you're still learning what a kernel is. Learn the notebook itself in Colab and Anaconda first; bring in git once there's something worth tracking.

Creating and running your first notebook — the loop is identical everywhere

Whichever of the three you're using, the interaction is the same: choose New notebook (Colab), click Python 3 (ipykernel) under Notebook in JupyterLab's Launcher (Anaconda), or create/open a .ipynb file in VS Code. A new file opens with one empty cell. Type 2 + 2 and press Shift+Enter — the cell executes, prints its result below itself, and a new cell is selected below it. That single interaction is the core loop of every notebook session, on every platform: write code in a cell, execute it, read the result immediately underneath, then move to the next cell.

Common mistake: Assuming closing the browser tab (or VS Code window) stops the notebook. The process backing your notebook (the kernel, Module 1.2) keeps running in the background until you explicitly shut it down — closing the tab just closes the view. Long-running background kernels silently consuming memory is a common surprise for beginners who wonder why their machine is sluggish after a day of notebook work. (Colab's equivalent surprise runs the other way: its runtime disconnects — and wipes all variables — after a period of inactivity, so it's the opposite failure mode of the same underlying concept.)

Module 1.2 — The Notebook Interface & Kernel Model

Skip-check (test-out): Explain, without looking it up, why a variable can exist in a notebook's memory even after the cell that created it has been deleted, and demonstrate restarting a kernel to clear that state.
Skip if: You already understand the kernel as a separate, persistent process from the notebook document, and know the difference between Command and Edit mode.
Unlocks: 1.3, 1.4, 3.1

The notebook document is not the same thing as the kernel

An .ipynb file is a JSON document storing your cells (code, Markdown), their execution outputs, and metadata. The kernel is a completely separate, running Python (or R, Julia, etc.) process that actually executes your code and holds all your variables in memory. This separation explains a behavior that confuses every beginner at least once: deleting a cell from the notebook document does not remove the variables it created from the kernel's memory — those variables persist until you restart the kernel, no matter what the visible notebook looks like now.

Execution count: the only honest record of what actually ran

The number in brackets to the left of a cell (In [7]:) is the kernel's execution count — it increments every time any cell runs, in the order cells were actually executed, not the order they appear in the document. A notebook showing In [3] above In [1] is direct evidence that cells were run out of visual order — exactly the situation that produces "works on my machine" results that silently break the moment someone else opens the file and runs top-to-bottom.

Command mode vs. Edit mode

A cell has a blue left border in Command mode (keyboard shortcuts act on the cell as a whole — dd deletes it, b inserts a new one below) and a green border in Edit mode (you're typing inside the cell itself). Press Esc to leave Edit mode and enter Command mode, Enter to go the other way. Beginners who don't know this distinction often discover it by accident — typing dd while in Command mode on the wrong cell deletes it instantly, with no confirmation dialog.

Common mistake: Believing a notebook that "runs fine" for you interactively will run fine for someone else, when your kernel's memory actually holds leftover variables from cells you ran once, then deleted or reordered. The only real test is Module 3.1's "Restart Kernel and Run All" — anything less is not a genuine reproducibility check.

Markdown cells are what separate a notebook from a script

Change a cell's type with the dropdown in the toolbar (or the keyboard shortcut m in Command mode) to Markdown, then run it with Shift+Enter to render it. This is the mechanism that turns a notebook from "a script with print statements" into a literate document — narrative explanation and executable analysis interleaved in the order a reader actually needs them, not separated into a code file and a README that inevitably drift apart.

Math notation with LaTeX

Jupyter's Markdown cells support inline and display LaTeX math via MathJax, the same $...$ / $$...$$ delimiter convention used in R Markdown and most scientific publishing tools:

The profit margin is $\text{Profit Margin} = \dfrac{\text{Profit}}{\text{Sales}}$.

$$\bar{x} = \frac{1}{n}\sum_{i=1}^{n} x_i$$

This is worth knowing even for non-mathematical notebooks — reporting a formula for a KPI or a statistical test cleanly, instead of as an ASCII approximation, makes the notebook readable as a real analytical document rather than just a code log.

Structuring a notebook top-to-bottom

A well-structured analysis notebook typically follows: a title/purpose Markdown cell, an imports cell, a data-loading cell, then alternating Markdown-explanation and code-analysis cells building toward a conclusion. This isn't cosmetic — a notebook with no structure forces a reader (including future you) to run every cell and read every line of code to find out what it does; clear Markdown section headers let a reader skim the story before deciding which part to actually run.

What magic commands are

The notebook kernel is IPython, an enhanced interactive Python shell, not plain Python — and magic commands (prefixed % for line magics, %% for cell magics) are IPython-specific commands that aren't valid Python syntax on their own. This is why copy-pasting notebook code containing a %-line into a plain .py script and running it with python script.py fails — magics only exist inside an IPython/Jupyter kernel.

The magics worth knowing early

%timeit sum(range(1000))          # benchmarks a single line, averaging many runs

%%time
total = 0
for i in range(1_000_000):
    total += i                     # times an entire cell, once

%matplotlib inline                 # renders matplotlib figures inline in the notebook, not a popup window

%who                                # lists variables currently defined in the kernel
%reset -f                          # clears all variables from kernel memory (use before a clean re-run)

%timeit and %%time answer genuinely different questions: %timeit runs the line many times and reports statistically meaningful average/best timing (correct for benchmarking a fast operation), while %%time times the cell's contents exactly once (correct when the code itself has side effects you don't want repeated, like writing to a file or a database).

Running shell commands from a cell

!pip list | grep pandas
!ls -la ../datasets/superstore-sales

A leading ! passes the rest of the line to the system shell rather than the Python interpreter — genuinely useful for checking installed package versions or inspecting files without leaving the notebook, but it's a shell escape hatch, not a reproducible part of your analysis: a !pip install run once, interactively, doesn't record itself anywhere a colleague opening your notebook later would see it. Module 4.1 covers pinning environment dependencies properly instead of relying on ad hoc !pip install cells.

Common mistake: Treating %matplotlib inline as optional boilerplate copied from an old tutorial. On current JupyterLab it is usually unnecessary (inline rendering is the default), but on some kernel/backend combinations omitting it silently opens plots in a separate window or produces no visible output at all — if a chart isn't appearing, this is the first thing to check.

Retrieval practice: before checking the magics reference above, write from memory the line magic that benchmarks a single line of code by running it many times, and the cell magic that times an entire cell exactly once — then compare.

Why the last line of a cell looks "special"

import pandas as pd
sales = pd.read_csv("superstore_sales.csv")
sales.head()

Jupyter automatically displays the value of a cell's last expression using its richest available representation — for a DataFrame, that's a styled HTML table via a special _repr_html_ method the object defines, not plain text. print(df), by contrast, always produces plain text, because print() bypasses Jupyter's rich-display mechanism entirely and writes directly to stdout. This is why swapping df for print(df) at the end of a cell — a natural habit for anyone coming from script-based Python — quietly downgrades a nicely formatted table into a cramped text dump.

Configuring what pandas actually shows

pd.set_option("display.max_rows", 100)
pd.set_option("display.max_columns", 50)
pd.set_option("display.float_format", "{:.2f}".format)

Without these, pandas silently truncates wide or long DataFrames with a "..." — easy to miss the first few times, and a real problem if you're scanning a table by eye for an outlier that happens to fall in a truncated row.

Displaying multiple rich outputs from one cell

from IPython.display import display

for region in sales["Region"].unique():
    display(sales[sales["Region"] == region].head(3))

Only a cell's last expression auto-displays — calling display() explicitly is how you show more than one rich object (multiple tables, a table and a chart) from a single cell, which a bare last-expression trick can't do.

Disambiguation: "Rich output" (this module's HTML/image/JSON representations Jupyter renders in the notebook) is a different thing from a magic command's plain-text output (Module 1.4) — rich display is about how objects render; magics are IPython commands that may or may not produce rich output themselves.

Static charts with matplotlib and seaborn

import matplotlib.pyplot as plt
import seaborn as sns

fig, ax = plt.subplots(figsize=(8, 4))
sns.lineplot(data=sales.groupby("Order Date")["Sales"].sum().reset_index(),
             x="Order Date", y="Sales", ax=ax)
ax.set_title("Daily Sales Trend")
plt.show()

Calling plt.show() (or simply leaving the figure as the cell's last expression) renders the chart as a static image embedded directly in the notebook's saved output — meaning the chart is visible even to someone who opens the .ipynb file without re-running any code, which matters the moment you share a notebook as a report rather than as executable code.

Interactive charts with Plotly

import plotly.express as px

fig = px.bar(sales.groupby("Region")["Sales"].sum().reset_index(),
             x="Region", y="Sales", title="Total Sales by Region")
fig.show()

Plotly renders as an embedded interactive widget (hover tooltips, zoom, pan) rather than a flat image — the tradeoff is that an interactive Plotly output only stays interactive in contexts that can execute its embedded JavaScript (a live notebook, nbviewer, or a converted HTML export); some static conversion paths (certain PDF exports) flatten it back to an image.

Sizing figures correctly the first time

The most common early frustration is a matplotlib figure that's either too small to read or overflows the notebook's width. Set figsize=(width, height) in inches explicitly on every figure rather than accepting the tiny default — a chart meant to be read, not just glanced at, is rarely legible at matplotlib's default 6.4×4.8 inch size once it's shrunk to fit a notebook cell's output area.

Common mistake: Calling plt.figure() or creating a new figure repeatedly across cells without closing the previous one, then wondering why old, half-finished plots reappear or blank figures accumulate. Use fig, ax = plt.subplots() once per chart and build on ax explicitly — it's far less error-prone than the older implicit-state matplotlib API once a notebook has more than 2–3 charts.

The fastest path to interactivity: @interact

from ipywidgets import interact

@interact(region=sales["Region"].unique().tolist())
def plot_region(region):
    subset = sales[sales["Region"] == region]
    subset.groupby("Order Date")["Sales"].sum().plot(figsize=(8, 4), title=f"Sales Trend — {region}")
    plt.show()

@interact inspects the function's parameters and the values you pass it, and auto-generates the right widget (a dropdown for a list of choices, a slider for a numeric range) — this is the reason it's worth learning before building widgets manually: most exploratory filtering needs are a one-line decorator away, not a custom widget layout.

Manual widgets for more control

import ipywidgets as widgets
from IPython.display import display, clear_output

region_dropdown = widgets.Dropdown(options=sales["Region"].unique().tolist(), description="Region:")
output = widgets.Output()

def on_change(change):
    with output:
        clear_output(wait=True)
        subset = sales[sales["Region"] == change["new"]]
        print(f"Total sales: {subset['Sales'].sum():,.2f}")

region_dropdown.observe(on_change, names="value")
display(region_dropdown, output)

The Output widget plus clear_output(wait=True) is the standard pattern for "redraw this area in place" — without clear_output, every dropdown change would append a new result below the last instead of replacing it, and the notebook would fill with stale, superseded output.

Common mistake: Building an elaborate custom widget layout with Output/observe for a case @interact would have handled in one line. Reach for the manual pattern only once you need multiple linked widgets, custom layout, or state that persists across more than one callback — not by default.

Post-mortem debugging with %debug

def compute_margin(row):
    return row["Profit"] / row["Sales"]

sales["Margin"] = sales.apply(compute_margin, axis=1)

If a row has Sales == 0, this raises a ZeroDivisionError mid-run. Running %debug in the very next cell drops you into an interactive post-mortem debugger at the exact frame where the exception occurred — you can inspect row, check which columns are involved, and confirm the exact cause, instead of guessing from the traceback text alone or re-running with print statements sprinkled in.

Profiling with %prun and %%prun

%prun sales.groupby(["Region", "Category"]).agg({"Sales": "sum", "Profit": "sum"})

%prun runs the cProfile profiler on the expression and reports a function-by-function breakdown of time spent — the correct tool the moment "this cell is slow" needs to become "this specific line inside this cell is slow," rather than guessing which of several operations is the actual bottleneck.

Line-level timing with %%timeit

%%timeit
sales[sales["Region"] == "West"]["Sales"].sum()

Use %%timeit (cell magic) when comparing whole-cell alternatives, and plain %timeit (line magic, Module 1.4) for single-expression comparisons — the distinction matters once a cell contains several lines you don't want individually re-run thousands of times just to benchmark one of them.

Common mistake: Debugging a notebook exception by inserting print() statements, re-running the whole notebook, reading the new output, then deleting the prints — a slow loop compared to %debug's single-shot inspection of the actual failure state.

Module 3.1 — Notebook Hygiene: Restart & Run All

Level: Intermediate · Prereqs: 1.2 · Time: ~1.5h
Skip-check (test-out): Explain precisely why a notebook that "runs fine" interactively can still fail a "Restart Kernel and Run All" check, and identify the two or three most common causes.
Skip if: You already treat "Restart & Run All, no errors, top to bottom" as the non-negotiable definition of "done" for any notebook.
Unlocks: 3.2, 3.3, 3.4

The single most important habit in this entire guide

Before considering any notebook finished — sharing it, committing it, or handing it to a colleague — run Kernel → Restart Kernel and Run All Cells. This is the only way to confirm the notebook is actually reproducible from a clean state, because Module 1.2 established that a kernel's memory can silently hold leftover variables from cells you deleted, reordered, or ran multiple times. A notebook that "just works" when you personally step through it cell by cell proves nothing about whether it works for anyone else, including future-you three months from now.

The most common ways Restart & Run All exposes a broken notebook

  • Hidden order dependency — a later cell references a variable that only exists because an earlier cell (now deleted or moved) once ran first.
  • Stateful side effects run more than once — a cell that appends to a list or increments a counter produces a different result the second time it's re-run versus the first.
  • Environment drift — a package version installed ad hoc via !pip install mid-session isn't actually recorded anywhere a fresh environment would pick up (Module 4.1 fixes this properly).

Automating the check from the command line

jupyter execute notebook.ipynb --output executed.ipynb

Running this in a fresh terminal (fresh kernel, no leftover state from any interactive session) is the closest thing to a genuine reproducibility test, and it's the same underlying mechanism CI systems use to catch a broken notebook before it's merged — Module 3.3 builds on this exact command for parameterized, automated runs.

Common mistake: Treating "no red error text visible right now" as proof a notebook works. The only valid proof is a clean Restart & Run All (or jupyter execute) from a fresh kernel — anything short of that is trusting whatever state happens to currently be sitting in memory.

Module 3.2 — Version Control for Notebooks

Level: Intermediate · Prereqs: 3.1 · Time: ~2h
Skip-check (test-out): Set up either nbstripout or Jupytext pairing on a git-tracked notebook project, and demonstrate a clean, reviewable diff after a code change.
Skip if: You already keep notebook projects under git with a working strategy for clean diffs.
Unlocks: Phase 3 capstone

Why raw .ipynb diffs are unreadable

An .ipynb file is JSON containing not just your code but every cell's output (including binary image data, base64-encoded, for embedded charts) and execution counts. Changing one line of code inside a chart-producing cell regenerates that base64 image blob, so a one-line code change can produce a git diff hundreds of lines long, dominated by unreadable binary noise — making code review on a raw notebook diff nearly useless.

Option 1: nbstripout — strip outputs before every commit

pip install nbstripout
nbstripout --install

This installs a git filter that strips all cell outputs from a notebook automatically at commit time, while your local working copy keeps its outputs untouched. The tracked history then only shows meaningful code changes — at the cost of the repository never storing rendered output, so a reviewer has to actually run the notebook to see results.

Option 2: Jupytext — pair a notebook with a plain-text representation

pip install jupytext
jupytext --set-formats ipynb,py:percent notebook.ipynb

Jupytext keeps a .ipynb and a paired plain .py file (using # %% cell markers) in sync — you edit either one, and the other updates on save. Committing the .py pair instead of (or alongside) the .ipynb gives genuinely clean, line-by-line diffable history, since it's just Python source with comment markers, no JSON, no embedded binary output.

Choosing between them

Use nbstripout when you want to keep working exclusively in .ipynb files with minimal workflow change — it's a one-time setup with almost no new habits to learn. Use Jupytext when the team wants notebooks reviewable like code in a pull request (diffs that read like a code review, not a JSON dump) — it requires committing to the paired-file workflow but produces much better collaboration ergonomics for teams that review each other's analysis.

Common mistake: Committing raw .ipynb files with full outputs to a shared repository "to save time," then having every subsequent PR review buried in unreadable binary diffs. Set up nbstripout or Jupytext on day one of a shared notebook project, not after the repository history is already polluted.

Tagging a parameters cell

In JupyterLab, select a cell (usually near the top, right after imports), open the cell tag panel (View → Right Sidebar → Notebook Tools → Cell Tag), and add the tag parameters. That cell's variable assignments become the notebook's default parameter values:

# Tagged "parameters"
region = "West"
min_date = "2024-01-01"

Papermill works by injecting a new cell directly after the tagged one, overriding these defaults — it never edits the tagged cell itself, so the notebook's default behavior (opened normally, run interactively) is completely unaffected by parameterization.

Executing programmatically

import papermill as pm

for region in ["West", "East", "Central", "South"]:
    pm.execute_notebook(
        "regional_analysis.ipynb",
        f"output_{region.lower()}.ipynb",
        parameters=dict(region=region, min_date="2024-01-01")
    )

Each call executes the full notebook fresh in its own kernel with the given parameters, saving a complete, independently viewable output notebook — this is the mechanism that turns "one analyst manually re-running and re-editing a notebook four times" into "one script producing four correct reports unattended," and it's the same command-line-callable behavior a scheduler (cron, Airflow) can trigger with no human involved.

Command-line equivalent

papermill regional_analysis.ipynb output_west.ipynb -p region West -p min_date 2024-01-01

Common mistake: Parameterizing a notebook that hasn't first passed Module 3.1's Restart & Run All check. Papermill executes from a fresh kernel every time — a notebook that only "worked" because of leftover interactive kernel state will fail (or worse, silently produce wrong output) the moment Papermill runs it clean.

Module 4.1 — Environments & Kernels

Level: Intermediate · Prereqs: 1.2 · Time: ~2h
Skip-check (test-out): Create a new virtual environment, register it as a distinct Jupyter kernel, and switch a notebook between two different kernels, confirming each has an independent package set.

A kernel is bound to an environment, not to JupyterLab itself

JupyterLab is just the interface; each notebook connects to a kernel, and each kernel is backed by a specific Python environment (a venv, conda env, or your system Python) with its own installed packages. Installing every project's dependencies into one shared global environment is the single most common cause of "it worked yesterday, now this notebook is broken" — a later project's conflicting package version silently breaks an earlier project's notebook, because they were never actually isolated from each other.

Registering a project-specific kernel

python -m venv .venv
source .venv/bin/activate
pip install ipykernel pandas matplotlib
python -m ipykernel install --user --name superstore-project --display-name "Python (superstore-project)"

This registers the virtual environment as a selectable kernel in JupyterLab's Launcher and in any notebook's Kernel → Change Kernel menu — "Python (superstore-project)" now appears as its own option, isolated from whatever else is installed globally or in other projects' environments.

Pinning dependencies so the environment itself is reproducible

pip freeze > requirements.txt

A notebook that passes Restart & Run All today can still fail for a colleague six months from now if the packages it depends on have released breaking changes since. A pinned requirements.txt (or a conda environment.yml) committed alongside the notebook is what actually closes that gap — "the notebook runs" is only a meaningful claim relative to a specific, recorded set of package versions.

Common mistake: Running !pip install some-package inside a notebook cell as a substitute for proper environment management. It installs into whatever environment the current kernel happens to be using, doesn't get recorded in any requirements file, and gives a false sense that the dependency is "handled" when it's actually invisible to anyone re-creating the environment from scratch.

GitHub's built-in static preview

Pushing an .ipynb to GitHub gets you a free, automatic static render of the notebook (code, Markdown, and saved outputs) right in the repository browser — no setup required, but it's read-only: a viewer sees exactly what was saved, and cannot execute or modify a single cell.

Google Colab: zero-setup, executable, free compute

A notebook opened via an "Open in Colab" badge (linking to colab.research.google.com/github/<user>/<repo>/blob/main/notebook.ipynb) runs on Google's hosted infrastructure — a recipient with just a Google account can execute every cell with no local Python install at all, including free (rate-limited) GPU access. # https://mybinder.org/v2/gh/<user>/<repo>/HEAD

Binder builds a complete, ephemeral Docker container matching your repository's declared requirements.txt (or environment.yml) and launches JupyterLab inside it — the closest thing to "hand someone your exact environment" without them installing anything locally. It's slower to start (a fresh container build) and the session is temporary (changes aren't saved back to the repo), which makes it right for demos and workshops, not for ongoing collaborative editing.

What JupyterHub actually is

JupyterHub is a multi-user server that spawns, manages, and proxies a separate, isolated JupyterLab (or Notebook) instance per authenticated user — it is not a bigger JupyterLab, it's infrastructure around many single-user JupyterLab instances. Three components matter: the Hub (handles authentication and manages user sessions), the proxy (routes each user's browser traffic to their own private server instance), and a spawner (the pluggable mechanism that actually starts each user's server — a local process, a Docker container, or a Kubernetes pod, depending on deployment scale).

When JupyterHub is the right tool

Reach for JupyterHub once you're responsible for giving a team (not just yourself) reliable, authenticated, isolated notebook access — a classroom, a research group, or a company data team sharing compute resources. It is deliberate overkill for a single person's own analysis work; the operational overhead (authentication setup, a spawner choice, server maintenance) only pays for itself once genuinely multiple users need it.

Module 4.4 — Notebooks vs. Quarto vs. Scripts

Level: Intermediate–Advanced · Prereqs: 3.1, 3.4 · Time: ~1.5h
Skip-check (test-out): Given a real analysis task, correctly identify whether a notebook, a Quarto document, or a plain Python script is the right tool, and justify the choice in one paragraph.

Three tools, three different jobs

A notebook excels at exploration: a tight, forgiving feedback loop for poking at data, checking assumptions, and understanding why a result looks wrong, with state that persists between cells so you don't re-run everything after every small change. A Quarto document (or R Markdown, for R users — see this guide's companion R Markdown guide) is stricter by design: it renders from a clean process every time, acts like a compiler that either produces a coherent report or fails outright, and is the right tool once your analysis logic has stabilized and the deliverable is a polished, shareable report rather than an exploration space. A plain .py script is the right tool once code needs to run unattended in production — a scheduled job, a pipeline step, an imported library — where there's no human present to read cell-by-cell output at all.

Recurring scheduled job, no human watching it runPlain scriptNo notebook server, no cell-execution overhead; runs via cron/Airflow directly
Reusable function called from multiple notebooksPlain script (imported module)A function copy-pasted across notebooks drifts out of sync; import it instead

The pattern that actually resolves the tension

The strongest teams don't pick one tool forever — they move the same work through the pipeline as it matures: explore in a notebook, extract the analysis logic that turned out to matter into a plain .py module once it stabilizes (so it's importable and testable), and either keep a thin notebook that imports and calls that module for further exploration, or migrate the final reporting layer into Quarto/R Markdown for the polished, recurring deliverable. Treating "notebook vs. script vs. Quarto" as a permanent, one-time decision for a whole project is usually the wrong framing — it's a decision made per piece of work, and it changes as that work matures.

Disambiguation: This is not the same choice as Module 3.4's "nbconvert vs. Voila" — that's about exporting an existing notebook for two different audiences. This module is about which authoring tool to start in for a given piece of work in the first place.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Core Concepts

Notebook document (.ipynb)
A JSON file storing a sequence of cells (code, Markdown), their saved outputs, and metadata — the persisted artifact you save, share, and version-control.
Avoid: "Notebook" alone when the distinction from the kernel matters — see Kernel.
Kernel
A separate, running process (IPython for Python) that executes a notebook's code and holds its variables in memory, independent of the notebook document itself.
Avoid: Assuming the kernel resets whenever the notebook document changes — it only resets on an explicit restart.
Execution count
The number shown as In [n]: beside a cell, reflecting the order cells were actually run by the kernel, not their visual order in the document.
Avoid: "Cell number" — that implies document position, not run order.
Magic command
An IPython-specific command, prefixed % (line) or %% (cell), that isn't valid plain Python and only works inside an IPython/Jupyter kernel.
Avoid: Assuming magic-command code will run unmodified if pasted into a plain .py script.
Rich output / display
Jupyter's mechanism for rendering an object's richest representation (HTML, image, JSON) via methods like _repr_html_, shown automatically for a cell's last expression or explicitly via IPython.display.display().
Avoid: Confusing with print() output — print() always writes plain text, bypassing rich display entirely.
Command mode / Edit mode
The two interaction modes for a cell — Command mode (blue border) for cell-level keyboard shortcuts, Edit mode (green border) for typing inside the cell.
Avoid: Assuming Command-mode shortcuts (like dd to delete) require a confirmation dialog — they don't.

Reproducibility & Collaboration

Restart & Run All
The practice of restarting the kernel and executing every cell top to bottom in one pass, the only valid check that a notebook is genuinely reproducible from a clean state.
Avoid: Treating "no errors visible right now" (while interactively stepping through cells) as equivalent proof — it isn't.
nbstripout
A git filter tool that automatically strips all cell outputs from a notebook at commit time, keeping tracked history free of binary output noise.
Avoid: Confusing with Jupytext — nbstripout removes outputs; Jupytext maintains an entirely separate plain-text paired file.
Jupytext pairing
A synchronization between an .ipynb file and a plain-text representation (e.g. .py with %% cell markers) that stays in sync as either file is edited and saved.
Avoid: "Notebook export" — pairing is a live, two-way sync, not a one-time conversion.
Parameterized notebook
A notebook with a cell tagged parameters, whose variable defaults can be overridden at execution time by a tool like Papermill without editing the notebook by hand.
Avoid: "Templated notebook" — not the standard term in this ecosystem; use "parameterized."
Papermill
A tool that executes a notebook programmatically with injected parameter overrides, producing a fully executed, independently viewable output notebook per run.
Avoid: Assuming Papermill edits the original notebook's tagged cell — it injects a new cell after it instead.

Sharing & Deployment

nbconvert
The tool (and library) that converts a notebook to another format — HTML, PDF, a plain script, and more — optionally re-executing it fresh first with the --execute flag.
Avoid: Assuming a converted export always reflects current data — without --execute, it exports whatever outputs were last saved.
Voila
A tool that serves a notebook as a live, interactive web application, keeping widget reactivity while hiding every code cell from the viewer.
Avoid: "Dashboard" alone — Voila specifically runs the underlying notebook's kernel live; a static export has no running kernel at all.
Kernel spec
The registered configuration (via ipykernel install) that makes a specific Python environment selectable as a named kernel in Jupyter's interface.
Avoid: Assuming installing a package updates every kernel — it only affects the specific environment that kernel spec points to.
JupyterHub
A multi-user server that authenticates users and spawns an isolated, single-user JupyterLab instance per person, via a pluggable spawner (local process, Docker, Kubernetes).
Avoid: Treating JupyterHub as "JupyterLab for more people" — it's separate infrastructure surrounding many isolated single-user instances, not a shared multi-user editing session.
Binder
A service that builds an ephemeral, reproducible container from a git repository's declared dependencies and launches a temporary JupyterLab session inside it.
Avoid: Assuming a Binder session persists changes back to the source repository — sessions are temporary and unsaved by default.
