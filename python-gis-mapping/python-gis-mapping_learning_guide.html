How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Use the Placement Quiz below to find your entry point, or jump straight to any module using the Module Index. Every exercise and capstone uses the same realistic TindaHub Orders scenario — the same 5,000-row Philippine sari-sari-store distribution order register used elsewhere in this workspace, extended here with a small bundled city-coordinate lookup so every order and customer can be placed on a map.

Scope note: this guide assumes you already write everyday Python and pandas — DataFrames, merge, groupby, reading a CSV. If that's shaky, work through the Python Learning Guide and the pandas modules of the Data Analyst guide first. This guide starts where those stop: turning tabular rows into actual geometry, and geometry into maps. Shapely gives you the geometric objects and operations; GeoPandas puts those geometries into pandas-shaped tables with coordinate-system awareness, spatial joins, and static plotting; Folium turns the result into an interactive, web-embeddable map. Statistical or ML modeling of spatial data (spatial autocorrelation, kriging, point-pattern statistics) is out of scope — this guide is about representing, joining, and visualizing location data correctly, not spatial statistics.

Level: Beginner–Intermediate · Prereqs: None (comfortable writing everyday Python) · Time: ~2h
Skip-check (test-out): Create a Point, a LineString, and a Polygon from coordinate tuples, and explain what .wkt and .bounds return for each.
Skip if: You already default to Shapely for representing coordinates, shapes, and boundaries.
Unlocks: Module 1.2, Module 2.1

Why Shapely exists: geometry as first-class objects

A latitude/longitude pair stored as two plain floats can't answer "is this point inside that boundary" or "how far apart are these two shapes" without you hand-rolling the math. Shapely wraps coordinates into real geometric objects — Point, LineString, Polygon, and their Multi- variants — backed by GEOS, the same battle-tested C++ geometry engine used by PostGIS and QGIS. Once a coordinate is a Shapely object rather than a bare tuple, every spatial question (Module 1.2) and operation (Module 1.3) becomes a method call instead of a from-scratch math problem.

from shapely.geometry import Point, LineString, Polygon

manila = Point(120.9842, 14.5995)          # (lon, lat) — Shapely is x, y, i.e. lon, lat
route = LineString([(120.9842, 14.5995), (121.0244, 14.5547)])  # Manila → Makati
service_area = Polygon([
    (120.95, 14.55), (121.05, 14.55), (121.05, 14.65), (120.95, 14.65)
])

print(manila.wkt)          # 'POINT (120.9842 14.5995)' — Well-Known Text
print(route.length)        # straight-line length in coordinate units (degrees here — see Module 2.2)
print(service_area.bounds) # (minx, miny, maxx, maxy) bounding box
print(service_area.area)   # area in coordinate units² — not square meters until reprojected

Common mistake: passing (latitude, longitude) instead of (longitude, latitude). Shapely, like most geometry libraries, orders coordinates as (x, y) — and geographic x is longitude, y is latitude. Swap them and every point silently lands in the wrong hemisphere-adjacent location without any error being raised.

Multi-part geometries

Real-world features often aren't a single contiguous shape — a province made of several islands, a delivery network with disconnected route segments. MultiPoint, MultiLineString, and MultiPolygon hold a collection of same-type geometries as one logical object, which matters because a GeoPandas column (Module 2.1) expects one geometry value per row, even when that row's true shape is multi-part.

from shapely.geometry import MultiPoint

tindahub_hub_cities = MultiPoint([(120.9842, 14.5995), (123.8854, 10.3157), (125.4553, 7.1907)])
print(tindahub_hub_cities.geoms[0])   # access individual Point members via .geoms

WKT and WKB: how geometries move between systems

WKT (Well-Known Text) is the human-readable string form of a geometry ("POINT (120.9842 14.5995)"); WKB (Well-Known Binary) is its compact binary form, used when geometries are stored in a database column or a file format. Both are round-trippable with shapely.from_wkt/.wkt and shapely.from_wkb/.wkb — the format that lets a geometry created in Shapely be written to a file and read back identically later.

Skip if: These four predicates and the difference between them are already second nature.
Unlocks: Module 1.3, Module 1.4, Module 2.3

The core predicates

Shapely's spatial predicates answer yes/no questions about how two geometries relate. a.intersects(b) is true if they share any point at all (including just touching at an edge); a.contains(b) is true if b is entirely inside a with no boundary touching; a.within(b) is the mirror of contains (true if a is entirely inside b); a.touches(b) is true only if they share a boundary point but no interior points. Getting contains and intersects confused is the single most common spatial-predicate bug: a point sitting exactly on a polygon's edge satisfies intersects but not contains, which matters for edge-case delivery addresses sitting exactly on a zone boundary.

from shapely.geometry import Point, Polygon

zone = Polygon([(120.95, 14.55), (121.05, 14.55), (121.05, 14.65), (120.95, 14.65)])
inside_point = Point(121.00, 14.60)
edge_point = Point(120.95, 14.60)          # exactly on the zone's left edge
outside_point = Point(121.20, 14.60)

print(zone.contains(inside_point))    # True
print(zone.contains(edge_point))      # False — boundary points don't count as "contained"
print(zone.intersects(edge_point))    # True — touching the boundary is enough for intersects
print(zone.contains(outside_point))   # False

Common mistake: using intersects when you meant contains (or vice versa) for a point-in-polygon check. If an address sits exactly on a delivery-zone boundary, intersects counts it as served and contains does not — pick deliberately based on whether boundary-exact cases should count, don't default to whichever one you remember first.

distance and nearest relationships

a.distance(b) returns the shortest distance between two geometries (0 if they intersect), in whatever units the coordinates are in — degrees for unprojected lon/lat data, which is rarely what you actually want for a real distance (Module 2.2 covers projecting to get meters). For finding the closest of many candidates, shapely.ops.nearest_points returns the actual closest point pair, not just the distance.

from shapely.ops import nearest_points
from shapely.geometry import Point

customer = Point(121.05, 14.58)
hub_a = Point(120.9842, 14.5995)   # Manila hub
hub_b = Point(121.0244, 14.5547)   # Makati hub

nearer_hub = min([hub_a, hub_b], key=lambda h: customer.distance(h))
p1, p2 = nearest_points(customer, hub_b)

Module 1.3 — Geometric Operations: Buffer, Union, Intersection, Simplify

buffer: growing a shape outward

geometry.buffer(distance) returns a new polygon expanded outward by distance in every direction — the standard way to represent "everything within X of this point/line/shape," such as a delivery hub's coverage radius or a road's right-of-way. The distance is in the geometry's own coordinate units, which is exactly why buffering directly on unprojected lon/lat coordinates is a trap: 0.05 degrees is roughly 5.5 km near the equator but noticeably less further from it, so the same buffer distance means a different real-world radius depending on latitude. Module 2.2 covers projecting to a metric CRS before buffering for anything where the real distance matters.

from shapely.geometry import Point

hub = Point(120.9842, 14.5995)          # Manila hub, in degrees (unprojected)
rough_coverage = hub.buffer(0.05)        # ~5.5 km-ish near Manila — approximate, don't trust for precise work
print(rough_coverage.area)

union, intersection, difference

These three set-like operations combine two geometries: a.union(b) is everything covered by either; a.intersection(b) is only the overlapping area; a.difference(b) is a with b's area removed. For combining many geometries at once (e.g., unioning all 17 cities' buffer zones into one coverage footprint), shapely.ops.unary_union is far more efficient than folding .union() in a Python loop.

from shapely.ops import unary_union
from shapely.geometry import Point

zone_a = Point(121.00, 14.60).buffer(0.08)
zone_b = Point(121.05, 14.62).buffer(0.08)

overlap = zone_a.intersection(zone_b)     # area served by both hubs — a candidate for consolidation
combined = unary_union([zone_a, zone_b])  # total footprint served by either hub
exclusive_a = zone_a.difference(zone_b)   # area only zone_a covers

simplify: reducing vertex count

geometry.simplify(tolerance) reduces a polygon or line's vertex count while staying within tolerance distance of the original shape (Douglas-Peucker algorithm) — useful when a boundary file has far more detail than a given map's zoom level needs, since fewer vertices means faster rendering and smaller file sizes, especially noticeable once you're pushing GeoJSON to a Folium map (Phase 3).

Level: Intermediate · Prereqs: Module 1.2 · Time: ~2h
Skip-check (test-out): Build an STRtree from a list of geometries and use .query() to find candidates near a target, explaining why this is faster than checking every geometry in a loop.

Why brute-force point-in-polygon checks don't scale

Checking whether a point falls inside any of N polygons by looping and testing polygon.contains(point) for every polygon is O(N) per point — fine for the 3 hub zones in Exercise 1.3, but a real bottleneck once N is in the hundreds or thousands (all Philippine municipalities, say) and you're checking thousands of points against them. A spatial index pre-organizes geometries by location so a query only has to check a small, spatially-relevant subset rather than everything.

from shapely import STRtree
from shapely.geometry import Point

candidate_zones = [Point(121.0 + i * 0.01, 14.6).buffer(0.02) for i in range(500)]
tree = STRtree(candidate_zones)

query_point = Point(121.15, 14.6)
nearby_indices = tree.query(query_point)              # fast: only spatially-plausible candidates
actual_hits = [i for i in nearby_indices if candidate_zones[i].contains(query_point)]

tree.query() returns candidates whose bounding boxes are near the query geometry — a fast, approximate first pass. It does not guarantee an actual contains/intersects match, so a precise predicate check on the returned candidates (as above) is still required; skipping that second check is a common correctness bug once a spatial index is introduced.

GeoDataFrame: a DataFrame with one geometry-typed column

A GeoDataFrame is a pandas DataFrame with one column (by convention named geometry) holding Shapely geometry objects instead of numbers or strings, plus CRS metadata (Module 2.2) attached to the whole table. Every pandas operation you already know — merge, groupby, boolean filtering — still works, because GeoDataFrame subclasses DataFrame; the geometry column just adds spatial methods (.distance(), .buffer(), .plot()) on top.

import geopandas as gpd
import pandas as pd
from shapely.geometry import Point

cities = pd.read_csv("tindahub_city_coords.csv")
cities_gdf = gpd.GeoDataFrame(
    cities,
    geometry=gpd.points_from_xy(cities["Lon"], cities["Lat"]),
    crs="EPSG:4326"          # WGS84 — the standard lat/lon CRS; see Module 2.2
)
print(cities_gdf.geometry.iloc[0])   # a real Shapely Point, not a string
print(type(cities_gdf))              # geopandas.geodataframe.GeoDataFrame

gpd.points_from_xy is the fast, vectorized way to build a whole geometry column from x/y arrays — far preferable to constructing a Python list of Point objects in a loop for anything beyond a handful of rows.

Reading and writing files: pyogrio is the current default engine

As of GeoPandas 1.0, pyogrio is the default engine behind gpd.read_file() and .to_file(), replacing the older fiona-based default — pyogrio is measured at 5–20x faster for bulk reads and writes, which matters once a boundary file has thousands of features. This guide's GeoPandas is 1.1.x, where you don't need to do anything to get pyogrio; it's automatic. If you're following an older tutorial that explicitly imports or configures fiona, that's a pre-1.0 pattern — not wrong, just outdated as the default.

import geopandas as gpd

# GeoJSON, Shapefile, GeoPackage — gpd.read_file auto-detects format, uses pyogrio by default
provinces = gpd.read_file("ph_provinces.geojson")
cities_gdf.to_file("tindahub_cities.gpkg", driver="GPKG")   # GeoPackage: the modern preferred format over .shp

Common mistake: defaulting to the legacy Shapefile format (.shp) for new work. A Shapefile is actually a bundle of 3+ separate files (.shp, .shx, .dbf, ...) that must all travel together, truncates column names to 10 characters, and has no native CRS storage without a companion .prj file. GeoPackage (.gpkg, a single SQLite-based file) or GeoJSON avoid all three problems and are the better default for anything you're creating today.

Module 2.2 — Coordinate Reference Systems & Reprojection

Level: Intermediate · Prereqs: Module 2.1 · Time: ~3h
Skip-check (test-out): Explain the difference between a geographic and a projected CRS, reproject a GeoDataFrame to a metric CRS with .to_crs(), and compute a real-world distance in meters/kilometers.
Skip if: CRS concepts and .to_crs() are already comfortable.
Unlocks: Module 2.3, Module 2.4, Module 4.2

Geographic vs. projected CRS

A geographic CRS (like EPSG:4326/WGS84) expresses positions as angles — degrees of latitude and longitude on a sphere/ellipsoid — and is what GPS coordinates come in. A projected CRS flattens that sphere onto a 2D plane using a specific mathematical projection, expressing positions in linear units (usually meters), which is what makes area, distance, and buffer calculations behave the way you'd intuitively expect. Every geometric measurement in Module 1.3 (buffer, area, distance) computed on unprojected lon/lat data was returning values in degrees, not meters — technically correct, practically meaningless for real-world distance.

EPSG codes and choosing a projection

Every CRS has a standard EPSG code identifying it precisely (EPSG:4326 for WGS84 lon/lat, EPSG:3857 for Web Mercator used by most web maps, EPSG:32651 for UTM Zone 51N, which covers most of the Philippines with good local accuracy for area/distance work). The choice matters: Web Mercator is fine for web-map display but distorts area badly at higher latitudes, so it's a poor choice for actual area/distance measurement — a locally-appropriate UTM zone is the better choice when the numbers themselves need to be trustworthy, not just visually reasonable.

import geopandas as gpd

cities_gdf = gpd.GeoDataFrame(
    {"City": ["Manila", "Cebu City"]},
    geometry=gpd.points_from_xy([120.9842, 123.8854], [14.5995, 10.3157]),
    crs="EPSG:4326"
)

print(cities_gdf.crs)                     # EPSG:4326 — degrees
manila_pt = cities_gdf.geometry.iloc[0]
cebu_pt = cities_gdf.geometry.iloc[1]
print(manila_pt.distance(cebu_pt))        # a number in degrees — not meaningful on its own

utm_gdf = cities_gdf.to_crs("EPSG:32651")  # reproject to UTM Zone 51N — meters now
manila_utm = utm_gdf.geometry.iloc[0]
cebu_utm = utm_gdf.geometry.iloc[1]
distance_km = manila_utm.distance(cebu_utm) / 1000
print(f"{distance_km:.0f} km")             # a real, trustworthy distance

Common mistake: calling .buffer(), .distance(), or .area on a GeoDataFrame still in EPSG:4326 and treating the result as meters or square meters. It isn't — it's degrees. Always .to_crs() to an appropriate projected CRS first when the actual real-world magnitude of a measurement matters, not just its relative comparison.

sjoin: joining on spatial relationship, not a shared key

A normal pandas merge joins rows where a column value matches exactly (e.g., City == City). A spatial join (geopandas.sjoin) joins rows based on a spatial relationship between their geometries instead — "which polygon contains this point," "which points fall within this buffer" — with no shared key column required at all. This is the tool for attaching a boundary's attributes (province name, region) to a set of points purely by location.

import geopandas as gpd

points_gdf = gpd.GeoDataFrame(
    {"City": ["Manila", "Cebu City"]},
    geometry=gpd.points_from_xy([120.9842, 123.8854], [14.5995, 10.3157]),
    crs="EPSG:4326"
)
provinces_gdf = gpd.read_file("ph_provinces.geojson")   # polygons with a "PROVINCE" column

joined = gpd.sjoin(points_gdf, provinces_gdf, how="left", predicate="within")
print(joined[["City", "PROVINCE"]])

The predicate argument accepts the same relationships from Module 1.2 ("intersects", "within", "contains", ...) — choosing the wrong one produces the same boundary-edge-case bugs discussed there, now silently affecting an entire joined table instead of one manual check.

Combining a spatial join with a normal attribute join

A typical real workflow chains both: spatially join points to polygons to attach a region/province label, then use that label to do a normal pandas groupby or attribute merge against a non-spatial table (like sales-by-province targets).

folium.Map: a Leaflet map in one line

Folium is a thin, Pythonic wrapper around Leaflet.js, the JavaScript library behind most interactive web maps you've ever used. Calling folium.Map() produces an object that, when saved or displayed, renders as a real pannable, zoomable web map — no JavaScript required, though the output is an HTML/JS file under the hood, which is what makes it trivially shareable or embeddable.

import folium

m = folium.Map(location=[14.5995, 120.9842], zoom_start=11)   # centered on Manila; note (lat, lon) here — Folium's order, opposite Shapely's
folium.Marker(
    location=[14.5995, 120.9842],
    popup="Manila Hub — 1,204 orders this month",
    tooltip="Click for details"
).add_to(m)
m.save("tindahub_manila_hub.html")

Disambiguation: Folium takes coordinates as (lat, lon), the opposite order from Shapely/GeoPandas's (lon, lat)/(x, y) convention. Both conventions are individually correct within their own library; the trap is copying a Shapely (x, y) tuple straight into a Folium call (or vice versa) and getting a point that's silently rotated 90 degrees off, or in the wrong hemisphere. Always check which order a specific function expects.

Popups vs. tooltips

A popup opens on click and stays open until dismissed — good for detailed information the user chooses to inspect. A tooltip shows on hover and disappears immediately — good for a quick label that doesn't require a click. Both accept HTML content, not just plain text, which lets a popup show a small formatted table or an embedded chart image.

popup_html = """
Manila Hub

Orders this month: 1,204

Revenue: ₱487,300
"""
folium.Marker(
    location=[14.5995, 120.9842],
    popup=folium.Popup(popup_html, max_width=250),
    tooltip="Manila Hub"
).add_to(m)

FeatureGroup and LayerControl: toggleable layers

A folium.FeatureGroup is a named container for a set of map elements that can be shown or hidden together via a folium.LayerControl toggle — the standard way to let a map viewer switch between, say, "Delivered orders" and "Cancelled orders" without cluttering the view with both at once.

import folium

m = folium.Map(location=[12.5, 122.0], zoom_start=6)

delivered_layer = folium.FeatureGroup(name="Delivered orders")
cancelled_layer = folium.FeatureGroup(name="Cancelled orders")

folium.CircleMarker(location=[14.5995, 120.9842], radius=6, color="#0d7a6e", fill=True).add_to(delivered_layer)
folium.CircleMarker(location=[10.3157, 123.8854], radius=6, color="#ff6b47", fill=True).add_to(cancelled_layer)

delivered_layer.add_to(m)
cancelled_layer.add_to(m)
folium.LayerControl(collapsed=False).add_to(m)   # must be added AFTER all layers, or new ones won't appear in it

Common mistake: adding LayerControl before all the layers it should control. Folium builds the control's list from whatever's on the map at the moment .add_to(m) is called on the control itself — layers added afterward won't show up in the toggle list, even though they're still on the map.

MarkerCluster: keeping hundreds of markers readable

Plotting one marker per order across 5,000 rows produces an unreadable wall of overlapping pins at any reasonable zoom level. folium.plugins.MarkerCluster groups nearby markers into a single numbered cluster icon that expands as the viewer zooms in — the standard fix for exactly this problem, and one of the plugins bundled with Folium itself (from folium.plugins import MarkerCluster).

from folium.plugins import MarkerCluster
import folium

m = folium.Map(location=[12.5, 122.0], zoom_start=6)
cluster = MarkerCluster(name="All orders").add_to(m)

for lat, lon, city in [(14.5995, 120.9842, "Manila"), (10.3157, 123.8854, "Cebu City")]:
    folium.Marker(location=[lat, lon], tooltip=city).add_to(cluster)

folium.Choropleth: GeoJSON in, colored regions out

folium.Choropleth takes a GeoJSON-shaped input (a GeoDataFrame works directly, or a file path) and a pandas DataFrame of values, joining them on a shared key field, then renders a color-shaded polygon layer on the map — the interactive counterpart to Module 2.4's static .plot(column=...). The most common setup mistake is a mismatch between the key_on field (which must reference the GeoJSON's feature property path, prefixed "feature.properties.") and the actual column name in the data being joined.

import folium
import geopandas as gpd
import pandas as pd

provinces_gdf = gpd.read_file("ph_provinces_approx.geojson")   # has a "PROVINCE" property
revenue_by_province = pd.DataFrame({
    "PROVINCE": ["Metro Manila", "Cebu", "Davao del Sur"],
    "revenue": [487300, 298400, 176200]
})

m = folium.Map(location=[12.5, 122.0], zoom_start=6)
folium.Choropleth(
    geo_data=provinces_gdf,
    data=revenue_by_province,
    columns=["PROVINCE", "revenue"],
    key_on="feature.properties.PROVINCE",     # must match the GeoJSON property name exactly, including case
    fill_color="YlGnBu",
    legend_name="Total Revenue (₱)"
).add_to(m)

Common mistake: a key_on value that doesn't exactly match the GeoJSON property name (including case and whitespace) — the choropleth silently renders with no color at all (every region defaults to the same shade) rather than raising an error, since unmatched joins are just treated as missing data.

What geocoding actually does

Geocoding converts a human-readable address or place name ("Barangay Poblacion, Calamba, Laguna") into coordinates; reverse geocoding does the opposite. GeoPandas doesn't geocode itself — it delegates to the geopy library's geocode() function, which in turn calls an external service (Nominatim/OpenStreetMap by default, free but rate-limited; commercial providers for higher volume).

import geopandas as gpd

addresses = ["Barangay Poblacion, Calamba, Laguna, Philippines", "Barangay Rizal, Cebu City, Philippines"]
geocoded = gpd.tools.geocode(addresses, provider="nominatim", user_agent="tindahub-guide-exercise")
print(geocoded[["geometry", "address"]])

This single call actually issues one HTTP request per address to a shared public service — which is exactly why it needs to be rate-limited (Nominatim's usage policy caps request frequency) and why results should be cached locally rather than re-geocoded on every script run. For this guide's own exercises, the bundled tindahub_city_coords.csv exists precisely to avoid needing live geocoding calls for the running example — a real project would geocode once, save the result, and treat that saved file the same way this guide treats the bundled CSV.

Common mistake: geocoding the same address list repeatedly across script re-runs instead of caching results. Beyond wasting time on redundant network calls, this risks tripping a free provider's rate limit and getting temporarily blocked — geocode once, persist the result (CSV, GeoPackage, database), and load from that thereafter.

Geocoding accuracy and ambiguity

Geocoding results are only as good as the input address's specificity and the provider's data coverage for that region — a barangay-level address in a smaller Philippine municipality may resolve only to municipality-level accuracy (or fail entirely), which is worth explicitly checking (e.g., inspecting the returned address string) rather than assuming every geocoded point is precise to the street.

The full pipeline, combined

This module is deliberately just an application of Phases 1–3's tools in sequence, on a slightly harder version of the same problem: Shapely builds and measures the geometry (buffers, real projected distances), GeoPandas holds the tabular-plus-spatial data and performs the join, and Folium renders the interactive result for a non-technical stakeholder to actually look at.

import geopandas as gpd
import folium
from folium.plugins import MarkerCluster

# 1. Shapely/GeoPandas: real (projected) coverage buffers around 3 hubs
hubs_gdf = gpd.GeoDataFrame(
    {"hub_name": ["Manila Hub", "Cebu Hub", "Davao Hub"]},
    geometry=gpd.points_from_xy([120.9842, 123.8854, 125.4553], [14.5995, 10.3157, 7.1907]),
    crs="EPSG:4326"
).to_crs("EPSG:32651")
hubs_gdf["coverage"] = hubs_gdf.geometry.buffer(150_000)   # a real 150 km radius, in meters
coverage_gdf = hubs_gdf.set_geometry("coverage")

# 2. GeoPandas: spatial join assigning every city to a hub's coverage
cities_gdf = gpd.read_file("tindahub_cities.gpkg").to_crs("EPSG:32651")
assigned = gpd.sjoin(cities_gdf, coverage_gdf[["hub_name", "coverage"]].set_geometry("coverage"),
                      how="left", predicate="within")

# 3. Folium: render the assignment back in EPSG:4326 (Folium expects lat/lon)
assigned_wgs84 = assigned.to_crs("EPSG:4326")
m = folium.Map(location=[12.5, 122.0], zoom_start=6)
cluster = MarkerCluster().add_to(m)
for _, row in assigned_wgs84.iterrows():
    folium.Marker(
        location=[row.geometry.y, row.geometry.x],
        popup=f"{row['City']} → {row.get('hub_name', 'Unassigned')}"
    ).add_to(cluster)
m.save("tindahub_zone_assignment.html")

Level: Intermediate · Prereqs: at least one module from each of Phases 1–3 · Time: ~1.5h

A decision framework

QuestionToolWhy
Need to construct or test a single geometric object/relationship, no table involved?ShapelyThe lightweight geometry primitive layer everything else is built on.
Have (or need) many geometries alongside tabular attributes?GeoPandasPandas-native table with CRS-aware geometry column, joins, and file I/O.
Need to join data by spatial relationship instead of a shared key?GeoPandas sjoinPurpose-built; a plain pandas merge can't join on "is inside."
Need a real-world distance, area, or buffer radius?GeoPandas .to_crs() to a projected CRS, then Shapely opsUnprojected lon/lat measurements are in degrees, not meters.
Need a polished static map for a report or document?GeoPandas .plot() + contextilyMatplotlib-based, print-quality, no browser needed.
Need a pannable/zoomable map a non-technical stakeholder can click around in?FoliumReal interactivity via Leaflet.js; shareable as one HTML file.
Need to convert an address into coordinates?geopy via gpd.tools.geocodeNot built into core GeoPandas; calls an external geocoding service.

The throughline: geometry, then table, then presentation

Across this whole guide, the natural order is Shapely (define what a shape is and how shapes relate) → GeoPandas (attach shapes to real tabular data, handle projections and joins correctly) → Folium or contextily (present the result to a human, interactively or statically). Skipping straight to a map without getting the CRS and join logic right underneath it is the single most common source of a beautiful-looking map with a wrong answer baked in — a choropleth can render perfectly while joining on a mismatched key or measuring unprojected degrees as if they were kilometers, and nothing about the visual output will tell you that happened.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Shapely Geometry

Point / LineString / Polygon
Shapely's three core single-part geometry types: a single coordinate, an ordered sequence of connected coordinates, and a closed area bounded by an ordered coordinate ring, respectively.
Avoid: "coordinate" as a substitute for "Point" — a coordinate is a raw (x, y) pair; a Point is the Shapely object wrapping one, with spatial methods attached.
Spatial predicate
A method that answers a yes/no question about how two geometries relate (e.g., intersects, contains, within, touches).
Avoid: treating "intersects" and "contains" as interchangeable — they disagree precisely on boundary-touching cases.
Buffer
A new polygon representing every point within a given distance of a source geometry.
Avoid: assuming a buffer distance on unprojected (lon/lat) coordinates is a real-world distance — it's in degrees unless the geometry has been reprojected first.
WKT / WKB
Well-Known Text and Well-Known Binary: the standard human-readable and binary serialization formats for a geometry, used to move geometries between libraries, files, and databases.
Avoid: confusing WKT/WKB with GeoJSON — GeoJSON is a separate, JSON-based format also capable of encoding geometry, commonly used for web maps.
Spatial index (STRtree)
A data structure that organizes geometries by location so a spatial query only has to check a small, relevant subset instead of every geometry in a collection.
Avoid: assuming an index query alone confirms an exact spatial match — it returns fast candidates that still need a precise predicate check.

GeoPandas & CRS

GeoDataFrame
A pandas DataFrame subclass with one designated geometry-typed column and CRS metadata attached to the whole table.
Avoid: "spatial DataFrame" as a casual substitute — GeoDataFrame is the specific, correctly-cased class name.
CRS (Coordinate Reference System)
The specific system, including its unit of measurement and reference surface, that gives a geometry's coordinates real-world meaning.
Avoid: "projection" as a strict synonym — a geographic CRS (like WGS84) isn't a projection at all; "projected CRS" is the narrower term for CRSes that flatten the earth onto a plane.
EPSG code
A standardized numeric identifier for one specific CRS (e.g., EPSG:4326 for WGS84 lon/lat).
Avoid: assuming all EPSG codes use the same coordinate order or unit — each CRS defines its own.
Spatial join (sjoin)
A join between two GeoDataFrames based on the spatial relationship between their geometries, rather than a matching key column.
Avoid: "merge" as a substitute term — pandas merge requires a shared key column and has no concept of spatial relationship.
Choropleth
A map where regions are shaded according to a data value associated with each region.
Avoid: "heat map" as a synonym — a heat map typically shades continuous density from point data, not discrete regions from a joined attribute.

Folium & Web Mapping

Leaflet.js
The JavaScript mapping library that Folium generates code for; Folium itself never renders a map directly, it emits Leaflet-compatible HTML/JS.
Avoid: describing Folium as "a mapping engine" — it's a Python code generator for Leaflet, not a rendering engine in its own right.
Tile layer
The base imagery (roads, labels, terrain) a map is drawn on top of, served as small image tiles from a provider (OpenStreetMap, CartoDB, etc.).
Avoid: "basemap" as a strict synonym in Folium's own API — Folium's class is specifically named TileLayer, though "basemap" is fine as a general descriptive term.
FeatureGroup
A named container grouping Folium map elements so they can be shown, hidden, or toggled together as one unit.
Avoid: confusing a FeatureGroup with a LayerControl — the group holds elements; the control is the separate UI widget that lets a viewer toggle groups on/off.
GeoJson layer
A Folium layer rendering raw GeoJSON (or a GeoDataFrame) directly onto the map, without the data-joining behavior Choropleth adds on top.
Avoid: reaching for folium.Choropleth when you just need to draw shapes with no associated data-driven coloring — plain folium.GeoJson is simpler for that case.
