Phase 1: Sheets Power Foundations

Weeks 1–3 | Goal: run TindaTrack's daily operations from a clean, formula-driven workbook

Module 1.1 — Spreadsheet Fundamentals & Data Hygiene

Level: Beginner · Prereqs: None · Time: ~4h
Skip-check (test-out): Build a sheet with a native Table, a dropdown from a range, a date-format column, and conditional formatting that highlights overdue rows — in under 20 minutes.
Skip if: You already keep structured, validated data in Sheets and know the difference between a Table and a formatted range.
Unlocks: 1.2, 3.1, 4.1

Structure before features

Everything later in this guide — formulas, Apps Script, AppSheet, the web app — assumes your data is shaped like a database table: one header row, one record per row, one value per cell, no merged cells, no blank separator rows. This is the single highest-leverage habit in the whole guide. A "pretty" sheet with merged headers and subtotal rows mixed into the data will break QUERY, confuse AppSheet's schema detection, and force every script you write to special-case junk rows.

Set up the TindaTrack workbook now. Create a spreadsheet named TindaTrack with four sheets and these headers in row 1:

Products : SKU | Name | Category | UnitPrice | StockQty | ReorderLevel
Customers: CustomerID | StoreName | OwnerName | Barangay | City | Phone | JoinedDate
Orders   : OrderID | OrderDate | CustomerID | SKU | Qty | UnitPrice | LineTotal | Status | DeliveredDate
Payments : PaymentID | OrderID | PaidDate | Amount | Method | Reference

Seed at least 15 products, 10 customers, 60 order rows, and 30 payments — realistic values, Philippine peso prices, statuses drawn from Pending / Packed / Delivered / Cancelled. You will reuse this exact workbook in every exercise through the Final Capstone.

Native Tables, validation, and formats

Convert each range to a native Table (Format → Convert to table). Tables — a 2024+ feature now central to Sheets — give you column types, per-column filters, alternating colors, and structured references like Orders[Status], and both AppSheet and Gemini-powered features read them more reliably than loose ranges. If you paste unformatted data, current Sheets versions will even offer a Gemini-powered "Convert to table" prompt.

Then lock the data down with data validation (Data → Data validation): Status becomes a dropdown from a list, CustomerID in Orders a dropdown from the Customers range, dates get date validation. Validation is not cosmetic: every typo it prevents is a bug you will not have to debug in Phase 2's scripts or Phase 3's API, because "Deliverd" silently fails every filter that looks for "Delivered".

Finish with number formats (₱ currency: custom format "₱"#,##0.00), conditional formatting (highlight Orders rows where Status = "Pending" and OrderDate is more than 7 days old), and named ranges for anything scripts will reference later.

Collaboration primitives

Learn the sharing model deliberately — it becomes your web app's security model in Phase 3. Practice: share with view-only vs. editor roles, protect the Products sheet so only you can edit it, use comments with @-mentions, and inspect Version history (File → Version history) to restore a prior state. Smart chips (@ to insert people, files, dates) and the Payments sheet's date chips make the workbook self-documenting.

Module 1.2 — Formulas That Do the Work

Level: Beginner · Prereqs: 1.1 · Time: ~6h
Skip-check (test-out): Without documentation, write an XLOOKUP joining Orders to Products, a SUMIFS of delivered revenue per customer, and one LET+LAMBDA formula.
Skip if: You already reach for XLOOKUP/SUMIFS/ARRAYFORMULA by instinct and have used LET at least once.
Unlocks: 1.3, 2.1

The lookup family — joining tables

Spreadsheet "joins" are lookups. Use XLOOKUP as your default — it replaces the older VLOOKUP pattern, searches any direction, and has a built-in not-found argument, which matters because an unhandled #N/A propagates into every formula downstream and later into scripts that read the cell:

=XLOOKUP(D2, Products[SKU], Products[Name], "UNKNOWN SKU")

=XLOOKUP(C2, Customers[CustomerID], Customers[StoreName], "?")

' Multi-column pull in one spill:
=XLOOKUP(D2, Products[SKU], Products[Name]:Products[UnitPrice])

Conditional aggregation

Reports are almost always "sum/count where…". Learn the -IFS family plus the pattern of building criteria from cells, not literals, so one report cell can be repointed without editing formulas:

=SUMIFS(Orders[LineTotal], Orders[Status], "Delivered", Orders[CustomerID], A2)

=COUNTIFS(Orders[Status], "Pending", Orders[OrderDate], "<"&TODAY()-7)

=SUMIFS(Orders[LineTotal], Orders[OrderDate], ">="&DATE(2026,7,1),
        Orders[OrderDate], "<="&EOMONTH(DATE(2026,7,1),0))

Array thinking: ARRAYFORMULA, LET, LAMBDA

Dragging a formula down 5,000 rows creates 5,000 formulas to maintain; one array formula in the header row creates one. This is also a performance lever — recalculation cost scales with formula count, and a laggy workbook is usually a dragged-formula workbook:

=ARRAYFORMULA(IF(Orders[Qty]="",, Orders[Qty] * Orders[UnitPrice]))

=LET(due, Orders[OrderDate] + 7,
     open, Orders[Status] = "Pending",
     ARRAYFORMULA(IF(open * (due < TODAY()), "OVERDUE", "")))

=MAP(Orders[LineTotal], LAMBDA(x, IF(x > 5000, "BULK", "REGULAR")))

LET names intermediate values (readability + speed, since each is computed once); LAMBDA with helpers like MAP, BYROW, and SCAN gives you reusable logic — and Named Functions (Data → Named functions) let you package a LAMBDA as your own function, shareable across files.

Module 1.3 — QUERY, FILTER & Cross-File Data

Level: Beginner–Intermediate · Prereqs: 1.2 · Time: ~5h
Skip-check (test-out): Write one QUERY producing monthly revenue by category, and pull the Products table into a second spreadsheet with IMPORTRANGE.
Skip if: You already write grouped QUERY reports and manage IMPORTRANGE permission grants.
Unlocks: Capstone 1, 4.3

QUERY — SQL inside a cell

QUERY is the closest thing Sheets has to SQL, and it is the mental bridge to Phase 3's data-layer thinking. Columns are addressed by letter (Col1 style when fed an expression result). One formula can select, filter, aggregate, sort, and label:

=QUERY(Orders[#ALL],
  "select D, sum(G)
   where H = 'Delivered'
   group by D
   order by sum(G) desc
   label sum(G) 'Revenue'", 1)

=QUERY(Orders[#ALL],
  "select year(B), month(B)+1, sum(G)
   where H <> 'Cancelled'
   group by year(B), month(B)+1
   label sum(G) 'Monthly Revenue'", 1)

Know its sharp edges: QUERY coerces each column to the majority type and blanks the minority — a column mixing text SKUs like 1001 and A-1001 will silently lose rows. That is a data-hygiene failure from Module 1.1, not a QUERY bug.

FILTER, SORT, UNIQUE — composable spills

=FILTER(Orders[#ALL], Orders[Status]="Pending", Orders[OrderDate] < TODAY()-7)

=SORT(UNIQUE(Orders[CustomerID]))

=LET(top, SORTN(QUERY(Orders[#ALL],"select C, sum(G) group by C",1), 6, 0, 2, FALSE), top)

Prefer FILTER when the result must feed another formula (it returns real arrays), and QUERY when you need grouping or labels.

IMPORTRANGE and the multi-file architecture

Real deployments split files: a private master workbook, and separate shared views per audience. IMPORTRANGE("spreadsheet_url", "Orders!A:I") is the plumbing — the first use requires an explicit permission grant, and that grant is per source-file/destination-file pair. This matters for security: anyone with edit access to a destination file inherits read access to the granted range, so never point IMPORTRANGE from a widely-shared file at a sheet containing anything private. Wrap imports in QUERY or FILTER to expose only needed columns.

Common mistake: treating IMPORTRANGE as a sync tool. It is a live read-only view with its own refresh cadence and quota behavior — chains of imports (A imports B imports C) are slow and fragile. For anything beyond one hop, move the data with Apps Script (Module 2.4) instead.

Module 2.1 — JavaScript & the V8 Runtime

Level: Beginner · Prereqs: None · Time: ~6h
Skip-check (test-out): In the Apps Script editor, write and run a function using const, an arrow function, map/filter/reduce, template literals, and destructuring, and read its output in the execution log.
Skip if: You already write modern JavaScript (ES2020+) and have run code in the Apps Script editor.
Unlocks: 2.2, 3.1

The environment

Apps Script is JavaScript running on Google's servers with privileged access to Workspace services. Since January 31, 2026 the legacy Rhino runtime is fully retired — everything runs on V8, so modern JavaScript (classes, arrow functions, destructuring, spread, optional chaining, template literals) is the baseline, and any tutorial teaching var-era idioms or Rhino workarounds is outdated. Open the editor from any Sheet via Extensions → Apps Script. Code lives in the cloud with the file (container-bound) or standalone; execution is capped at 6 minutes per run — a constraint that shapes every design in this guide.

Core JavaScript you will actually use

Sheet data arrives as 2-D arrays, so array methods are 90% of your daily JavaScript:

function jsWarmup() {
  const orders = [
    { id: "ORD-0001", qty: 12, unitPrice: 55, status: "Delivered" },
    { id: "ORD-0002", qty: 3,  unitPrice: 240, status: "Pending" },
    { id: "ORD-0003", qty: 8,  unitPrice: 55, status: "Delivered" },
  ];

  const delivered = orders.filter(o => o.status === "Delivered");
  const revenue = delivered.reduce((sum, o) => sum + o.qty * o.unitPrice, 0);
  const lines = orders.map(({ id, status }) => `${id}: ${status}`);

  console.log(`Delivered revenue: ${revenue}`);   // 1100
  console.log(lines.join("\n"));
}

Use console.log and read output in the Executions panel — this log is also where trigger failures surface later, so build the habit of checking it now, not after your first silent 2 a.m. trigger failure.

Services, scopes, and authorization

Global service objects (SpreadsheetApp, GmailApp, DriveApp, UrlFetchApp, Utilities) are the API. The first run of a script requests OAuth scopes derived from the services you call — and users can now grant scopes granularly, so a script asking for broad access may get only part of it. Request the narrowest scopes you can (e.g. spreadsheets.currentonly via an explicit oauthScopes list in appsscript.json): over-broad scopes scare users off and widen the blast radius if the script misbehaves.

Module 2.2 — SpreadsheetApp CRUD

Level: Beginner–Intermediate · Prereqs: 2.1 · Time: ~6h
Skip-check (test-out): Read all Orders with one getValues(), mark every overdue Pending row "Flagged" in memory, and write back with one setValues() call.
Skip if: You already batch reads/writes by habit and can explain why per-cell getValue() loops are slow.
Unlocks: 2.3, 2.4, 3.1

The batch principle

Every call from script to Sheet crosses a network boundary. One getValues() on 10,000 rows takes about the same time as one getValue() on one cell — so a loop of per-cell calls is often 100× slower than read-once/transform/write-once. This single idea separates scripts that finish in 2 seconds from scripts that hit the 6-minute ceiling:

function flagOverdueOrders() {
  const ss = SpreadsheetApp.getActive();
  const sheet = ss.getSheetByName("Orders");
  const range = sheet.getDataRange();
  const rows = range.getValues();            // ONE read
  const header = rows[0];
  const iDate = header.indexOf("OrderDate");
  const iStatus = header.indexOf("Status");

  const cutoff = new Date();
  cutoff.setDate(cutoff.getDate() - 7);

  for (let r = 1; r < rows.length; r++) {
    if (rows[r][iStatus] === "Pending" && rows[r][iDate] < cutoff) {
      rows[r][iStatus] = "Flagged";
    }
  }
  range.setValues(rows);                     // ONE write
}

Address columns by header name (indexOf), never by hard-coded index — the first time someone inserts a column, index-based code silently corrupts data instead of failing loudly.

Objects in, objects out

Convert 2-D arrays to objects at the boundary and back again; all business logic then works with named fields. This helper pair is the seed of Phase 3's data layer:

function rowsToObjects(values) {
  const [header, ...data] = values;
  return data.map(row =>
    Object.fromEntries(header.map((key, i) => [key, row[i]])));
}

function objectsToRows(objects, header) {
  return objects.map(obj => header.map(key => obj[key] ?? ""));
}

function getDeliveredRevenueByCustomer() {
  const values = SpreadsheetApp.getActive()
    .getSheetByName("Orders").getDataRange().getValues();
  const orders = rowsToObjects(values);
  const revenue = {};
  for (const o of orders) {
    if (o.Status !== "Delivered") continue;
    revenue[o.CustomerID] = (revenue[o.CustomerID] || 0) + Number(o.LineTotal);
  }
  return revenue;
}

Appending, deleting, and dates

Use sheet.appendRow([...]) for single inserts (it is atomic per call) and ranged setValues for bulk loads. Deleting rows inside a forward loop skips rows — iterate bottom-up, or better, mark rows with a DeletedAt value instead of destroying them (soft delete — the same convention your Supabase projects use). Dates come back as JavaScript Date objects in the script's time zone; set the project time zone (Asia/Manila) in appsscript.json or day-boundary logic will be silently off by hours.

Module 2.3 — Custom Functions, Menus & Sidebars

Level: Intermediate · Prereqs: 2.2 · Time: ~5h

Custom functions — formulas you invent

Any plain function returning a value (or 2-D array) can be called from a cell. Custom functions run on every recalculation and cannot call services requiring authorization — keep them pure and fast, or the whole sheet lags:

/**
 * Days an order has been pending, or 0 if not pending.
 * @customfunction
 */
function DAYS_PENDING(status, orderDate) {
  if (status !== "Pending" || !(orderDate instanceof Date)) return 0;
  return Math.floor((Date.now() - orderDate.getTime()) / 86400000);
}

Menus and dialogs

function onOpen() {
  SpreadsheetApp.getUi()
    .createMenu("TindaTrack")
    .addItem("Flag overdue orders", "flagOverdueOrders")
    .addItem("Restock report", "showRestockSidebar")
    .addToUi();
}

The simple onOpen trigger runs automatically on file open — this is how you give non-technical colleagues one-click access to your scripts, which is the difference between an automation that gets used and one that only you remember exists.

HTML Service — your first frontend

Sidebars and dialogs are real HTML/CSS/JS pages served in an iframe, talking to server functions asynchronously through google.script.run. This exact client-server bridge is the foundation of the Phase 3 web app, just embedded in the Sheet:

function showRestockSidebar() {
  const html = HtmlService.createHtmlOutputFromFile("RestockSidebar")
    .setTitle("Restock Report");
  SpreadsheetApp.getUi().showSidebar(html);
}
<!-- RestockSidebar.html -->
<div id="list">Loading…</div>
<script>
  google.script.run
    .withSuccessHandler(function (items) {
      document.getElementById("list").innerHTML = items
        .map(function (p) {
          return "<p><b>" + p.Name + "</b> — stock " +
                 p.StockQty + " / reorder at " + p.ReorderLevel + "</p>";
        })
        .join("");
    })
    .withFailureHandler(function (err) {
      document.getElementById("list").textContent = "Error: " + err.message;
    })
    .restockReport();
</script>

Always attach a withFailureHandler — without it server errors vanish and the sidebar just sits on "Loading…" forever, which users will report as "it's broken" with no further detail.

A sheet is a table — treat it like one

When a Sheet becomes a database, spreadsheet habits become schema decisions. The rules: every table gets a stable, generated ID column (never the row number — rows renumber on every sort, insert, and delete, so a position-based "ID" points at a different record tomorrow); every column name is a code identifier (no spaces you'll regret); mutations are soft deletes and status changes, not row deletion; and audit columns (CreatedAt, UpdatedAt) go on anything a user can touch. These are the same conventions you would apply in Postgres — the storage engine changed, not the discipline.

A generic DAL in Apps Script

Build one table-access class instead of per-sheet copy-paste. This becomes the only code that knows data lives in a spreadsheet:

class SheetTable {
  constructor(sheetName, idField) {
    this.sheet = SpreadsheetApp.getActive().getSheetByName(sheetName);
    this.idField = idField;
    const values = this.sheet.getDataRange().getValues();
    this.header = values[0];
    this.rows = values.slice(1);
  }

  all() {
    return this.rows
      .map((row, i) => {
        const obj = Object.fromEntries(this.header.map((k, c) => [k, row[c]]));
        obj._rowIndex = i + 2;               // physical position, internal only
        return obj;
      })
      .filter(o => !o.DeletedAt);
  }

  findById(id) {
    return this.all().find(o => o[this.idField] === id) || null;
  }

  insert(obj) {
    obj.CreatedAt = new Date();
    this.sheet.appendRow(this.header.map(k => obj[k] ?? ""));
    return obj;
  }

  update(id, patch) {
    const rec = this.findById(id);
    if (!rec) throw new Error(`${this.idField} ${id} not found`);
    const merged = { ...rec, ...patch, UpdatedAt: new Date() };
    this.sheet.getRange(rec._rowIndex, 1, 1, this.header.length)
      .setValues([this.header.map(k => merged[k] ?? "")]);
    return merged;
  }

  softDelete(id) { return this.update(id, { DeletedAt: new Date() }); }
}

function nextId(prefix, table, idField) {
  const max = new SheetTable(table, idField).all()
    .reduce((m, o) => Math.max(m, Number(String(o[idField]).split("-")[1] || 0)), 0);
  return `${prefix}-${String(max + 1).padStart(4, "0")}`;
}

Note _rowIndex: the physical row is looked up fresh on every operation and never stored or exposed. That is what makes the DAL safe against concurrent sorting and inserts.

Relationships and derived data

"Joins" happen in script: read both tables once, index one side with a Map keyed by ID, then enrich. Never store derived values you can compute (a customer's balance) unless recomputing is measurably too slow — stored derivations drift out of sync, and reconciling them later costs more than computing them ever did. Validate every inbound record against a schema object (required fields, allowed statuses) at the DAL boundary, exactly as Zod guards your Next.js APIs.

doGet, doPost, and ContentService

Deploying a script as a Web App gives it a public URL; Apps Script calls your doGet(e) for GET and doPost(e) for POST. Return JSON with ContentService — one router function keeps the API surface explicit:

function doGet(e) {
  return handle_(e, {
    listOrders:   () => new SheetTable("Orders", "OrderID").all(),
    listProducts: () => new SheetTable("Products", "SKU").all(),
    statement:    p  => getCustomerStatement(p.customerId),
  });
}

function doPost(e) {
  const body = JSON.parse(e.postData.contents || "{}");
  return handle_({ parameter: body }, {
    createOrder: p => {
      validateOrder(p.order);
      p.order.OrderID = nextId("ORD", "Orders", "OrderID");
      return new SheetTable("Orders", "OrderID").insert(p.order);
    },
    updateStatus: p => new SheetTable("Orders", "OrderID")
      .update(p.orderId, { Status: p.status }),
  });
}

function handle_(e, routes) {
  let payload;
  try {
    const action = e.parameter.action;
    if (!routes[action]) throw new Error(`Unknown action: ${action}`);
    payload = { ok: true, data: routes[action](e.parameter) };
  } catch (err) {
    payload = { ok: false, error: err.message };
  }
  return ContentService.createTextOutput(JSON.stringify(payload))
    .setMimeType(ContentService.MimeType.JSON);
}

Two behaviors surprise everyone: web app responses arrive via a 302 redirect to a one-time googleusercontent.com URL (clients must follow redirects), and you cannot set custom status codes or response headers — errors travel inside the JSON body, hence the ok/error envelope.

Deployment model: identity and versions

Deploy → New deployment → Web app. Two dropdowns define your entire security model:

  • Execute as: Me — every request runs with your authority against a sheet only you can open. This is the common pattern for public-facing tools: the sheet stays private, the API is the only door. It also means the API's power is yours — which is why the router whitelist above matters.
  • Execute as: User accessing + access limited to your domain — each user must authorize, requests run with their identity, and Session.getActiveUser().getEmail() is trustworthy. Right for internal tools with per-user permissions.

Deployments are versioned: the deployment URL pins a snapshot, so pushing code changes nothing until you create a new version on that deployment. Use "Test deployments" (/dev URL) while iterating — it always runs head code. Forgetting to bump the version is the #1 "why isn't my fix live?" mystery.

Minimal auth for Execute-as-Me APIs

An Execute-as-Me web app set to "Anyone" is an open API. Add at least a shared-secret check — an apiKey field validated against a Script Property — and reject early in handle_. It is not OAuth, but it turns "anyone on the internet" into "anyone holding the key", which for a small ops console is usually the right cost/benefit point. Never put the key in client code you ship publicly.

CORS and the preflight trick

Apps Script web apps answer simple cross-origin requests with permissive CORS but cannot answer preflight OPTIONS requests. A fetch with Content-Type: application/json triggers preflight and fails; the same request sent as text/plain (a "simple request") sails through — and your doPost still just JSON.parses the body. This one paragraph saves most learners a lost evening:

const API = "https://script.google.com/macros/s/DEPLOYMENT_ID/exec";
const KEY = "stored-server-side-or-user-entered, never in public source";

async function api(action, params = {}) {
  const res = await fetch(API, {
    method: "POST",
    headers: { "Content-Type": "text/plain;charset=utf-8" },  // no preflight
    body: JSON.stringify({ action, apiKey: KEY, ...params }),
  });
  const json = await res.json();          // fetch followed the 302 for us
  if (!json.ok) throw new Error(json.error);
  return json.data;
}

async function loadOrders() {
  const orders = await api("listOrders");
  renderTable(orders);
}

async function createOrder(order) {
  await api("createOrder", { order });
  await loadOrders();                      // re-read after write
}

The single-file app pattern

For internal consoles, one self-contained .html file (vanilla JS or React via a build step) backed by the web app is a complete, deployable product — no server, no hosting bill, storage and API both living in Google's free tier. Structure it like any client: an api() wrapper, optimistic-or-refetch state updates, loading and error states for every call (Apps Script cold starts add 1–3 s of latency — an unspinnered button will get triple-clicked, creating triple orders).

Alternative read path: Sheets API v4

When a frontend (or an external service) only needs to read published data, the official Sheets API v4 (sheets.googleapis.com/v4/spreadsheets/<id>/values/<range>, API key + sheet shared "anyone with link can view") skips Apps Script entirely and returns value arrays fast. Writes through Sheets API v4 need OAuth and are better mediated by your web app, which is where validation and IDs live. Rule of thumb: reads can go direct; writes go through the API you control.

LockService — serializing writers

Two simultaneous createOrder calls can both read max ID 60 and both write ORD-0061. Sheets has no transactions; LockService is your mutex — take it around every read-modify-write:

function createOrderSafe(order) {
  const lock = LockService.getScriptLock();
  lock.waitLock(10000);                       // ms; throws if not acquired
  try {
    validateOrder(order);
    order.OrderID = nextId("ORD", "Orders", "OrderID");
    return new SheetTable("Orders", "OrderID").insert(order);
  } finally {
    lock.releaseLock();
  }
}

Locks serialize, which caps write throughput: if a locked section takes 800 ms, you can complete at most ~75 writes/minute no matter how many users you have. Keep locked sections minimal — validate before locking, log after releasing.

CacheService — protecting the read path

Most traffic is reads of slowly-changing data. CacheService (up to 6 hours, 100 KB per key) can absorb them so the sheet is read once per TTL instead of once per request, cutting both latency and quota burn:

function cachedProducts() {
  const cache = CacheService.getScriptCache();
  const hit = cache.get("products");
  if (hit) return JSON.parse(hit);
  const data = new SheetTable("Products", "SKU").all();
  cache.put("products", JSON.stringify(data), 300);   // 5-minute TTL
  return data;
}

Invalidate (cache.remove) inside every write path that touches the cached table, or users will report "my edit disappeared" when it is merely hidden for a TTL.

The quota landscape — know your ceilings

Consumer-account ceilings that matter (Workspace accounts get more): 6 min per execution, 30 simultaneous executions per user, 90 min/day total trigger runtime, ~100 email recipients/day via GmailApp, and 10 million cells per spreadsheet. The separate Sheets API v4 has per-minute request quotas (currently in the hundreds per minute per project — check the live limits page, and note Google has announced that quota overages will become billable during 2026). None of these are "big data" numbers, and that is the point: a sheet-backed app is a deliberate trade of scale for zero infrastructure.

When to graduate — and how

Move to a real database when any of these become true: sustained concurrent writers beyond a handful; row counts pushing past ~50k with per-request reads; access-control needs finer than the sharing model; or audit/compliance requirements. Because Phase 3 put every sheet access behind SheetTable and every client call behind api(), graduation is a contained rewrite: reimplement the DAL against Supabase/Postgres, keep the API contract, and the frontend never knows. Design for that day from day one — it is the cheapest insurance in this guide.

Common mistake: benchmarking a sheet-backed app with one user and extrapolating. Latency is fine solo and degrades under lock contention — always test with parallel writers (even just two terminal loops of curl) before promising the app to a team.

The expression language

AppSheet expressions are spreadsheet-formula-like, evaluated per row. Square brackets reference columns; dotted derefs walk refs. These four cover most real apps:

Line total (virtual column on Orders):
  [Qty] * [SKU].[UnitPrice]

Customer balance (virtual column on Customers):
  SUM(SELECT(Orders[LineTotal], AND([CustomerID] = [_THISROW].[CustomerID],
                                    [Status] = "Delivered")))
  - SUM(SELECT(Payments[Amount], [OrderID].[CustomerID] = [_THISROW].[CustomerID]))

Overdue flag (format rule condition on Orders):
  AND([Status] = "Pending", [OrderDate] < TODAY() - 7)

Valid_If on Qty:
  AND([Qty] > 0, [Qty] <= [SKU].[StockQty])

Virtual columns recompute on sync — a heavy SELECT over thousands of rows makes every sync slow for every user, so push expensive derivations back into the Sheet (Phase 2 scripts) when sync times creep past a few seconds.

Slices, format rules, and roles

Slices are filtered virtual tables ([Status] = "Pending" → a "Pending Orders" slice) that drive focused views and limit what actions apply. Format rules color/icon rows on conditions. For roles, use USEREMAIL() in security filters — e.g. delivery riders see only orders where [AssignedTo] = USEREMAIL(). A security filter is enforced server-side and also shrinks the data synced to each device, which is your main performance lever on slow connections.

Automation → Bots: an event (data change, schedule) fires a process (steps: send email/SMS/notification, update rows, call a webhook, run a task). Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Spreadsheet Core

Table (native)
A first-class Sheets structure over a range that adds column types, structured references like Orders[Status], and per-column filtering.
Avoid: "formatted range", "table" meaning any grid — a colored range has none of the structural behavior.
Data validation
A per-cell rule constraining what values may be entered, such as a dropdown from a range or a date requirement.
Avoid: "dropdown" as the whole concept — the dropdown is one UI of the rule, not the rule.
Named range
A saved name pointing at a range, referencable from formulas and scripts instead of coordinates.
Avoid: confusing with Named Functions, which package a LAMBDA formula, not a location.
Spill
The behavior of an array-returning formula writing results into neighboring cells below/beside its own cell.
Avoid: "overflow" — and note a spill fails with #REF! if any target cell is occupied.
QUERY
A Sheets function running a SQL-like language (select/where/group by) over a range within one formula.
Avoid: "SQL" unqualified — the Query Language is a small dialect, not a SQL engine.
IMPORTRANGE
A function creating a live read-only view of a range from another spreadsheet file, gated by a one-time permission grant.
Avoid: "sync" or "import" — nothing is copied or pushed; it is a dependent view.
Smart chip
An inline interactive object in a cell (person, file, date, place) inserted with @, carrying metadata beyond its display text.
Avoid: "link" — a chip is structured data, not a URL.

Apps Script

Container-bound script
An Apps Script project attached to a specific Sheet, Doc, or Form, with implicit access to that file via getActive().
Avoid: "macro" — macros are one recorded feature; bound scripts are full projects.
V8 runtime
The Chrome JavaScript engine that executes all Apps Script since the Rhino runtime's retirement in January 2026, enabling modern ECMAScript syntax.
Avoid: treating "Apps Script" as its own language — it is standard JavaScript plus Google service globals.
Simple trigger
A function like onOpen or onEdit that Apps Script runs automatically by name, without authorization and with restricted capabilities.
Avoid: conflating with installable triggers, which are registered explicitly and run with full authorization.
Installable trigger
An explicitly registered trigger (time-driven, onEdit, onChange, onFormSubmit) that executes as the installing user with their OAuth grants.
Avoid: "cron" for the time-driven kind — close, but quotas and ownership semantics differ.
OAuth scope
A named permission (e.g. read spreadsheets, send mail) a script must be granted before calling the corresponding service.
Avoid: "permissions" loosely — sharing permissions on the file and OAuth scopes on the script are separate systems.
PropertiesService
A small key-value store attached to a script, user, or document, used for state and secrets across executions.
Avoid: "database" — values are strings with tight size limits; it is a config store.
clasp
Google's command-line tool (v3.x) that syncs Apps Script projects with local files for editor-based development and version control.
Avoid: "deploy tool" — clasp syncs and can deploy, but deployments themselves are an Apps Script platform concept.

Web-App Backend

Web App (deployment)
An Apps Script deployment type that exposes doGet/doPost handlers at a public /exec URL, pinned to a code version.
Avoid: "the script" — one script can have many deployments at different versions simultaneously.
Execute as Me
A web app identity mode where every request runs with the script owner's authority, regardless of who calls it.
Avoid: assuming the caller is identifiable in this mode — getActiveUser() is generally empty for anonymous access.
ContentService
The Apps Script service that builds raw text responses (JSON, CSV) for web app handlers, with a MIME type but no custom status codes or headers.
Avoid: confusing with HtmlService, which serves sandboxed HTML pages.
Preflight
The browser's automatic OPTIONS request before "non-simple" cross-origin calls — which Apps Script cannot answer, hence the text/plain pattern.
Avoid: "CORS error" as a diagnosis — the failure is specifically the unanswered preflight, and the fix is to avoid triggering one.
LockService
A mutual-exclusion service serializing script executions around a critical section, standing in for the transactions Sheets lacks.
Avoid: "transaction" — a lock prevents interleaving but gives no rollback.
Soft delete
Marking a record deleted via a DeletedAt value while keeping the row, so references and audit history survive.
Avoid: "archiving" — archiving moves data; soft delete only flags it.
DAL (data access layer)
The single module through which all reads and writes of the storage happen — in this guide, the SheetTable class.
Avoid: "ORM" — the DAL here maps rows to objects but has no query language or relations engine.
Quota
A platform-imposed ceiling on executions, runtime, calls, or cells that a sheet-backed architecture must be designed within.
Avoid: "rate limit" for all of them — some quotas are daily totals or absolute sizes, not rates.

AppSheet

Ref
An AppSheet column type declaring that a column's values are keys of another table, generating dropdowns and related-record views.
Avoid: "foreign key" — conceptually close, but nothing is enforced in the underlying Sheet.
Virtual column
A column that exists only in the app, computed from an expression at sync time and never written to the Sheet.
Avoid: "formula column" — Sheet formula columns live in the data; virtual columns do not.
Slice
A saved filtered subset of a table (rows, columns, and permitted actions) used as a data source for views.
Avoid: "filter" — a view filter is per-view UI; a slice is a reusable data object.
Security filter
A server-side row filter evaluated per user (typically via USEREMAIL()) that limits both access and the data synced to the device.
Avoid: confusing with slices — a slice hides rows in the UI; a security filter withholds them from the device entirely.
Bot
An AppSheet automation: an event (data change or schedule) bound to a process of steps such as emails, row updates, webhooks, or AI tasks.
Avoid: "trigger" — reserve that word for Apps Script to keep the two platforms distinct.
Regenerate structure
The action that re-reads the data source's schema into AppSheet after columns are added, removed, or renamed.
Avoid: "sync" — sync moves row data; regeneration updates the schema.
Valid_If
A per-column expression that constrains acceptable input values in forms, evaluated against the row being edited.
Avoid: "validation rule" unqualified — Sheets data validation and AppSheet Valid_If enforce at different layers and do not see each other.
