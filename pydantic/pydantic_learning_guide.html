The silent-bug problem in data analysis

Analysts load data from CSVs, APIs, and databases — and every source can deliver wrong types, missing values, or out-of-range numbers. Python dicts accept anything without complaint, so a bad value can propagate silently through dozens of calculations before surfacing as a wrong report.

order = {"order_id": "ORD-001", "quantity": "two", "unit_price": 19.99}

# This raises TypeError at the multiplication — far from where the bad data entered
total = order["quantity"] * order["unit_price"]

How Pydantic stops the problem at the boundary

Pydantic validates data the moment it enters your model — before any calculation runs. The error message tells you exactly which field failed and why, which turns a mystery bug into a clear action item.

from pydantic import BaseModel, ValidationError

class Order(BaseModel):
    order_id: str
    quantity: int
    unit_price: float

try:
    order = Order(order_id="ORD-001", quantity="two", unit_price=19.99)
except ValidationError as e:
    print(e)
# 1 validation error for Order
# quantity
#   Input should be a valid integer, unable to parse string as an integer
#   [type=int_parsing, input_value='two', ...]

Why Pydantic v2 over alternatives

Python dataclasses do not validate types at runtime — they only annotate them. Pydantic v2 (released 2023) is written in Rust, runs 5–50x faster than v1, and ships JSON Schema export, settings management, and strict mode out of the box. For data analysts, the combination of instant validation, readable errors, and DataFrame interoperability makes it the best fit.

Defining a model

A Pydantic model is a class that inherits BaseModel. Every class attribute with a type annotation becomes a validated field. Without a default, the field is required — missing it raises a ValidationError at instantiation, not silently later.

from pydantic import BaseModel
from datetime import date
from typing import Optional

class OrderRecord(BaseModel):
    order_id: str
    customer_email: str
    product_sku: str
    quantity: int
    unit_price: float
    discount_pct: Optional[float] = None
    order_date: date
    status: str

order = OrderRecord(
    order_id="ORD-001",
    customer_email="juan@example.com",
    product_sku="SKU-A1",
    quantity=3,
    unit_price=299.00,
    order_date="2024-01-15",
    status="pending"
)
print(order.quantity)        # 3
print(type(order.order_date))  # <class 'datetime.date'>

Optional fields and defaults

Optional[float] = None means the field accepts a float or None, and defaults to None if omitted. Omitting a required field (no default) always raises a ValidationError — there is no silent None fallback. This distinction matters when loading CSVs where a column might simply not be present.

Serialization: model_dump() and model_dump_json()

d = order.model_dump()
print(d["order_date"])        # datetime.date(2024, 1, 15)

j = order.model_dump_json()
print(j)
# {"order_id":"ORD-001","customer_email":"juan@example.com",...,"order_date":"2024-01-15"}

model_dump() returns a Python dict with native Python types. model_dump_json() returns a JSON string with dates serialized as ISO strings — ready to write to a file or send over HTTP.

Model copy and updates

updated = order.model_copy(update={"status": "shipped", "quantity": 5})
print(updated.status)    # shipped
print(order.status)      # pending  — original is unchanged

Built-in Python types

Pydantic validates all standard Python types: str, int, float, bool, bytes, list, dict, datetime.date, datetime.datetime, uuid.UUID. The key behavior is coercion in lax mode: Pydantic will attempt to convert an incoming value to the declared type before failing. A string "2024-01-15" becomes a datetime.date; the string "3" becomes an int. This matters for CSV data, where every value starts as a string.

Pydantic-specific types: EmailStr, UUID, HttpUrl

Field constraints with Field()

from pydantic import BaseModel, Field
from typing import Optional

class OrderRecord(BaseModel):
    order_id: str = Field(min_length=3, max_length=50)
    quantity: int = Field(ge=1, description="Units ordered, at least 1")
    unit_price: float = Field(gt=0.0, description="Price per unit in PHP")
    discount_pct: Optional[float] = Field(None, ge=0.0, le=1.0)

ge (greater-than-or-equal), gt (greater-than), le (less-than-or-equal), lt (less-than) are enforced at validation time. If quantity=0 arrives, Pydantic raises a ValidationError immediately — no need for a manual if check.

Common mistake: Pydantic v2 is stricter than v1. In v1, passing True for an int field was silently accepted (Python bool is a subclass of int). In v2 strict mode, that raises an error. When migrating a v1 codebase, run with model_config = ConfigDict(strict=False) first to surface coercion differences before tightening to strict mode.

Strict mode

from pydantic import BaseModel, ConfigDict

class StrictOrder(BaseModel):
    model_config = ConfigDict(strict=True)
    quantity: int
    unit_price: float

# In strict mode, "3" does NOT coerce to int — it raises a ValidationError
# Use strict mode when your source data should already be typed correctly
# (e.g., a validated database result) and coercion would hide a bug.
try:
    StrictOrder(quantity="3", unit_price=9.99)
except Exception as e:
    print(e)
# 1 validation error for StrictOrder
# quantity
#   Input should be a valid integer [type=int_type, ...]

@field_validator — single-field rules

A @field_validator runs after Pydantic has already coerced the value to the declared type (in mode="after", the default). Raise ValueError to reject the input; return the (optionally transformed) value to accept it. The @classmethod decorator is required — Pydantic uses it to detect validators at class definition time.

from pydantic import BaseModel, field_validator
from typing import Optional

class OrderRecord(BaseModel):
    order_id: str
    quantity: int
    unit_price: float
    discount_pct: Optional[float] = None
    region: str

    @field_validator("quantity")
    @classmethod
    def quantity_must_be_positive(cls, v: int) -> int:
        if v < 1:
            raise ValueError("quantity must be at least 1")
        return v

    @field_validator("region", mode="before")
    @classmethod
    def normalize_region(cls, v: str) -> str:
        allowed = {"NCR", "LUZON", "VISAYAS", "MINDANAO"}
        normalized = v.strip().upper()
        if normalized not in allowed:
            raise ValueError(f"region must be one of {allowed}")
        return normalized

mode="before" vs mode="after"

mode="before" receives the raw input value before Pydantic's type coercion — useful for cleaning strings (strip whitespace, uppercase) before they are validated. mode="after" receives the already-coerced typed value — useful for range and business-rule checks. Using the wrong mode can cause validators to receive a type they don't expect.

@model_validator — cross-field rules

When a rule involves two or more fields together, use @model_validator(mode="after"). It runs after all field validators have passed, so all fields on self are already validated and typed.

from pydantic import BaseModel, model_validator
from datetime import date
from typing import Optional

class OrderRecord(BaseModel):
    order_id: str
    order_date: date
    ship_date: Optional[date] = None
    discount_pct: Optional[float] = None
    unit_price: float

    @model_validator(mode="after")
    def ship_after_order(self) -> "OrderRecord":
        if self.ship_date and self.ship_date < self.order_date:
            raise ValueError(
                f"ship_date {self.ship_date} cannot be before order_date {self.order_date}"
            )
        return self

Validator execution order

Validators run in this sequence: mode="before" field validators → Pydantic type coercion → mode="after" field validators → @model_validator(mode="after"). If any step fails, subsequent validators for that field do not run. This means a @model_validator is guaranteed to see fully typed, field-validated data.

Nested models

Any Pydantic model can be used as the type of another model's field. Pydantic validates the nested model recursively — a ValidationError on a nested field reports the full path (e.g., customer.address.city), making it easy to trace where invalid data originated.

from pydantic import BaseModel, EmailStr
from typing import Optional

class Address(BaseModel):
    street: str
    city: str
    province: str
    barangay: Optional[str] = None

class Customer(BaseModel):
    customer_id: str
    email: EmailStr
    address: Address

class OrderRecord(BaseModel):
    order_id: str
    customer: Customer
    product_sku: str
    quantity: int
    unit_price: float

order_data = {
    "order_id": "ORD-001",
    "customer": {
        "customer_id": "CUST-001",
        "email": "pedro@shop.ph",
        "address": {
            "street": "123 Rizal St.",
            "city": "Cebu City",
            "province": "Cebu"
        }
    },
    "product_sku": "SKU-A1",
    "quantity": 2,
    "unit_price": 499.00
}

order = OrderRecord.model_validate(order_data)
print(order.customer.address.city)   # Cebu City
print(order.customer.address.barangay)  # None

List fields and Dict fields

from pydantic import BaseModel
from typing import List, Dict

class LineItem(BaseModel):
    product_sku: str

class OrderRecord(BaseModel):
    order_id: str
    items: List[LineItem]

order = OrderRecord(

print(order.items[0].unit_price)  # 299.0

model_dump() with nested structures

Calling model_dump() on a model with nested sub-models returns a fully nested dict — all sub-models are also converted to dicts, recursively. This makes it easy to pass validated data to a database insert or a downstream function that expects plain Python dicts.

model_validate() — the primary entry point

model_validate(data) is the Pydantic v2 method for constructing a model from any Python object — a dict, another model instance, or an ORM row. It runs all validators. Direct instantiation (Model(**kwargs)) also validates, but model_validate() is preferred when the input is already a dict because it explicitly signals "this data comes from outside."

Common mistake: Pydantic v1 used parse_obj(), parse_raw(), and from_orm(). All three are removed in v2. The v2 equivalents are model_validate(), model_validate_json(), and model_validate(obj, from_attributes=True). If you see a parse_obj call in older code, replace it with model_validate().

Batch loading from a CSV

import csv
from pydantic import BaseModel, ValidationError, field_validator, EmailStr
from datetime import date
from typing import Optional, List, Dict, Any
from enum import Enum

class OrderStatus(str, Enum):
    pending = "pending"
    processing = "processing"
    shipped = "shipped"
    delivered = "delivered"
    cancelled = "cancelled"

class OrderRecord(BaseModel):
    order_id: str
    customer_email: EmailStr
    product_sku: str
    quantity: int
    unit_price: float
    discount_pct: Optional[float] = None
    order_date: date
    status: OrderStatus

def load_orders_from_csv(filepath: str):
    valid_orders: List[OrderRecord] = []
    errors: List[Dict[str, Any]] = []
    with open(filepath, newline="", encoding="utf-8") as f:
        reader = csv.DictReader(f)
        for row_num, row in enumerate(reader, start=2):
            try:
                order = OrderRecord.model_validate(row)
                valid_orders.append(order)
            except ValidationError as e:
                errors.append({
                    "row": row_num,
                    "order_id": row.get("order_id", "UNKNOWN"),
                    "error_count": e.error_count(),
                    "errors": e.errors()
                })
    return valid_orders, errors

Transforming values — validators as normalizers

A validator that returns a transformed value is called a normalizer. Normalization at the model boundary means downstream code never needs to clean the data — it is always in the canonical form. For a data analyst, this eliminates the strip/upper/coerce logic that otherwise scatters across multiple pipeline scripts.

from pydantic import BaseModel, field_validator
from typing import Optional

class OrderRecord(BaseModel):
    order_id: str
    region: str
    discount_pct: Optional[float] = None
    product_sku: str

    @field_validator("order_id", mode="before")
    @classmethod
    def normalize_order_id(cls, v: str) -> str:
        return v.strip().upper()

    @field_validator("region", mode="before")
    @classmethod
    def validate_region(cls, v: str) -> str:
        allowed = {"NCR", "LUZON", "VISAYAS", "MINDANAO"}
        normalized = v.strip().upper()
        if normalized not in allowed:
            raise ValueError(f"'{v}' is not a valid region. Allowed: {allowed}")
        return normalized

    @field_validator("discount_pct", mode="after")
    @classmethod
    def round_discount(cls, v: Optional[float]) -> Optional[float]:
        if v is not None:
            return round(v, 4)
        return v

    @field_validator("product_sku", mode="before")
    @classmethod
    def normalize_sku(cls, v: str) -> str:
        return v.strip().upper().replace(" ", "-")

Handling Optional fields in validators

When a field is Optional[float] = None and the validator uses mode="after", Pydantic will not call the validator at all if the value is None and the field has a default. If you need to run logic on None (e.g., replace it with a computed default), use mode="before" where you receive the raw input before the Optional check.

Row-by-row validation from a DataFrame

DataFrames do not validate types — a column declared as float64 can silently contain NaN, and a string column can contain mixed types after a join. Validating rows with Pydantic before analysis ensures every calculation operates on clean, typed data.

import pandas as pd
from pydantic import BaseModel, ValidationError, field_validator, Field
from datetime import date
from typing import Optional, List, Dict, Any
from enum import Enum

class OrderStatus(str, Enum):
    pending = "pending"
    processing = "processing"
    shipped = "shipped"
    delivered = "delivered"
    cancelled = "cancelled"

class OrderRecord(BaseModel):
    order_id: str
    quantity: int = Field(ge=1)
    unit_price: float = Field(gt=0)
    order_date: date
    status: OrderStatus
    discount_pct: Optional[float] = Field(None, ge=0.0, le=1.0)

def validate_dataframe(df: pd.DataFrame):
    valid_records: List[OrderRecord] = []
    errors: List[Dict[str, Any]] = []
    for idx, row in df.iterrows():
        try:
            record = OrderRecord.model_validate(row.to_dict())
            valid_records.append(record)
        except ValidationError as e:
            errors.append({"row_index": idx, "errors": e.errors()})
    clean_df = pd.DataFrame([r.model_dump(mode="json") for r in valid_records])
    return clean_df, errors

clean_df, errors = validate_dataframe(df)
print(f"Clean rows: {len(clean_df)}, Invalid: {len(errors)}")

TypeAdapter for batch validation

TypeAdapter validates a full list in one call and raises a combined ValidationError listing every failure across all items. It is faster than a Python loop for large DataFrames but gives less per-row control — if one item fails, the whole batch is rejected. Use row-by-row for partial-success pipelines; use TypeAdapter when you need all-or-nothing batch validation.

from pydantic import TypeAdapter
from typing import List

adapter = TypeAdapter(List[OrderRecord])
records = df.to_dict(orient="records")

# All-or-nothing: raises ValidationError if any row is invalid
validated = adapter.validate_python(records)
clean_df = pd.DataFrame([r.model_dump(mode="json") for r in validated])

Handling NaN from Pandas

Pandas represents missing values as float('nan'), which Pydantic treats as a float, not as None. For Optional[float] fields, add a mode="before" validator to convert NaN to None before validation.

import math
from pydantic import field_validator
from typing import Optional

class OrderRecord(BaseModel):
    discount_pct: Optional[float] = None

            return None
        return v

FastAPI + Pydantic — the natural pairing

FastAPI uses Pydantic natively: every request body is a Pydantic model, and every response model is validated before it is sent. This means your data contract — the exact shape and types the API accepts and returns — is declared once in Python and automatically reflected in the OpenAPI docs at /docs.

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, EmailStr, Field
from datetime import date
from typing import Optional
from enum import Enum

app = FastAPI()

class OrderStatus(str, Enum):
    pending = "pending"
    processing = "processing"
    shipped = "shipped"
    delivered = "delivered"

class CreateOrderRequest(BaseModel):
    customer_email: EmailStr
    product_sku: str
    quantity: int = Field(ge=1)
    unit_price: float = Field(gt=0)
    order_date: date
    discount_pct: Optional[float] = Field(None, ge=0.0, le=1.0)

class OrderResponse(BaseModel):
    order_id: str
    customer_email: str
    total_amount: float
    status: OrderStatus

@app.post("/orders", response_model=OrderResponse, status_code=201)
async def create_order(order: CreateOrderRequest):
    total = order.quantity * order.unit_price
    if order.discount_pct:
        total = total * (1 - order.discount_pct)
    return OrderResponse(
        order_id="ORD-AUTO-001",
        customer_email=order.customer_email,
        total_amount=round(total, 2),
        status=OrderStatus.pending

Automatic validation errors from FastAPI

When a request body fails Pydantic validation, FastAPI returns an HTTP 422 Unprocessable Entity with the full ValidationError detail in the response body — no manual error handling needed. The error shape matches the Pydantic .errors() format, so API consumers get actionable field-level messages.

response_model — filtering and shaping the response

The response_model parameter tells FastAPI which fields to include in the response. If your handler returns a database object with extra fields (like hashed_password), response_model filters them out before the response is sent. This is the cleanest way to prevent accidental data leaks in an API.

What is a data contract?

A data contract is a formal, versioned specification of what a data source promises to deliver — field names, types, constraints, and nullability. When the source violates the contract (a field disappears, a type changes), the consumer detects it immediately. Without a contract, schema drift is discovered weeks later when an analysis produces nonsense results.

The ValidationError structure

Every ValidationError exposes .errors() as a list of dicts. Each dict has: loc (tuple of field path), msg (human-readable message), type (machine-readable error code like int_parsing or value_error), and input (the original value that failed). Aggregating by type across all invalid rows identifies the most common data quality issues in a source file.

from pydantic import BaseModel, ValidationError, field_validator, Field
from datetime import date
from typing import Optional, List, Dict, Any
from collections import Counter
import csv

class OrderRecord(BaseModel):
    order_id: str
    quantity: int = Field(ge=1)
    unit_price: float = Field(gt=0)
    order_date: date
    status: str
    discount_pct: Optional[float] = Field(None, ge=0.0, le=1.0)

def validate_csv_with_report(filepath: str) -> Dict[str, Any]:
    valid_records: List[OrderRecord] = []
    error_rows: List[Dict] = []
    error_type_counter: Counter = Counter()

    with open(filepath, newline="", encoding="utf-8") as f:
        reader = csv.DictReader(f)
        for row_num, row in enumerate(reader, start=2):
            try:
                record = OrderRecord.model_validate(row)
                valid_records.append(record)
            except ValidationError as e:
                for err in e.errors():
                    field = ".".join(str(loc) for loc in err["loc"])
                    error_type_counter[f"{field}:{err['type']}"] += 1
                error_rows.append({
                    "row": row_num,
                    "order_id": row.get("order_id", "UNKNOWN"),
                    "errors": [
                        {
                            "field": ".".join(str(loc) for loc in err["loc"]),
                            "message": err["msg"],
                            "type": err["type"],
                            "input": err.get("input")
                        }
                        for err in e.errors()
                    ]
                })

    total = len(valid_records) + len(error_rows)
    return {
        "total_rows": total,
        "valid": len(valid_records),
        "invalid": len(error_rows),
        "error_rate_pct": round(len(error_rows) / max(total, 1) * 100, 2),
        "top_errors": error_type_counter.most_common(5),
        "error_rows": error_rows
    }

report = validate_csv_with_report("ecommerce_orders.csv")
print(f"Valid: {report['valid']}, Invalid: {report['invalid']}, Rate: {report['error_rate_pct']}%")
print("Top errors:", report["top_errors"])

By default, Pydantic stops validating a model after the first error in a given field. Set model_config = ConfigDict(validate_default=True) to continue validating all fields even after early failures. For reporting purposes, you want every error in a row, not just the first.

The problem Pydantic AI exists to solve

An LLM is a text generator: ask it for an order and it returns prose, or JSON-that-looks-right, or JSON with the quantity as the word "three". Everything you learned in Phases 1–3 was about never trusting external data — and an LLM is the least trustworthy data source you will ever integrate, because it is confidently wrong. Pydantic AI, built by the Pydantic team, makes the agent's result a validated Pydantic model: the same BaseModel, Field constraints, and validators from this guide now police what the model is allowed to return. If the LLM's output does not satisfy the schema, you get a ValidationError (or an automatic retry) instead of a corrupt record three steps downstream.

"Return JSON" is not a contract — a schema is

Prompting "respond in JSON" is a request the model can ignore, mis-format, or hallucinate fields into. Declaring an output_type is enforcement: Pydantic AI sends the model your model's JSON Schema, then validates the response against it before handing it back. The difference is exactly the difference between a comment saying "this should be a positive integer" and a Field(gt=0) that raises when it isn't — Phase 1's central lesson, now applied to the model's mouth.

    name: str | None = None
    city: str

class OrderRequest(BaseModel):
    sku: str = Field(pattern=r"^SKU-\d+$")     # reject hallucinated SKU formats
    quantity: int = Field(gt=0, le=1000)        # constraints police the LLM
    customer: Customer

order_agent = Agent(
    "anthropic:claude-sonnet-4-6",
    output_type=OrderRequest,
    instructions=(
        "Extract the order from the customer message. "
        "SKUs look like 'SKU-100'. If the city is missing, ask for it via the error."
    ),
)

result = order_agent.run_sync("hey, 5x sku-42 for Maria over in Cebu please")
order = result.output                  # a validated OrderRequest, not a string
print(order.quantity, order.customer.city)   # 5 Cebu
print(order.model_dump_json())         # ready to feed Phase 3's pipeline

When the model can't comply, validation is your safety net

If the customer message implies quantity: 0 or a malformed SKU, your Field constraints raise a ValidationError exactly as they would for any other input — the bad record never enters your system. This is the bridge that makes the whole guide cohere: the agent's output flows into the same model_validate / model_dump / TypeAdapter machinery you built in Phases 2–3.

Retrieval practice: before running it, predict from memory what happens when the model returns quantity: -2 for your Field(gt=0) field — exception type, and where it surfaces. Then test it.

Unlocks: 4.4 (validators that also use dependencies); the capstone.

Tools let the agent fetch facts instead of inventing them

An LLM has no access to your inventory, your database, or today's prices — left alone it will hallucinate them. A tool is a plain Python function you register with the agent; the model can call it during a run to get real data. Pydantic AI validates the tool's arguments against its type hints (your schema discipline again) and feeds the return value back to the model. This is how you keep the agent honest: it reasons, but it grounds its reasoning in functions you control.

Dependencies and RunContext: typed, injected, testable

deps_type declares what external resources a run needs (a DB connection, an inventory dict, an HTTP client); you pass the actual object into agent.run(...), and tools read it through RunContext[Deps]. Because dependencies are injected per-run rather than hard-coded, you can pass a real database in production and a fake dict in tests — the same dependency-injection benefit FastAPI gives you, applied to agents.

from dataclasses import dataclass
from pydantic_ai import Agent, RunContext

@dataclass
class Deps:
    inventory: dict[str, int]        # swap for a real DB in production

stock_agent = Agent(
    "anthropic:claude-sonnet-4-6",
    deps_type=Deps,
    output_type=OrderRequest,
    instructions="Extract the order. Before confirming, check stock with the tool.",
)

@stock_agent.tool
def stock_level(ctx: RunContext[Deps], sku: str) -> int:
    """Return the units currently in stock for a SKU."""
    return ctx.deps.inventory.get(sku, 0)      # grounded in real data, not guessed

result = stock_agent.run_sync(
    "I want 2 of SKU-7 to Davao",
    deps=Deps(inventory={"SKU-7": 10, "SKU-42": 0}),
)
print(result.output)
# Inspect which tools the model called and with what arguments:
for msg in result.all_messages():
    print(msg)

ModelRetry: turn a validation failure into a second chance

Schema validation rejects bad output; sometimes you want the agent to fix it instead. An output validator runs after the model produces a result, and raising ModelRetry sends the error message back to the model so it can try again with that feedback. This is the agentic version of a model_validator: a cross-field business rule ("quantity must not exceed stock") that, on failure, prompts a correction rather than a crash. Cap retries (the agent's retries= setting) so a model that cannot satisfy the rule fails loudly instead of looping forever.

from pydantic_ai import Agent, RunContext, ModelRetry

checkout_agent = Agent(
    "anthropic:claude-sonnet-4-6",
    deps_type=Deps,
    output_type=OrderRequest,
    retries=2,                       # bound the self-correction loop
    instructions="Extract a valid, fulfillable order from the message.",
)

@checkout_agent.output_validator
def within_stock(ctx: RunContext[Deps], output: OrderRequest) -> OrderRequest:
    available = ctx.deps.inventory.get(output.sku, 0)
    if output.quantity > available:
        # Feedback goes back to the model, which retries with this hint
        raise ModelRetry(
            f"Only {available} units of {output.sku} are in stock; "
            f"reduce the quantity or suggest a backorder."
        )
    return output

result = checkout_agent.run_sync(
    "Give me 50 of SKU-7 to Manila",
    deps=Deps(inventory={"SKU-7": 10}),
)
print(result.output)     # the agent has reconciled quantity against real stock

Streaming: structured output, delivered live

For chat-style UX you do not want the user staring at a blank screen while a long response generates. agent.run_stream(...) yields the output as it arrives — text deltas for prose, or progressively-validated structured data — so you can render tokens immediately. Streaming is the right default for any user-facing agent where latency is visible; it does not change the validation guarantees, only when you see the result.

import asyncio

async def main():
    async with checkout_agent.run_stream(
        "2 of SKU-7 to Cebu",
        deps=Deps(inventory={"SKU-7": 10}),
    ) as stream:
        async for text in stream.stream_text(delta=True):
            print(text, end="", flush=True)     # render live, token by token
        final = await stream.get_output()        # validated OrderRequest at the end
        print("\n", final.model_dump_json())

asyncio.run(main())

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Core Concepts

BaseModel
A Pydantic class that, when subclassed, turns annotated class attributes into validated, type-checked fields instantiated at construction time.
Avoid: "data class", "schema class" — these imply no runtime validation. A BaseModel always validates.
ValidationError
An exception raised by Pydantic when one or more fields fail validation; it aggregates all field errors into a single object with a structured .errors() list.
Avoid: "Pydantic error", "parse error" — too vague. The specific class name matters for catching it.
Type coercion
Pydantic's automatic conversion of an input value to the declared field type in lax mode — for example, converting the string "3" to the integer 3.
Avoid: "casting", "type conversion" — both imply explicit programmer intent. Coercion is implicit and controlled by Pydantic's mode setting.
Strict mode
A Pydantic configuration where no type coercion is performed; the input must already be the exact declared type or the field raises a ValidationError.
Avoid: "no-coercion mode" — the official name is strict mode (ConfigDict(strict=True)).
Lax mode
The default Pydantic validation mode where reasonable type conversions (coercion) are attempted before failing; the opposite of strict mode.
Avoid: "lenient mode", "default mode" — the official name is lax mode.

Validators & Fields

field_validator
A classmethod decorator that attaches a custom validation or transformation function to one or more named fields on a BaseModel.
Avoid: "validator" (the v1 name) — removed in v2. Always use @field_validator.
model_validator
A classmethod decorator that attaches a validation function to the entire model, running after all field validators have passed; used for cross-field rules.
Avoid: "root_validator" (the v1 name) — removed in v2.
Field()
A Pydantic function used as a field default to declare constraints (ge, le, min_length), a description, an alias, or other metadata on a model field.
Avoid: confusing it with Python's built-in dataclasses.field() — same name, different purpose.
TypeAdapter
A Pydantic utility class that wraps any type (including List[Model]) and exposes validate_python() and validate_json() without requiring a BaseModel subclass.
Avoid: using it as a replacement for BaseModel when you need per-record error isolation — TypeAdapter raises a single combined error for the whole batch.
model_validate
The v2 method for constructing a Pydantic model from a dict, ORM object, or another model instance, running all validators.
Avoid: parse_obj() — the v1 equivalent, removed in v2.

Integration & Output

model_dump
A BaseModel method that returns the model's data as a plain Python dict, with all sub-models also converted to dicts recursively.
Avoid: dict() — the v1 equivalent, deprecated in v2.
JSON Schema
A vocabulary for describing the structure and constraints of JSON data; Pydantic generates it automatically via model_json_schema().
Avoid: "Pydantic schema" — the output is standard JSON Schema (draft 2020-12), usable by any JSON Schema validator, not just Pydantic.
BaseSettings
A Pydantic model class (from pydantic-settings) that reads and validates configuration from environment variables and .env files.
Avoid: confusing it with BaseModel — BaseSettings adds env-variable sourcing on top of BaseModel's validation.
Data contract
A formal, versioned agreement between a data producer and a data consumer that specifies field names, types, constraints, and nullability of a dataset.
Avoid: "schema" as a synonym when communicating across teams — schema implies structure only; a contract implies obligation and versioning.

Pydantic AI

Agent
The core Pydantic AI object that binds a model, instructions, dependencies, tools, and an output type into one runnable, type-safe unit invoked with run / run_sync.
Avoid: "chatbot", "chain" — an Agent is a typed wrapper around a model run, not a conversation UI or a LangChain-style pipeline.
output_type
The Pydantic type an agent is constrained to return; result.output is a validated instance of it, so the LLM's response is schema-checked before you use it.
Avoid: result_type — the older name for the same parameter; current Pydantic AI uses output_type.
Tool
A Python function registered on an agent (via @agent.tool) that the model may call mid-run to fetch real data; its arguments are validated against the function's type hints.
Avoid: "plugin", "function call" loosely — in Pydantic AI a tool is specifically a typed, registered Python callable.
RunContext
The object passed to tools and validators that carries the run's injected dependencies (ctx.deps), usage, and message history.
Avoid: "session", "state" — RunContext is per-run and typed via deps_type, not a persistent store.
deps_type
The declared type of an agent's runtime dependencies (DB connections, API clients, lookup data), injected at run time and read inside tools through RunContext.
Avoid: hard-coding resources inside tools — injecting via deps_type is what makes an agent testable with fakes.
ModelRetry
An exception raised inside a tool or output validator that sends its message back to the model so it can correct its previous attempt, bounded by the agent's retries setting.
Avoid: confusing it with ValidationError — a ValidationError rejects output; a ModelRetry asks the model to fix it.
