How to use this guide — you do NOT have to start at Module 1.1
This guide is built to be non-linear. Each module is self-contained with its own prerequisites, skip-check, and outcomes. Setting up the local VM

On Apple Silicon, always use an ARM64 Linux ISO — an x86 image runs under emulation and everything feels broken-slow. Ubuntu Server is the right image because Phase 5 targets Ubuntu Server 24.04 LTS; practicing on the same family removes translation friction. # During install: enable the OpenSSH server option, note the VM's IP from `ip addr`

Module 1.2 — Filesystem & Shell Basics

Level: Beginner · Prereqs: 1.1 · Time: ~4h
Skip-check (test-out): Navigate to /var/log, list files by modification time, and copy the 3 most recent to /tmp — without looking anything up.
Skip if: You can explain what lives in /etc, /var, /usr, /proc and use wildcards fluently.
Unlocks: 1.3, 1.5, 2.1, 2.2, 2.4, 2.6

The filesystem hierarchy is a map, not trivia

Every troubleshooting session starts with knowing where to look: configs live in /etc, variable data (logs, spools, databases) in /var, installed software in /usr, runtime kernel state in /proc and /sys, and device files in /dev. When a service misbehaves in Phase 5, the difference between a 5-minute fix and an hour of flailing is knowing that its config is in /etc/<name>/ and its log trail is in /var/log/ before you even start.

Moving and manipulating

pwd                        # where am I
ls -lah                    # long list, hidden files, human sizes
ls -lt /var/log            # sort by modification time, newest first
cd /var/log ; cd -         # jump and jump back
cp nginx/access.log /tmp/  # copy
mv report.txt report.bak   # rename or move
rm -i old.log              # -i prompts; build the habit before you need it
mkdir -p demo/a/b/c        # create nested dirs in one shot
ls *.log                   # glob: all .log files
ls syslog.?                # ? matches exactly one character
find /var/log -name "*.gz" -mtime -7   # .gz files modified in the last 7 days

Absolute paths start with / and always mean the same thing; relative paths depend on where you stand. Scripts that assume a working directory break the moment cron runs them from / — prefer absolute paths anywhere automation is involved (this bites for real in Module 3.3).

Module 1.3 — Permissions & Ownership

Level: Beginner · Prereqs: 1.2 · Time: ~3h
Skip-check (test-out): Create a shared directory where a group can read/write but members cannot delete each other's files.
Skip if: You can read rwxr-xr-x, set it with symbolic and octal chmod, explain the sticky bit, and predict the effect of umask 022.
Unlocks: 1.4, 3.4

Reading and setting permissions

Every file has three permission triads — owner, group, other — each holding read (4), write (2), execute (1). rwxr-xr-x is 755: owner does everything, everyone else reads and executes. Permissions are the first thing to check when a service "mysteriously" can't read its own config: a root-owned 600 file is invisible to the service account, and the error message rarely says so plainly.

ls -l app.conf                 # -rw-r--r-- 1 root root ...
chmod 640 app.conf             # octal: owner rw, group r, other nothing
chmod u+x deploy.sh            # symbolic: add execute for owner
chmod g-w,o-r shared.txt       # remove group write, other read
chown appuser:appgroup app.conf  # change owner and group together
umask                          # 022 -> new files 644, new dirs 755
stat -c "%a %U %G %n" app.conf # numeric mode, owner, group, name

The special bits

The sticky bit on a directory (chmod +t, shown as t in ls -l) means only a file's owner can delete it — this is why /tmp is world-writable yet users can't delete each other's files. Setgid on a directory (chmod g+s) makes new files inherit the directory's group instead of the creator's primary group — essential for shared project directories, and exactly what NFS exports in Phase 5 rely on to keep group ownership consistent.

Exercise 1.3 — The Shared Drop Directory

Module 1.4 — Users, Groups & sudo

Level: Beginner · Prereqs: 1.3 · Time: ~2h
Skip-check (test-out): Provision a new sudo-capable user on a fresh install with no direct root login.
Skip if: You can explain what /etc/sudoers controls vs /etc/passwd, and why visudo exists.
Unlocks: 2.5, 4.4, 5.1

Accounts, groups, and where they live

/etc/passwd defines who exists (username, UID, home, shell); /etc/shadow holds the password hashes; /etc/group defines group membership; /etc/sudoers defines who may act as root and how. Editing sudoers directly is how people lock themselves out of their own servers — visudo syntax-checks before saving, which is the entire reason it exists.

sudo adduser deploy                    # interactive: creates home, sets shell
sudo usermod -aG sudo deploy           # -aG appends to group; forgetting -a REPLACES all groups
groups deploy                          # verify membership
id deploy                              # uid, gid, all groups
sudo passwd -l root                    # lock direct root password login
getent passwd | awk -F: '$3 >= 1000 {print $1}'   # list human users

Why services get their own users

Every service in Phase 5 (billing, RADIUS, VOD backend) runs as its own unprivileged user. If the VOD process is compromised, the blast radius is one account's files — not the RADIUS secrets sitting two directories away. Create service accounts with --system --no-create-home --shell /usr/sbin/nologin: they exist to own files and processes, never to log in.

Module 1.5 — Package Management

Level: Beginner · Prereqs: 1.2 · Time: ~2h
Skip-check (test-out): Install a package, inspect what files it placed where, remove it cleanly, and explain apt upgrade vs apt full-upgrade.
Skip if: You already resolve dependency conflicts on your distro without a search engine.
Unlocks: 3.2, 5.1

The apt workflow

Packages come from signed repositories listed under /etc/apt/sources.list.d/. apt update refreshes the index (it installs nothing); apt upgrade applies updates without removing anything; apt full-upgrade may remove packages to resolve changed dependencies — which is why unattended production boxes run plain upgrade semantics. Skipping apt update first is the classic reason a documented package "doesn't exist."

sudo apt update                    # refresh package index
apt search fail2ban                # find it
apt show fail2ban                  # version, deps, description
sudo apt install fail2ban          # install with dependency resolution
dpkg -L fail2ban | head            # what files did it place, where
apt-cache rdepends fail2ban        # what depends ON it
sudo apt remove fail2ban           # remove binaries, keep config
sudo apt purge fail2ban            # remove config too
sudo apt autoremove                # clean orphaned dependencies
apt list --upgradable              # what's pending before you upgrade

Beyond apt: snap and source

Some tools now ship primarily as snaps (certbot's official install method is snap install certbot --classic) or as vendor apt repos you add yourself (Caddy, Docker). Adding a vendor repo means trusting its signing key — always fetch keys over HTTPS from the vendor's own domain, and prefer the modern keyring pattern (/etc/apt/keyrings/) over the deprecated apt-key.

Module 2.1 — Process Management

Level: Beginner–Intermediate · Prereqs: 1.2 · Time: ~3h
Skip-check (test-out): Find a runaway process by name, check its resource use, and kill it cleanly — without -9 first.
Skip if: You use ps, htop, job control, and nice comfortably.
Unlocks: 3.2

Seeing what's running

ps aux | grep nginx            # classic: every process, filtered
pgrep -a nginx                 # cleaner: PIDs + command line by name
htop                           # interactive: sort by CPU/mem, tree view (F5)
top -o %MEM                    # plain top, sorted by memory
kill 1234                      # send SIGTERM (15): "please shut down cleanly"
kill -9 1234                   # SIGKILL: no cleanup, no flush, no goodbye
pkill -f "node server.js"      # kill by full command-line match
nice -n 10 ./batch-job.sh      # start at lower priority
renice 5 -p 1234               # lower priority of a running process

Common mistake: reaching for kill -9 first. SIGKILL cannot be caught, so the process gets no chance to flush buffers, release locks, or remove its PID file — which is how you corrupt a database or strand a stale lock that blocks the next start. Send SIGTERM, wait a few seconds, and escalate to -9 only if the process ignores it.

Job control

Inside one shell session: command & starts in the background, Ctrl-Z suspends the foreground job, bg resumes it in the background, fg brings it back, jobs lists them. This is session-scoped convenience — anything that must survive your logout belongs in systemd (Module 3.2), not a backgrounded job. That rule becomes non-negotiable in Phase 5.

Module 2.2 — Text Processing & Pipes

Level: Beginner–Intermediate · Prereqs: 1.2 · Time: ~6h — the highest-leverage module in Phase 2
Skip-check (test-out): From an nginx access log, extract the top 10 IPs by request count using only pipes.
Skip if: You chain grep, sed, awk, cut, sort, uniq without a reference.
Unlocks: 2.3, 3.1

The pipeline mindset

Each tool does one thing to a stream of lines; the pipe hands one tool's output to the next. Mastering this is what makes logs, CSVs, and command output searchable in seconds instead of importable-into-a-spreadsheet in minutes — and every diagnostic one-liner in Phases 4–5 is built from exactly these parts.

grep " 404 " access.log                      # lines containing a 404 status
grep -c " 500 " access.log                   # just count them
grep -v "healthcheck" access.log             # everything EXCEPT healthchecks
awk '{print $1}' access.log                  # first field (client IP)
cut -d' ' -f1 access.log                     # same, with cut
awk '$9 == 500 {print $7}' access.log        # URLs that returned 500
sed 's/\.gz$//' filelist.txt                 # strip a suffix
sort ips.txt | uniq -c | sort -rn | head     # the counting idiom: tally + rank
wc -l access.log                             # how many requests total

The counting idiom, dissected

The single most reused pipeline in operations: awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10. Extract the field, sort so duplicates are adjacent (uniq only collapses adjacent duplicates — skipping the first sort silently undercounts, and nothing warns you), count with uniq -c, rank numerically descending, take the top. Learn it as a template: swap the first stage to count anything — user agents, URLs, status codes, SSH usernames under attack.

Module 2.3 — I/O Redirection & Streams

Level: Beginner–Intermediate · Prereqs: 2.2 · Time: ~2h
Skip-check (test-out): Explain the difference between cmd > file 2>&1 and cmd 2>&1 > file, and predict what each produces.
Skip if: stdin/stdout/stderr and redirection order hold no surprises for you.
Unlocks: 3.1

Three streams, two operators

Every process gets stdin (0), stdout (1), stderr (2). Pipes and > only carry stdout — which is why error messages still hit your screen when you redirect "everything" to a file, and why a cron job's failure email is empty when the actual error went to an unredirected stderr.

command > out.txt              # stdout to file (truncate)
command >> out.txt             # stdout to file (append)
command 2> err.txt             # stderr to file
command > all.txt 2>&1         # both to one file: redirect stdout FIRST, then point stderr at it
command &> all.txt             # bash shorthand for the same
command 2> /dev/null           # discard errors (use sparingly — errors are information)
command < input.txt            # stdin from file
cmd1 | tee mid.txt | cmd2      # split the stream: save a copy AND keep piping

Why order matters

Redirections apply left to right. cmd > file 2>&1 first points stdout at the file, then points stderr at wherever stdout currently points — the file. Reversed, cmd 2>&1 > file points stderr at the terminal (stdout's current target), then moves stdout to the file — so errors still splash on screen. Getting this wrong in a backup script means the log you check after a silent 3 a.m. failure contains nothing useful.

Exercise 2.3 — Stream Plumbing

Module 2.4 — Archiving & Compression

Level: Beginner · Prereqs: 1.2 · Time: ~1h

Skip if: tar -czf / -xzf are muscle memory.

tar bundles, gzip squeezes

tar packs a directory tree (preserving permissions and ownership — the reason it's the Unix default) into one file; gzip compresses that stream. zip does both at once but stores permissions poorly, so it's for sending files to Windows users, not for backups. A backup that loses its execute bits and owners restores into a broken system — this is why Phase 5's DR drill uses tar/rsync, never zip.

tar -czf backup-$(date +%F).tar.gz /srv/app   # create, gzip, file
tar -tzf backup-2026-07-19.tar.gz | head      # list contents WITHOUT extracting
tar -xzf backup-2026-07-19.tar.gz -C /tmp/restore   # extract to a target dir
tar -cJf logs.tar.xz /var/log/app             # xz: slower, ~30% smaller
gzip -k report.txt                            # compress single file, keep original
gunzip report.txt.gz
zcat access.log.gz | grep " 500 "             # search inside without extracting

Choosing compression

gzip is the fast default; xz trades CPU time for the smallest archives (cold storage); zstd gives near-gzip speed with better ratios and is the modern choice where installed. For nightly backups over the LAN in Module 5.6, compression speed matters more than ratio — the NAS has terabytes, but your backup window has minutes.

Variables and PATH

When you type caddy, the shell walks the colon-separated directories in PATH in order and runs the first match — which caddy shows the winner. A variable set with = lives only in the current shell; export passes it to child processes. This distinction is why a script can't see the variable you "set" a minute ago without exporting it.

printenv | sort | head             # what the environment actually contains
alias ll='ls -lah'                 # convenience alias
echo 'alias ll="ls -lah"' >> ~/.bashrc ; source ~/.bashrc

Login shells (SSH session, console) read .bash_profile / .profile; interactive non-login shells (a new terminal tab) read .bashrc. The trap that matters: cron and systemd read neither — a script that works in your terminal but dies at 3 a.m. is almost always missing an environment variable or a PATH entry it silently inherited from your dotfiles (Module 3.3 revisits this).

Module 3.1 — Bash Scripting

Level: Intermediate · Prereqs: 2.2, 2.3 · Time: ~8h
Skip-check (test-out): Write a backup script — compress a directory, timestamp it, rsync to a remote host, exit non-zero on any failure — without a reference.

Unlocks: 3.3, 5.6

Scripts that fail loudly

The default shell behavior — keep going after errors, treat unset variables as empty — is exactly wrong for automation. set -euo pipefail flips all three: exit on error (-e), error on unset variables (-u), and make a pipeline's exit code reflect any failing stage (pipefail). Without it, rm -rf "$BACKUP_DIR/"* with an unset BACKUP_DIR quietly becomes rm -rf /*. That is not a hypothetical; it is the canonical way people destroy servers.

The working template

#!/usr/bin/env bash
set -euo pipefail

SRC="/srv/app"
DEST="lab:/srv/backups"
STAMP="$(date +%F-%H%M)"
ARCHIVE="/tmp/app-${STAMP}.tar.gz"
LOG="/var/log/backup-app.log"

log() { printf '%s %s\n' "$(date '+%F %T')" "$*" >> "$LOG"; }

main() {
  log "backup start"
  tar -czf "$ARCHIVE" -C "$(dirname "$SRC")" "$(basename "$SRC")"
  rsync -az "$ARCHIVE" "$DEST/"
  rm -f "$ARCHIVE"
  log "backup ok: app-${STAMP}.tar.gz"
}

trap 'log "backup FAILED at line $LINENO"; exit 1' ERR
main "$@"

Every technique in this template earns its place: quoted variables survive spaces in paths; the log function timestamps every line so 3 a.m. failures are reconstructable; trap ... ERR guarantees a failure is recorded even when -e aborts mid-script; -C keeps archive paths relative so restores don't recreate absolute trees. Conditionals (if [[ -d "$SRC" ]]), loops (for f in "$dir"/*.log), and argument checks ([[ $# -ge 1 ]] || { echo "usage: $0 <dir>"; exit 64; }) bolt onto this skeleton.

Module 3.2 — systemd & Services

Level: Intermediate · Prereqs: 2.1 · Time: ~5h

Skip if: Unit file anatomy and systemctl/journalctl workflows are familiar.

Unit file anatomy

systemd is PID 1 on every mainstream distro: it starts services at boot, restarts them on crash, and owns their logs. A process without a unit file — launched from nohup or a tmux pane — dies silently with your session and restarts never. That is the difference between a demo and a service.

# /etc/systemd/system/vod.service
[Unit]
Description=VOD streaming backend
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=vodapp
WorkingDirectory=/srv/vod
ExecStart=/usr/bin/node /srv/vod/server.js
Restart=on-failure
RestartSec=3
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target

After= orders startup (start me after the network is up); Wants=/Requires= declare dependency (pull that target in, softly or hard). Ordering without dependency, or vice versa, is the classic boot-race bug — a service that works on manual start but fails at boot because the network wasn't there yet.

The operating loop

sudo systemctl daemon-reload            # after ANY unit file edit
sudo systemctl enable --now vod         # start now AND at every boot
systemctl status vod                    # state, PID, last log lines
journalctl -u vod -f                    # follow this service's log live
journalctl -u vod --since "10 min ago"  # scoped history
sudo systemctl restart vod
systemctl list-units --failed           # anything red on this box?

Crontab syntax and its environment trap

# m h dom mon dow  command
30 2 * * *   /home/hayah-admin/bin/backup.sh /srv/app >> /var/log/backup-cron.log 2>&1
0 */6 * * *  /usr/local/bin/health-probe.sh
15 3 * * 0   /usr/sbin/logrotate -f /etc/logrotate.d/vod

Cron runs with a near-empty environment: minimal PATH (/usr/bin:/bin), no .bashrc, home not guaranteed. The fix is mechanical — absolute paths for every command and file, redirect both streams to a log (or errors vanish), and set PATH= at the top of the crontab if a script needs more. systemd timers — when cron isn't enough

A timer pairs with a service unit (backup.timer + backup.service). Choose timers when you need: Persistent=true (a missed run fires at next boot — cron just skips it, and a box that's off at 02:30 backs up never), logs in journalctl, or dependency ordering (don't back up before the NFS mount exists). OnCalendar=*-*-* 02:30:00 replaces the cron field dance; systemctl list-timers shows the schedule with next/last run — something cron cannot tell you at all.

Level: Intermediate · Prereqs: 1.3 · Time: ~4h

Block devices, filesystems, mounts

lsblk -f                        # devices, partitions, filesystems, mountpoints
sudo fdisk -l /dev/vdb          # partition table detail
sudo mkfs.ext4 /dev/vdb1        # create a filesystem (DESTROYS existing data)
sudo mount /dev/vdb1 /mnt/data  # attach it to the tree
findmnt /mnt/data               # verify what's mounted where, with options
df -h                           # free space per filesystem (the "disk full?" tool)
sudo du -xsh /var/* | sort -rh | head   # which directory is eating the disk
sudo umount /mnt/data

df answers "which filesystem is full"; du answers "what inside it is responsible." The pairing matters during incidents: a service crashing with "no space left on device" gets diagnosed in two commands, not twenty.

fstab and network mounts

# /etc/fstab — one line per persistent mount
UUID=3f1c...  /mnt/data  ext4  defaults  0 2
nas.lan:/volume1/backups  /mnt/nas  nfs  defaults,_netdev,noatime  0 0

sudo blkid /dev/vdb1        # get the UUID (device names shift; UUIDs don't)
sudo mount -a               # test fstab WITHOUT rebooting — errors now, not at boot
sudo systemctl daemon-reload  # systemd generates mount units from fstab

_netdev tells systemd this mount needs the network, so it waits for network-online instead of trying at local-disk time. Omit it and the boot either hangs waiting for an unreachable server or drops to emergency mode — on a headless box with no monitor, that means a machine that never comes back from a power cut. Module 5.2 validates this with a deliberate power-cycle test.

Two logging worlds, one box

The journal (journalctl) captures everything systemd supervises — structured, queryable, per-unit. What fail2ban actually does

fail2ban tails log files against regex filters; when an IP crosses the threshold (default: 5 failures in 10 minutes), it inserts a temporary firewall drop rule via nftables — then removes it when the ban expires. SELinux/AppArmor, at this level, one concept: mandatory access control confines what a process may touch even as root. Ubuntu ships AppArmor enabled; sudo aa-status shows what's confined. Know it exists and how to read a denial in the journal — deep policy work is beyond this guide's scope.

The practical layer model

Forget memorizing all seven OSI layers — operators think in four: Ethernet/Wi-Fi moves frames between adjacent machines using MAC addresses; IP routes packets between networks using IP addresses; TCP/UDP multiplexes them to processes using ports; the application (HTTP, DNS, SSH) speaks on top. Every diagnostic in Module 4.2 is really the question "which layer is broken?" — and ARP is the glue that maps IP to MAC on the local segment (ip neigh shows the table).

CIDR without tears

A /26 means 26 prefix bits, leaving 6 host bits: 2⁶ = 64 addresses per block, so blocks start at 0, 64, 128, 192. 192.168.1.0/24 therefore splits into .0/26, .64/26, .128/26, .192/26 — each with 62 usable hosts (network and broadcast addresses are reserved). The general rule: hosts = 2^(32−prefix) − 2. Subnetting matters practically the day you put NAS management on an isolated VLAN (a Phase 5 known-limit mitigation) and need to know which addresses are inside it.

ip addr                    # my interfaces and addresses (note the /24 on the address)
ip route                   # routing table; 'default via' = my gateway
ip neigh                   # ARP table: IP-to-MAC on the local segment
# Well-known ports to know cold:
#   22 SSH · 53 DNS · 80 HTTP · 443 HTTPS · 123 NTP
#   1812/1813 RADIUS auth/accounting · 2049 NFS · 51820 WireGuard

Module 4.2 — Core Diagnostic Tools

Level: Intermediate · Prereqs: 4.1 · Time: ~5h

The triage ladder

Debug bottom-up, one layer per question, and you can't get lost:

ping -c3 1.1.1.1            # 1. Do I have IP connectivity at all?
dig example.com +short      # 2. Does the name resolve? To what?
ping -c3 example.com        # 3. Is the resolved host reachable?
mtr -rw example.com         # 4. WHERE does the path degrade? (traceroute + loss stats)
ss -tulpn | grep :443       # 5. (server side) Is anything listening on the port?
curl -v https://example.com # 6. What does the app layer actually say?
curl -I  https://example.com # headers only: status, redirects, cache

Each step eliminates a layer: step 1 failing is local network/gateway; step 2 failing is DNS; 3–4 failing is routing or firewall; 5 empty is a dead service; 6 erroring is the application. Skipping the ladder to "just check the app" is how people restart healthy services while a DNS record sits wrong for another hour.

ss and tcpdump — seeing the actual traffic

ss -tulpn (tcp, udp, listening, processes, numeric) is the server-side truth: what is listening, on which address, owned by which PID. A service bound to 127.0.0.1:8080 instead of 0.0.0.0:8080 is invisible from the LAN — the single most common "it works locally but not remotely" cause. When ss and curl disagree with expectation, tcpdump shows the wire itself: sudo tcpdump -ni eth0 port 443 -c 20 answers "are packets even arriving?" — which cleanly splits firewall problems from application problems.

Module 4.3 — DNS & TLS

Level: Intermediate · Prereqs: 4.2 · Time: ~4h
Skip-check (test-out): Explain the TLS handshake and SNI, and set up automated cert issuance/renewal.
Skip if: Record types, TTLs, and ACME automation are familiar.
Unlocks: 4.5

DNS records and resolution

The records that matter daily: A (name → IPv4), AAAA (→ IPv6), CNAME (name → another name), MX (mail), TXT (verification, SPF), NS (who's authoritative). Resolution order on the box: /etc/hosts first, then the resolver in /etc/resolv.conf (systemd-resolved on Ubuntu — resolvectl status shows the real upstream).

dig vod.hayah.example +short          # the answer, tersely
dig vod.hayah.example                 # full response: TTL, authority, query time
dig @1.1.1.1 vod.hayah.example        # ask a SPECIFIC resolver (bypass local cache)
dig +trace vod.hayah.example          # walk root -> TLD -> authoritative
dig -x 203.0.113.10                   # reverse: IP -> name
resolvectl status | head              # what resolver is this box actually using

Common mistake: "waiting for DNS propagation" as if it were weather. Records don't propagate — caches expire. A change is visible everywhere once every resolver's cached TTL runs out. Check the TTL before changing a record (drop it to 300 ahead of a migration), verify with dig @authoritative-ns immediately, and you never have to "wait and hope" again.

TLS: handshake, SNI, and free automated certs

In one paragraph: the client sends ClientHello (including SNI — the hostname it wants, in clear text, which is how one IP serves many HTTPS sites); the server answers with its certificate chain; the client verifies the chain up to a trusted CA and checks the name matches; both sides derive session keys; encrypted traffic begins. When TLS fails, it's almost always one of: expired cert, wrong name, or incomplete chain — curl -v shows which.

Let's Encrypt made certs free and 90-day-short on purpose: renewal must be automated or it isn't real. Caddy (Module 4.5) does ACME automatically with zero config. For nginx setups, certbot is the standard client — installed via snap per current official docs (sudo snap install certbot --classic), with certbot renew --dry-run to prove the automation works before the 90 days do.

Module 4.4 — Firewalls & Access Control

Level: Intermediate · Prereqs: 4.1, 1.4 · Time: ~4h
Skip-check (test-out): Read a legacy iptables ruleset, manage day-to-day rules in ufw, and explain what fail2ban does at the firewall layer.

The stack: nftables under, ufw on top

Modern kernels filter packets with nftables; it replaced iptables as the default backend years ago (Ubuntu 20.10+, Debian 10+), though the iptables command survives as a compatibility shim and you will meet old rulesets written in it. ufw is Ubuntu's front-end that compiles simple intent into nftables rules — the right day-to-day tool for a single server. Cloud security groups are the same concept enforced outside the box; run both, because defense that depends on one layer being configured correctly isn't defense.

sudo ufw default deny incoming        # the posture that makes everything else work
sudo ufw default allow outgoing
sudo ufw allow 22/tcp comment 'SSH'
sudo ufw allow 80,443/tcp comment 'web'
sudo ufw limit 22/tcp                 # built-in rate limit on SSH
sudo ufw enable
sudo ufw status verbose               # ALWAYS verify what you think you configured
sudo nft list ruleset | head -40      # the real rules ufw generated
sudo iptables -L -n -v | head         # reading legacy rulesets (via the nft shim)

Default-deny thinking

Allow-listing inverts the security question from "what should I block?" (unanswerable — attackers invent new things) to "what did I intend to expose?" (a list you can hold in your head: 22, 80, 443). Everything Phase 5 exposes publicly is exactly that list, and the Validation Gate's port scan is simply checking that reality matches intent. Order matters in rulesets: first match wins, so a broad early accept swallows the specific deny below it — the classic review mistake when reading legacy iptables files.

Module 4.5 — Reverse Proxy & Load Balancing

Level: Intermediate · Prereqs: 4.3, 4.4 · Time: ~5h
Skip-check (test-out): Stand up a reverse proxy with path-based routing to two backend services, with correct header forwarding.
Skip if: proxy_pass/reverse_proxy, upstreams, and forwarded headers are familiar territory.
Unlocks: 5.4

One front door, many rooms

A reverse proxy is the single public entry point that terminates TLS and routes requests to backends that only listen on localhost. The payoff is architectural: backends never face the internet, certs live in one place, and adding a service is a routing line — not a new public port. This is exactly the pattern that keeps the NAS invisible in Phase 5. Caddy is this guide's default because TLS automation is built in (currently v2.11.x); nginx remains worth reading because you will encounter it everywhere.

# /etc/caddy/Caddyfile
vod.hayah.example {
    reverse_proxy 127.0.0.1:8096
}

apps.hayah.example {
    handle_path /billing/* {
        reverse_proxy 127.0.0.1:3001
    }
    handle_path /radius/* {
        reverse_proxy 127.0.0.1:3002
    }
    handle {
        respond "Hayah apps gateway" 200
    }
}

That's a complete config including automatic HTTPS — Caddy fetches and renews certs for both names on first run. The nginx equivalent adds the header block you must know by heart, because without it backends see the proxy as the client — breaking logs, rate limits, and anything IP-based:

location /billing/ {
    proxy_pass http://127.0.0.1:3001/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

Load balancing, briefly

Point the proxy at multiple upstreams (reverse_proxy 127.0.0.1:3001 127.0.0.1:3011) and it distributes — round-robin by default, lb_policy least_conn when request costs vary. Health checks eject dead backends automatically. For the homelab's single node this stays conceptual; it becomes real the day one VOD backend can't hold the stream count.

Module 4.6 — Tunneling & Remote Access

Level: Intermediate · Prereqs: 2.5 · Time: ~4h
Skip-check (test-out): Set up local, remote, and dynamic SSH forwarding, and stand up a basic WireGuard tunnel between two boxes.
Skip if: -L/-R/-D and WireGuard peer configs need no reference.

SSH tunnels — the three directions

ssh -L 9000:localhost:8096 lab     # LOCAL: my :9000 -> lab's :8096 (reach a private admin UI)
ssh -R 8080:localhost:3000 vps     # REMOTE: vps's :8080 -> my :3000 (demo a local dev app)
ssh -D 1080 vps                    # DYNAMIC: SOCKS proxy through vps (whole-browser tunnel)
# ~/.ssh/config multiplexing — instant subsequent connections:
# Host *
#     ControlMaster auto
#     ControlPath ~/.ssh/cm-%r@%h:%p
#     ControlPersist 10m

The mnemonic: -L brings a remote port to you; -R pushes a local port to them; -D proxies everything. Local forwarding is the professional pattern for admin interfaces — DSM, Metabase, anything with a login page — reachable without ever exposing them publicly. This is how you'll touch the NAS UI after Phase 5 locks the network down.

WireGuard — the persistent tunnel

SSH tunnels are per-session; WireGuard is a permanent encrypted interface (in the mainline kernel — no daemon, one config file). Each peer has a keypair; AllowedIPs is both routing and firewall: it declares which addresses live on the other end of the tunnel.

# /etc/wireguard/wg0.conf  (VPS side; mirror-image on the laptop)
[Interface]
PrivateKey = <vps-private-key>
Address = 10.8.0.1/24
ListenPort = 51820

[Peer]
PublicKey = <laptop-public-key>
AllowedIPs = 10.8.0.2/32
wg genkey | tee private.key | wg pubkey > public.key
sudo systemctl enable --now wg-quick@wg0
sudo wg show          # handshake time + transfer counters = tunnel truth

Bridges, ports, and the DNS trick

Docker (Engine 29.x current) puts containers on a private bridge network; -p 8080:80 punches a NAT hole from host port to container port. The detail that matters: on custom networks (which Compose creates per project automatically), Docker runs an embedded DNS server so containers resolve each other by name — the default bridge network doesn't do this. That's why Compose services talk via db:5432 with no IPs anywhere, and why hardcoding a container IP is always wrong: they change on every recreate.

# compose.yaml — app + Postgres, service-name DNS, no hardcoded IPs
services:
  app:
    image: node:22-alpine
    working_dir: /srv
    volumes: [ "./app:/srv" ]
    command: node server.js
    environment:
      DATABASE_URL: postgres://hayah:secret@db:5432/appdb
    ports: [ "8080:3000" ]
    depends_on: [ db ]
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: hayah
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes: [ "dbdata:/var/lib/postgresql/data" ]
volumes:
  dbdata:
docker compose up -d
docker network ls                          # note the project network
docker network inspect <project>_default   # subnet, connected containers, IPs
docker compose exec app ping -c2 db        # service-name resolution, live
ss -tlnp | grep 8080                       # the published port on the host

Mapping to Kubernetes, in one breath

The same ideas wear bigger names in k8s: a Service is the stable DNS name in front of pods (like Compose service names), an Ingress is the reverse proxy layer (like your Caddyfile). Learn the pattern here and the k8s vocabulary attaches to concepts you already own.

Module 5.5 — systemd Service Wrapping (CAP-5)

No nohup, no bare tmux

Every app process — billing service, RADIUS, VOD backend — gets a proper unit file. A process in a tmux pane is invisible to the init system: it doesn't start at boot, doesn't restart on crash, and its logs die with the scrollback. The unit pattern from Module 3.2, hardened for production:

# /etc/systemd/system/billing.service
[Unit]
Description=ISP billing service
After=network-online.target mnt-nas-media.mount
Wants=network-online.target

[Service]
Type=simple
User=billing
WorkingDirectory=/srv/billing
ExecStart=/usr/bin/node /srv/billing/server.js
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/srv/billing /var/log/billing
PrivateTmp=true

[Install]
WantedBy=multi-user.target

The last four [Service] lines are systemd's built-in sandboxing: the process can't gain privileges, sees the OS read-only except its declared paths, and gets a private /tmp. Free defense-in-depth — a compromised billing process can't touch RADIUS files even before AppArmor enters the picture. Note the After=mnt-nas-media.mount: services that need the NFS mount must order after it, or they race it at boot.

The kill test is the checkpoint

sleep 5 ; systemctl status billing --no-pager    # resurrection
journalctl -u billing --since "2 min ago"        # both events, logged

Nightly, automated, verified

The Module 3.1 backup script, grown up: nightly systemd timer (persistent — a missed night runs at next boot), rsync to the NAS, and a freshness marker that makes "did last night run?" a one-line check instead of an assumption.

#!/usr/bin/env bash
# /usr/local/bin/nightly-backup.sh
set -euo pipefail
DEST="/mnt/nas/backups/minipc"
LOG="/var/log/nightly-backup.log"
log(){ printf '%s %s\n' "$(date '+%F %T')" "$*" >> "$LOG"; }

log "start"
rsync -a --delete /etc/                 "$DEST/etc/"
rsync -a --delete /srv/                 "$DEST/srv/"
rsync -a /var/log/caddy/                "$DEST/logs/caddy/"
systemctl list-unit-files --state=enabled --no-pager > "$DEST/enabled-units.txt"
dpkg --get-selections > "$DEST/packages.txt"
date '+%F %T' > "$DEST/LAST_RUN"
log "ok"

The enabled-units.txt and packages.txt exports are what turn a file backup into a system backup — restore is "install packages, copy configs, enable units," not archaeology.

A backup you haven't restored is a hope

The drill: take any spare x86 box, install Ubuntu Server, and rebuild the mini-PC's role from the NAS backup — timed. Running it once for real surfaces everything the SOP forgot (the render-group membership, the netplan file, the router reservation) while the stakes are zero. This is also the mitigation for the tracked SPOF risk: any x86 box is a valid cold spare only if the restore path is proven.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Systems

shell
The interactive program (bash here) that reads your command lines, expands them, and launches processes.
Avoid: "terminal", "console" — those are the window and the device; the shell is the interpreter running inside them.
process
A running instance of a program, with its own PID, memory, and three standard streams.
Avoid: "program", "task" — a program is the file on disk; one program can run as many processes.
service (unit)
A process managed by systemd via a unit file: started at boot, restarted on failure, logged in the journal.
Avoid: "daemon" as a synonym — a daemon is any background process; a service is one systemd supervises.
exit code
The integer a process returns on termination; 0 means success, anything else encodes a failure.
Avoid: "error code" — success also returns one; the code is always there, not only on error.
umask
A per-process mask that removes permission bits from newly created files and directories.
Avoid: thinking of it as "default permissions" — it subtracts from the maximum; it never grants.
sticky bit
A directory mode bit restricting deletion to each file's owner, even in world-writable directories.
Avoid: confusing with setgid — setgid controls group inheritance of new files; sticky controls deletion.
journal
systemd's structured, binary log store, queried through journalctl and scoped per unit and per boot.
Avoid: "syslog" — syslog is the older text-file pipeline into /var/log; both coexist on Ubuntu.
timer
A systemd unit that triggers a paired service on a calendar or interval, with optional catch-up for missed runs.
Avoid: "cron job" for these — cron is the separate legacy scheduler with its own syntax and stripped environment.

Networking

CIDR prefix
The /N notation stating how many leading bits of an address identify the network; the rest identify hosts.
Avoid: "subnet mask" interchangeably — the dotted mask (255.255.255.0) encodes the same fact in older clothing.
port
A 16-bit number that lets TCP/UDP deliver packets to a specific process on a host.
Avoid: conflating with a physical switch port — same word, entirely different layer.
bind address
The address a listening socket attaches to: 127.0.0.1 is reachable only locally, 0.0.0.0 from any interface.
Avoid: "the server's IP" — one machine has many addresses; the bind choice decides visibility.
DNS record TTL
The seconds a resolver may cache a record before re-querying; it bounds how long a change takes to be seen.
Avoid: "propagation time" — nothing propagates; caches expire.
SNI
The cleartext hostname in a TLS ClientHello that lets one IP serve certificates for many names.
Avoid: treating it as private — SNI is visible on the wire (ECH, its encrypted successor, is not yet universal).
reverse proxy
A server that terminates client connections and forwards requests to internal backends it chooses by hostname or path.
Avoid: "proxy" alone — a forward proxy represents clients going out; a reverse proxy represents servers facing in.
NAT
Rewriting of packet addresses at a boundary so many private hosts share one public address.
Avoid: "the firewall" — NAT hides; filtering blocks. Routers do both, which blurs the words.
tunnel
An encrypted channel (SSH forwarding, WireGuard) that carries traffic between networks as if directly connected.
Avoid: "VPN" for single-port SSH forwards — a VPN routes whole networks; a forward carries one port.

Production Ops

headless
A machine operated with no monitor or keyboard, administered entirely over the network.
Avoid: "remote" — a headless box can sit on your desk; the word is about missing peripherals, not distance.
static IP
An address configured on the host (or reserved for it) so it never changes across reboots or lease renewals.
Avoid: "DHCP reservation" as identical — a reservation is the router promising; static is the host asserting. Production uses both.
NFS export
A directory a file server publishes over the network, scoped by client address and permission flags.
Avoid: "share" generically — SMB shares and NFS exports differ in auth model and mount semantics.
hardware transcode
Video encode/decode performed by dedicated GPU silicon (Quick Sync here) instead of CPU instructions.
Avoid: assuming it from smooth playback — silent software fallback looks identical until concurrent load.
SPOF
Single point of failure: a component whose loss takes down the whole system, mitigated by spares and proven restores.
Avoid: using it only for hardware — an unrenewed cert or a single admin who knows the passwords is also one.
DR drill
A rehearsed, timed execution of the disaster-recovery procedure on real hardware, not a document review.
Avoid: "we have backups" as equivalent — an untested restore is a hypothesis.
default-deny
A firewall posture that drops everything except explicitly allowed traffic.
Avoid: "blocklist" thinking — enumerating badness always loses; enumerate intent instead.
runbook
The living operations document: provisioning steps, health checks, log locations, and restore procedure for a system.
Avoid: "documentation" broadly — a runbook is executable by a stranger under stress, or it isn't one.
