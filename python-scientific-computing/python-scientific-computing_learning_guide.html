The stdlib math module: scalars only

Python's built-in math module wraps the C standard library's math functions — sqrt, log, exp, sin/cos, factorial, gcd, and the constants math.pi and math.e. It operates on one Python number at a time and returns one Python number. That's the whole contract, and it matters: math functions cannot take a list as input. Passing a list to math.sqrt raises TypeError, because math was designed for single-value scalar math, not collections — not because of a missing feature, but because that's outside its scope by design.

import math

# math works on one number at a time
print(math.sqrt(49))        # 7.0
print(math.log(100, 10))    # 2.0
print(math.gcd(48, 18))     # 6
print(math.isclose(0.1 + 0.2, 0.3))  # True — safe float comparison

# this fails: math has no concept of "a list of numbers"
prices = [49, 100, 225]
# math.sqrt(prices)  # TypeError: must be real number, not list

The naive fix is a loop or a list comprehension:

roots = [math.sqrt(p) for p in prices]  # [7.0, 10.0, 15.0]

This works, but it's slow at scale: each iteration re-enters the Python interpreter, does type-checking, and allocates a new float object. For 5,000 TindaHub order rows this is fine; for 5 million it becomes a bottleneck, and the fix isn't a faster loop — it's not looping in Python at all.

Why NumPy exists: vectorized, typed, contiguous

NumPy's core object, the ndarray, stores numbers in one contiguous, uniformly-typed block of memory (unlike a Python list, which is an array of pointers to separately-allocated Python objects). Operations on an ndarray run as compiled C loops under the hood — numpy.sqrt(arr) computes every element's square root without a Python-level loop at all. This is why NumPy is the substrate SciPy, SymPy's numeric bridge, pandas, and virtually every other Python numerical library are built on: it's the answer to "how do I represent and operate on large blocks of numbers efficiently," and everything above it assumes that answer.

import numpy as np

prices = np.array([49, 100, 225])
roots = np.sqrt(prices)          # array([ 7., 10., 15.]) — no Python loop
print(roots.dtype)                # float64

Getting this distinction backwards — reaching for math on a collection, or writing a manual loop where np.sqrt would do — is the single most common habit this phase exists to break.

Common mistake: writing [math.sqrt(x) for x in arr] on a NumPy array. It works (NumPy arrays are iterable), but it throws away every performance and readability benefit of using NumPy in the first place — you've converted a vectorized array back into a Python-level loop. Use np.sqrt(arr) instead.

When math is still the right tool

math still wins for genuinely scalar, one-off calculations — a single interest-rate conversion, a config constant, a quick math.ceil() on a page count — where importing NumPy for one number is overkill. The decision rule carried through this whole guide: one number, use math; a collection of numbers, use NumPy. Module 4.1 formalizes this into a fuller decision table once SciPy and SymPy are in the picture too.

Creating arrays

NumPy gives you several constructors depending on what you're building: np.array() from existing Python data, np.arange(start, stop, step) for evenly-spaced integers, np.linspace(start, stop, num) for a fixed count of evenly-spaced floats (the one to reach for when you need exactly N points, not a step size), and np.zeros/np.ones/np.full for pre-allocated arrays you'll fill in later.

import numpy as np

a = np.array([1, 2, 3, 4])          # from a list
b = np.arange(0, 20, 5)             # array([ 0,  5, 10, 15]) — step-based
c = np.linspace(0, 1, 5)            # array([0.  , 0.25, 0.5 , 0.75, 1.  ]) — count-based
d = np.zeros((3, 4))                # 3x4 array of 0.0, pre-allocated for later filling

# from the TindaHub CSV, skipping the header row
qty, unit_price = np.genfromtxt(
    "../datasets/tindahub-orders/tindahub_orders.csv",
    delimiter=",", skip_header=1, usecols=(10, 11), unpack=True
)

np.genfromtxt is the right stdlib-adjacent tool for quick numeric-column loads; for anything with mixed types, missing values, or a need to keep the whole table together, pandas (already covered in the main Python guide's Module 2.3) is the better choice — NumPy arrays are single-dtype, so a table with both text and numbers doesn't fit one array cleanly.

dtype: why the type of your numbers matters

Every ndarray has one dtype shared by all its elements — int64, float64, bool, and so on. This is not a formality: an int32 array silently wraps around on overflow instead of raising an error the way Python's arbitrary-precision int would, and mixing int and float arrays in one operation upcasts the result to float64, which can introduce rounding you didn't ask for on values that should stay exact (like peso amounts in centavos). Always check .dtype before trusting the precision of a computed total.

totals = np.array([234, 99, 56, 288], dtype=np.int64)
print(totals.dtype)          # int64

overflow_demo = np.array([2_000_000_000], dtype=np.int32)
print(overflow_demo + overflow_demo)   # wraps to a negative number — silent, no error

Common mistake: assuming NumPy integer overflow raises an error the way Python's built-in int does. It does not — fixed-width integer types wrap silently. For peso totals that could plausibly grow large, default to float64 or int64, not int32.

Indexing, slicing, and boolean masks

Beyond simple arr[3] or arr[1:4] slicing, NumPy's boolean masking lets you filter without a loop: arr[arr > 100] returns only the elements where the condition is true. This is the array-native equivalent of a spreadsheet filter or a SQL WHERE clause, and it composes with & (and) and | (or) for multiple conditions — each condition must be wrapped in parentheses, since Python's operator precedence binds & tighter than comparison operators.

amounts = np.array([234.0, 99.0, 56.0, 288.0, 1200.0])
statuses_delivered = np.array([True, False, True, True, True])

big_delivered = amounts[(amounts > 100) & statuses_delivered]
print(big_delivered)   # array([ 288., 1200.])

Vectorization and ufuncs

A ufunc (universal function) is a NumPy function that operates element-wise on arrays, implemented as a compiled loop rather than a Python one — np.add, np.sqrt, np.exp, and the operators +, *, > are all ufuncs under the hood. Writing "vectorized" code means expressing a computation as ufunc calls over whole arrays instead of per-element Python loops; this is the single biggest performance lever in ordinary NumPy code, typically 10–100x faster than the equivalent pure-Python loop for arrays in the thousands-to-millions range.

Broadcasting: the shape-matching rules

Broadcasting is NumPy's rule set for combining arrays of different (but compatible) shapes without explicitly copying data to match sizes. Two dimensions are compatible if they're equal, or one of them is 1. NumPy compares shapes from the trailing (rightmost) dimension inward. Getting this wrong produces either a silent wrong answer (when shapes are compatible but not the way you intended) or a ValueError: operands could not be broadcast together (when they aren't) — and the silent case is the dangerous one, since nothing crashes to tell you it happened.

import numpy as np

qty = np.array([18, 3, 8, 16])          # shape (4,)
unit_price = np.array([13.0, 33.0, 7.0, 18.0])  # shape (4,)
amounts = qty * unit_price               # element-wise, shape (4,) — same-shape broadcast

discounts = np.array([[0.05], [0.10]])   # shape (2, 1)
prices = np.array([100.0, 200.0, 300.0]) # shape (3,)
# (2,1) and (3,) broadcast to (2,3): each discount row applied to every price
discounted = prices * (1 - discounts)
print(discounted.shape)                  # (2, 3)

Common mistake: confusing a (5000,) 1D array with a (5000, 1) column vector. They look similar printed out, but broadcasting a (5000,) array against a (5000,) array does element-wise pairing, while a (5000, 1) against a (1, 5000) produces a full (5000, 5000) outer-product-style result — silently, and often accidentally, if you meant element-wise. Check .shape whenever a broadcast result looks larger than expected.

Measuring performance honestly

Use %timeit in a Jupyter/IPython session, or timeit.timeit() in a script, to compare a loop-based and a vectorized version on the same data and problem size — performance claims about NumPy only mean something relative to a specific array size, since the fixed overhead of a single ufunc call can make it slower than a plain Python loop for arrays of, say, 3 elements.

import timeit
import numpy as np

n = 100_000
data = np.random.default_rng(42).uniform(1, 1000, size=n)

def loop_version():
    return [x / 1.12 for x in data]

def vector_version():
    return data / 1.12

t_loop = timeit.timeit(loop_version, number=20)
t_vec = timeit.timeit(vector_version, number=20)
print(f"loop: {t_loop:.4f}s  vector: {t_vec:.4f}s  speedup: {t_loop / t_vec:.1f}x")

Retrieval practice: before running the code above, predict roughly what order of magnitude the speedup will be (2x? 20x? 200x?) and write down your guess — then compare against the actual output. The gap between your intuition and the measured number is exactly the calibration this module is trying to build.

Matrices as 2D arrays

A matrix is just a 2D ndarray; NumPy distinguishes element-wise multiplication (*) from true matrix multiplication (@ or np.matmul) — using * where you meant @ is a common source of silently-wrong linear algebra, since both run without error but compute a different thing.

import numpy as np

A = np.array([[2.0, 1.0], [1.0, 3.0]])
b = np.array([8.0, 13.0])

x = np.linalg.solve(A, b)     # exact solution to Ax = b
print(x)                       # array([2.2, 3.6])

det = np.linalg.det(A)         # 5.0 — nonzero, so A is invertible
inv = np.linalg.inv(A)         # explicit inverse (rarely needed — solve() is more stable)

Prefer np.linalg.solve(A, b) over np.linalg.inv(A) @ b for solving systems: computing an explicit inverse is both slower and less numerically stable than a direct solver, for the same reason long division is more reliable than computing 1/x and multiplying.

Least squares: fitting a trend when there's no exact solution

np.linalg.lstsq finds the best-fit solution when a system is over-determined (more equations than unknowns) — the classic case being fitting a straight line through noisy data points where no line passes through all of them exactly. This is the NumPy-native way to do simple linear regression without pulling in a stats or ML library.

months = np.array([1, 2, 3, 4, 5, 6])                 # Jan–Jun 2026
revenue = np.array([842_000, 861_000, 855_000, 900_000, 918_000, 940_000])

# design matrix: column of months, column of 1s (for the intercept)
X = np.vstack([months, np.ones_like(months)]).T
slope, intercept = np.linalg.lstsq(X, revenue, rcond=None)[0]
print(f"revenue ≈ {slope:.0f} * month + {intercept:.0f}")

projected_month_7 = slope * 7 + intercept

Distribution objects: pdf, cdf, rvs

Every distribution in scipy.stats (norm, expon, poisson, dozens more) is an object exposing a consistent set of methods: .pdf(x)/.pmf(x) (density or mass at a point), .cdf(x) (cumulative probability up to x), and .rvs(size=n) (draw random samples). Learning this one shape once means you already know most of the interface for every distribution in the module.

from scipy import stats

order_values = stats.norm(loc=250, scale=80)   # a Normal(250, 80) model of order size
print(order_values.cdf(500))    # P(order value <= 500)
samples = order_values.rvs(size=1000, random_state=42)

# a two-sample t-test — one line, but interpreting it correctly is a statistics
# question, not a SciPy question; see the Statistics with Python guide
t_stat, p_value = stats.ttest_ind(samples[:500], samples[500:])

Minimizing a function of one variable

scipy.optimize.minimize_scalar finds the input that minimizes a scalar function without you deriving calculus by hand. The classic operations-research example is the Economic Order Quantity (EOQ) problem: ordering more units at once reduces per-order costs but increases holding costs, and there's a quantity that minimizes their sum.

from scipy.optimize import minimize_scalar

def total_cost(order_qty, annual_demand=12_000, order_cost=150, holding_cost_per_unit=8):
    if order_qty <= 0:
        return float("inf")
    ordering = (annual_demand / order_qty) * order_cost
    holding = (order_qty / 2) * holding_cost_per_unit
    return ordering + holding

result = minimize_scalar(total_cost, bounds=(1, 5000), method="bounded")
print(f"optimal order qty: {result.x:.0f} units, cost: ₱{result.fun:,.0f}")

Minimizing over multiple variables, and root-finding

scipy.optimize.minimize generalizes to multiple decision variables (needs an initial guess x0 and, for many methods, benefits from a gradient); scipy.optimize.root and brentq find where a function crosses zero rather than where it's smallest — the tool to reach for when the question is "at what input does this equation balance" rather than "what input minimizes this."

from scipy.optimize import minimize, brentq

def two_var_cost(x):
    qty_a, qty_b = x
    return (qty_a - 40) ** 2 + (qty_b - 25) ** 2 + 0.1 * qty_a * qty_b

result = minimize(two_var_cost, x0=[0, 0])
print(result.x)   # approximate optimal [qty_a, qty_b]

# root-finding: at what price does profit break even?
def profit(price, fixed_cost=50_000, unit_cost=30, demand_slope=-200):
    units_sold = max(demand_slope * (price - unit_cost) + 5000, 0)
    return units_sold * (price - unit_cost) - fixed_cost

break_even_price = brentq(profit, a=unit_cost + 0.01, b=1000)

Common mistake: assuming minimize found the global minimum. Gradient-based methods can settle into a local minimum that isn't the best possible answer, especially on non-convex cost functions with multiple valleys. For anything business-critical, re-run with several different x0 starting guesses and check whether they converge to the same answer — if they don't, you have local minima to worry about.

Definite integrals with quad

scipy.integrate.quad numerically computes a definite integral — the area under a curve between two bounds — for functions that either can't be integrated symbolically in closed form, or where you just don't need the exact symbolic antiderivative (SymPy's integrate, covered in Module 3.2, is the tool when you do need the exact form).

from scipy.integrate import quad

    return 40 + 15 * np.sin(t / 7) * np.exp(-t / 90)

Ordinary differential equations with solve_ivp

An ODE describes how a quantity changes over time via its rate of change (dy/dt = f(t, y)) rather than giving y directly; solve_ivp numerically integrates that rate forward from a starting condition. A natural TindaHub example: modeling how a fixed inventory quantity depletes over time under a demand rate that itself changes, or how a customer base grows toward a saturation point (logistic growth) rather than growing forever.

from scipy.integrate import solve_ivp
import numpy as np

def logistic_growth(t, y, carrying_capacity=5000, growth_rate=0.08):
    return growth_rate * y * (1 - y / carrying_capacity)

solution = solve_ivp(
    logistic_growth, t_span=(0, 365), y0=[200],
    t_eval=np.linspace(0, 365, 13)   # monthly checkpoints over a year
)
print(solution.y[0])   # customer-count estimate at each checkpoint

Symbols: variables that stay variables

SymPy's Symbol objects represent mathematical variables that are never evaluated to a number unless you explicitly ask — the opposite of how every other variable in Python behaves. This is the entire point of a Computer Algebra System (CAS): x + x in SymPy stays as the expression 2*x, exactly, rather than requiring you to have already decided what number x is.

import sympy as sp

x, y = sp.symbols("x y")
expr = (x + y) ** 2
print(expr)                 # (x + y)**2 — unevaluated
print(sp.expand(expr))      # x**2 + 2*x*y + y**2

simplify, expand, factor, together, apart

These five functions cover most day-to-day symbolic manipulation: expand multiplies out products and powers; factor does the reverse, pulling out common structure; simplify is a general-purpose (and comparatively slow) attempt to find the "simplest" equivalent form, trying several strategies internally; together combines fractions over a common denominator, and apart splits a fraction into partial fractions.

expr2 = x**2 - 4
print(sp.factor(expr2))               # (x - 2)*(x + 2)

expr3 = (x**2 + 3*x + 2) / (x + 1)
print(sp.simplify(expr3))             # x + 2 — cancels the common factor exactly

fraction_sum = 1 / x + 1 / y
print(sp.together(fraction_sum))      # (x + y)/(x*y)

Disambiguation: simplify is not a "make it correct" button and is not always the right first choice — it can be slow on large expressions and doesn't always produce the form you actually want (e.g., you might want a factored form, which factor gives directly and more predictably). Reach for the specific transformation (expand, factor, together) when you know what shape you want; use simplify as a fallback when you don't.

Rational numbers stay exact

SymPy's Rational (and the shorthand sp.Rational(1, 3)) keeps fractions as exact ratios rather than converting to a floating-point approximation — sp.Rational(1, 3) + sp.Rational(1, 3) is exactly 2/3, not 0.6666666666666666. This exactness is the core value proposition of SymPy over NumPy: NumPy is fast and approximate, SymPy is slower and exact. Module 4.1 turns this into an explicit decision rule.

diff and integrate

sp.diff(expr, x) returns the exact symbolic derivative; sp.integrate(expr, x) returns the exact symbolic antiderivative (or a definite value if you pass bounds). Both handle standard functions (polynomials, trig, exp, log) and their combinations via the chain, product, and quotient rules automatically — the calculus you'd otherwise do by hand.

import sympy as sp

x = sp.symbols("x")
revenue = 200 * x - 3 * x**2       # revenue as a function of price discount x

marginal_revenue = sp.diff(revenue, x)         # 200 - 6*x — the exact derivative
print(marginal_revenue)

total_over_range = sp.integrate(revenue, (x, 0, 10))  # definite integral, exact
print(total_over_range)

limit and series

sp.limit evaluates the exact limiting value of an expression as a variable approaches a point (including infinity), correctly handling forms like 0/0 that would need L'Hopital's rule by hand. sp.series produces a Taylor/Maclaurin series expansion around a point — a polynomial approximation of a function useful when you need a fast, simple stand-in for something more complex nearby a specific value.

limit_val = sp.limit(sp.sin(x) / x, x, 0)      # 1 — the classic 0/0 limit, exact
print(limit_val)

taylor = sp.series(sp.exp(x), x, 0, 5)          # Maclaurin series to 5 terms
print(taylor)   # 1 + x + x**2/2 + x**3/6 + x**4/24 + O(x**5)

solve and solveset

sp.solve(equation, variable) is the general-purpose equation solver, returning exact solutions (including irrational and complex ones) rather than a single numeric approximation. solveset is the newer, more mathematically rigorous successor that's explicit about the solution set's domain (real vs. complex) — prefer solveset for new code when you need that precision, though solve remains more common in examples and simpler for quick one-off use.

import sympy as sp

x = sp.symbols("x")
solutions = sp.solve(sp.Eq(x**2 - 5*x + 6, 0), x)
print(solutions)   # [2, 3] — exact, not approximate

from sympy import solveset, S
real_solutions = solveset(x**2 - 5*x + 6, x, domain=S.Reals)

linsolve and nonlinsolve for systems

linsolve solves systems of linear equations symbolically (the SymPy counterpart to numpy.linalg.solve, but exact and able to report infinite-solution or no-solution cases explicitly rather than raising a numerical error); nonlinsolve handles systems with at least one non-linear equation, where NumPy's linear-algebra tools don't apply at all.

from sympy import linsolve, nonlinsolve, symbols

a, b = symbols("a b")
linear_system = linsolve([2*a + b - 280, a + 3*b - 390], (a, b))
print(linear_system)    # {(78, 104)} — exact prices for products X and Y

nonlinear_system = nonlinsolve([a**2 + b**2 - 25, a - b - 1], (a, b))

Common mistake: reaching for nonlinsolve (or SymPy generally) on a large, purely numeric system where numpy.linalg.solve or scipy.optimize would be far faster and entirely sufficient. Symbolic solving is for when you need the exact, general-form answer (or the equation has genuinely symbolic, not-yet-numeric coefficients) — not a default replacement for numeric linear algebra. Why you can't just hand a NumPy array to a SymPy expression

A SymPy expression is a symbolic tree, not a compiled function — evaluating it at one point via .subs(x, value) walks that tree and substitutes, which is slow if repeated thousands of times. sp.lambdify(symbol, expr, "numpy") compiles the symbolic expression into an actual Python function backed by NumPy ufuncs, so it can be called once on an entire array at native NumPy speed — this is the bridge between "derive it exactly" (SymPy) and "evaluate it fast, many times" (NumPy).

import sympy as sp
import numpy as np

x = sp.symbols("x")
profit_expr = (500 - 4*x) * (x - 30)

profit_fast = sp.lambdify(x, profit_expr, "numpy")   # a real, fast callable now

prices = np.linspace(30, 125, 1000)
profits = profit_fast(prices)          # one vectorized call over 1000 points
print(profits.max())

The exactness/speed trade-off, restated

The throughline across this whole guide: math and NumPy are fast and numeric (floating-point, therefore approximate at the bit level); SymPy is exact but slow, because it manipulates symbolic expression trees instead of raw numbers. SciPy sits on the numeric side, offering purpose-built numerical algorithms (optimization, integration, interpolation) for problems where an exact symbolic answer either doesn't exist or isn't needed. Picking the wrong one isn't usually a correctness bug — it's a needless performance or precision cost, which is exactly why this decision deserves a deliberate check rather than a reflexive default.

Common mistake: using SymPy on a problem with thousands of numeric data points (e.g., trying to solve a different equation per row of a DataFrame). SymPy's per-call overhead makes this dramatically slower than an equivalent NumPy/SciPy vectorized approach — symbolic tools are for deriving a formula once, not for repeated per-row numeric work.

Why hand the optimizer an exact gradient

scipy.optimize.minimize can estimate a gradient numerically (finite differences) if you don't supply one, but a numerically-estimated gradient is both slower to compute (extra function evaluations per step) and less accurate than an exact one. When your cost function is differentiable in closed form, SymPy can derive that gradient exactly once, lambdify converts it to a fast callable, and you pass it to minimize via the jac parameter — combining all three libraries' strengths in a single workflow.

import sympy as sp
import numpy as np
from scipy.optimize import minimize

qty_a, qty_b = sp.symbols("qty_a qty_b")
# delivery cost: base per-trip cost + distance penalty that grows with imbalance
cost_expr = 50 * (qty_a + qty_b) + 0.4 * (qty_a - qty_b) ** 2 + 1200

cost_fn = sp.lambdify((qty_a, qty_b), cost_expr, "numpy")
grad_a = sp.lambdify((qty_a, qty_b), sp.diff(cost_expr, qty_a), "numpy")
grad_b = sp.lambdify((qty_a, qty_b), sp.diff(cost_expr, qty_b), "numpy")

def cost_wrapper(x):
    return cost_fn(x[0], x[1])

def grad_wrapper(x):
    return np.array([grad_a(x[0], x[1]), grad_b(x[0], x[1])])

result = minimize(cost_wrapper, x0=[10, 10], jac=grad_wrapper, method="BFGS")
print(result.x, result.fun)

Floating-point isn't exact, and comparisons must account for that

Binary floating-point can't represent most decimal fractions exactly (0.1 in binary is a repeating fraction, truncated), so 0.1 + 0.2 evaluates to 0.30000000000000004, not 0.3. Direct equality checks (==) on floats are therefore unreliable after any arithmetic; np.isclose (or math.isclose for scalars) checks equality within a tolerance instead, which is the correct habit for any float comparison in this guide's code — and in any numeric code at all.

import numpy as np

print(0.1 + 0.2 == 0.3)          # False — the trap
print(np.isclose(0.1 + 0.2, 0.3))  # True — the fix

Condition numbers: when a linear system is fragile

A matrix's condition number (np.linalg.cond(A)) measures how sensitive solve(A, b)'s answer is to tiny errors in A or b — a high condition number (loosely, above ~104–106 depending on your precision needs) means small input noise can produce wildly different solutions, a warning sign worth checking before trusting a numeric linear-algebra result on real-world (noisy) data.

import numpy as np

well_conditioned = np.array([[2.0, 0.0], [0.0, 2.0]])
ill_conditioned = np.array([[1.0, 1.0], [1.0, 1.0001]])

print(np.linalg.cond(well_conditioned))   # ~1 — very stable
print(np.linalg.cond(ill_conditioned))    # large — small input noise, big answer swings

Where SymPy's exactness sidesteps floating-point error entirely

Because SymPy keeps rational numbers as exact fractions and symbolic constants (like sp.pi or sp.sqrt(2)) unevaluated until you ask, a symbolic computation chain never accumulates the small rounding errors that a floating-point chain does — at the cost of speed. This is why a SymPy-derived exact break-even price (Module 3.3) is worth cross-checking against a SciPy numeric optimizer's answer (Module 2.2): if they disagree by more than rounding, something in the numeric setup (tolerance, starting guess, local minimum) is suspect, not the exact symbolic one.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

NumPy Core

ndarray
NumPy's core data structure: a fixed-size, single-dtype, contiguous block of memory holding a grid of values of the same type.
Avoid: "NumPy list", "array" (bare) — a Python list is not an ndarray and behaves very differently under arithmetic.
dtype
The single data type (e.g., int64, float64, bool) shared by every element of an ndarray.
Avoid: "type" (bare) — conflates Python's per-object type() with NumPy's array-wide dtype.
ufunc
A NumPy function (universal function) that applies element-wise across arrays via a compiled loop, e.g., np.add, np.sqrt.
Avoid: "vectorized function" as a strict synonym — all ufuncs are vectorized, but "vectorization" also describes writing array-expression code generally, not just calling a ufunc.
Broadcasting
NumPy's rule set for combining arrays of different, but compatible, shapes without explicitly copying data, by comparing shapes from the trailing dimension inward.
Avoid: "auto-resizing" — broadcasting never actually resizes the underlying array in memory; it conceptually stretches it during the operation only.
View vs. copy
A view shares the original array's underlying memory (modifying it modifies the source); a copy is an independent block of memory. Basic slicing (arr[1:3]) returns a view; boolean-mask indexing (arr[arr > 0]) returns a copy.
Avoid: assuming all indexing returns the same thing — whether you get a view or a copy depends on the indexing method used, and this affects whether edits propagate back.

SciPy Numerical Methods

Quadrature
The numerical (approximate, not exact-symbolic) computation of a definite integral, as performed by scipy.integrate.quad.
Avoid: "integration" (bare) when precision matters — SymPy's integrate is exact/symbolic; SciPy's quad is numeric/approximate. Same word, different guarantee.
ODE (Ordinary Differential Equation)
An equation describing a quantity's rate of change over one independent variable (usually time), rather than giving the quantity's value directly.
Avoid: "equation" (bare) — an ODE is specifically about rates of change, not a static algebraic relationship.
Local minimum
A point where a function's value is lower than all nearby points, but not necessarily the lowest value overall (the global minimum).
Avoid: assuming any scipy.optimize.minimize result is the global minimum — gradient-based methods can and do settle on local ones.
Interpolation
Estimating a value strictly between two known data points along the domain the known data actually covers.
Avoid: "extrapolation" as a synonym — extrapolation estimates values outside the known range and carries much weaker accuracy guarantees.

SymPy Symbolic Math

Symbol
A SymPy object representing an unevaluated mathematical variable, which stays symbolic through arithmetic until explicitly substituted with a value.
Avoid: "variable" (bare) in a Python-semantics sense — a Python variable holds a value immediately; a SymPy Symbol deliberately does not.
Expression
A tree of SymPy operations and symbols (e.g., (x + y)**2) that represents a mathematical formula without evaluating it to a number.
Avoid: confusing an unevaluated expression with its numeric result — printing an expression shows the formula, not a computed value, until you call .subs() or .evalf().
lambdify
A SymPy function that compiles a symbolic expression into an ordinary, fast, callable Python function (typically NumPy-backed), for repeated numeric evaluation.
Avoid: "evaluate" as a substitute term for what lambdify does — .subs() and .evalf() evaluate a single point; lambdify instead produces a reusable, vectorizable function.
Rational
SymPy's exact fraction type, stored as an integer numerator/denominator pair rather than a floating-point approximation.
Avoid: "float" or "decimal" — a Rational stays exact through arithmetic; converting to a Python float immediately reintroduces floating-point rounding.
solveset
SymPy's newer equation-solving function that returns a mathematically explicit solution set, with an explicit domain (real, complex, etc.).
Avoid: treating solve and solveset as fully interchangeable — they can differ in output form and in how they handle infinite or no-solution cases.
