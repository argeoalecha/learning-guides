Module 1.1 — Set Theory & the Relational Model

Level: Beginner · Prereqs: None · Time: ~4h
Skip-check (test-out): Explain, without notes, why a SQL table with duplicate rows and no primary key is not a true "relation" in the mathematical sense.
Skip if: You've studied relational algebra or discrete math and can map SELECT/JOIN/UNION to their algebraic operators from memory.
Unlocks: 1.2, 2.1

Why SQL looks the way it does

SQL is an implementation of the relational model, a theory Edgar Codd published in 1970 that treats data as relations — sets of tuples over named attributes. A "relation" is not the same thing as a database table: a true relation has no duplicate rows (it's a set) and no meaningful row order, because set membership doesn't care about order or repetition. SQL tables relax both rules for practical reasons — but every time a query behaves in a way that surprises you (duplicate rows surviving a query you expected to deduplicate, row order changing between runs), it's usually because SQL is quietly reverting to its set-theoretic roots or exposing where it diverges from them. Knowing the theory tells you which behavior to expect instead of discovering it by trial and error in production.

A tuple is one row: an ordered set of values, one per attribute. An attribute is a named column bound to a domain — the set of legal values it can hold (e.g., the domain of rental_rate is "positive decimal with 2 places"). SQL's NOT NULL, CHECK, and type constraints are how a table enforces its declared domains; without them, the column accepts anything the storage engine can hold, which is a much larger domain than the business actually intends.

Relational algebra: the five primitive operators

Every SQL query, however complex, decomposes into combinations of five primitive operators from relational algebra. Recognizing them makes unfamiliar SQL readable, because you're pattern-matching against five shapes instead of memorizing syntax:

  • Selection (σ) — filter rows by a predicate → SQL's WHERE
  • Projection (π) — choose a subset of columns → SQL's column list after SELECT
  • Union (∪) — combine two relations of the same shape → SQL's UNION
  • Set Difference (−) — rows in A not in B → SQL's EXCEPT
  • Cartesian Product (×) — every row of A paired with every row of B → SQL's CROSS JOIN, and implicitly the basis every other join type is built from

Everything else — INNER JOIN, GROUP BY, INTERSECT — is a derived operator expressible in terms of these five. A JOIN, for instance, is a Cartesian product followed by a selection on the join predicate; the query planner doesn't literally compute the full product (that would be catastrophically slow on real data), but the algebra explains why a join without a proper condition silently degenerates into a Cartesian product instead of erroring — SQL has no way to distinguish "I forgot the ON clause" from "I meant to cross every row."

-- Selection + Projection: which columns, which rows
SELECT first_name, last_name, email
FROM customer
WHERE activebool = true;

-- Cartesian product made explicit (rarely what you want directly,
-- but this is the operator every JOIN is built on top of)
SELECT c.first_name, s.store_id
FROM customer c
CROSS JOIN store s;   -- every customer paired with every store

-- Set difference: customers who have never rented
SELECT customer_id FROM customer
EXCEPT
SELECT customer_id FROM rental;

NULL and three-valued logic

The relational model as originally conceived has no place for "unknown" — every attribute either has a value from its domain or the tuple doesn't exist. SQL's NULL is a practical compromise that breaks ordinary two-valued (true/false) logic into three-valued logic: TRUE, FALSE, and UNKNOWN. NULL = NULL evaluates to UNKNOWN, not TRUE — which is why WHERE column = NULL silently returns zero rows instead of erroring, a mistake that costs beginners hours of "why is my filter empty" debugging. The correct predicate is WHERE column IS NULL.

-- Wrong: always returns zero rows, no error, no warning
SELECT * FROM customer WHERE email = NULL;

-- Correct: IS NULL / IS NOT NULL are the only predicates that
-- treat NULL as a first-class comparison target
SELECT * FROM customer WHERE email IS NULL;

-- COALESCE substitutes a default when a value is NULL — useful
-- in both filters and computed columns
SELECT customer_id, COALESCE(email, 'no-email-on-file') AS email
FROM customer;

Common mistake: Assuming NOT IN (SELECT ... ) behaves like NOT EXISTS. If the subquery returns even one NULL, three-valued logic makes the entire NOT IN comparison UNKNOWN for every row, and the outer query silently returns zero rows — a notorious, hard-to-spot bug covered in depth in Module 3.1.

Module 1.2 — Normalization & Functional Dependencies

Level: Beginner–Intermediate · Prereqs: 1.1 · Time: ~5h
Skip-check (test-out): Given a flat, spreadsheet-style table, identify every functional dependency and decompose it into 3NF without prompting.
Skip if: You've formally normalized a schema to at least 3NF and can defend a denormalization decision with a specific tradeoff.
Unlocks: Phase 1 Capstone, 4.3

Functional dependencies: the atom of normalization

A functional dependency (FD) exists between attributes A and B, written A → B, when knowing the value of A always determines the value of B. customer_id → email is a functional dependency — one customer has exactly one email on file. Normalization is nothing more than systematically finding functional dependencies that don't depend on the whole primary key, and moving them into their own table. Skipping this step is why "just add more columns" schemas rot: every FD you leave un-normalized is a fact stored in more than one place, and facts stored in more than one place inevitably go out of sync when only one copy gets updated.

1NF through BCNF, with a concrete before/after

Consider a single flat table exported from a spreadsheet, modeling the same rental-store domain Pagila represents normalized:

-- The messy starting point: one flat table, several repeating groups
-- and functional dependencies buried inside it
CREATE TABLE rental_log_flat (
  rental_id      INT,
  customer_name  TEXT,
  customer_email TEXT,
  film_title     TEXT,
  film_rating    TEXT,
  actor_names    TEXT,   -- 'PENELOPE GUINESS, CHRISTIAN GABLE' — repeating group
  rental_date    DATE,
  return_date    DATE,
  staff_name     TEXT,
  store_address  TEXT
);
  • 1NF (First Normal Form) — every column holds a single atomic value; no repeating groups. actor_names violates 1NF outright — it packs an unbounded list into one text field, which makes "find every rental of a film starring this actor" require string parsing instead of a join.
  • 2NF — 1NF, plus every non-key attribute depends on the whole primary key, not part of it. This only matters with composite keys: if the key were (rental_id, actor_name), then film_title would depend only on rental_id, not on actor_name — a partial dependency that violates 2NF.
  • 3NF — 2NF, plus no transitive dependencies: a non-key attribute must depend on the key, not on another non-key attribute. Here, film_rating depends on film_title, not directly on rental_id — a transitive dependency. Update one film's rating and, in the flat table, you must find and fix it in every rental row that mentions that film, or the copies drift apart.
  • BCNF (Boyce-Codd Normal Form) — a stricter 3NF that also handles cases where a non-candidate-key attribute determines part of a composite candidate key. It matters mainly in schemas with multiple overlapping candidate keys; most business schemas that reach 3NF are already in BCNF.
-- Normalized: this is (a simplified view of) what Pagila's actual
-- schema looks like — each fact stored exactly once
CREATE TABLE customer (
  customer_id  SERIAL PRIMARY KEY,
  first_name   TEXT NOT NULL,
  last_name    TEXT NOT NULL,
  email        TEXT
);

CREATE TABLE film (
  film_id      SERIAL PRIMARY KEY,
  title        TEXT NOT NULL,
  rating       TEXT   -- depends only on film_id now — no transitive dependency
);

CREATE TABLE actor (
  actor_id     SERIAL PRIMARY KEY,
  first_name   TEXT NOT NULL,
  last_name    TEXT NOT NULL
);

CREATE TABLE film_actor (          -- resolves the repeating-group / many-to-many
  film_id   INT REFERENCES film(film_id),
  actor_id  INT REFERENCES actor(actor_id),
  PRIMARY KEY (film_id, actor_id)
);

CREATE TABLE rental (
  rental_id     SERIAL PRIMARY KEY,
  rental_date   TIMESTAMP NOT NULL,
  return_date   TIMESTAMP,
  customer_id   INT REFERENCES customer(customer_id),
  staff_id      INT REFERENCES staff(staff_id)
);

When to denormalize on purpose

Normalization optimizes for write-safety and storage economy, not read speed — every join you add back at query time costs something. Denormalizing (deliberately storing a derived or duplicated value) is a legitimate engineering tradeoff when a value is read far more often than it changes and the join cost is measurable, for example caching a film_title onto a reporting table that's queried thousands of times per minute. The rule that keeps this safe: denormalize data warehouses and read replicas freely, but keep the system of record normalized — otherwise you've reintroduced the update-anomaly problem 3NF exists to prevent, just one layer down.

Disambiguation: "Normalization" (schema design discipline) is unrelated to "data normalization" in statistics/ML (rescaling numeric ranges to 0–1 or z-scores). Same word, two different fields — context always disambiguates which one a source means.

Logical query processing order

SQL is declarative — you state what you want, not the steps to get it — but the engine still processes clauses in a fixed logical order that does not match the order you type them in. Knowing this order explains otherwise-confusing errors, like why a column alias defined in SELECT can't be used in WHERE:

FROM  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  ORDER BY  →  LIMIT/OFFSET

WHERE runs before SELECT, so a SELECT-defined alias doesn't exist yet when WHERE evaluates — this is why WHERE full_price * 0.9 AS discounted < 5 is illegal, but repeating the expression in WHERE directly works.

-- ORDER BY runs LAST, so it's the one clause allowed to reference
-- a SELECT-list alias
SELECT customer_id, amount * 0.9 AS discounted_amount
FROM payment
WHERE amount > 2.00              -- can't say "WHERE discounted_amount > 1.8" here
ORDER BY discounted_amount DESC  -- but CAN order by it here
LIMIT 10;

Filtering and sorting precisely

-- Multi-condition filtering with explicit parentheses — never rely on
-- AND/OR precedence being "obvious"; it silently changes results
SELECT film_id, title, rental_rate, rating
FROM film
WHERE (rating = 'PG' OR rating = 'G')
  AND rental_rate <= 2.99
ORDER BY rental_rate DESC, title ASC;

-- Pattern matching: LIKE for simple wildcards, ILIKE for case-insensitive
-- (PostgreSQL-specific; standard SQL uses LOWER(col) LIKE '...')
SELECT title FROM film WHERE title ILIKE 'star%';

-- LIMIT/OFFSET for pagination (PostgreSQL/MySQL/SQLite syntax —
-- SQL Server differs; see Module 5.1)
SELECT title FROM film ORDER BY title LIMIT 20 OFFSET 40;

Set operations: combining result sets as sets

UNION, INTERSECT, and EXCEPT require both queries to return the same number of columns with compatible types — this isn't a stylistic convention, it's what makes the two result sets a valid pair of relations to combine under set theory (Module 1.1). UNION deduplicates by default because a mathematical set can't contain the same element twice; UNION ALL skips that dedup pass and is almost always faster when you know the inputs are already disjoint.

-- Customers who are either active OR have rented in the last 30 days
-- (UNION, deduplicated automatically)
SELECT customer_id FROM customer WHERE activebool = true
UNION
SELECT customer_id FROM rental WHERE rental_date > NOW() - INTERVAL '30 days';

-- Customers present in BOTH the active list and the recent-renter list
SELECT customer_id FROM customer WHERE activebool = true
INTERSECT
SELECT customer_id FROM rental WHERE rental_date > NOW() - INTERVAL '30 days';

-- UNION ALL when you already know there's no overlap and want to skip
-- the (costly) deduplication pass
SELECT 'store_1' AS source, customer_id FROM customer WHERE store_id = 1
UNION ALL
SELECT 'store_2' AS source, customer_id FROM customer WHERE store_id = 2;

Module 2.2 — Joins Deep Dive

Level: Beginner–Intermediate · Prereqs: 2.1 · Time: ~4h
Skip-check (test-out): Write INNER, LEFT, FULL, and a self-join from scratch against an unfamiliar schema, correctly predicting NULL behavior in each.
Skip if: You can explain, without running the query, exactly which rows a LEFT JOIN with a WHERE filter on the right table will silently drop.
Unlocks: 2.3, 3.1

Join types as relational algebra with a predicate

Every join is conceptually a Cartesian product (Module 1.1) filtered by a join predicate — the type of join only changes what happens to rows that don't find a match.

  • INNER JOIN — keep only rows where the predicate matches on both sides. Unmatched rows from either side vanish entirely.
  • LEFT JOIN — keep every row from the left table; unmatched rows get NULLs for every right-table column.
  • RIGHT JOIN — the mirror of LEFT; rarely used in practice because you can always rewrite it as a LEFT JOIN by swapping table order, and consistent style beats having two equivalent syntaxes in a codebase.
  • FULL (OUTER) JOIN — keep every row from both sides, NULL-filling whichever side has no match. SQLite lacks native FULL JOIN support; Module 5.1 covers the UNION-based workaround.
  • CROSS JOIN — the raw Cartesian product, no predicate at all. Legitimate for generating combinations (e.g., every date × every store), dangerous when it happens by accident.
  • SELF JOIN — not a distinct join type, just a table joined to itself under different aliases, for hierarchical or peer relationships within one table (e.g., an employee's manager, also an employee).
-- INNER JOIN: only rentals with a matching customer AND film survive
SELECT r.rental_id, c.first_name, f.title
FROM rental r
JOIN customer c ON r.customer_id = c.customer_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film f ON i.film_id = f.film_id;

-- LEFT JOIN: every customer appears, even those with zero rentals —
-- rental columns are NULL for them
SELECT c.customer_id, c.first_name, r.rental_id
FROM customer c
LEFT JOIN rental r ON c.customer_id = r.customer_id;

-- The classic trap: putting a right-table filter in WHERE instead of ON
-- silently turns a LEFT JOIN back into an INNER JOIN
SELECT c.customer_id, r.rental_id
FROM customer c
LEFT JOIN rental r ON c.customer_id = r.customer_id
WHERE r.rental_date > '2026-01-01';   -- drops every customer with r.rental_id NULL —
                                       -- NULL > '2026-01-01' is UNKNOWN, not TRUE

-- Fixed: move the condition into the ON clause so it only narrows
-- the RIGHT side, not the whole result
SELECT c.customer_id, r.rental_id
FROM customer c
LEFT JOIN rental r
  ON c.customer_id = r.customer_id AND r.rental_date > '2026-01-01';

-- SELF JOIN: staff members who report to the same manager (hypothetical
-- manager_id column added to staff for illustration)
SELECT a.first_name AS staff, b.first_name AS coworker
FROM staff a
JOIN staff b ON a.manager_id = b.manager_id AND a.staff_id <> b.staff_id;

Common mistake: Filtering a LEFT JOIN's outer table in WHERE instead of ON. Because WHERE runs after the join (logical processing order, Module 2.1), a condition on the right table's columns silently discards the NULL-filled rows the LEFT JOIN existed to keep — turning it into an INNER JOIN with no error raised.

Module 2.3 — Aggregation & Grouping

Level: Beginner–Intermediate · Prereqs: 2.1 · Time: ~4h
Skip-check (test-out): Write a GROUP BY query with HAVING and a FILTER clause, and explain why an ungrouped non-aggregate column in the SELECT list is a query error.
Skip if: GROUP BY/HAVING/aggregate functions are already second nature.
Unlocks: 3.1, 3.2

GROUP BY collapses rows into sets — literally

GROUP BY partitions rows into groups sharing the same value(s) in the grouping column(s), then collapses each group into one output row. Every column in the SELECT list must therefore be either a grouping column or wrapped in an aggregate function (COUNT, SUM, AVG, MIN, MAX) — the engine has no rule for picking which of many possible values an ungrouped column should show for a collapsed group, so standard SQL rejects the query outright rather than guess. (MySQL historically allowed this and picked an arbitrary row's value — a well-known footgun fixed by ONLY_FULL_GROUP_BY mode, on by default since MySQL 5.7.)

WHERE vs. HAVING: different points in the pipeline

Per the logical processing order (Module 2.1), WHERE filters rows before grouping; HAVING filters groups after aggregation. WHERE can't reference an aggregate (the aggregate doesn't exist yet at that stage); HAVING can't cheaply filter on a non-aggregated, non-grouped column. Using HAVING where WHERE would work wastes effort — it forces the engine to aggregate rows it could have discarded first.

-- Revenue per film category, only categories over $500 total,
-- restricted to 2026 payments (WHERE narrows rows first; HAVING
-- narrows the resulting groups)
SELECT cat.name AS category, SUM(p.amount) AS total_revenue
FROM payment p
JOIN rental r ON p.rental_id = r.rental_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film_category fc ON i.film_id = fc.film_id
JOIN category cat ON fc.category_id = cat.category_id
WHERE p.payment_date >= '2026-01-01'
GROUP BY cat.name
HAVING SUM(p.amount) > 500
ORDER BY total_revenue DESC;

GROUPING SETS, ROLLUP, CUBE, and FILTER

A single GROUP BY produces one grouping granularity. ROLLUP and CUBE compute multiple granularities — including subtotals and a grand total — in one query instead of a UNION of several separate GROUP BY queries, which is both more concise and lets the engine share the underlying scan.

-- ROLLUP: revenue by store, then by store+staff, then a grand total —
-- three granularities in one pass
SELECT store_id, staff_id, SUM(amount) AS revenue
FROM payment p JOIN staff s USING (staff_id)
GROUP BY ROLLUP (store_id, staff_id);

-- FILTER: compute two differently-filtered aggregates in one row,
-- without two separate queries or a CASE-inside-SUM workaround
SELECT
  cat.name,
  COUNT(*) FILTER (WHERE f.rating = 'PG')  AS pg_count,
  COUNT(*) FILTER (WHERE f.rating = 'R')   AS r_count
FROM film f
JOIN film_category fc ON f.film_id = fc.film_id
JOIN category cat ON fc.category_id = cat.category_id
GROUP BY cat.name;

Scalar, row, and correlated subqueries

A scalar subquery returns exactly one row, one column, and can be used anywhere a single value is expected. A correlated subquery references a column from the outer query, so it conceptually re-runs once per outer row — powerful, but potentially slow if the planner can't rewrite it into a join (Module 4.1 covers how to check).

-- Scalar subquery: single value, used inline
SELECT title, rental_rate,
  rental_rate - (SELECT AVG(rental_rate) FROM film) AS vs_avg
FROM film;

-- Correlated subquery: references the outer row (f.film_id) —
-- "how many times has THIS film been rented"
SELECT f.title,
  (SELECT COUNT(*) FROM inventory i JOIN rental r ON r.inventory_id = i.inventory_id
   WHERE i.film_id = f.film_id) AS times_rented
FROM film f;

-- EXISTS vs IN: EXISTS stops at the first match and is NULL-safe;
-- prefer it over IN/NOT IN when the subquery might return NULLs
SELECT c.customer_id, c.first_name
FROM customer c
WHERE EXISTS (
  SELECT 1 FROM rental r WHERE r.customer_id = c.customer_id
);

-- The NOT IN / NULL trap from Module 1.1, concretely: if ANY row
-- in the subquery has a NULL customer_id, this returns ZERO rows —
-- not "customers with no rental," but nothing at all
SELECT c.customer_id FROM customer c
WHERE c.customer_id NOT IN (SELECT customer_id FROM rental);  -- risky

-- NOT EXISTS is the NULL-safe equivalent — always prefer it for
-- "not in" logic over a subquery you don't fully control
SELECT c.customer_id FROM customer c
WHERE NOT EXISTS (
  SELECT 1 FROM rental r WHERE r.customer_id = c.customer_id
);

CTEs: named, readable subqueries

A Common Table Expression (WITH) names a subquery so it can be referenced once and read top-to-bottom, which matters more for maintainability than performance — in PostgreSQL 12+, MySQL 8+, and SQL Server, a non-recursive CTE is generally inlined by the optimizer exactly like an equivalent subquery, so choosing a CTE over a nested subquery is a readability decision, not a speed one.

WITH monthly_revenue AS (
  SELECT DATE_TRUNC('month', payment_date) AS month, SUM(amount) AS revenue
  FROM payment
  GROUP BY 1
)
SELECT month, revenue,
  revenue - LAG(revenue) OVER (ORDER BY month) AS change_from_prior_month
FROM monthly_revenue
ORDER BY month;

Recursive CTEs: walking a hierarchy

A recursive CTE has an anchor query (the base case) UNIONed with a recursive query that references the CTE's own name, repeating until the recursive part returns zero rows. This is the standard SQL way to walk trees and graphs — org charts, category hierarchies, bill-of-materials — without procedural loops.

-- Walk a hypothetical category tree (Pagila's real category table is
-- flat, so this models a self-referencing parent_category_id you'd
-- add for a richer taxonomy)
WITH RECURSIVE category_tree AS (
  -- Anchor: top-level categories (no parent)
  SELECT category_id, name, parent_category_id, 1 AS depth
  FROM category
  WHERE parent_category_id IS NULL

  UNION ALL

  -- Recursive step: join children to the rows found so far
  SELECT c.category_id, c.name, c.parent_category_id, ct.depth + 1
  FROM category c
  JOIN category_tree ct ON c.parent_category_id = ct.category_id
)
SELECT * FROM category_tree ORDER BY depth, name;

Retrieval practice: before running the recursive CTE above, trace through two iterations by hand on paper — write down what rows the anchor produces, then what the first recursive pass adds. Comparing your trace to the actual output reveals whether you've genuinely internalized how the recursion terminates.

OVER, PARTITION BY: aggregation without collapsing rows

A window function computes a value across a set of related rows — the "window" — without collapsing the result set the way GROUP BY does. This is the single biggest advantage over a plain aggregate: you keep every original row and get group-level context on each one, which is exactly what "rank within category," "% of category total," or "compare to previous row" questions need.

-- Every film alongside its rank within its own rating category —
-- one row per film, not one row per category
SELECT title, rating, rental_rate,
  RANK() OVER (PARTITION BY rating ORDER BY rental_rate DESC) AS price_rank_in_rating
FROM film;

The ranking family: RANK, DENSE_RANK, ROW_NUMBER — they diverge on ties

  • ROW_NUMBER() — always unique, 1, 2, 3, 4… even for exact ties. Use when you need exactly one row per rank position (e.g., "pick exactly one row per group" deduplication, Module 3.3).
  • RANK() — ties share a rank, but the next rank skips (1, 1, 3, 4). Matches how sports leaderboards usually work.
  • DENSE_RANK() — ties share a rank, no gap (1, 1, 2, 3). Use when you want a compact "how many distinct tiers exist" count.

Picking the wrong one silently changes downstream counts — a "top 3 films per category" query using RANK() can return more than 3 rows per category when there's a tie for 3rd place, which is correct behavior for a leaderboard but a bug if the requirement was strictly "at most 3 rows."

Frame clauses: ROWS vs. RANGE vs. GROUPS

The frame clause controls exactly which rows within a partition participate in the calculation for the current row — this is where most window-function bugs actually live, because the default frame is easy to get wrong silently.

-- Running total: ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
-- is the physical-row interpretation — exactly the prior rows, by position
SELECT payment_date, amount,
  SUM(amount) OVER (ORDER BY payment_date
                     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM payment;

-- RANGE differs from ROWS when ORDER BY values tie: RANGE includes
-- ALL rows with the same ORDER BY value in the frame, not just the
-- physically-preceding ones — this changes results whenever the
-- ordering column has duplicates (e.g., multiple payments same date)
SELECT payment_date, amount,
  SUM(amount) OVER (ORDER BY payment_date
                     RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total_range
FROM payment;

-- A moving 3-row average — frame relative to the current row, not
-- an absolute range
SELECT payment_date, amount,
  AVG(amount) OVER (ORDER BY payment_date
                     ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving_avg_3
FROM payment;

Common mistake: Omitting the frame clause entirely. With an ORDER BY present but no explicit frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which silently produces wrong running totals the moment two rows share the same ORDER BY value, because RANGE folds every tied row into one step instead of accumulating them one at a time. Always write the frame clause explicitly for running totals.

LAG, LEAD, and first/last value

-- Compare each payment to the customer's previous payment
SELECT customer_id, payment_date, amount,
  LAG(amount) OVER (PARTITION BY customer_id ORDER BY payment_date) AS prev_amount,
  amount - LAG(amount) OVER (PARTITION BY customer_id ORDER BY payment_date) AS change
FROM payment;

-- FIRST_VALUE: each customer's very first payment amount, shown
-- alongside every subsequent row
SELECT customer_id, payment_date, amount,
  FIRST_VALUE(amount) OVER (PARTITION BY customer_id ORDER BY payment_date
                             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS first_payment
FROM payment;

Pivoting with conditional aggregation

Standard SQL has no universal PIVOT keyword — SQL Server and Oracle have vendor-specific syntax, PostgreSQL requires the tablefunc extension's crosstab(). The portable technique that works identically on every dialect is conditional aggregation: a CASE expression inside an aggregate function, once per target column.

-- Pivot: one row per store, one column per rating, counts of films
-- rented — portable across every SQL dialect, no PIVOT keyword needed
SELECT
  i.store_id,
  COUNT(*) FILTER (WHERE f.rating = 'G')  AS g_rentals,
  COUNT(*) FILTER (WHERE f.rating = 'PG') AS pg_rentals,
  COUNT(*) FILTER (WHERE f.rating = 'R')  AS r_rentals
FROM rental r
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film f ON i.film_id = f.film_id
GROUP BY i.store_id;

-- The universally-portable equivalent using CASE instead of FILTER
-- (FILTER is PostgreSQL/SQL:2023; CASE-in-SUM works everywhere,
-- including older MySQL and SQL Server)
SELECT
  i.store_id,
  SUM(CASE WHEN f.rating = 'G'  THEN 1 ELSE 0 END) AS g_rentals,
  SUM(CASE WHEN f.rating = 'PG' THEN 1 ELSE 0 END) AS pg_rentals,
  SUM(CASE WHEN f.rating = 'R'  THEN 1 ELSE 0 END) AS r_rentals
FROM rental r
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film f ON i.film_id = f.film_id
GROUP BY i.store_id;

Gaps and islands: finding consecutive runs

"Gaps and islands" describes any problem where you need to find consecutive runs (islands) or breaks in sequence (gaps) — consecutive login days, a customer's continuous rental streak, uninterrupted stretches of a sensor reading. The canonical technique subtracts a ROW_NUMBER() from the actual date; within one unbroken run, that difference is constant, which gives you a free grouping key for the island.

-- Find each customer's longest streak of consecutive rental-days
WITH rental_days AS (
  SELECT DISTINCT customer_id, rental_date::date AS rental_day
  FROM rental
),
numbered AS (
  SELECT customer_id, rental_day,
    ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY rental_day) AS rn
  FROM rental_days
),
islands AS (
  SELECT customer_id, rental_day,
    rental_day - (rn * INTERVAL '1 day') AS island_key   -- constant within a streak
  FROM numbered
)
SELECT customer_id, MIN(rental_day) AS streak_start, MAX(rental_day) AS streak_end,
  COUNT(*) AS streak_length
FROM islands
GROUP BY customer_id, island_key
ORDER BY streak_length DESC;

Deduplication with ROW_NUMBER

When duplicate rows exist without a natural unique key to DISTINCT on (e.g., a messy import with true duplicates plus rows that differ only in an unimportant timestamp), ROW_NUMBER() partitioned by the logical dedup key and filtered to rn = 1 is the portable, precise way to keep exactly one row per group — and unlike DISTINCT, it lets you control which duplicate survives via the ORDER BY.

-- Keep only the most recent payment per (customer_id, rental_id) pair,
-- discarding older duplicate/corrected rows
WITH ranked AS (
  SELECT *,
    ROW_NUMBER() OVER (PARTITION BY customer_id, rental_id
                        ORDER BY payment_date DESC) AS rn
  FROM payment
)
SELECT * FROM ranked WHERE rn = 1;

Declarative SQL, procedural execution

You write what you want; the query planner (also called the optimizer) decides how to get it — which indexes to use, which join algorithm, what order to join tables in. Two queries that return identical results can execute completely differently, and the same query can execute differently on different days as table statistics change. This is precisely why "it worked fine yesterday" is a real phenomenon and not user error: the planner re-decides its strategy based on current statistics, not the query text alone.

EXPLAIN vs. EXPLAIN ANALYZE

EXPLAIN shows the planner's intended plan and its cost estimates, without running the query. EXPLAIN ANALYZE actually executes the query and shows real elapsed time and real row counts alongside the estimates — the gap between estimated and actual rows is often the single most useful diagnostic signal in performance work, because a large gap means the planner's statistics are stale or its assumptions about your data's distribution are wrong, and every downstream decision (join algorithm, memory allocation) was made on bad information.

EXPLAIN ANALYZE
SELECT c.first_name, c.last_name, SUM(p.amount) AS total_spent
FROM customer c
JOIN payment p ON c.customer_id = p.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
ORDER BY total_spent DESC
LIMIT 10;
Limit  (cost=1250.34..1250.36 rows=10 width=64) (actual time=18.221..18.224 rows=10 loops=1)
  ->  Sort  (cost=1250.34..1257.84 rows=3000 width=64) (actual time=18.219..18.220 rows=10 loops=1)
        Sort Key: (sum(p.amount)) DESC
        ->  HashAggregate  (cost=1100.00..1180.00 rows=3000 width=64) (actual time=15.900..17.100 rows=599 loops=1)
              Group Key: c.customer_id
              ->  Hash Join  (cost=85.50..950.00 rows=16000 width=24) (actual time=1.200..12.500 rows=16044 loops=1)
                    Hash Cond: (p.customer_id = c.customer_id)
                    ->  Seq Scan on payment p  (cost=0.00..750.00 rows=16000 width=10) (actual time=0.010..5.200 rows=16044 loops=1)
                    ->  Hash  (cost=60.99..60.99 rows=599 width=18) (actual time=1.100..1.101 rows=599 loops=1)
                          ->  Seq Scan on customer c  (cost=0.00..60.99 rows=599 width=18) (actual time=0.005..0.450 rows=599 loops=1)

Read plans from the innermost/bottom node outward — that's the order execution actually happens in, even though the outermost node (here, Limit) is printed first. Here, estimated and actual row counts on Seq Scan on payment match almost exactly (16000 vs 16044) — the planner's statistics are accurate, so this plan is trustworthy. A large mismatch would be the signal to run ANALYZE payment; to refresh statistics before trusting anything else in the plan.

Join algorithms: nested loop, hash, merge

  • Nested Loop — for each row of the outer table, scan the inner table (or probe an index). Efficient when one side is small or a good index exists on the join column; catastrophic on two large unindexed tables because cost grows with the product of both sizes.
  • Hash Join — builds an in-memory hash table on the smaller input, then probes it once per row of the larger input. Excellent for large equi-joins (= conditions) when the smaller side fits comfortably in memory.
  • Merge Join — both inputs sorted on the join key, then merged in one pass. Efficient when both sides are already sorted (e.g., via an index) or the data is naturally ordered, avoiding a separate hash-build step entirely.

You rarely force a join algorithm directly — the planner picks based on estimated table sizes, available indexes, and available memory (work_mem in PostgreSQL). Recognizing which one is chosen tells you what to fix: a nested loop where you expected a hash join usually means the planner thinks one side is smaller than it actually is, which traces back to stale statistics or a missing index.

B-tree mechanics, briefly

The default index type on every major relational engine is a B-tree — a balanced, sorted tree structure that turns "find rows matching X" from a full table scan (O(n)) into a small number of page reads (O(log n)). This is why an index helps equality and range predicates (=, <, BETWEEN, ORDER BY) but does nothing for a predicate that can't be expressed as a sorted-tree lookup, like WHERE column % 2 = 0 or a leading-wildcard LIKE '%term' — the tree is sorted on the column's raw value, and neither of those predicates can be answered by walking a sorted structure without touching every row anyway.

Composite index column order matters — a lot

A composite (multi-column) index is one sorted structure across several columns, in the order you declare them — not several independent single-column indexes glued together. The tree is sorted by the first column, then by the second within each value of the first, and so on. This has a direct practical consequence: a composite index on (a, b) can serve queries filtering on a alone or on a AND b, but generally cannot efficiently serve a query filtering on b alone — the tree isn't sorted by b at the top level, so the engine can't jump straight to the relevant rows.

The standard heuristic: put the column with an equality predicate before columns with a range predicate, and put higher-selectivity columns (those that narrow the result set the most) earlier when several columns are all filtered by equality. Selectivity is the fraction of rows a predicate eliminates — a column like customer_id (thousands of distinct values) is highly selective; a column like rating (5 distinct values) barely narrows anything and gains little from being first in a composite index.

-- Query: filter by customer_id (equality) AND a payment_date range
SELECT * FROM payment
WHERE customer_id = 42 AND payment_date >= '2026-01-01';

-- Good composite index: equality column first, range column second —
-- the tree can jump straight to customer_id=42, then scan a contiguous
-- sorted range of dates within that
CREATE INDEX idx_payment_customer_date ON payment (customer_id, payment_date);

-- A composite index in the WRONG order (range column first) can only
-- use payment_date to narrow the scan, then must check customer_id
-- row-by-row within that broader range — far less effective

Covering indexes and index-only scans

When an index contains every column a query needs — both the filtered columns and the selected columns — the engine can answer the query entirely from the index without touching the underlying table at all. This is an index-only scan, and it's often the single biggest optimization available for a hot, narrow, frequently-run query, because it eliminates a whole layer of random-access disk/page reads.

When an index hurts

Every index costs write throughput (every INSERT/UPDATE/DELETE must also update the index) and storage. An index is actively counterproductive when: the column has very low selectivity (a boolean flag with a 90/10 split gains little), the table is small enough that a sequential scan is already fast, or the table is write-heavy with few reads against that column. "Add an index" is not a free action — the right question is always whether the read-time savings outweigh the write-time and storage cost for this specific table's access pattern, not a blanket rule.

Common mistake: Indexing every foreign key "just in case." Foreign keys used only for referential integrity checks and never filtered/joined on in actual queries gain nothing from an index but still pay the full write-time cost — index the columns your queries actually touch, verified with EXPLAIN, not the columns that merely look important in the schema.

ACID, briefly and precisely

Atomicity — a transaction's statements all succeed or all roll back together, never partially. Consistency — a transaction moves the database from one valid state to another, respecting every constraint. Isolation — concurrent transactions don't see each other's uncommitted work (to a degree controlled by isolation level — see below). Durability — once committed, a transaction survives a crash. Isolation is the one engineers most often get wrong in practice, because unlike the other three it's not all-or-nothing — it's a dial with real tradeoffs at every setting.

Concurrency anomalies

  • Dirty read — reading another transaction's uncommitted changes, which might later roll back, leaving you having acted on data that never actually existed.
  • Non-repeatable read — reading the same row twice in one transaction and getting different values because another transaction committed a change in between.
  • Phantom read — re-running the same query twice in one transaction and getting a different set of rows (not just different values), because another transaction inserted or deleted rows matching your predicate in between.

MVCC vs. locking: how "isolation" actually gets implemented

PostgreSQL, MySQL/InnoDB, and Oracle implement isolation primarily through MVCC (Multi-Version Concurrency Control): instead of blocking readers behind writers, the engine keeps multiple versions of a row and gives each transaction a consistent snapshot as of when it started. This is why, in these engines, readers never block writers and writers never block readers under the default isolation level — a genuinely different experience from older lock-based systems where a long-running read could stall writes across the whole table. Writers still block other writers on the same row (via row-level locks), which is where deadlocks come from: two transactions each holding a lock the other needs, resolved by the engine detecting the cycle and forcibly aborting one transaction.

-- Choosing isolation level explicitly for a transaction that must
-- see a fully consistent view for its entire duration (e.g., a
-- financial reconciliation report that reads several tables)
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT SUM(amount) FROM payment WHERE payment_date < '2026-06-01';
-- ... more reads across other tables, all seeing the same snapshot ...
COMMIT;

-- SERIALIZABLE for a case where correctness under concurrent writes
-- genuinely matters more than throughput — e.g., checking then
-- decrementing available inventory without a race condition
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT quantity FROM inventory WHERE inventory_id = 501 FOR UPDATE;
-- ... application checks quantity > 0, then updates ...
COMMIT;

The practical rule: default to READ COMMITTED for ordinary OLTP work — it's fast and prevents the anomaly (dirty reads) most likely to cause real damage. Reach for REPEATABLE READ or SERIALIZABLE only for the specific operations where a race condition would cause a correctness bug (double-booking, double-spending, double-decrementing inventory) — the stronger the isolation level, the more transactions abort-and-retry under contention, so applying it everywhere by default trades away throughput you didn't need to give up.

SQL:2023: the current standard

SQL:2023 (ISO/IEC 9075:2023), adopted June 2023, is the current edition of the SQL standard — the first update since SQL:2016. Its headline addition is a proper JSON data type with a simplified dot-notation query syntax, plus new scalar/aggregate functions including GREATEST, LEAST, ANY_VALUE, and padding/trim functions (RPAD, LPAD, RTRIM, LTRIM). It also introduced SQL/PGQ, a property-graph query sublanguage layered on top of relational tables — a sign that graph-shaped querying is being pulled into mainstream SQL rather than staying a specialty NoSQL feature. Engine adoption of SQL:2023 features varies and is still catching up as of 2026; check current release notes per engine before relying on a specific feature being available.

JSON/JSONB across engines

Every major engine now supports storing and querying JSON documents inside relational tables — useful for genuinely semi-structured data (an API payload, user preferences) without forcing a schema onto data that doesn't have one, but the query syntax still diverges sharply by vendor.

-- PostgreSQL: -> for JSON, ->> for text extraction, jsonb_path_query
-- for more complex paths. JSONB (binary JSON) is generally preferred
-- over plain JSON — it's indexable and doesn't preserve key order/whitespace
SELECT customer_id, preferences->>'newsletter' AS newsletter_opt_in
FROM customer_prefs
WHERE preferences @> '{"newsletter": true}';

-- MySQL: JSON_EXTRACT / the -> shorthand, ->> for unquoted text
SELECT customer_id, preferences->>'$.newsletter' AS newsletter_opt_in
FROM customer_prefs
WHERE JSON_EXTRACT(preferences, '$.newsletter') = true;

-- SQL Server: JSON_VALUE for scalar extraction, JSON_QUERY for objects/arrays
SELECT customer_id, JSON_VALUE(preferences, '$.newsletter') AS newsletter_opt_in
FROM customer_prefs
WHERE JSON_VALUE(preferences, '$.newsletter') = 'true';

Generated (computed) columns

A generated column is computed automatically from other columns in the same row, either on read (VIRTUAL) or stored on write (STORED) — useful for derived values you want to filter/index without duplicating write logic across every application code path that inserts a row.

-- PostgreSQL / MySQL / SQLite: STORED generated column
ALTER TABLE payment ADD COLUMN amount_with_tax NUMERIC
  GENERATED ALWAYS AS (amount * 1.12) STORED;

-- SQL Server: computed column (PERSISTED is the STORED equivalent)
ALTER TABLE payment ADD amount_with_tax AS (amount * 1.12) PERSISTED;

MERGE: the SQL:2023-standard upsert

Unlike the vendor-specific upserts in Module 5.1, MERGE is part of the SQL standard itself (since SQL:2003, refined since) and is the most portable way to express "insert or update" logic once your target engine supports it — PostgreSQL added MERGE in version 15, so on a current Postgres 18 install you can use either ON CONFLICT or standard MERGE, with MERGE being the more portable choice if the same logic needs to run against SQL Server too.

Storage/compute separation: what "serverless Postgres" actually means

Traditional Postgres couples storage and compute on the same machine — the database process and its data files live together, so scaling either one means resizing the whole instance. Modern serverless Postgres platforms (Neon is the clearest current example) separate the two: storage is a durable, versioned layer; compute is a stateless process that can start, stop, and scale independently against that storage. This single architectural choice is what makes the rest of this module's features possible — none of them are Postgres-the-language features, they're deployment-layer capabilities built on top of standard Postgres.

Database branching: schema changes without shared-environment risk

Because storage is copy-on-write, creating a full copy of a database — every table, every row — becomes a near-instant, cheap metadata operation instead of a multi-hour pg_dump/restore. The practical workflow this enables: a fresh database branch per pull request, seeded from a copy of production or staging data, so a migration or a risky query can be tested against realistic data without touching the shared environment at all. This directly changes how you'd validate the optimization work from Phase 4 in a team setting — you test the index/rewrite on a branch with production-scale data, not on a shared staging database other engineers are also using, and not on a synthetic dataset too small to reveal the real performance problem.

Scale-to-zero and autoscaling

Because compute is decoupled from storage, an idle branch's compute can pause completely — no queries running, no cost accruing — and resume automatically within seconds when a new connection arrives. This changes the economics of preview/test environments specifically: a database-per-PR pattern that would be wasteful with always-on compute becomes close to free when idle branches cost nothing.

Connection pooling

Postgres connections are relatively expensive (each is a full OS process), which becomes a real constraint under high-concurrency, short-lived-connection workloads — classically, serverless application functions that each open a fresh connection per invocation. A connection pooler (PgBouncer is the standard, and most serverless Postgres platforms run an equivalent transparently) sits between the application and the database, reusing a small pool of real backend connections across many logical client connections. The practical implication: an application deployed to a serverless/edge runtime should connect through the platform's pooled connection string, not the direct database connection string, or it risks exhausting the database's connection limit under bursty traffic.

Read replicas and OLTP vs. OLAP

A read replica is a continuously-updated copy of the database that serves read-only queries, offloading reporting/analytics load from the primary so it doesn't compete with transactional (OLTP) writes for resources. This is the deployment-layer answer to a tension every Phase 4 optimization discussion eventually runs into: a heavy analytical query and a latency-sensitive transactional query have genuinely different resource profiles, and at scale the fix is often architectural (route reads to a replica, or to a purpose-built analytical engine like DuckDB for genuinely OLAP-shaped workloads) rather than purely a better index.

Glossary

Canonical terms for this guide. Definitions state what a term is, not how to use it. Each Avoid line lists synonyms that cause confusion.

Relational Theory & Design

Relation
A set of tuples sharing the same attributes — the mathematical object a SQL table approximates, but with no duplicate rows and no inherent order.
Avoid: "table" as a strict synonym — a SQL table can have duplicate rows and a physical storage order, which a true relation cannot.
Tuple
One element of a relation — an ordered set of attribute values, corresponding to one row.
Avoid: using "record" and "tuple" interchangeably in a theory context — "record" is a storage-layer term, "tuple" is the algebra term.
Attribute
A named element of a relation's structure, bound to a domain of legal values — corresponds to a column.
Avoid: "field" — common in application/ORM code, but not the relational-theory term.
Relational Algebra
The formal set of operators (selection, projection, union, difference, Cartesian product, and derived operators like join) that any relational query, including SQL, decomposes into.
Avoid: confusing with "algebraic" in the loose everyday sense — this refers specifically to Codd's five primitive operators and their derivatives.
Functional Dependency
A constraint A → B meaning the value of A always determines the value of B within a relation — the atomic unit normalization theory reasons about.
Avoid: "correlation" — a functional dependency is a strict, always-true determination, not a statistical association.
Normal Form (1NF–BCNF)
A named level of guarantee against a specific class of update anomaly, achieved by progressively removing partial and transitive functional dependencies from a table.
Avoid: "normalization" (statistics/ML rescaling) — an unrelated concept from a different field that happens to share the word.
Denormalization
A deliberate departure from a fully normalized schema, storing a derived or duplicated value to avoid a join at read time.
Avoid: treating this as a mistake by default — it's a legitimate tradeoff when applied deliberately to reporting/read layers, not the system of record.
Primary Key vs. Candidate Key
A candidate key is any minimal set of attributes that uniquely identifies a tuple; the primary key is the one candidate key a schema designates as the official identifier.
Avoid: assuming a table has only one candidate key — most tables have several (e.g., both an auto-increment ID and a unique email), and only one becomes "primary" by choice, not necessity.
Foreign Key
An attribute (or set of attributes) in one relation whose value must match a candidate key value in another relation (or be NULL), enforcing referential integrity between them.
Avoid: "reference" as a strict synonym in DDL contexts — application code loosely says "reference" for any pointer-like relationship, but a foreign key is a specifically enforced database constraint.
Entity-Relationship Model
A conceptual modeling notation (entities, attributes, relationships, cardinality) used to design a schema before translating it into relational tables.
Avoid: conflating with the finished relational schema itself — an ER diagram is a design artifact, not the physical table structure.

Querying

Predicate
A boolean-valued (in SQL: true/false/unknown) expression used to filter rows, as in a WHERE, HAVING, JOIN ON, or window PARTITION BY clause.
Avoid: "condition" is fine informally, but "predicate" is the precise term used in query-plan output and formal discussion.
Join
A relational operator combining rows from two relations based on a predicate — derived from a Cartesian product filtered by that predicate.
Avoid: assuming "join" implies "INNER JOIN" by default in every context — always specify the join type when precision matters.
Cartesian Product
The result of pairing every row of one relation with every row of another, with no filtering predicate applied.
Avoid: "cross join" as a purely negative term — it's a legitimate operator for generating combinations, only a bug when it happens unintentionally via a missing join predicate.
Subquery (Scalar / Correlated)
A query nested inside another; scalar means it returns exactly one value, correlated means it references a column from the enclosing query and conceptually re-evaluates per outer row.
Avoid: "nested query" as a precise synonym — informally fine, but doesn't distinguish scalar from correlated, which matters for both correctness and performance reasoning.
CTE (Common Table Expression)
A named, WITH-declared subquery, referenceable once (or, if recursive, referenceable within its own definition) within the statement that declares it.
Avoid: assuming a CTE is always materialized separately from the main query — in most current engines a non-recursive CTE is typically inlined by the optimizer like an ordinary subquery.
Window Function
A function computing a value across a set of related rows (a "window," defined by PARTITION BY and a frame clause) without collapsing the result set, unlike GROUP BY.
Avoid: "aggregate function" as a strict synonym — an aggregate function collapses rows; the same function used with OVER() does not.
Frame Clause
The part of a window function's OVER() clause (ROWS/RANGE/GROUPS BETWEEN ...) that defines exactly which rows within the current partition participate in the calculation for the current row.
Avoid: assuming the default frame is always "all rows in the partition" — with an ORDER BY present, the implicit default is RANGE UNBOUNDED PRECEDING TO CURRENT ROW, a common source of silent bugs.
Set Operation
UNION, INTERSECT, or EXCEPT — an operator that combines two result sets treated as true sets, requiring matching column count and compatible types.
Avoid: confusing with a JOIN — set operations combine result sets vertically (more rows, same columns); joins combine tables horizontally (same rows, more columns).
Aggregate Function
A function (COUNT, SUM, AVG, MIN, MAX) that collapses a group of rows into a single summary value.
Avoid: assuming every aggregate ignores NULLs identically — COUNT(*) counts NULL rows, COUNT(column) does not, and most other aggregates skip NULLs in their input silently.
NULL / Three-Valued Logic
SQL's representation of an unknown or missing value, which makes every comparison against it evaluate to UNKNOWN rather than TRUE or FALSE.
Avoid: "zero" or "empty string" as equivalents — NULL specifically means "no value/unknown," a distinct concept from any actual value in the column's domain.

Optimization & Execution

Query Plan
The concrete sequence of operations (scans, joins, sorts, aggregations) the engine will execute, or did execute, to answer a query — shown by EXPLAIN / EXPLAIN ANALYZE.
Avoid: assuming the same query always produces the same plan — the planner re-decides based on current statistics, which change as data changes.
Cost-Based Optimizer
The component that estimates the resource cost of multiple possible execution strategies for a query and selects the cheapest one it can find.
Avoid: assuming "cheapest" means "fastest in every case" — cost estimates depend on statistics that can be stale or wrong, producing a plan that's cheapest in theory but slow in practice.
Cardinality Estimation
The optimizer's prediction of how many rows a given step in a query plan will produce, based on table statistics.
Avoid: treating EXPLAIN's estimated row counts as ground truth — EXPLAIN ANALYZE's actual counts are the only reliable check.
Index
A separate, ordered data structure (typically a B-tree) that lets the engine locate rows matching a predicate without scanning the entire table.
Avoid: treating an index as a free performance upgrade — every index adds write-time and storage cost.
B-Tree Index
The default index structure on every major relational engine: a balanced, sorted tree enabling O(log n) lookups for equality and range predicates.
Avoid: assuming a B-tree helps every predicate type — it does nothing for predicates that can't be expressed as a sorted-tree lookup, like a leading-wildcard LIKE.
Covering Index / Index-Only Scan
An index containing every column a query needs (filtered and selected), letting the engine answer the query without touching the underlying table at all.
Avoid: assuming any index that happens to include the right columns automatically produces an index-only scan — engine-specific visibility/freshness rules can still force a table lookup.
Selectivity
The fraction of rows a predicate eliminates — a high-selectivity predicate (or column) narrows the result set sharply; a low-selectivity one barely narrows it at all.
Avoid: confusing with "specificity" in a general-English sense — selectivity is a precise, statistics-driven quantity the optimizer computes.
Join Algorithm
The specific method (nested loop, hash join, merge join) the engine uses to physically combine two row sets during execution, chosen by the optimizer per query.
Avoid: "join type" as a synonym — join type (INNER/LEFT/etc.) is what you write in SQL; join algorithm is how the engine executes it, chosen independently of the type.
Transaction
A sequence of one or more statements executed as a single atomic unit — either all effects commit, or none do.
Avoid: assuming every statement outside an explicit BEGIN/COMMIT block is transaction-free — most engines wrap each individual statement in an implicit transaction by default.
Isolation Level
A configurable setting controlling which concurrency anomalies (dirty read, non-repeatable read, phantom read) a transaction is protected against.
Avoid: assuming a stricter isolation level is always better — stronger isolation increases abort/retry rates under contention, a real throughput cost.
MVCC (Multi-Version Concurrency Control)
A concurrency-control technique where the engine keeps multiple versions of a row so readers see a consistent snapshot without blocking concurrent writers.
Avoid: "locking" as a synonym — MVCC is specifically designed to avoid the reader/writer blocking that pure lock-based concurrency control causes.

Modern & Portable SQL

Dialect
A specific engine's implementation of SQL, including its extensions beyond and deviations from the ANSI/ISO standard.
Avoid: assuming "standard SQL" is a complete, directly-runnable language on its own — every real engine is a dialect with its own extensions layered on the standard core.
SQL Standard (ANSI/ISO SQL:2023)
The formally published specification (ISO/IEC 9075) that defines core SQL syntax and semantics; SQL:2023 is the current edition as of 2026.
Avoid: assuming every engine implements the full current standard — conformance is partial and varies significantly by engine and by feature.
Upsert
A single operation that inserts a row if it doesn't exist or updates it if it does, keyed on a uniqueness constraint.
Avoid: assuming upsert syntax is portable — it's one of the sharpest dialect divergence points in SQL (Module 5.1).
JSON / JSONB
Semi-structured document data stored inside a relational column; JSONB (PostgreSQL-specific) is a parsed binary representation that supports indexing, unlike plain-text JSON.
Avoid: using JSON/JSONB as a substitute for proper normalization of genuinely structured, frequently-queried data — it's suited to sparse or truly variable-shape data, not a shortcut around schema design.
Generated Column
A column whose value is computed automatically from other columns in the same row, either on read or stored on write.
Avoid: "computed column" as a universal term — it's the correct SQL Server term specifically; other engines call the same concept a generated column.
Serverless Database
A database deployment model where compute is decoupled from storage and can scale independently, including down to zero when idle.
Avoid: assuming "serverless" means "no server exists" — it means server management and scaling are abstracted away, not that there's no underlying compute.
Database Branching
Creating a full, independent, cheaply-copied instance of a database (typically via copy-on-write storage) for isolated testing, most commonly one branch per pull request.
Avoid: confusing with a read replica — a branch is independently writable and diverges from its source; a replica stays in lockstep, read-only.
Connection Pooling
Reusing a small set of real database connections across many logical client connections, to avoid exhausting the database's connection limit under high concurrency.
Avoid: assuming connection pooling is only relevant to serverless deployments — any high-concurrency application benefits, serverless just makes it unavoidable.
Read Replica
A continuously-updated, read-only copy of a database used to offload read/reporting traffic from the primary write instance.
Avoid: "database branch" as a synonym — a replica is read-only and stays synchronized; a branch is writable and diverges once created.
OLTP vs. OLAP
OLTP (Online Transaction Processing) describes many small, fast read/write operations typical of application databases; OLAP (Online Analytical Processing) describes fewer, larger, read-heavy analytical queries typical of reporting/BI.
Avoid: assuming one engine configuration serves both workloads equally well at scale — the resource profiles genuinely conflict, which is why read replicas and dedicated analytical engines exist.
