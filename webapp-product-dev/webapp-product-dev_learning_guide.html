What a PRD Is (and Is Not)

A Product Requirements Document defines what to build and why — not how. It is the contract between the person with the idea and the person (often the same person) who writes the code. A good PRD stops scope creep before the first commit. The test of a good PRD: a developer should be able to read it and build the right thing without asking a single clarifying question.

A PRD is not a design document (that is the TDD), not a UI spec (that is a wireframe), and not a backlog (that is a TODO list). Each serves a different purpose. The most common beginner mistake is collapsing all four into one document — the result serves none of those purposes well and causes arguments at every stage of development.

PRD Structure — the Eight Sections

## [Product Name] — Product Requirements Document
Version: X.Y | Date: YYYY-MM-DD | Owner: [Name]
Status: Draft / Active / Archived

## 1. Overview
One paragraph: what the product does, who it is for, what problem it solves.
Current stage (prototype / MVP / growth).

## 2. Problem Statement
What pain exists today? What happens if we do not build this?
Be specific: "Maintenance supervisors spend 2h/day interpreting raw SCADA numbers
with no failure-mode guidance."

## 3. Goals & Success Metrics
| Goal | Metric | Target |
|---|---|---|
| Demonstrate value | Demo completion rate | > 60% |

## 4. Target Users
Primary / Secondary / Tertiary personas. One sentence each.

## 5. User Stories & Acceptance Criteria
- As a [persona], I want [action] so that [outcome].
  - AC: [verifiable condition 1]
  - AC: [verifiable condition 2]

## 6. Functional Requirements
| ID | Requirement | Priority |
|---|---|---|
| FR-01 | [Must Have / Should Have / Nice to Have] | Must Have |

## 7. Non-Functional Requirements
Performance · Security · Scalability · Availability · Accessibility

## 8. Out of Scope
List explicitly. "We will NOT build X in this version."

Writing Acceptance Criteria

Every user story needs at least one AC. A good AC is binary — it either passes or fails. Use this formula: Given [context], when [action], then [observable outcome].

Bad AC: "The dashboard loads quickly." Good AC: "Dashboard initial render completes in < 3 seconds on a 10 Mbps connection."

Prioritization: MoSCoW

Label every functional requirement. Must Have — MVP is broken without it. Should Have — important but workaroundable. Could Have — nice to have, cut if time-pressed. Won't Have — explicitly out of scope for this version.

Common mistake: Labeling everything "Must Have" defeats the purpose. If your MVP is truly broken without all 20 requirements, you have not defined an MVP — you have defined v1.0. Force the constraint: if you could only ship 5 FRs, which 5? Those are your real Must Haves. Everything else is a Should Have or lower until proven otherwise.

Disambiguation: TDD here means Technical Design Document — not Test-Driven Development. Both acronyms are common in software. This module covers documentation; Module 5.1 covers testing.

TDD Structure — the Nine Sections

A Technical Design Document answers how the PRD requirements will be built. It is written once per project and updated as architecture decisions change. Every decision in the TDD should trace back to a requirement in the PRD. If you cannot point to a PRD requirement that justifies a technology choice, that choice is either unnecessary complexity or a missing requirement — either way, it should be challenged before you write a line of code.

## [Product Name] — Technical Design Document
Version: X.Y | Date: YYYY-MM-DD | Author: [Name]
Related PRD: [link]

## 1. Summary
3–5 sentences: full-stack overview, key technology choices, scope.

## 2. Architecture Overview
ASCII diagram showing: browser → frontend → API layer → database → external services.
Include data flow arrows and key component names.

## 3. Tech Stack
| Layer | Technology | Rationale |
|---|---|---|
| Frontend | Next.js 16 App Router + TypeScript | SSR + API routes, strict types |
| Auth | Supabase Auth (magic link) | Passwordless, cookie sessions |
| Database | Supabase PostgreSQL + RLS | Managed Postgres, built-in auth |
| AI/LLM | Anthropic Claude API (claude-sonnet-4-6) | Streaming diagnostics, prompt caching |
| Deployment | Vercel | GitHub integration, preview URLs |

## 4. Component Design
One subsection per major component. For each:
- Purpose (one sentence)
- Inputs / Outputs
- Key logic
- State (if React component)

## 5. Data Models
Full schema: table name, columns (name, type, nullable), constraints, indexes.
Note which columns have RLS policies.

## 6. API Design
| Method | Path | Auth | Body | Response |
|---|---|---|---|---|
| POST | /api/analyze-csv | Required | multipart/form-data | ReadableStream |

## 7. AI Integration
- Which model, which endpoint
- Prompt architecture (system prompt + user message structure)
- Streaming protocol
- Token limits and cost controls

## 8. Security Model
- Auth mechanism
- RLS policy matrix (table × role → allowed operations)
- Rate limiting (which routes, which limits)
- Secrets management

## 9. Testing Strategy
- Unit: what to test with Vitest
- Integration: what to test with Playwright
- CI: when tests run

Multi-Tenant Schema Patterns

SaaS apps need data isolation between customers. The most practical approach at Supabase scale is shared schema with org-scoped RLS: one set of tables, every row tagged with an organization_id, and RLS policies that filter to the current user's org.

-- Organizations table (one row per customer account)
CREATE TABLE organizations (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- User profiles (one per auth.users row, linked to one org)
CREATE TABLE profiles (
  id              UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  organization_id UUID NOT NULL REFERENCES organizations(id),
  full_name       TEXT,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Helper: returns the current user's org_id
CREATE OR REPLACE FUNCTION my_org() RETURNS UUID
  LANGUAGE sql STABLE SECURITY DEFINER AS $$
  SELECT organization_id FROM profiles WHERE id = auth.uid()
$$;

Row-Level Security Policies

RLS is enforced at the database level — it cannot be bypassed by a bug in application code. Every table should have RLS enabled and explicit policies. No policy = no access. Without RLS, a single bug in your API layer — a missing .eq("organization_id", orgId) filter — exposes every tenant's data to every other tenant. RLS makes that class of bug structurally impossible: the database enforces the tenant boundary regardless of what your application code does.

-- Assets table
CREATE TABLE assets (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id UUID NOT NULL REFERENCES organizations(id),
  name            TEXT NOT NULL,
  tag_number      TEXT NOT NULL,
  asset_type      TEXT NOT NULL,
  is_demo         BOOLEAN NOT NULL DEFAULT false,
  is_active       BOOLEAN NOT NULL DEFAULT true,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE assets ENABLE ROW LEVEL SECURITY;

-- Anon users see only demo rows; authenticated users see their org
CREATE POLICY "assets_select" ON assets FOR SELECT USING (
  is_demo = true
  OR organization_id = my_org()
);

-- Only authenticated users in the same org can insert/update
CREATE POLICY "assets_insert" ON assets FOR INSERT WITH CHECK (
  organization_id = my_org()
);

CREATE POLICY "assets_update" ON assets FOR UPDATE USING (
  organization_id = my_org()
);

Soft Deletes and Audit Columns

Never hard-delete user-facing records. Add deleted_at TIMESTAMPTZ and filter WHERE deleted_at IS NULL. Add created_at and updated_at to every table. Use a trigger to auto-update updated_at.

-- health_reports: stores AI diagnostic output (never raw sensor data)
CREATE TABLE health_reports (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id UUID NOT NULL REFERENCES organizations(id),
  asset_id        UUID REFERENCES assets(id),
  user_id         UUID NOT NULL REFERENCES auth.users(id),
  health_score    INTEGER CHECK (health_score BETWEEN 0 AND 100),
  report_text     TEXT NOT NULL,
  model_used      TEXT NOT NULL,
  source          TEXT NOT NULL DEFAULT 'csv', -- 'csv' | 'dashboard'
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE health_reports ENABLE ROW LEVEL SECURITY;

CREATE POLICY "health_reports_select" ON health_reports FOR SELECT USING (
  organization_id = my_org()
);
CREATE POLICY "health_reports_insert" ON health_reports FOR INSERT WITH CHECK (
  organization_id = my_org()
);

Indexes for Query Performance

Add compound indexes on every column pair you will use in a WHERE clause together. For time-series data, always index on (asset_id, ts DESC).

-- sensor_readings time-series index
CREATE INDEX idx_sensor_readings_asset_ts
  ON sensor_readings (asset_id, ts DESC);

-- health_reports per-user count (used for free-tier enforcement)
CREATE INDEX idx_health_reports_user_id
  ON health_reports (user_id);

TypeScript Strict Mode

Edit tsconfig.json to enable strict mode and path aliases. The strict flag enables noImplicitAny, strictNullChecks, and strictFunctionTypes — all necessary for catching bugs at compile time rather than runtime. In practice, strictNullChecks catches the most real-world bugs: without it, TypeScript lets you call .map() on a value that could be undefined, and you find out in production rather than at the keyboard. noUncheckedIndexedAccess catches the array-index equivalent — arr[0] becomes string | undefined, not string.

{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "paths": {
      "@/*": ["./src/*"]
    },
    "target": "ES2022",
    "lib": ["dom", "dom.iterable", "esnext"],
    "module": "esnext",
    "moduleResolution": "bundler",
    "jsx": "preserve",
    "incremental": true,
    "plugins": [{ "name": "next" }]
  },
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts"],
  "exclude": ["node_modules"]
}

Supabase Client Factories

The @supabase/ssr package provides cookie-aware clients. You need three separate factories — one for the browser (cookie read/write), one for server components (cookie read only), and one for the service role (bypasses RLS — use sparingly).

// src/lib/supabase-browser.ts
// ALWAYS use this on the client side — never import from supabase-server
import { createBrowserClient } from "@supabase/ssr";

export function createBrowserSupabase() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
  );
}
// src/lib/supabase-server.ts
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

export async function createServerSupabase() {
  const cookieStore = await cookies();
  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() { return cookieStore.getAll(); },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value, options }) =>
            cookieStore.set(name, value, options)
          );
        },
      },
    }
  );
}

Magic links remove the entire password surface from your system: no password hashing to get right, no password-reset flow to build, no brute-force or credential-stuffing vectors. Route Protection Middleware

// src/middleware.ts
import { createServerClient } from "@supabase/ssr";
import { NextRequest, NextResponse } from "next/server";

export async function middleware(request: NextRequest) {
  let response = NextResponse.next({ request });
  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() { return request.cookies.getAll(); },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) =>
            request.cookies.set(name, value)
          );
          response = NextResponse.next({ request });
          cookiesToSet.forEach(({ name, value, options }) =>
            response.cookies.set(name, value, options)
          );
        },
      },
    }
  );

  // Use getUser() — NOT getSession() — in server code. getUser() revalidates the
  // JWT against the Supabase Auth server; getSession() only decodes the cookie and
  // can be spoofed. Calling getUser() here also refreshes the session cookie.
  const { data: { user } } = await supabase.auth.getUser();

  if (!user && request.nextUrl.pathname.startsWith("/dashboard")) {
    return NextResponse.redirect(new URL("/auth/sign-in", request.url));
  }

  return response;
}

export const config = {
  matcher: ["/dashboard/:path*"],
};

Security gotcha: In server code (middleware, Server Components, route handlers) always authenticate with supabase.auth.getUser(). It makes a request to the Auth server to verify the token. getSession() reads the session straight from the cookie without revalidating it, so a forged cookie passes — never gate access on it server-side. On the client, getSession() is fine because there is no trust boundary to cross.

Zod Input Validation

Never trust request bodies. Parse and validate with Zod at the route boundary before any business logic runs. Without validation: a null body crashes your handler with an unhandled exception (opaque 500 to the caller, noise in your logs); an oversized string field bloats your database; a malformed UUID surfaces as a confusing Postgres error deep in the stack rather than a clear 400 at the API surface. Validation is the contract between your API and its callers — enforce it at the entry point, not downstream.

// src/app/api/leads/route.ts
import { NextRequest, NextResponse } from "next/server";
import { z } from "zod";
import { createServerSupabase } from "@/lib/supabase-server";

const LeadSchema = z.object({
  email: z.string().email(),
  name: z.string().min(1).max(200),
  company: z.string().max(200).optional(),
  message: z.string().max(2000).optional(),
  source: z.enum(["landing_hero", "dashboard_cta", "csv_limit"]),
});

  return NextResponse.json({ success: true }, { status: 201 });
}

Parallel Queries with Promise.all

// src/app/api/anomalies/route.ts
import { NextRequest, NextResponse } from "next/server";
import { createServerSupabase } from "@/lib/supabase-server";
import { z } from "zod";

const QuerySchema = z.object({
  assetId: z.string().uuid(),
  days: z.coerce.number().int().min(1).max(90).default(7),
});

export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url);
  const parsed = QuerySchema.safeParse({
    assetId: searchParams.get("assetId"),
    days: searchParams.get("days"),
  });

  if (!parsed.success) {
    return NextResponse.json({ error: "Invalid query params" }, { status: 400 });
  }

  const { assetId, days } = parsed.data;
  const since = new Date(Date.now() - days * 86_400_000).toISOString();
  const supabase = await createServerSupabase();

  const [readingsResult, anomaliesResult] = await Promise.all([
    supabase
      .from("sensor_readings")
      .select("ts, vibration, temperature, pressure, motor_current")
      .eq("asset_id", assetId)
      .gte("ts", since)
      .order("ts", { ascending: true })
      .limit(2000),
    supabase
      .from("anomaly_scores")
      .select("ts, severity, max_z_score")
      .eq("asset_id", assetId)
      .gte("ts", since)
      .order("ts", { ascending: true }),
  ]);

  if (readingsResult.error || anomaliesResult.error) {
    return NextResponse.json({ error: "Query failed" }, { status: 500 });
  }

  return NextResponse.json({
    readings: readingsResult.data,
    anomalies: anomaliesResult.data,
  });
}

DECISION RULE — Server vs. Client Component

Use SERVER component when:
  - Fetching data directly from Supabase (no useEffect needed)
  - Reading environment variables
  - The component has no interactivity

  Example: /dashboard/reports/page.tsx — fetches user reports on the server,
  no client state needed

Use CLIENT component ("use client") when:
  - Using useState, useEffect, useCallback, useContext
  - Responding to user events (onClick, onChange)
  - Using browser APIs (localStorage, window, navigator)

  Example: DashboardPage — needs selectedId state, useEffect for fetch

WRONG: Adding "use client" to every component because "it's easier"
RIGHT: Default to Server; add "use client" only when required

Streaming API Route with Prompt Caching

// src/app/api/report/route.ts
import Anthropic from "@anthropic-ai/sdk";
import { NextRequest, NextResponse } from "next/server";
import { createServerSupabase } from "@/lib/supabase-server";
import { logger } from "@/lib/logger";
import { z } from "zod";

const CLAUDE_MODEL = "claude-sonnet-4-6";

const DIAGNOSTIC_SYSTEM_PROMPT = `You are an expert predictive maintenance engineer.
Analyze the sensor statistics provided and return a concise diagnostic report in 3 parts:
1. Overall status and trend
2. Root cause hypothesis with named failure modes and evidence
3. Urgency-graded action: Monitor / Schedule maintenance / Act Now — inspect within 48h

Write in field-engineer language. Reference specific z-score deviations. Be concise — 150 to 400 tokens.`;

const RequestSchema = z.object({
  assetId: z.string().uuid(),
  healthScore: z.number().int().min(0).max(100),
  anomalyCount7d: z.number().int().min(0),
  peakVibrationSigma: z.number(),
  trend: z.enum(["stable", "degrading", "critical"]),
});

export async function POST(request: NextRequest) {
  const supabase = await createServerSupabase();
  // Server-side auth: getUser() revalidates the JWT; getSession() would be spoofable.
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });

  const body = await request.json().catch(() => null);
  const parsed = RequestSchema.safeParse(body);
  if (!parsed.success) return NextResponse.json({ error: "Invalid input" }, { status: 400 });

  const { assetId, healthScore, anomalyCount7d, peakVibrationSigma, trend } = parsed.data;

  // org membership lives in the profiles table (see Module 1.3) — not in user_metadata
  const { data: profile } = await supabase
    .from("profiles")
    .select("organization_id")
    .eq("id", user.id)
    .single();

  if (!profile) return NextResponse.json({ error: "No profile" }, { status: 403 });

  const anthropic = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

  const llmStream = anthropic.messages.stream({
    model: CLAUDE_MODEL,
    max_tokens: 400,
    system: [
      {
        type: "text",
        text: DIAGNOSTIC_SYSTEM_PROMPT,
        cache_control: { type: "ephemeral" },   // prompt caching — reduces cost on repeated calls
      },
    ],
    messages: [
      {
        role: "user",
        content: `Asset ID: ${assetId}
Health Score: ${healthScore}/100
7-day Anomaly Count: ${anomalyCount7d}
Peak Vibration Sigma: ${peakVibrationSigma.toFixed(2)}σ
Trend: ${trend}

Generate diagnostic report.`,
      },
    ],
  });

  // Build a PLAIN-TEXT stream from the SDK's text deltas. Do NOT return
  // llmStream.toReadableStream() directly — that emits raw JSON event objects,
  // and the client decodes the body as text, so it would render JSON, not prose.
  const encoder = new TextEncoder();
  let fullText = "";

  const readable = new ReadableStream<Uint8Array>({
    async start(controller) {
      try {
        for await (const event of llmStream) {
          if (
            event.type === "content_block_delta" &&
            event.delta.type === "text_delta"
          ) {
            fullText += event.delta.text;
            controller.enqueue(encoder.encode(event.delta.text));
          }
        }
      } catch (err) {
        controller.error(err);
        return;
      }
      controller.close();

      // Fire-and-forget: persist the assembled report after the stream completes.
      supabase
        .from("health_reports")
        .insert({
          organization_id: profile.organization_id,
          asset_id: assetId,
          user_id: user.id,
          health_score: healthScore,
          report_text: fullText,
          model_used: CLAUDE_MODEL,
          source: "dashboard",
        })
        .then(({ error }) => {
          if (error) logger.error({ event: "report_persist_failed", err: error.message });
        });
    },
  });

  return new NextResponse(readable, {
    headers: { "Content-Type": "text/plain; charset=utf-8" },
  });
}

Why prompt caching matters: The DIAGNOSTIC_SYSTEM_PROMPT is roughly 80 tokens. Without caching, every call to /api/report bills those tokens at full input pricing. With cache_control: { type: "ephemeral" }, Anthropic caches the prompt for up to 5 minutes — subsequent calls within that window are billed at cache-read pricing, which is approximately 90% cheaper for cached input tokens. For a feature users trigger repeatedly throughout a session, this compounds quickly. Log cache_read_input_tokens from the usage field to verify the cache is hitting.

Rendering the Stream in React

// src/components/AIReportPanel.tsx  (simplified)
"use client";
import { useState, useRef } from "react";

interface AIReportPanelProps {
  assetId: string;
  healthScore: number;
  anomalyCount7d: number;
  peakVibrationSigma: number;
  trend: "stable" | "degrading" | "critical";
}

export function AIReportPanel(props: AIReportPanelProps) {
  const [report, setReport] = useState("");
  const [streaming, setStreaming] = useState(false);
  const abortRef = useRef<AbortController | null>(null);

  async function runAnalysis() {
    abortRef.current = new AbortController();
    setStreaming(true);
    setReport("");

    const res = await fetch("/api/report", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(props),
      signal: abortRef.current.signal,
    });

    if (!res.body) return;
    const reader = res.body.getReader();
    const decoder = new TextDecoder();

    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      setReport(prev => prev + decoder.decode(value, { stream: true }));
    }
    setStreaming(false);
  }

  return (
    <div>
      <button onClick={runAnalysis} disabled={streaming}>
        {streaming ? "Analyzing…" : "Run Analysis"}
      </button>
      {streaming && (
        <button onClick={() => abortRef.current?.abort()}>Cancel</button>
      )}
      <pre>{report}</pre>
    </div>
  );
}

import { Ratelimit } from "@upstash/ratelimit";

function makeRatelimit(tokens: number, window: string) {
  if (!process.env.UPSTASH_REDIS_REST_URL || !process.env.UPSTASH_REDIS_REST_TOKEN) {
    // PASS_THROUGH in local dev — no Redis required

      limit: async () => ({ success: true, limit: tokens, remaining: tokens, reset: 0 }),

    redis: Redis.fromEnv(),
    limiter: Ratelimit.slidingWindow(tokens, window as `${number} ${"s" | "m" | "h" | "d"}`),

}

// src/lib/withRequestLog.ts
import { NextRequest, NextResponse } from "next/server";
import { logger } from "@/lib/logger";

type RouteHandler = (req: NextRequest) => Promise<NextResponse>;

export function withRequestLog(handler: RouteHandler): RouteHandler {
  return async (req: NextRequest) => {
    const start = Date.now();
    let status = 500;
    try {
      const res = await handler(req);
      status = res.status;
      return res;
    } catch (err) {
      logger.error({ event: "request_error", path: req.nextUrl.pathname, err });
      return NextResponse.json({ error: "Internal server error" }, { status: 500 });
    } finally {
      logger.info({
        event: "request",
        method: req.method,
        path: req.nextUrl.pathname,
        status,
        duration_ms: Date.now() - start,
      });
    }
  };
}

Glossary

Canonical terms for this guide. Definitions are tight by design — one or two sentences stating what a term is, not how to use it. Each entry includes an Avoid line listing synonyms or near-misses that cause confusion. Once a term appears here, it is used consistently across every module.

Product Definition

PRD (Product Requirements Document)
The contract that defines what to build and why — scope, target users, user stories, acceptance criteria, and prioritized functional requirements. The TDD answers how; the PRD answers what and why.
Avoid: spec, product spec, requirements doc — these terms blur the boundary between what and how that the PRD/TDD split enforces.
TDD (Technical Design Document)
The document that answers how the PRD will be built — architecture, technology choices with rationale, component design, API contracts, and security model. Every decision traces back to a PRD requirement. Not to be confused with Test-Driven Development.
Avoid: architecture doc, tech spec — acceptable elsewhere but not used in this guide; TDD is used consistently to mean the design document.
User Story
A requirement written from a persona's perspective: "As a [persona], I want [action] so that [outcome]." The "so that" clause is non-negotiable — it anchors the requirement to a real outcome and makes the story testable.
Avoid: feature request, ticket — both lack the persona and outcome context that make a story verifiable.
Acceptance Criteria (AC)
A binary, verifiable condition that a user story must satisfy before it is considered done. Written in Given/When/Then form: Given [context], when [action], then [observable outcome]. Binary means pass or fail — no partial credit.
Avoid: definition of done (broader, team-level agreement), success criteria (often qualitative and non-binary).
MoSCoW
A prioritization framework for functional requirements: Must Have (MVP breaks without it), Should Have (important but workaroundable), Could Have (cut if time-pressed), Won't Have (explicitly deferred). Forces ranking — if everything is Must Have, nothing is.
Avoid: high/medium/low priority — no shared definition of those levels across a team.
MVP (Minimum Viable Product)
The smallest set of Must Have features that delivers the core value proposition to real users and generates real feedback. A shipped product, not a prototype.
Avoid: prototype (not shipped to real users), v1 (implies a fuller feature set than MVP).
Scope Creep
The gradual, informal expansion of requirements beyond the agreed PRD — usually through ad hoc additions during development. An explicit Out of Scope section in the PRD is the primary defense.
Avoid: feature bloat — that is the outcome of scope creep, not the process itself.
Functional Requirement (FR)
A specific capability the system must provide, numbered and MoSCoW-prioritized in the PRD. Each FR should map to at least one TDD section that implements it.
Avoid: feature — a feature implies a user-facing unit of UX; a FR is a capability that may cross multiple features.
Non-Functional Requirement (NFR)
A quality attribute the system must have — performance, security, scalability, availability, or accessibility — rather than a specific capability. NFRs constrain how FRs are implemented.
Avoid: technical requirement — conflates NFRs with implementation details that belong in the TDD.

Project Setup & Database

Row-Level Security (RLS)
A PostgreSQL mechanism that filters the rows visible to any query based on a policy evaluated for the current session's role and claims. Enforced at the database level — cannot be bypassed by application code bugs.
Avoid: app-level filtering — application WHERE clauses can be accidentally omitted; RLS cannot be.
Multi-tenant
An architecture where a single database and application instance serves multiple customer organizations, with strict data isolation between tenants. In SensorHub, isolation is implemented via organization_id on every table plus RLS policies.
Avoid: multi-user — users share one organization; tenants are separate organizations with separate data.
Soft Delete
Marking a record as deleted by setting a deleted_at timestamp instead of removing the row. Preserves audit history and allows recovery. All queries must include WHERE deleted_at IS NULL.
Avoid: logical delete (same concept; soft delete is the more common term in this stack), archive.
Audit Columns
The standard set of created_at, updated_at, and optionally created_by columns on every table, tracking record history. updated_at is maintained by a database trigger, not application code.
Avoid: timestamps — too generic; audit columns have a defined purpose beyond time-tracking.
Migration
A versioned SQL file that transforms the database schema from one state to another. Applied sequentially by the Supabase CLI. Never edit a migration already applied to a shared environment — create a new one instead.
Avoid: SQL script, schema update — neither implies versioning or sequential application guarantees.
Anon Role
The Supabase database role used for unauthenticated requests. RLS policies for the anon role control what non-logged-in users can read. In SensorHub, anon users see only rows where is_demo = true.
Avoid: guest, public — user-experience terms; anon is the database role name used in RLS policies.
my_org()
The SQL helper function that returns the organization_id of the currently authenticated user by reading from the profiles table. Used in every RLS policy to enforce tenant isolation without repeating the JOIN logic in each policy.
Avoid: tenant helper — use the specific function name my_org() when referencing this function.
getUser() vs getSession()
getUser() revalidates the JWT against the Supabase Auth server — required in all server-side code where the trust boundary exists (middleware, Route Handlers, Server Components). getSession() decodes the cookie locally without revalidation — acceptable on the client, spoofable on the server.
Avoid: using getSession() server-side for any access-control decision.

Core Development

Server Component
A React component that runs only on the server, with direct database and environment-variable access. Sends HTML to the client — no JavaScript bundle. The default in Next.js App Router. Cannot use useState, useEffect, event handlers, or browser APIs.
Avoid: SSR component — SSR is a rendering strategy; Server Component is a component model. Related but distinct.
Client Component
A React component marked with "use client" that ships a JavaScript bundle to the browser and can use hooks, event handlers, and browser APIs. Push the boundary as deep in the component tree as possible to minimize bundle size.
Avoid: frontend component — all components are frontend; the distinction is where they execute (server vs. browser).
Route Handler
A Next.js App Router API endpoint defined in a route.ts file. Handles HTTP methods (GET, POST, etc.) and returns a NextResponse. The App Router replacement for Pages Router API routes.
Avoid: API route (the Pages Router term for the equivalent concept), serverless function (infrastructure layer).
Route Group
A Next.js App Router directory wrapped in parentheses — e.g. (marketing) — that groups routes under a shared layout without contributing a URL path segment. Used in SensorHub to separate the public marketing layout from the auth-required dashboard layout.
Avoid: layout group, folder grouping.
Zod safeParse
The non-throwing variant of Zod validation. Returns { success: true, data } or { success: false, error } instead of throwing. Required in Route Handlers: a thrown validation error surfaces as a 500; safeParse lets you return a clean 400.
Avoid: .parse() in route handlers — throws on invalid input, masking the validation failure as an internal server error.
Magic Link
A passwordless sign-in method where a one-time URL is emailed to the user. Implemented via Supabase signInWithOtp. Removes password storage, reset flows, and brute-force attack surface from the system.
Avoid: OTP link (OTP usually implies a numeric code, not a URL), passwordless email (describes the medium, not the mechanism).
Cookie Session
An authentication session stored in an HTTP-only cookie, accessible to server-side code. Required for Next.js App Router auth. Managed by @supabase/ssr via createServerClient with a cookie adapter.
Avoid: JWT in localStorage — not accessible server-side and vulnerable to XSS.
Middleware (Next.js)
A function in src/middleware.ts that runs on the Edge Runtime before matched requests are processed. In SensorHub, calls getUser() and redirects unauthenticated users away from /dashboard/*.
Avoid: auth guard (describes intent, not the mechanism), interceptor (term from other frameworks).

AI & Production

Streaming (LLM)
Delivering LLM response tokens to the client as they are generated, rather than waiting for the full response. In SensorHub, the Route Handler enqueues text deltas into a ReadableStream; the client reads with res.body.getReader(). Reduces perceived latency for long AI responses.
Avoid: server-sent events (a different protocol), chunked transfer (HTTP infrastructure term, not the application-level pattern).
Prompt Caching
An Anthropic API feature that stores a prompt prefix server-side for up to 5 minutes. Applied via cache_control: { type: "ephemeral" } on the system message. Subsequent requests reusing the same prefix are billed at cache-read pricing — approximately 90% cheaper for input tokens.
Avoid: response caching (caches the output, not the input), memoization (in-memory client-side concept).
Fire-and-Forget
An async operation that is started but not awaited — the caller does not wait for completion or handle the result. Used in SensorHub to persist the health report to health_reports after the stream closes, without blocking the streaming response to the client.
Avoid: background job — implies a queue with retry and failure handling; fire-and-forget is unqueued and not retried on error.
Rate Limiting
Restricting how many requests a caller can make within a time window. In SensorHub, implemented with Upstash sliding-window limiting keyed on IP (public routes) or user ID (authenticated routes). Returns HTTP 429 with a Retry-After header when exceeded.
Avoid: throttling — usually means slowing requests down, not blocking them.
Sliding Window (rate limiting)
A rate-limiting algorithm that counts requests within a rolling window relative to the current moment, not a fixed clock boundary. Avoids the burst-at-boundary problem of fixed-window limiting, where two windows' worth of requests can be sent at a reset boundary.
Avoid: fixed window — counts from a fixed clock interval and is vulnerable to burst attacks at reset boundaries.
Structured Logging
Emitting log lines as JSON objects with named, typed fields (event, level, duration_ms, etc.) rather than free-form strings. Structured logs can be queried, aggregated, and alerted on by log management tools.
Avoid: console.log("string") for production instrumentation — unqueryable and loses context.
Preview Deployment
A unique, short-lived Vercel URL generated for every pull-request branch. Allows testing in a production-like environment before merging to main. Automatically receives the preview environment variables set in the Vercel dashboard.
Avoid: staging environment — staging is a single persistent environment; preview deployments are ephemeral per PR.
Security Headers
HTTP response headers that instruct browsers to enforce content policies and reject certain attack vectors. In SensorHub, applied globally via next.config.mjs's headers() function. Includes Content-Security-Policy, X-Frame-Options, and Strict-Transport-Security.
Avoid: CORS headers — a related but separate concept; CORS controls cross-origin request permissions, not content security policy.
